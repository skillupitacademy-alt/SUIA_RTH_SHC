## 4. ACTIVE BLOCK SELECTION POLICY

### Deterministic Algorithm

**Policy:** Viewport Anchor Zone + Intersection Scoring

```
VIEWPORT ANCHOR ZONE: Top 25% of viewport (0-250px for 1000px viewport)
    Rationale: Natural reading position for scrolling content

SELECTION ALGORITHM:
1. For each visible block, calculate intersection with anchor zone
2. Score = (intersection height × 1000) - (block top position)
   - Higher intersection = higher score
   - Higher on screen (lower top) = tie-breaker boost
3. Select block with highest score
4. If no blocks intersect anchor: select topmost visible block
5. If no blocks visible: activeBlock = null
```

### Examples

| Scenario | Block Positions | Active Block | Reason |
|----------|----------------|--------------|---------|
| Single block in anchor | Block A: 100-200px | **A** | Only candidate |
| Two blocks, one in anchor | A: 50-150px, B: 300-400px | **A** | A intersects anchor zone |
| Two blocks, both in anchor | A: 50-150px, B: 100-200px | **A** | A scores higher (further into anchor) |
| Two blocks below anchor | A: 300-400px, B: 450-550px | **A** | Fallback: topmost visible |
| No blocks visible | (all offscreen) | **null** | No active block |

✅ Block enters viewport

**Responsibilities:**
- Query DOM for `[data-block-id]` elements
- Create single IntersectionObserver for all blocks

- Update React state only when active block changes

## 6. INTERSECTIONOBSERVER LIFECYCLE

### Initialization

```
1. Provider mounts
2. Query container (or document) for [data-block-id]
3. Create IntersectionObserver with thresholds: [0, 0.1, 0.25, 0.5, 0.75, 1.0]
4. Observe all block elements
5. Initial intersection callbacks fire
6. Active block calculated and set
```

### Runtime

```
User scrolls
    ↓
IntersectionObserver callback fires
    ↓
Update visibleBlocks Map (add/remove entries)
    ↓
Schedule update via requestAnimationFrame (throttled)
    ↓
Calculate new active block
    ↓
Compare with current state
    ↓
Update state only if changed (prevent unnecessary renders)
```

### Cleanup

```
Provider unmounts
    ↓
Cancel pending requestAnimationFrame
    ↓
Disconnect IntersectionObserver
    ↓
Clear visibleBlocks Map
```

### Performance Optimizations

✅ **Single observer** for all blocks (not one per block)  
✅ **requestAnimationFrame throttling** (prevents excessive updates)  
✅ **State comparison** (only update if active block actually changed)  
✅ **Stable callbacks** (prevent observer recreation)  
✅ **No continuous polling** (event-driven via IntersectionObserver)

## 7. NESTED / CONTAINER BLOCK BEHAVIOR

### Observation Strategy

**Container blocks AND child blocks are both observed independently:**

```html
<div data-block-id="container-1" data-block-type="two-column">
  ↑ Observed
  <div data-block-id="child-1" data-block-type="heading">
    ↑ Observed
  </div>
  <div data-block-id="child-2" data-block-type="paragraph">
    ↑ Observed
  </div>
</div>
```

**Selection Behavior:**
- Container and children compete using same deterministic policy
- If container intersects anchor zone: container may be active
- If child intersects anchor zone better: child is active
- No special parent/child semantics (neutral treatment)

**Rationale:**
- Phase 3 establishes technical viewport identity only
- ILS learning semantics (Phase 4+) will decide if containers are "learning units"
- Current architecture preserves maximum flexibility

## 17. ARCHITECTURAL NOTES

### Design Decisions

**Decision 1: Single Observer vs Multiple Observers**
- ✅ **Chosen:** Single IntersectionObserver for all blocks
- **Rationale:** Better performance, simpler lifecycle management
- **Trade-off:** Slightly more complex selection logic

**Decision 2: Anchor Zone Position**
- ✅ **Chosen:** Top 25% of viewport (configurable)
- **Rationale:** Natural reading position for sequential content
- **Alternative Considered:** Viewport center (rejected - less intuitive for scrolling)

**Decision 3: Container Block Handling**
- ✅ **Chosen:** Observe both container and children
- **Rationale:** Phase 3 is identity-agnostic; ILS semantics decided later
- **Trade-off:** Container/child competition for active status

**Decision 4: State Update Throttling**
- ✅ **Chosen:** requestAnimationFrame throttling
- **Rationale:** Smooth updates without excessive React renders
- **Alternative Considered:** Debounce (rejected - introduces lag)

### Future Considerations

**Accessibility:**
- Active block detection is viewport-based (visual)
- Screen reader users need alternative "focus" mechanism
- Recommend: keyboard navigation support (Phase 5+)

**Performance:**
- Current implementation efficient for <100 blocks
- For very long tutorials (>500 blocks): consider virtualization
- No observable performance issues in testing

**Mobile:**
- Anchor zone policy works for mobile viewports
- Tested conceptually (unit tests with different innerHeight values)
- Recommend: Real device testing before production
