# Automatic continuation through the existing hierarchy worker

13 November 2026. DESIGN PROPOSAL ONLY. Owner approval is required before implementation. The explicitly invoked bounded repair remains functional.

The current implementation processes at most 100 requested entities, defaults to 50, and yields between entities after 30 seconds. A transaction already in progress finishes or rolls back before yielding. Its JSON nextCursor identifies an entity kind and UUID. The cursor is authenticated when included in a QStash-signed request body. It currently has no independent signature. An unfinished page returns complete=false, remaining=null and HTTP 409. A failed entity produces HTTP 503. A completed page with no unresolved failure returns HTTP 200.

The existing QStash receiver verifies the signature, issuer, expiry and body digest. The backend's existing internal transport/CSRF boundary also applies. No deployed schedule, hierarchy-reconciliation publisher or durable reconciliation checkpoint was established from the scoped source/configuration. Provider configuration presence proves neither a deployed schedule nor delivery/retry guarantees. No provider control-plane operation was performed.

The proposed extension would use the existing worker and existing QStash transport. An authorized initiating request would provide a fixed run ID, bounded scope, first cursor, expiry, page budget and retry budget. The server would issue an HMAC-signed versioned continuation containing the run ID, authorized scope digest, current position, expiry and cumulative page/work limits. The receiver would validate both the provider signature and cursor signature and reject altered, expired, mismatched or exhausted cursors before reading databases. Keys would use existing server secret facilities with an explicit purpose binding and rotation policy. Raw credentials would never appear in the cursor.

Each page would reconcile under existing MainDB ancestor locks and actual TutorialDB transactions, verify after commit, and publish its next signed page to the same endpoint. The request could acknowledge only after successful provider publication or final completion. Publication failure would produce a retryable failure. The deduplication identity would bind run ID, scope and page position. Provider retries must be explicitly bounded and verified against the installed SDK and actual account settings before activation. No scheduler or new endpoint is proposed.

At-least-once execution can repeat a page after a crash between publishing and acknowledging. Existing entity locks and idempotent comparisons make repeated repairs safe. They do not prevent the cost of repeated scans. Provider deduplication has a limited retention window. Different run IDs can overlap. A strict single active run and durable global work budget cannot be guaranteed by a cursor alone.

A page containing failed entities must not advance past them and later report the run complete. Either retain the same position for a bounded retry or include an authenticated bounded unresolved list. Retained deleted mappings require operator disposition and must not be restored automatically. COMPLETED requires reaching the end with no unresolved entities and no unpublished continuation. PARTIAL covers an outstanding cursor or exhausted budget. FAILED covers unavailable authority, invalid continuation or exhausted failure retries. A single page cannot prove that the complete hierarchy stayed unchanged while all pages were scanned. New rows ordered before a cursor require a later full pass.

Crash recovery is the material limitation. Publishing the next provider message and committing TutorialDB changes are separate operations. Retrying the unacknowledged input safely rediscovers state, but losing the input after provider retention expires loses the continuation. Current tables identify mapping drift and permit restarting from the beginning. They do not preserve a durable reconciliation run, page history or final completion receipt. The existing background_jobs table has an unrelated user-owned job contract. Repurposing it would require an explicit owner-approved persistence contract and is outside this proposal's implementation authorization.

| Choice for a later owner decision | Guarantee and limitation |
| --- | --- |
| Approve bounded QStash continuation using the existing endpoint | Automatic page chaining with bounded retries, idempotent replay and operator restart from the beginning after lost continuation. Durable exactly-once execution and indefinite restart recovery remain unproved. Requires provider configuration verification and explicit activation approval. |
| Require durable restart from the last acknowledged position | First approve a suitable existing persistence contract after verifying its ownership, lifecycle and recovery semantics. If none fits, a new durable store would require separate architecture approval. |
| Keep explicit operation while deciding | Signed bounded requests repair scoped drift now. Operators carry the cursor, inspect unresolved outcomes and restart scans when necessary. |

Required implementation tests after approval include cursor tampering, wrong scope/key/version, expiry, budget exhaustion, duplicate delivery, concurrent runs, publication rejection, crash before publication, crash after publication before acknowledgment, failed-item retention, deleted-parent races, lock timeout, TutorialDB rollback, MainDB completion failure, late insertions before the cursor, provider retention expiry and final completion receipts. Real provider behavior would need separately authorized nonproduction execution. Local signed HTTP and PostgreSQL tests already establish the bounded repair mechanism, with their exact limits recorded in the R5 review.

Automatic continuation is PENDING OWNER DESIGN APPROVAL. No automatic publisher, schedule, durable checkpoint, database schema or infrastructure was added by this proposal.
