## Learner credential consumers

- `apps/api-server/src/modules/auth/login.service.ts`: canonical brand learner password login issues access + refresh credentials and persists the refresh hash. Bind newly issued access credentials to that exact refresh hash.
- `apps/api-server/src/modules/auth/token-refresh.service.ts`: canonical refresh rotates the persisted refresh record atomically. Bind the successor access credential to the successor refresh hash. Existing brand-admin/SHC/infra token classes must retain their contracts.
- `src/share-branding/middleware/authProxy.ts` → `auth/currentLearnerSession.ts`: private SUIA/RTH browser pages and BFFs already call the real gateway identity endpoint. Missing refresh credentials must fail before admission; exact pair binding is enforced at the backend.
- `apps/api-server/src/app/api/auth/me/route.ts`: current account/session authority; remove the any-active-session fallback for learner web credentials and compare the signed access binding to the presented refresh hash before the persisted owner/session lookup.
- `apps/api-server/src/lib/auth-context.ts`: shared backend private resource admission. Apply the same bound pair rule to learner JWT/browser requests; preserve independently authenticated tokenless internal-service requests.
- `apps/api-server/src/proxy.ts`: common backend JWT gate for quiz, analytics, reports, notifications, progress and other private routes. These handlers often verify JWTs directly rather than calling `getAuthContext`; the common gate needs current learner session admission too. Auth endpoints are excluded from this gate; protected auth session/heartbeat endpoints need explicit coverage.
- `src/share-branding/auth/unifiedBffAuth.ts` and `apps/skillup-web/src/lib/student-auth.ts`: local resource helpers verify learner JWTs; the common browser proxy supplies live admission. Existing own-user/brand checks remain required.
- `apps/skillup-web/src/app/api/auth/test-fixture-session/route.ts`: explicitly gated isolated fixture issuer currently produces access-only credentials without a persisted device session. It is not evidence of a real learner login and must not acquire a production bypass. Tests needing real protected sessions should use the canonical synthetic password-login fixture instead.
- `apps/api-server/src/modules/auth/admin-auth.service.ts` and `shc-auth.service.ts`: separate administrative issuers, outside the new learner pair contract.
- Worker QStash/signature boundaries, configured cron/internal API keys and tokenless verified internal service principals are separately authenticated contracts; do not route them through learner-cookie requirements.

Compatibility: an old learner access token has no cryptographic device binding. Merely adding a valid refresh cookie cannot prove it belongs to the same device. Such tokens must refresh through the existing refresh endpoint or sign in again; do not accept them under the new browser contract. No independently approved third-party learner bearer-only client was established by the scoped source inventory. Do not infer that arbitrary bearer-only access is an authorized service contract.

## TutorialDB writers and deletion paths

- SHC `src/app/api/tutorial-left-sidebar/route.ts`: hierarchy synchronization inserts/upserts TutorialDB domain/subject/topic/subtopic rows; draft sidebar upsert; published sidebar + hierarchy transaction. MainDB topic and all referenced subtopic parents must remain locked through the TutorialDB commit.
- `packages/db-tutorial/src/repositories/tutorial-section.repository.ts`: canonical section create, content/version update, status/publication and soft deletion; invoked by `services/tutorial-composer.service.ts` and SHC composer routes. Existing section ownership resolves through the TutorialDB-to-MainDB hierarchy mapping; mapping must be validated under the same parent locks.
- API server `src/modules/hierarchy/hierarchy-sync.service.ts`: hierarchy upserts from MainDB into TutorialDB, including batch/retry entry points. Coordinate the original MainDB parent identities and hold through TutorialDB transactions.
- RTH `src/server/hierarchy-sync.service.ts`, invoked by the signed `src/app/api/workers/sync-hierarchy/route.ts`, upserts the full hierarchy in response to an event. It now locks the authoritative MainDB subtopic and ancestors and validates every supplied parent relationship before starting the TutorialDB transaction. Worker lease completion remains after commit and supports idempotent retry.
- SHC `src/lib/hierarchy/academic-hierarchy.service.ts`: topic/subtopic and ancestor deletion holds MainDB row locks and checks TutorialDB dependencies. Need consistent ancestor ordering and post-lock dependency reads against coordinated writers.
- API server `src/modules/admin-engine/admin.{domain,subject,topic,subtopic}.engine.ts` previously reached raw physical repository deletion. These alternate entry points now use the common exclusive parent-lock and retained TutorialDB dependency check before their existing repository mutation, with backend HTTP error translation.
- Operational scripts include `scripts/phase-8a-provision-canonical-tutorial.ts`, historical `scripts/audit/c1-009-publish-mechanism-RESULTS.ts`, and phase-11-18 forensic scripts with direct TutorialDB inserts. These are not proven scheduled runtime writers. Direct SQL and maintenance scripts must not be treated as covered by an application lock convention; operator procedures must enforce coordination or keep affected deletion blocked.

The scoped scan of application/package literal Drizzle writes identifies those four production writer families. Existing section content edits, status updates, snapshots and soft deletion do not create or reparent hierarchy references. Physically retained TutorialDB mappings now prevent their MainDB parent from being deleted even if a section is archived. New section creation holds the MainDB lock through the actual TutorialDB transaction.

`services/project-ai/app/verification/fixture_setup.py` is a manually invoked provisioning CLI with dedicated deterministic verification identities. Its `disposable_fixture_provisioner.py` workflow/janitor updates existing marked section content without reparenting it. These tools and historical SQL scripts are outside the runtime lock convention. They must run against their approved fixture environment. Direct SQL maintenance of MainDB-linked records during deletion requires the same lock order or an administrative maintenance window.

The API retry worker is signature protected but its current `retryFailed()` has an empty batch registry. Five older hierarchy-sync unit tests expect removed `tutorialSyncStatus` fields and functioning failed-row retry. This pre-existing discrepancy is preserved as an acceptance exception. R4 coordinates `sync`, `syncAll` and any work entering `executeSync`; it does not claim the empty retry registry performs recovery.

MainDB locks use domain, subject, topic, subtopic order and sorted UUIDs. Topic writer locks are exclusive, ancestor and subtopic locks are shared. Parents and relationships are checked after lock acquisition. Deletion takes an exclusive target row lock before its dependency read. This serializes overlapping writers/deletes while avoiding a child-to-parent lock order. Arbitrary direct SQL and cross-database transactional atomicity remain outside this application convention.
