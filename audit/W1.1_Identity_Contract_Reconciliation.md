## Executive Summary

This reconciliation establishes the foundation for tenant-independent learner identities as clarified by the project owner. The governing architecture document (`FinalArchitecture.md`) describes a shared global learner identity model. The owner has clarified that SUIA and RTH own independent learner identities and records; SHC provides authorized shared services but does not own or unify learner accounts.

Source evidence confirms **separate tenant databases already exist** (`DATABASE_URL_SKILLUP`, `DATABASE_URL_RTH`) with brand-specific routing in `brand-db.ts`. Each tenant database maintains its own `users` table with unique email constraints, permitting email duplication across tenants at the brand level.

However, an **identity bridge** projects each brand user into a shared SHC people database (`db-people`) for cross-platform service coordination. The people DB `users` table enforces unique email **without tenant scoping**, creating a cross-tenant conflict when the same email registers in both tenants.

### Key Findings

1. **Database Topology Confirmed:** Three separate authentication databases exist (skillup, realtutorialhub, default/shared), plus one SHC people projection database. Brand-db.ts routes connections per tenant.
2. **Identity Bridge Semantics:** `originalUserId` = brand user ID (tenant-scoped); `shadowUserId` = people DB projection ID (SHC cross-reference). This is projection mapping, not impersonation.
3. **Email Conflict in People DB:** `packages/db-people/src/schema/users.ts` line 10 enforces unique email globally. When a user with the same email signs up in both tenants, the second bridge projection fails.
4. **Session Storage Uncertain:** `CreateSessionInput` includes `brand` field, but schema files show no `brand` column in `sessions` tables. Actual session repository and persistence unknown.
5. **Missing Tenant Contracts:** No explicit validation registry for `brand`/`platform` values. Middleware checks exist per-app but no centralized tenant authority enforcement.

```typescript
async syncUser(input: SyncUserInput): Promise<SyncUserResult> {
  if (input.externalBrand !== input.platform) {
    throw new Error(
      `Identity bridge mismatch: externalBrand "${input.externalBrand}" does not match platform "${input.platform}"`
    );
  }

  const existing = await this.database
    .select({ id: users.id, email: users.email })
    .from(users)
    .where(
      and(
        eq(users.externalId, input.externalId),
        eq(users.platform, input.platform),
        isNull(users.deletedAt),
      ),
    )
    .limit(1);

  if (existing.length > 0) {
    const shadowUser = existing[0];

    await this.database
      .update(users)
      .set({ email: input.email, updatedAt: new Date() })
      .where(eq(users.id, shadowUser.id));

    return { shadowUserId: shadowUser.id, created: false };
  }

  const newUser = await this.database
    .insert(users)
    .values({
      externalId: input.externalId,
      externalBrand: input.externalBrand,
      email: input.email,
      platform: input.platform,
      role: input.role ?? 'student',
      passwordHash: '',
    })
    .returning({ id: users.id });

  const shadowUserId = newUser[0].id;

  await this.database.insert(platformAccess).values({
    userId: shadowUserId,
    platform: input.platform,
  });

  return { shadowUserId, created: true };
}
```

|---|---|---|---|---|---|

- `originalUserId` = tenant's local user ID
- `shadowUserId` = SHC's cross-reference projection ID

## 3. Corrected Identity Contracts

### 3.1 Learner Identity (Tenant-Scoped, Dual-ID Projection System)

**Tenant Context:** `'skillup'` or `'realtutorialhub'` (never `'shared'` or `'skillhubcore'`)

**Brand User ID (`originalUserId`):**
- **Owner:** SUIA (skillup) or RTH (realtutorialhub) tenant
- **Namespace:** Unique within tenant database
- **Storage:** `db-skillup.users.id` or `db-rth.users.id`
- **Lifecycle:** Created at signup in tenant, persisted in tenant DB
- **Token Claim:** `originalUserId`

**Shadow User ID (`shadowUserId`):**
- **Owner:** SHC people database (infrastructure)
- **Namespace:** Unique within people DB
- **Storage:** `db-people.users.id`
- **Lifecycle:** Created by identity bridge on first login/signup, linked via `(externalId=brandUserId, platform=tenantContext)` unique index
- **Token Claim:** `shadowUserId`, also used as JWT `sub`

**Qualified Learner Identity:** `(tenantContext, brandUserId)` pair. The shadow ID is a cross-reference for SHC service coordination, not a replacement canonical ID.

**Token Validation Requirements:**
1. Signature and expiration valid.
2. `aud === 'user'`
3. `brand` is `'skillup'` or `'realtutorialhub'`.
4. Both `originalUserId` and `shadowUserId` are non-empty strings (enforced by `assertIdentityClaims`).
5. Services validate `brand` matches the intended tenant boundary.

**Cross-Tenant Isolation:**
- Learner A in `skillup` with brand ID `abc123` is independent from Learner B in `realtutorialhub` with brand ID `abc123`.
- **Brand databases already enforce this isolation.** Each tenant DB has its own ID namespace.
- **People DB does NOT enforce this isolation** due to unique email constraint (see Section 4).

### 3.2 Service Identity

**Owner:** SHC infrastructure

**Token Claims:**
- `aud`: `'infra'` or `'admin'` (service may use admin audience)
- `portalIdentity`: `'infrastructure'`
- `brand`: Absent or `'skillhubcore'`

**Authorization:**
- Service tokens MUST NOT be used to impersonate learners.
- Service requests on behalf of a learner must include explicit `(tenantContext, brandUserId)` or `shadowUserId` delegation claims, validated at service boundaries.

### 3.3 SHC Administrator Identity

**Owner:** SHC

**Token Claims:**

### 3.4 Tenant Context Validation (Missing Registry)

**Problem:** No centralized validation that `brand` or `platform` values are legitimate tenant identifiers.

**Recommendation:** Define tenant registry and validation functions:

```typescript
export const LEARNER_TENANTS = ['skillup', 'realtutorialhub'] as const;
export type LearnerTenant = typeof LEARNER_TENANTS[number];

export const RESOURCE_SCOPES = ['skillup', 'realtutorialhub', 'shared'] as const;
export type ResourceScope = typeof RESOURCE_SCOPES[number];

export function isLearnerTenant(value: unknown): value is LearnerTenant {
  return typeof value === 'string' && (LEARNER_TENANTS as readonly string[]).includes(value);
}

export function validateLearnerTenantContext(brand: unknown): LearnerTenant {
  if (!isLearnerTenant(brand)) {
    throw new Error(`Invalid learner tenant context: ${String(brand)}`);
  }
  return brand;
}
```

## 4. The Real Email Conflict: People DB Unique Constraint

### 4.1 Problem Statement

**Schema:** `packages/db-people/src/schema/users.ts` line 10:

```typescript
email: text('email').notNull().unique(),  // Global unique, no tenant scoping
```

**Indexes (lines 19-26):**

- `idx_users_email_platform`: Non-unique composite index on `(email, platform)`.
- `idx_users_external_id_platform`: **Unique** index on `(externalId, platform)` (ensures one projection per brand user).

**Constraint:** Email uniqueness is enforced at the column level, not scoped by platform.

**Failure Scenario:**

1. `alice@example.com` signs up in `skillup` → brand user created in `db-skillup.users`.
2. Identity bridge creates people DB projection: `externalId=skillup-user-123`, `platform='skillup'`, `email='alice@example.com'`. ✅ Success.
3. `alice@example.com` signs up in `realtutorialhub` → brand user created in `db-rth.users`.
4. Identity bridge attempts people DB projection: `externalId=rth-user-789`, `platform='realtutorialhub'`, `email='alice@example.com'`. ❌ **Unique constraint violation on `email`.**

**Current Behavior:** Signup completes in brand database, but identity bridge sync fails. Error logged as `identity_bridge_sync_failed` (signup.service.ts lines 99-121). Retry queued but continues failing.

**Impact:**
- Second tenant signup succeeds at brand level but fails to create people DB projection.
- User has no `shadowUserId` for second tenant.
- Services relying on `shadowUserId` for cross-platform coordination may fail for this user.
- Contradicts owner's independent tenant learner model: same person with separate accounts per tenant is a valid use case.

### 4.2 Proposed Correction Options

**Option A: Remove Email Unique Constraint (Recommended)**

- Change `packages/db-people/src/schema/users.ts` line 10:
  ```typescript
  email: text('email').notNull(),  // NOT unique
  ```
- Rely on `(externalId, platform)` unique index for projection identity.
- Permits same email across tenants in people DB.
- **Tradeoff:** People DB can have multiple rows with same email (one per tenant projection). This is correct for independent tenant learners.

**Option B: Composite Unique Constraint**

- Change schema:
  ```typescript
  email: text('email').notNull(),
  ```
- Add table-level constraint:
  ```typescript
  (table) => ({
    emailPlatformUnique: unique().on(table.email, table.platform),
    // existing indexes
  })
  ```
- Enforces unique `(email, platform)` pairs.
- Same email can exist in different platforms.
- **Tradeoff:** Schema migration required; existing duplicate emails (if any) must be resolved first.

**Option C: Soft Unique Email with Platform Scope (Deferred)**

- Keep schema as-is.
- Modify identity bridge to check for existing email within same platform before insert.
- If email exists in different platform, allow duplicate.
- **Tradeoff:** Application-level enforcement instead of database constraint. Risk of race conditions.

**Recommendation:** **Option B (composite unique constraint)** is the smallest necessary schema change that preserves independent tenant learners while preventing accidental duplicate projections within the same platform. Requires migration and owner approval.

### 4.3 Unverified Migration and Deployment

**Source Evidence:** Migration file `packages/db-people/migrations/0000_perpetual_microbe.sql` line 63 shows `CONSTRAINT "users_email_unique" UNIQUE("email")` exists in the people DB initial migration.

**Unverified Questions:**
1. Is this migration deployed to production?
2. Are there existing learners with the same email in both tenants who already hit this constraint?
3. What is the retry/recovery behavior for failed identity bridge syncs?

**Recommendation:** Trace actual deployed schema state (read-only query) before proposing migration. This reconciliation documents source evidence only, not runtime verification.
