## Executive Summary

This reconciliation establishes the foundation for tenant-independent learner identities as clarified by the project owner. The governing architecture document (`FinalArchitecture.md`) describes a shared global learner identity model. The owner has clarified that SUIA and RTH own independent learner identities and records; SHC provides authorized shared services but does not own or unify learner accounts.

Source evidence confirms **separate tenant databases already exist** (`DATABASE_URL_SKILLUP`, `DATABASE_URL_RTH`) with brand-specific routing in `brand-db.ts`. Each tenant database maintains its own `users` table with unique email constraints, permitting email duplication across tenants at the brand level.

However, an **identity bridge** projects each brand user into a shared SHC people database (`db-people`) for cross-platform service coordination. The people DB `users` table enforces unique email **without tenant scoping**, creating a cross-tenant conflict when the same email registers in both tenants.

### Key Findings

1. **Database Routing Configured (Source Evidence):** Connection strings `DATABASE_URL_SKILLUP`, `DATABASE_URL_RTH`, `DATABASE_URL` (default) and `DATABASE_URL_PEOPLE` configure brand-specific routing in `brand-db.ts`. Source permits distinct deployed endpoints but does not prove physical separation. Each tenant database schema has unique email constraints scoped to that database.
2. **Identity Bridge Projection:** `originalUserId` = brand user ID (tenant-scoped); `shadowUserId` = people DB projection ID (SHC cross-reference). This is projection mapping, not impersonation.
3. **Email Uniqueness Conflict in People Schema:** `packages/db-people/src/schema/users.ts` line 10 enforces unique email globally without platform scoping. Migration `0000_perpetual_microbe.sql` line 63 confirms this constraint. When the same email registers in both tenants, the second bridge projection fails at insert.
4. **People Users Email Consumers:** `UserRepository.findByEmail` queries people DB without platform filter. Used for SHC admin authentication and cross-platform user lookups. Signup emits `identity.bridge.retry_requested` on bridge failure; subscriber execution and durable retry behavior remain unverified.
5. **Session Storage Investigation Required:** `CreateSessionInput` type includes `brand` field; schema definitions lack corresponding column. Concrete repository and tenant binding unverified. Bounded read-only investigation proposed rather than new storage.
6. **Missing Tenant Validation Registry:** No explicit validation that `brand`/`platform` token values are legitimate tenant identifiers. Per-app guards exist but no centralized enforcement.

### 2.2 Identity Bridge Projection Semantics

**File:** `packages/identity-bridge/src/UserIdentityBridgeService.ts`

**Lines 13-74 (`syncUser` method, complete):**

```typescript
async syncUser(input: SyncUserInput): Promise<SyncUserResult> {
  if (input.externalBrand !== input.platform) {
    throw new Error(
      `Identity bridge mismatch: externalBrand "${input.externalBrand}" does not match platform "${input.platform}"`
    );
  }

  const existing = await this.database
    .select({ id: users.id, email: users.email })
    .from(users)
    .where(
      and(
        eq(users.externalId, input.externalId),
        eq(users.platform, input.platform),
        isNull(users.deletedAt),
      ),
    )
    .limit(1);

  if (existing.length > 0) {
    const shadowUser = existing[0];

    await this.database
      .update(users)
      .set({ email: input.email, updatedAt: new Date() })
      .where(eq(users.id, shadowUser.id));

    return { shadowUserId: shadowUser.id, created: false };
  }

  const newUser = await this.database
    .insert(users)
    .values({
      externalId: input.externalId,
      externalBrand: input.externalBrand,
      email: input.email,
      platform: input.platform,
      role: input.role ?? 'student',
      passwordHash: '',
    })
    .returning({ id: users.id });

  const shadowUserId = newUser[0].id;

  await this.database.insert(platformAccess).values({
    userId: shadowUserId,
    platform: input.platform,
  });

  return { shadowUserId, created: true };
}
```

**Critical Distinction - Three Separate Value Domains:**

| Domain | Field/Claim | Valid Values | Meaning | Used For |
|---|---|---|---|---|
| **Learner Tenant Authority** | `brand` in learner token | `'skillup'`, `'realtutorialhub'` | Authenticated learner's tenant membership | Authorization: which tenant's resources this learner can access |
| **Resource Scope** | `scope` or resource metadata | `'skillup'`, `'realtutorialhub'`, `'shared'` | Which tenants can access a resource | Visibility: tutorial content marked `'shared'` is visible to both tenant learners |
| **Service/Staff Context** | `platforms` array in SHC/admin tokens | `['skillup']`, `['realtutorialhub']`, `['skillup', 'realtutorialhub']` | Which tenant contexts a service/staff member is authorized to operate in | Multi-tenant operations: staff can access both tenant admin panels |

**Corrected Semantics:**

- **Learner tokens:** `brand` is singular and identifies the learner's tenant. Learners do NOT have `platforms` array. A learner with accounts in both tenants holds TWO independent identities with separate tokens.

- **Service/Staff tokens:** `platforms` array indicates authorized operational contexts. A staff member may have `platforms: ['skillup', 'realtutorialhub']` meaning they can perform administrative operations in both tenant contexts. This does NOT mean they have learner accounts in both tenants.

- **Resource scope `'shared'`:** Denotes resource visibility/access policy, not a valid learner tenant or authentication authority. Resources scoped `'shared'` are accessible to learners from ANY tenant. The learner's `brand` claim still identifies their tenant membership; the resource's `'shared'` scope permits cross-tenant access to that specific resource.

- **Token validation:** A learner with `brand: 'skillup'` can access:
  - Resources scoped `'skillup'` (tenant-specific)
  - Resources scoped `'shared'` (cross-tenant visibility)
  - **CANNOT** access resources scoped `'realtutorialhub'` (other tenant's resources)

**Current Validation Gaps:**

1. Token validation enforces `brand` matches app context (e.g., SkillUp app rejects `brand !== 'skillup'`)
2. No centralized tenant registry validates that `brand` is a legitimate tenant identifier
3. Resource scope enforcement (`'shared'` vs tenant-specific) is per-service; no shared authorization library
4. `platforms` array semantics not explicitly documented; inferred from SHC token payload usage

## 3. Corrected Identity Contracts

### 3.1 Learner Identity (Tenant-Scoped, Dual-ID Projection System)

**Tenant Context:** `'skillup'` or `'realtutorialhub'` (never `'shared'` or `'skillhubcore'`)

**Brand User ID (`originalUserId`):**
- **Owner:** SUIA (skillup) or RTH (realtutorialhub) tenant
- **Namespace:** Unique within tenant database
- **Storage:** `db-skillup.users.id` or `db-rth.users.id`
- **Lifecycle:** Created at signup in tenant, persisted in tenant DB
- **Token Claim:** `originalUserId`

**Shadow User ID (`shadowUserId`):**
- **Owner:** SHC people database (infrastructure)
- **Namespace:** Unique within people DB
- **Storage:** `db-people.users.id`
- **Lifecycle:** Created by identity bridge on first login/signup, linked via `(externalId=brandUserId, platform=tenantContext)` unique index
- **Token Claim:** `shadowUserId`, also used as JWT `sub`

**Qualified Learner Identity:** `(tenantContext, brandUserId)` pair. The shadow ID is a cross-reference for SHC service coordination, not a replacement canonical ID.

**Token Validation Requirements:**
1. Signature and expiration valid.
2. `aud === 'user'`
3. `brand` is `'skillup'` or `'realtutorialhub'`.
4. Both `originalUserId` and `shadowUserId` are non-empty strings (enforced by `assertIdentityClaims`).
5. Services validate `brand` matches the intended tenant boundary.

**Cross-Tenant Isolation:**
- Learner A in `skillup` with brand ID `abc123` is independent from Learner B in `realtutorialhub` with brand ID `abc123`.
- **Brand databases already enforce this isolation.** Each tenant DB has its own ID namespace.
- **People DB does NOT enforce this isolation** due to unique email constraint (see Section 4).

### 3.2 Service Identity

**Owner:** SHC infrastructure

**Token Claims:**
- `aud`: `'infra'` or `'admin'` (service may use admin audience)
- `portalIdentity`: `'infrastructure'`
- `brand`: Absent or `'skillhubcore'`

**Authorization:**
- Service tokens MUST NOT be used to impersonate learners.
- Service requests on behalf of a learner must include explicit `(tenantContext, brandUserId)` or `shadowUserId` delegation claims, validated at service boundaries.

### 3.3 SHC Administrator Identity

**Owner:** SHC

**Token Claims:**
- `aud`: `'admin'`
- `isAdmin`: `true`
- `brand`: `'skillhubcore'` or absent
- `roles`: `['admin', 'super_admin']`

**Authorization Scope:**
- SHC administrative operations (taxonomy, system configuration).
- Cross-tenant learner data access requires explicit permission checks and audit logging (no automatic entitlement).

**Admin Impersonation (Unverified):** No explicit admin impersonation API found in source. The dual-ID system (`originalUserId` ≠ `shadowUserId`) is used for brand-to-people projection, not admin impersonation. If impersonation is a requirement, it must be explicitly designed with audit contracts.

### 3.4 Tenant Context Validation (Missing Registry)

**Problem:** No centralized validation that `brand` or `platform` values are legitimate tenant identifiers.

**Recommendation:** Define tenant registry and validation functions:

```typescript
export const LEARNER_TENANTS = ['skillup', 'realtutorialhub'] as const;
export type LearnerTenant = typeof LEARNER_TENANTS[number];

export const RESOURCE_SCOPES = ['skillup', 'realtutorialhub', 'shared'] as const;
export type ResourceScope = typeof RESOURCE_SCOPES[number];

export function isLearnerTenant(value: unknown): value is LearnerTenant {
  return typeof value === 'string' && (LEARNER_TENANTS as readonly string[]).includes(value);
}

export function validateLearnerTenantContext(brand: unknown): LearnerTenant {
  if (!isLearnerTenant(brand)) {
    throw new Error(`Invalid learner tenant context: ${String(brand)}`);
  }
  return brand;
}
```

**Integration Points:**
- `TokenService.verifyUserAccessToken`: Validate `brand` is a learner tenant.
- BFF/gateway middleware: Validate `X-Brand` header consistency.
- Repository/service boundaries: Require validated tenant context.

## 4. The Real Email Conflict: People DB Unique Constraint

### 4.1 Problem Statement

**Schema:** `packages/db-people/src/schema/users.ts` line 10:

```typescript
email: text('email').notNull().unique(),  // Global unique, no tenant scoping
```

**Indexes (lines 19-26):**

- `idx_users_email_platform`: Non-unique composite index on `(email, platform)`.
- `idx_users_external_id_platform`: **Unique** index on `(externalId, platform)` (ensures one projection per brand user).

**Constraint:** Email uniqueness is enforced at the column level, not scoped by platform.

**Failure Scenario:**

1. `alice@example.com` signs up in `skillup` → brand user created in `db-skillup.users`.
2. Identity bridge creates people DB projection: `externalId=skillup-user-123`, `platform='skillup'`, `email='alice@example.com'`. ✅ Success.
3. `alice@example.com` signs up in `realtutorialhub` → brand user created in `db-rth.users`.
4. Identity bridge attempts people DB projection: `externalId=rth-user-789`, `platform='realtutorialhub'`, `email='alice@example.com'`. ❌ **Unique constraint violation on `email`.**

**Current Behavior:** Signup completes in brand database, but identity bridge sync fails. Error logged as `identity_bridge_sync_failed` (signup.service.ts lines 99-121). Retry queued but continues failing.

**Impact:**
- Second tenant signup succeeds at brand level but fails to create people DB projection.
- User has no `shadowUserId` for second tenant.
- Services relying on `shadowUserId` for cross-platform coordination may fail for this user.
- Contradicts owner's independent tenant learner model: same person with separate accounts per tenant is a valid use case.

### 4.2 Proposed Correction and Bounded Recommendation

**Schema Risk (Source Evidence):** `packages/db-people/src/schema/users.ts` line 10 enforces unique email globally. Migration `packages/db-people/migrations/0000_perpetual_microbe.sql` line 63 confirms `CONSTRAINT "users_email_unique" UNIQUE("email")` in initial schema.

**Deployed State:** Unknown. This reconciliation does not query deployed databases or examine connection secrets.

**Recommended Correction (Schema Level):**

**Option B: Composite Unique Constraint on (email, platform)** - Minimal Schema Change

Change `packages/db-people/src/schema/users.ts`:

```diff
- email: text('email').notNull().unique(),  // Global unique, breaks independent tenant learners
+ email: text('email').notNull(),  // NOT globally unique
```

Add table-level constraint:

```typescript
(table) => ({
  idxUsersEmailPlatform: index('idx_users_email_platform')
    .on(table.email, table.platform)
    .where(sql`${table.deletedAt} IS NULL`),
  idxUsersExternalIdPlatform: uniqueIndex('idx_users_external_id_platform')
    .on(table.externalId, table.platform)
    .where(sql`${table.externalId} IS NOT NULL`),
  emailPlatformUnique: unique('users_email_platform_unique').on(table.email, table.platform),  // NEW
})
```

**Effect:** Enforces unique `(email, platform)` pairs. Same email can exist across different tenant projections (independent learner accounts). Duplicate email within same platform is prevented (accidental duplicate projection).

**Why This is Bounded:**

- Smallest schema change addressing the independent tenant learner requirement
- Preserves existing projection identity via `(externalId, platform)` unique index
- No change to token format, authentication flows, or existing IDs
- No new infrastructure (tenant registry, global learner account, account linking)
- Migration is straightforward if no existing duplicates (see pre-migration verification below)

**Pre-Migration Verification Required (Read-Only Queries):**

Before applying migration, verify deployed people DB state:

```sql

SELECT email, platform, COUNT(*) as count
FROM users
WHERE deleted_at IS NULL
GROUP BY email, platform
HAVING COUNT(*) > 1;

-- Check for orphaned brand users missing shadow projections
-- (Requires cross-database query or application-level check)
-- Look for users in db-skillup.users or db-rth.users where shadowUserId IS NULL
-- AND audit log shows identity_bridge_sync_failed for that userId
```

**If Duplicates Exist:**

1. Investigate whether they are:
   - Legitimate independent tenant learners (same person, separate accounts per tenant) - KEEP BOTH projections, assign correct `platform` value to each
   - Accidental duplicate projections within same tenant - DATA INTEGRITY ISSUE, resolve before migration
   - Failed bridge syncs with partial state - Reconcile brand user to shadow user mapping

2. Data cleanup strategy:
   - For cross-tenant independent learners: Ensure each projection has correct `platform` value matching the brand user's tenant
   - For accidental duplicates: Merge or deduplicate, update brand users' `shadowUserId` references
   - For failed syncs: Re-run bridge sync or manually create missing projections

**Consumer and Migration Ordering (Design Only):**

Before or atomically with any future uniqueness relaxation, identify and update all affected people-email lookup consumers. A learner identity lookup must require verified platform context and fail closed when scope is absent or ambiguous; never select an arbitrary first row using an optional platform filter. Staff authentication has a separate authority contract and must be explicitly disambiguated.

No migration is authorized here. Design tests for duplicate emails across platforms, absent/forged platform context, unexpected duplicate rows within a platform, staff authentication, retry/partial projection failure and safe rollback. Confirm deployed constraints separately through an approved environment verification task before execution. Data merging or cleanup needs separate approval.

**Alternatives Rejected:**

- **Option A (Remove email unique entirely):** Too permissive; allows accidental duplicate projections within same tenant
- **Option C (Application-level enforcement):** Race condition risk; database constraint is more reliable
- **Option D (Keep global unique email):** Contradicts owner's independent tenant learner direction

**Remaining Approval Decision:**

- **Owner:** Approve composite unique constraint as minimum viable schema correction
- **Engineering:** Design and test migration, verify deployed state, execute in staging before production
- **W1.2 Implementation:** Blocked until this schema correction is deployed
