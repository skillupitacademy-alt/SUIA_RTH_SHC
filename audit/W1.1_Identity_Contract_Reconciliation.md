## Executive Summary

This reconciliation establishes the foundation for tenant-independent learner identities as clarified by the project owner. The governing architecture document (`FinalAechitecture.md`) explicitly describes a shared global learner identity model with brand memberships. This directly contradicts the owner's confirmed intent: SUIA and RTH own independent learner identities and records; SHC provides authorized shared services but does not own or unify learner accounts.

Source evidence confirms the shared authentication infrastructure already exists with `brand` fields (`skillup`, `realtutorialhub`, `shared`) embedded in tokens and sessions. However, the actual tenant authority, identifier namespace isolation, and resource-entitlement boundaries require explicit contracts and enforcement.

### Key Findings

1. **Architecture Conflict:** Five locations in `FinalAechitecture.md` describe global learner identity as the target model.
2. **Existing Platform Values:** The wire values `skillup` and `realtutorialhub` already function as tenant context; `shared` denotes resource scope, not learner identity.
3. **Missing Tenant Contracts:** No explicit validation of tenant context exists; `brand`/`platform` fields are present but not systematically enforced as learner-tenant authority.
4. **Shadow/Original ID Ambiguity:** `shadowUserId` and `originalUserId` appear throughout tokens and headers but their tenant-binding semantics are undefined.
5. **Cross-Service Identity Transport:** Services forward `X-User-ID`, `X-Brand`, `X-Shadow-User-ID`, and `X-Original-User-ID` headers after token verification, creating implicit service-trust contracts that need explicit validation.

export async function requireStudent(request: Request) {
  const token = tokenService.getAccessToken(request, { scope: 'user' });
  
  if (token == null || token.trim() === '') {
    throw new AssignmentAuthError('Unauthorized', 401);
  }

  try {
    const payload = await TokenService.verifyAccessToken(token, { audience: 'user', isAdmin: false });
    if (payload.brand !== 'realtutorialhub') {
      throw new AssignmentAuthError('Forbidden - brand mismatch', 403);
    }
    if (typeof payload.userId !== 'string' || !payload.userId.trim()) {
      throw new AssignmentAuthError('Unauthorized', 401);
    }
    
    const roles = Array.isArray(payload.roles) ? payload.roles : [];
    const normalizedRoles = roles.map(role => role.toLowerCase().trim());
    const allowedRoles = ['student', 'admin', 'super_admin', 'faculty', 'user'];
    const hasValidRole = normalizedRoles.some(role => allowedRoles.includes(role));
    
    if (!hasValidRole) {
      throw new AssignmentAuthError('Forbidden - invalid role', 403);
    }
    
    return payload;
  } catch (error) {
    if (error instanceof AssignmentAuthError) {
      throw error;
    }
    throw new AssignmentAuthError('Unauthorized', 401);
  }
}

## 3. Proposed Canonical Identity Contracts

### 3.1 Learner Identity (Tenant-Scoped)

**Owner:** SUIA (`skillup`) or RTH (`realtutorialhub`)

**Canonical Identifier:** `learnerId` (currently `shadowUserId` in tokens)

**Namespace:** Unique within tenant. Not globally unique across tenants.

**Tenant Context:** Verified `platform` or `brand` value from token.

**Qualified Learner Identity:** `(tenantContext: 'skillup' | 'realtutorialhub', learnerId: string)`

**Token Claims:**
- `shadowUserId`: The effective learner ID used for all operations.
- `brand`: The tenant context. MUST be `'skillup'` or `'realtutorialhub'`, never `'shared'`.
- `aud`: `'user'`
- `iss`: `'skillhubcore.in'` (shared authentication infrastructure)
- `roles`: Tenant-specific roles, e.g., `['student']`, `['faculty']`

**Validation Requirements:**
1. Token signature and expiration.
2. `aud === 'user'`
3. `brand` is `'skillup'` or `'realtutorialhub'` (not `'shared'` or `'skillhubcore'`).
4. `shadowUserId` is non-empty string.
5. Requesting service validates that `brand` matches the intended tenant boundary.

**Lifecycle:**
- Created during tenant-specific sign-up or authentication.
- Persisted in tenant-specific database (or tenant-partitioned table).
- Revoked independently per tenant.

**Permitted Translations:**
- Wire alias: `userId` may still appear in legacy code; prefer `shadowUserId`.
- Header transport: `X-User-ID` = `shadowUserId`, `X-Brand` = tenant context.

**Cross-Tenant Isolation:**
- Learner A in `skillup` with ID `abc123` is independent from Learner B in `realtutorialhub` with ID `abc123`.
- Same email in both tenants identifies independent learners, not a shared account.

### 3.2 Service Identity

**Owner:** SHC infrastructure

**Canonical Identifier:** Service name or `sub` claim in service token

**Namespace:** Global (SHC-managed)

**Token Claims:**
- `aud`: `'infra'` or `'admin'`
- `portalIdentity`: `'infrastructure'`
- `roles`: Service-specific roles, e.g., `['background_job', 'ai_worker']`
- `brand`: May be absent or set to `'skillhubcore'`

**Validation:**
- Service tokens MUST NOT be used to impersonate learners.
- Service requests on behalf of a learner must include the learner's verified `(tenantContext, learnerId)` as separate claims.
- Audit logs must record service actor and delegated learner identity separately.

**Example Delegated Request:**
```json
{
  "actor": {
    "type": "service",
    "serviceId": "background-job-worker",
    "aud": "infra"
  },
  "delegatedLearner": {
    "tenantContext": "skillup",
    "learnerId": "abc123"
  }
}
```

### 3.3 SHC Administrator Identity

**Owner:** SHC (SkillHubCore)

**Canonical Identifier:** `adminId` (currently `shadowUserId` in admin tokens)

**Namespace:** Global SHC staff registry

**Token Claims:**
- `aud`: `'admin'`
- `isAdmin`: `true`
- `brand`: `'skillhubcore'` (or omitted)
- `roles`: `['admin', 'super_admin']`
- `portalIdentity`: `'admin'` or `'super_admin'`

**Authorization Scope:**
- SHC administrative operations (e.g., manage taxonomy, configure services).
- **NOT automatic learner impersonation.** Admin accessing tenant-specific learner data requires explicit impersonation flow with audit logging.

**Tenant Entitlement:**
- SHC admin identity does not automatically grant access to learner resources in `skillup` or `realtutorialhub`.
- Cross-tenant administrative operations require explicit permission checks and tenant context.

### 3.4 Authentication Session vs. Learning Session

**Authentication Session:**
- Token family: access + refresh tokens.
- Lifecycle: Managed by `SessionService`, persisted in `sessions` table (currently missing `brand` field in schema).
- Revocation: Per-session, per-user, or global.
- **Tenant Binding (missing):** Sessions should be tenant-bound. Schema and session service must store `brand`.

**Learning Session (ILS - Integrated Learning Session):**
- Application-level session tracking active learning time, progress, and interactions.
- Separate identifier from authentication session.
- **Audit Finding SU-ILS-003:** Client-controlled learning-session identifiers are forwarded without verification. This is a security gap.

**Recommendation:** Define learning-session creation server-side, bound to authenticated learner and tenant context. Do not trust client-supplied session IDs without validation.

### 3.5 originalUserId and shadowUserId Semantics

**Current State:** Both claims are mandatory (enforced by `assertIdentityClaims`), but their semantics are undefined.

**Proposed Contract:**

| Claim | Meaning | Use Case | Tenant Binding |
|---|---|---|---|
| `originalUserId` | Persistent learner identity, stable across sessions and tokens | Audit logs, account linking (if approved), long-term tracking | Tenant-scoped |
| `shadowUserId` | Effective identity for this session/token; may differ during impersonation or migration | Authorization decisions, resource ownership checks | Tenant-scoped |

**Normal Case:** `originalUserId === shadowUserId`. Both reference the same learner in the same tenant.

**Impersonation Case (if approved):**  
- Admin token might have `originalUserId = admin-123` (SHC admin) and `shadowUserId = learner-456` (impersonated learner in `skillup` tenant).
- Audit logs record both: admin actor + impersonated learner.
- Services use `shadowUserId` for resource access, `originalUserId` for audit trails.

**Migration Case (uncertain):**  
- If a learner's ID changes (e.g., database migration), `originalUserId` might preserve the old ID for historical record lookups, while `shadowUserId` is the new ID.

**Critical Requirement:** Document the exact use cases and update `assertIdentityClaims` with tenant-binding validation.

### 3.6 Tenant Context Validation Registry (Missing)

**Problem:** No centralized validation that `brand` or `platform` values are legitimate tenant identifiers.

**Proposed Registry:**

```typescript
export const LEARNER_TENANTS = ['skillup', 'realtutorialhub'] as const;
export type LearnerTenant = typeof LEARNER_TENANTS[number];

export const RESOURCE_SCOPES = ['skillup', 'realtutorialhub', 'shared'] as const;
export type ResourceScope = typeof RESOURCE_SCOPES[number];

export const SHC_CONTEXTS = ['skillhubcore'] as const;
export type SHCContext = typeof SHC_CONTEXTS[number];

export function isLearnerTenant(value: unknown): value is LearnerTenant {
  return typeof value === 'string' && LEARNER_TENANTS.includes(value as LearnerTenant);
}

export function isResourceScope(value: unknown): value is ResourceScope {
  return typeof value === 'string' && RESOURCE_SCOPES.includes(value as ResourceScope);
}

export function validateLearnerTenantContext(brand: unknown): LearnerTenant {
  if (!isLearnerTenant(brand)) {
    throw new Error(`Invalid learner tenant context: ${String(brand)}`);
  }
  return brand;
}
```

**Integration Points:**
- `TokenService.verifyUserAccessToken`: Validate `brand` is a learner tenant.
- BFF/Gateway middleware: Validate `X-Brand` header before forwarding.
- Repository/service boundaries: Require `tenantContext` parameter, validate at ingress.

## 4. SHC Boundary Flows and Authorization Patterns

### 4.1 Learner-Delegated Request (SUIA or RTH → SHC Shared Service)

**Example:** SkillUp learner requests tutorial content from SHC Tutorial Service.

**Flow:**

1. **Browser → SkillUp BFF:**  
   - Request includes `accessToken` cookie.
   - SkillUp BFF validates token: `aud: 'user'`, `brand: 'skillup'`.
   - Extracts `shadowUserId` (learner ID) and `brand` (tenant context).

2. **SkillUp BFF → SHC Tutorial Service:**  
   - Forwards request with headers:
     - `X-User-ID: <shadowUserId>`
     - `X-Brand: skillup`
     - `X-Gateway-Secret: <sharedSecret>`
   - Does NOT forward the original access token.

3. **SHC Tutorial Service:**  
   - Validates `X-Gateway-Secret` to trust the BFF.
   - Reads `X-User-ID` and `X-Brand`.
   - **Authorization Check:**
     - Resource (tutorial content) has `scope: 'shared'` → accessible by both tenants.
     - OR resource has `scope: 'skillup'` → accessible only if `X-Brand === 'skillup'`.
   - Returns content.

**Missing Validations:**

- **Audit Finding SU-TUTORIAL-002:** Tutorial service must reject requests with missing or invalid `X-Gateway-Secret`.
- **Resource-owner check:** Does the requested tutorial belong to the learner's tenant? Is `shared` scope explicitly recorded in resource metadata?

**Recommendation:** SHC Tutorial Service must validate:
1. `X-Gateway-Secret` presence and correctness.
2. `X-Brand` is a valid learner tenant.
3. Resource `scope` permits access from the requesting tenant.

### 4.2 Service-Only Request (No Learner Delegation)

**Example:** Background job triggers taxonomy rebuild.

**Flow:**

1. **Background Job → SHC Service:**  
   - Uses service token: `aud: 'infra'`, `portalIdentity: 'infrastructure'`.
   - No `X-User-ID` or `X-Brand` headers.

2. **SHC Service:**  
   - Validates service token.
   - Authorizes operation based on service identity and permissions.
   - **Does NOT fabricate a learner identity.**

**Critical:** Service-only requests must not invent `userId` or `brand` values. Audit logs record service actor, not a fake learner.

### 4.3 Administrative Request (SHC Admin → Tenant Resource)

**Example:** SHC admin reviews SkillUp learner progress for support investigation.

**Flow:**

1. **Admin Portal → SHC Admin BFF:**  
   - Admin authenticates: `aud: 'admin'`, `isAdmin: true`, `brand: 'skillhubcore'`.

2. **SHC Admin BFF → SkillUp Service:**  
   - Request includes:
     - Admin token or admin identity headers.
     - Target tenant context: `X-Target-Tenant: skillup`.
     - Target learner ID: `X-Target-Learner-ID: abc123`.
     - Admin justification/ticket ID (optional).

3. **SkillUp Service:**  
   - Validates admin token.
   - Checks admin has `cross_tenant_read` or `support_access` permission.
   - Validates `X-Target-Tenant` is a valid learner tenant.
   - **Audit Log:** Records admin actor, target tenant, target learner, timestamp, and operation.
   - Returns learner data.

**Missing Contract:** No explicit admin-to-tenant-resource authorization model defined.

**Recommendation:** Define administrative permission matrix (e.g., `support_read`, `tenant_admin`, `super_admin`) and audit-logging requirements before implementing cross-tenant admin operations.

### 4.4 Shared Resource Access

**Example:** Both SUIA and RTH learners access the same tutorial content.

**Resource Metadata:**

```json
{
  "contentId": "tutorial-intro-to-python",
  "scope": "shared",
  "visibleTo": ["skillup", "realtutorialhub"]
}
```

**Authorization:**

- Learner from `skillup` tenant requests content.
- Service validates `X-Brand === 'skillup'`.
- Checks resource `scope === 'shared'` and `'skillup' in visibleTo`.
- Access granted.

**Critical:** `shared` is a resource visibility scope, NOT a learner tenant. Learner authorization still requires verified tenant context.

## 7. Unresolved Decisions Requiring Owner Approval

### 7.1 Database and Schema Strategy

**Question:** Is the `users` table shared across tenants, or is there a separate database per tenant?

**Evidence:**
- `packages/db` references single `DATABASE_URL`.
- `users` table has unique `email` constraint (no tenant column visible).
- Contradicts independent tenant learners if email is globally unique.

**Options:**

**A. Tenant-Partitioned Databases:**
- Separate `skillup_db` and `rth_db` with independent `learners` tables.
- Each tenant has isolated email namespaces.
- Requires connection-string routing logic.

**B. Shared Auth DB with Tenant Column:**
- Add `tenant` column to `users` table.
- Composite unique constraint: `(email, tenant)`.
- Same email can exist in `skillup` and `realtutorialhub`.

**C. Shared Auth DB for Credentials, Tenant DBs for Learner Records:**
- Hybrid: Shared authentication (email, passwordHash, sessions) managed by SHC.
- Separate tenant databases for learner profiles, progress, enrollments.
- Learner ID linkage requires explicit mapping.

**Recommendation:** Present options A, B, C to owner. Choice impacts W1.2 implementation scope and migration complexity.

**Blocked Tickets:** Schema changes, session-brand persistence, email uniqueness validation.

### 7.2 `platforms` Array Semantics

**Question:** Does `platforms: ['skillup', 'realtutorialhub']` in a token mean:

**A.** The principal has learner accounts in both tenants (cross-tenant learner)?  
**B.** The principal is a staff/service member authorized to operate in both tenant contexts (not a learner)?  
**C.** The token is multi-tenant capable, but each request specifies one active tenant?

**Evidence:**
- `SkillHubCoreTokenPayload` includes `platforms` array.
- Learner tokens typically have `brand` (singular), not `platforms` array.
- Unclear if `platforms` ever applies to learners.

**Recommendation:** Define `platforms` as staff/service-only. Learner tokens use singular `brand` field. Clarify in token validation logic.

**Blocked Tickets:** Cross-tenant authorization rules, staff identity contracts.

### 7.3 Admin Impersonation and Audit Logging

**Question:** Is admin impersonation of learners an approved feature?

**Evidence:**
- `originalUserId` and `shadowUserId` separation suggests impersonation capability.
- No explicit admin impersonation API or audit-logging requirements documented.

**Options:**

**A.** Impersonation is approved: Admin can generate a learner-scoped token with `originalUserId = adminId`, `shadowUserId = learnerId`. Full audit logging required.

**B.** Impersonation is prohibited: Admin operations on learner data use admin credentials + explicit target-learner parameters. No token switching.

**Recommendation:** Present options to owner. If approved, define impersonation API, audit-log schema, and permission requirements before W1.2.

**Blocked Tickets:** Admin-to-learner authorization, impersonation token generation, audit actor contracts.

### 7.4 Learning Session (ILS) Identifier Validation

**Question:** Should learning-session IDs be server-generated and validated, or client-controlled?

**Evidence:**
- **Audit Finding SU-ILS-003:** Client-controlled learning-session identifiers are forwarded without verification.
- Current behavior: Client supplies session ID; server trusts it.

**Recommendation:** Server-generated, tenant-bound, learner-bound learning-session IDs. Server validates session ownership before accepting progress updates.

**Blocked Tickets:** ILS session creation API, session-ownership validation.

### 7.5 Compatibility and Migration Path

**Question:** Can `userId` (legacy) and `shadowUserId` (canonical) coexist during migration?

**Evidence:**
- SkillUp auth guard has fallback: `shadowUserId || userId`.
- Tokens include both fields.

**Recommendation:** Define migration timeline:
1. Phase 1 (current): Both fields present; services prefer `shadowUserId`.
2. Phase 2: All services migrated to `shadowUserId`; `userId` deprecated.
3. Phase 3: Remove `userId` from token payload.

**Blocked Tickets:** Token payload cleanup, service migration verification.
