### 3.2 The Strict End-to-End Ingress Contract

To prevent unauthenticated callers or forged headers from dictating database selection, the following contract rules must be implemented across the resolver and route handler:

#### Contract Rule 1.1: Strict Raw Header Validation in `request-brand.ts`
[`apps/api-server/src/lib/request-brand.ts`](file:///E:/onlinewebsites/quiz-platform/apps/api-server/src/lib/request-brand.ts) must be enhanced with a strict validation helper `resolveValidatedRequestBrand(headers)`:
1. **Explicit Brand Candidates**: Extract raw `x-brand` and `x-platform`.
2. **Conflicting Header Check**: If both `x-brand` and `x-platform` are present and normalize to different non-empty values, **fail closed immediately** (return `{ error: 'conflicting_brand_headers' }`).
3. **Invalid / Forbidden Values**: If any candidate equals `'shared'` or is not in the canonical list `['realtutorialhub', 'skillup', 'skillhubcore']`, **fail closed immediately** (return `{ error: 'invalid_brand_header', value: candidate }`).
4. **Missing Headers**: If neither header is present, return `{ brand: undefined }`.

#### Contract Rule 1.2: Route Handler Fail-Closed Ingress Enforcement
In [`apps/api-server/src/app/api/auth/refresh/route.ts`](file:///E:/onlinewebsites/quiz-platform/apps/api-server/src/app/api/auth/refresh/route.ts):
```typescript
const brandResolution = resolveValidatedRequestBrand(_req.headers);
if (brandResolution.error) {
  return ApiResponse.error(badRequest(`Invalid tenant context: ${brandResolution.error}`), 400);
}
// If brand is missing, do NOT silently fall back in auth.service.ts
const requestBrand = brandResolution.brand;
if (!requestBrand) {
  return ApiResponse.error(badRequest('Missing required tenant brand header'), 400);
}
```
This guarantees that `'shared'` or malformed headers are rejected with an explicit **400 Bad Request** at ingress and cannot silently default to `'realtutorialhub'`.

#### Contract Rule 1.3: Ingress Network Topology Boundary
- The BFF proxy injects `x-internal-secret: process.env.INTERNAL_GATEWAY_SECRET`.
- However, because direct edge firewall rules are not maintained in this Git repository, `apps/api-server` must treat all incoming HTTP headers as **unauthenticated routing hints** until cryptographically verified against the signed JWT `brand` claim in `TokenRefreshService`.

## 4. Strict Legacy Compatibility & Claim Normalization Contract (R2)

### 4.1 Strict Definitions of Token Claim States

When `TokenRefreshService.refresh` inspects the decrypted predecessor payload `oldPayload`, it must categorize the `brand` claim into one of three mutually exclusive states:

```
[Token Payload Brand Claim Evaluation]
   │
   ├─► Case 1: STRICTLY ABSENT (Legacy Token)
   │     Condition: oldPayload.brand === undefined || oldPayload.brand === null
   │     Action: Eligible for Legacy Evaluation (see Section 4.2).
   │
   ├─► Case 2: MALFORMED (Security Violation)
   │     Condition:
   │       typeof oldPayload.brand !== 'string' ||
   │       oldPayload.brand.trim().length === 0 ||
   │       !['realtutorialhub', 'skillup', 'skillhubcore'].includes(oldPayload.brand.trim().toLowerCase())
   │     Action: FAIL CLOSED immediately with 401 Unauthorized ('Invalid refresh token: malformed brand claim').
   │             (Catches numbers, booleans, objects, empty strings, and 'shared').
   │
   └─► Case 3: CANONICAL STRING (Modern Token)
         Condition: ['realtutorialhub', 'skillup', 'skillhubcore'].includes(oldPayload.brand.trim().toLowerCase())
         Action: Enforce Parity:
           if (oldPayload.brand.trim().toLowerCase() !== brand.toLowerCase()) {
             throw new Error('Invalid refresh token: tenant brand mismatch');
           }
```

### 4.2 Legacy Compatibility Policy (Proposal B — Subject to Sol Acceptance)

1. **Prerequisites for Legacy Rotation**:
   A refresh token lacking a `brand` claim (`oldPayload.brand === undefined`) may ONLY be rotated if all of the following conditions are simultaneously met:
   - The token cryptographic signature is valid (`verifyRefreshToken` passes).
   - The token has not expired (`exp > now`).
   - The SHA-256 token hash exists in the database selected by the validated `requestBrand` (`brandTokenRepo.findByHash`).
   - The stored session row is active (`revoked === false` and `expiresAt > now`).
   - The verified token subject matches the stored row owner (`oldPayload.userId === existingSession.userId`).
2. **Progressive Upgrade Semantics**:
   - When a legitimate legacy token satisfies all five prerequisites, `TokenRefreshService` consumes the legacy parent and mints the successor refresh token with an **explicit, canonical `brand` claim**.
   - Once rotated, the session is permanently upgraded. All subsequent rotations strictly enforce Invariant 2 (Canonical String Parity).
3. **Honest Limitations on Historical Usage**:
   - Generic refresh tokens are signed with a 7-day JWT expiration (`REFRESH_TOKEN_EXPIRE = '7d'`). In normal operation, all legacy tokens will naturally expire or upgrade within 7 days of deployment.
   - *However*, because rolling rotation issues a new 7-day token on every refresh, an active user who refreshes every few days could theoretically maintain an unbroken session chain. Progressive upgrade ensures that their very first post-deployment refresh upgrades the token, cutting off legacy tolerance after the first rotation.

## 6. Principal Boundaries, Privilege Escalation, and Demotion (R6)

Refresh rotation must strictly preserve authenticated principal classes. A refresh token issued for one portal/scope cannot cross boundaries:

### 6.1 Coherent Authority Matrix by Principal Class

| Principal Class | Audience (`aud`) | Cookie Name | Signing Secret | Token Type (`tokenType`) | Permitted Roles | Target Database |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **Learner** (SUIA / RTH) | `'user'` | `refreshToken` | `REFRESH_SECRET` | `'user'` | `['student']`, `['learner']`, `[]` | `db-skillup` or `db-rth` |
| **Tenant Admin** | `'admin'` | `admin_refreshToken` | `ADMIN_SECRET` | `'admin'` | `['admin']`, `['super_admin']`, `['faculty']` | `db-skillup` or `db-rth` |
| **SHC Infrastructure** | `'infra'` | `infra_refreshToken` | `ADMIN_SECRET` | `'admin'` | `['infrastructure']` | `db` (default tables) |

### 6.2 No Privilege Escalation via User Refresh Tokens
- **Contract Invariant**: If a user holding a learner refresh token (`aud: 'user'`, `tokenType: 'user'`) is assigned an `'admin'` role in the database, `TokenRefreshService` **MUST NOT** escalate the session:
  - It MUST NOT change `tokenType` to `'admin'`.
  - It MUST NOT sign the token with `ADMIN_SECRET`.
  - It MUST NOT set `isAdmin: true` on the successor access token.
- **Enforcement Rule**:
  ```typescript
  // Cap permissions to the authenticated session scope
  const isSessionAdminScope = requestedAudience === 'admin' || requestedAudience === 'infra';
  const isAdmin = isSessionAdminScope && (dbRoles.includes('admin') || dbRoles.includes('super_admin'));
  const tokenType = isSessionAdminScope ? 'admin' : 'user';
  ```
- **Administrative Access**: To obtain an admin access token, the user must authenticate through the dedicated [`AdminAuthService.login`](file:///E:/onlinewebsites/quiz-platform/apps/api-server/src/modules/auth/admin-auth.service.ts#L25) flow, which writes to `admin_refreshToken` using `ADMIN_SECRET`.

### 6.3 Demoted Administrator Behavior
- If a user presents an admin refresh token (`aud: 'admin'`, `admin_refreshToken`) but their freshly queried roles in the database no longer contain `'admin'` or `'super_admin'`:
  - `TokenRefreshService` MUST **fail closed immediately** with `throw new Error('access_denied:insufficient_permissions')`.
  - The request returns **401 Unauthorized**.
  - The admin session is terminated. It is NOT silently downgraded into a learner token.
