## 1. Executive Summary & Problem Formulation

In multi-tenant authentication across **RealTutorialHub (RTH)**, **SkillUp IT Academy (SUIA)**, and **SkillHubCore (SHC)**, refresh token rotation operates under an ambient database selection model:
$$\text{HTTP Request} \xrightarrow{\text{Headers}} \text{Route Handler} \xrightarrow{\text{brand parameter}} \text{TokenRefreshService} \xrightarrow{\text{getAuthBrandContext(brand)}} \text{Target DB}$$

### Core Defect Identified
Under the baseline implementation prior to this contract:
1. The tenant database (`db-rth`, `db-skillup`, or `db-core`) is selected strictly from untrusted HTTP request headers (`x-brand`, `x-platform`) or route defaults.
2. When the refresh token is presented, `TokenRefreshService.refresh` verifies the cryptographic signature and expiration of the token, but **never compares the token's embedded cryptographic `brand` claim (`oldPayload.brand`) against the target database or requested brand parameter**.
3. Similarly, `TokenRefreshService.refresh` selects the active session row from `refresh_tokens` by SHA-256 token hash (`findByHash`), but **never validates that the verified JWT subject/userId (`oldPayload.userId` or `oldPayload.sub`) matches the stored session owner (`existingSession.userId`)**.
4. Furthermore, `brandTokenRepo.updateLastUsed(oldTokenHash)` executes an unconditional database mutation **before** `verifyRefreshToken` validates the cryptographic signature or audience, allowing unauthenticated requests to modify database row state.

This document defines the formal **Token Authority & Brand Binding Security Contract** for `W1.2-REFRESH-05`. It establishes:
- The exact inventory of all refresh signers, verifiers, and claims across the ecosystem.
- The concrete identity authority agreement required before any database mutation or token rotation occurs.
- The backward-compatibility policy for legacy tokens lacking modern claims.
- The boundary between known gateway architecture and unverified production ingress network topology.
- A comprehensive negative and positive security regression test matrix.
- A minimal, surgical implementation whitelist for the subsequent coding ticket.

### 2.2 Critical Distinction: Generic Signer vs. SHC Helpers
- **Generic Signer (`generateRefreshToken`)**: Emits `userId`, `originalUserId`, `shadowUserId`, `tokenType`, `isAdmin`, `brand`, and `jti`. **Crucially, it deliberately omits `roles` and `email`**. Refresh tokens are lightweight credentials intended solely for rotating sessions; they are not capability tokens.
- **SHC Specialized Signer (`signSkillHubCoreRefreshToken`)**: Uses standard OpenID Connect claim naming (`sub`), introduces a token `family` claim, and explicitly stamps `iss: 'skillhubcore.in'`.
- **Legacy Tokens**: Tokens generated prior to recent remediation batches lack `jti` (resolved additively in `W1.2-REFRESH-02`) and in older historical releases lacked `brand`, `tokenType`, or `originalUserId`.

## 3. End-to-End Request Journey & Ingress Trust Analysis

### 3.1 Trace of Brand and Tenant Routing

```
[Client / Browser]
   │  Cookies: refreshToken / admin_refreshToken / infra_refreshToken
   │  Headers: (Client may attempt to send arbitrary x-brand, x-platform, Host)
   ▼
[Network Edge / Reverse Proxy (Nginx / Cloudflare / Hostinger)]
   │  ⚠️ Topology Unverified in Repository:
   │     Does the edge proxy strip external 'x-brand' / 'x-platform' headers?
   ▼
[BFF Gateway Layer] (apps/realtutorialhub-web, apps/skillup-web, src/share-branding/auth/authBffRoute.ts)
   │  1. publicHost = getRequestHost(request)  <-- Reads Node Host header or nextUrl.hostname (NOT x-forwarded-host)
   │  2. normalizedHost = extractHostnameFromHostHeader(publicHost)
   │  3. resolvedBrand = resolveBrandFromHostname(normalizedHost)
   │  4. Injects headers:
   │        x-brand: resolvedBrand
   │        x-forwarded-host: normalizedHost
   │        x-internal-secret: process.env.INTERNAL_GATEWAY_SECRET
   ▼
[API Server Ingress] (apps/api-server/src/app/api/auth/refresh/route.ts)
   │  1. portalIdentity = headers.get('x-portal-identity') ?? 'user'
   │  2. audience = (portalIdentity === 'infrastructure' ? 'infra' : portalIdentity === 'admin' ? 'admin' : 'user')
   │  3. requestBrand = resolveRequestBrandFromHeaders(headers)  <-- Reads x-brand, then x-platform
   │  4. Selects token from cookie based on portalIdentity
   │  5. Delegates to AuthService.refresh(...)
   ▼
[Core Service] (apps/api-server/src/modules/auth/token-refresh.service.ts)
   │  1. oldTokenHash = hashToken(oldRefreshToken)
   │  2. brandContext = getAuthBrandContext(brand)
   │  3. brandTokenRepo.findByHash(oldTokenHash)
   │  4. brandTokenRepo.updateLastUsed(oldTokenHash)  <-- ⚠️ UNVERIFIED DB WRITE HAPPENS HERE
   │  5. tokenService.verifyRefreshToken(oldRefreshToken, { audience })
   │  6. Generates new tokens & executes CAS consumeToken inside brandContext.db transaction
```

### 3.2 Ingress Trust Model & Unverified Topology Disclosure
1. **BFF Security Contract**: In [`src/share-branding/auth/authBffRoute.ts:140-199`](file:///E:/onlinewebsites/quiz-platform/src/share-branding/auth/authBffRoute.ts#L140-L199), the BFF explicitly distrusts `x-forwarded-host` from incoming client requests and inspects only the verified Node HTTP `Host` header. It resolves the brand using canonical domain mappings (`realtutorialhub.com` $\to$ `realtutorialhub`, `skillupitacademy.com` $\to$ `skillup`).
2. **API Server Vulnerability**: `apps/api-server` does not have a top-level `middleware.ts` running [`validateGatewaySecret`](file:///E:/onlinewebsites/quiz-platform/apps/api-server/src/middleware/gateway-auth.middleware.ts#L23). Route handlers read `resolveRequestBrandFromHeaders(req.headers)` directly without asserting that `x-internal-secret` is present or valid.
3. **Topology Uncertainty**: Whether external clients can bypass the BFF and reach `api-server:3000` directly depends entirely on host firewall, container networking, and reverse-proxy routing rules. In the git repository, this topology cannot be verified without live infrastructure inspection.
4. **Architectural Consequence**: Because header trust cannot be unconditionally assumed from the network layer alone, **the API server must enforce cryptographic brand agreement at the application layer**. The verified JWT `brand` claim must be authoritative.

## 4. The Proposed Identity Authority Agreement Contract

Before any database write, state modification, or successor token issuance is permitted, `TokenRefreshService.refresh` must enforce the following sequence of strict authority checks:

```
[Incoming Refresh Request: oldRefreshToken, brand, requestedAudience]
   │
   ├─► STEP 1: Cryptographic JWT Verification (CPU-only, No DB writes)
   │     Verify signature against REFRESH_SECRET / ADMIN_SECRET.
   │     Assert token is not expired (JWT exp).
   │     Assert audience matches requestedAudience.
   │     Result: oldPayload
   │
   ├─► STEP 2: Token Brand Authority vs. Requested Tenant Brand Parity
   │     If oldPayload.brand is present:
   │       Assert oldPayload.brand === brand
   │       (Mismatch -> FAIL CLOSED: "Token brand mismatch")
   │     Reject brand === 'shared' (FAIL CLOSED: "'shared' is not a valid tenant")
   │
   ├─► STEP 3: Database Session Existence & Active State
   │     Query tenant database selected by verified brand:
   │       brandTokenRepo.findByHash(oldTokenHash)
   │     Assert session exists, revoked === false, expiresAt > now.
   │     Result: existingSession
   │
   ├─► STEP 4: Token Subject vs. Stored Row Owner Parity
   │     Assert oldPayload.userId === existingSession.userId
   │     (Mismatch -> FAIL CLOSED: "Token subject does not match session owner")
   │
   ├─► STEP 5: Safe State Mutation (Only after all authority checks PASS)
   │     brandTokenRepo.updateLastUsed(oldTokenHash)
   │
   └─► STEP 6: Atomic Single-Consumer Rotation (W1.2-REFRESH-02)
         Transaction: consumeToken(oldTokenHash, userId) + createRefreshToken(...)
```

### 4.1 Detailed Contract Invariants

#### Invariant 1: Cryptographic Verification Must Precede DB Writes
- **Current Defect**: Line 116 of `token-refresh.service.ts` calls `await brandTokenRepo.updateLastUsed(oldTokenHash)` **before** line 125 calls `this.tokenService.verifyRefreshToken(...)`. An attacker with a forged, tampered, or expired JWT containing a known token hash can trigger database writes and update `lastUsedAt`.
- **Contract Rule**: `verifyRefreshToken` MUST be executed before `updateLastUsed`. If verification fails, the request terminates immediately with an audit log and 401; zero database writes are performed.

#### Invariant 2: Cryptographic Brand Claim Parity
- **Contract Rule**: If the verified JWT contains a `brand` claim (`typeof oldPayload.brand === 'string'`), the service must assert:
  $$\text{oldPayload.brand.toLowerCase()} === \text{brand.toLowerCase()}$$
- If `oldPayload.brand !== brand`, the request MUST fail closed with error `Invalid refresh token brand` and log `token_brand_mismatch`.
- **Swapped Platform Attack Prevention**: If a client holds a valid refresh token minted for `skillup` and presents it to `/api/auth/refresh` with `x-brand: realtutorialhub`, the request is rejected immediately before searching the RTH database or modifying state.

#### Invariant 3: Rejection of `'shared'` as a Tenant Brand Authority
- **Contract Rule**: The system recognizes `realtutorialhub`, `skillup`, and `skillhubcore` as valid `RequestBrand` values. `'shared'` is a CMS/theming identifier, never an authentication tenant or database boundary.
- Any request where `brand === 'shared'` or `oldPayload.brand === 'shared'` MUST be rejected immediately with `badRequest('Invalid tenant brand: shared')`.
- No new `tenantId` abstraction or tenant registry table shall be introduced (KISS / YAGNI).

#### Invariant 4: Token Subject vs. Stored Row Owner Agreement
- **Contract Rule**: The service must assert:
  $$\text{oldPayload.userId} === \text{existingSession.userId}$$
- (Or `oldPayload.sub === existingSession.userId` if evaluating an OIDC-style payload).
- If the token payload subject does not match the database row owner, the request MUST fail closed with `Invalid refresh token owner` and log `token_owner_mismatch`. This eliminates any possibility of identity discrepancy between the session record and minted access tokens.

## 5. Backward-Compatibility & Legacy Token Policy Decision

### 5.1 The Compatibility Dilemma
In any long-running multi-tenant system, tokens minted under earlier software releases may be actively stored in learner browsers:
1. **Tokens without `jti`**: Handled cleanly in `W1.2-REFRESH-02` (accepted backward-compatibility).
2. **Tokens without `brand` claim**: Early legacy tokens only contained `{ userId, isAdmin, aud }`.
3. **Tokens without `iss` (issuer)**: All generic tokens currently omit `iss`.

### 5.2 Analysis of Options

| Policy Option | Behavior for Tokens Lacking `brand` Claim | Security Posture | User / Business Impact | Recommendation |
| :--- | :--- | :--- | :--- | :--- |
| **Option A: Strict Immediate Invalidation** | Reject any refresh token missing `brand`. | High (zero legacy tolerance). | **Breaking Change**: Immediately forces all active users holding legacy tokens to be logged out and re-authenticate. | **REJECTED** |
| **Option B: Permissive Fallback with Progressive Upgrade (Recommended)** | If `oldPayload.brand` is present, strictly enforce equality. If absent, allow rotation only if the token hash exists in the selected DB, and inject the verified `brand` into the successor token. | High (transitional; bounds legacy to remaining TTL; once rotated, strictly enforced). | **Zero disruption**: Legitimate active learners rotate smoothly; legacy tokens permanently extinguish within 7 days. | **RECOMMENDED** |
| **Option C: Unconditional Issuer Enforcement** | Reject any token missing `iss: '...'`. | Incompatible. | **Catastrophic**: Breaks 100% of current user and admin logins because generic `generateRefreshToken` does not set `iss`. | **REJECTED** |

### 5.3 Architectural Recommendation: Option B (Progressive Upgrade)
1. **Legacy Brand Handling**:
   ```typescript
   if (typeof oldPayload.brand === 'string' && oldPayload.brand.length > 0) {
     if (oldPayload.brand.toLowerCase() !== brand.toLowerCase()) {
       throw new Error('Invalid refresh token brand');
     }
   } else {
     // Legacy token without brand claim:
     // Permit rotation ONLY IF stored token hash matches in the brand-selected database.
     // Successor token will be minted with explicit brand, upgrading the session.
     console.warn('[AUTH_SECURITY] Legacy refresh token rotated without brand claim', { userId });
   }
   ```
2. **Issuer Enforcement Deferral**: Do **NOT** add issuer enforcement to `verifyRefreshToken` at this time. Standard refresh tokens do not emit `iss`. Introducing an `iss` check requires a coordinated migration plan where all signers across all services emit a standardized issuer before verifiers enforce it.
