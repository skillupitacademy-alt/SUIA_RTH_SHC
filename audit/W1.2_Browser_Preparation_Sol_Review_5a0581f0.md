## R1 - cleanup must own its paths and preserve evidence

safe-reporter.ts onTestEnd unlinks any attachment.path; onEnd recursively removes
path.resolve(process.cwd(), 'test-results'). These paths are not checked against a
dedicated run-owned output root. This may remove unrelated reports or even arbitrary
files attached by path. It also deletes the child's/parent's shared directory during
nested sentinel runs. The workspace test-results directory exists at review time;
Sol therefore did not rerun the reporter's cleanup path against it.

Use an explicit dedicated, per-run output directory for this harness, separate from
the workspace's shared Playwright output and from nested child runs. Validate resolved
absolute path containment and run ownership before any deletion; reject escapes,
symlinks/junctions or foreign attachment paths. Do not delete arbitrary attachment
sources merely because a test references them. Prefer disabling raw capture at source
and scanning/removing only artifacts created inside the owned output root. Preserve
sanitized fixed-code failure/status evidence outside any raw-artifact cleanup.

Do not call fs.rmSync on the shared workspace test-results folder. Add offline tests
with a dedicated temporary run root, a foreign canary outside it and child/parent run
separation. Prove canaries and prior reports survive while synthetic secret artifacts
created by that run are not retained. Verify exact absolute cleanup targets; no live
test artifacts may be deleted during this correction.

The reporter still prints test.title/project/file directly; these are not validated
allowlisted IDs. Replace dynamic text with fixed project/scenario IDs or fixed unknown
labels. A dynamic title is another potential secret channel. Sentinel coverage must
include a fake secret title/global error/attachment and bare/split fake error output.
Do not assert universal 'zero leakage' solely from tested regex or a single fixture.

## R2 - browser requests need the same exact-origin policy as API calls

guardedApiFetch checks target origin against allowedOrigin. But
installNetworkOriginGuard(context) still only calls validateOriginSafety(requestUrl),
which allows EVERY localhost, *.localhost and *.local host/port. An offline fake-route
probe using the actual helper continued http://unapproved.localhost:61999/receive.
No network request was made: a fake context captured its routing callback and recorded
continue versus abort. Probe exit 0, continued=true.

Pass the project's explicit qualified origin set into the browser guard and reject
other local hosts/ports before dispatch, including form submissions and redirected
navigations. If a known local API origin is required, list it explicitly in that
project's controlled readiness record; do not expand to all local services. Reject
userinfo credentials in configured URLs. Keep serviceWorkers blocked and the API
helper's maxRedirects:0/exact-origin behavior. Return/await route.abort/continue so
errors are handled deterministically. Test browser and API target/port/redirect policy
with fake transport callbacks; no application or credentials required.

## R3 - account prerequisites are still evaluated after launch

The overridden context calls checkReadinessPrerequisites with projectName/projectOrigin
ONLY. requiredAccountVars is optional and omitted, so browser launch occurs without
checking that project's credentials. Specs then call enforceReadinessBoundary with
account fields in the test body, after page/context allocation. This contradicts the
handoff's pre-launch account guarantee. Wire a fixed project-to-account requirements
map (or typed fixture option) into context readiness. Unknown projects must fail closed.
Negative tests can have an explicit no-credential requirement but still require a
qualified controlled build/origin/fixture. Tests marked unsupported should skip without
allocating browser fixtures, rather than requesting auth then skipping in the body.

TEST_BUILD_REVISION and isolation flags are operator declarations, not independently
verified server deployment. Document what attests to build/fixture/account provenance;
do not describe nonempty env strings as proof the running server uses isolated data.
Supplied account/password information does not authorize production or establish a
blocked/same-email/private-resource fixture. Do not write passwords into configuration.

Add a fake browser-launch counter and run pre-fixture checks with all other fields
ready but account variables missing: assert zero launches. Also cover unknown project,
unqualified origin, absent build, and valid isolated fake prerequisites. Fake/mock
readiness tests do not establish actual Chromium login success.
