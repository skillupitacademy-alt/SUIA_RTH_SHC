## 2. Verification of Sol's 5 Review Findings

### Finding 1: Database Topology Traced via Routing and Connection Strings
- **Sol's Finding**: The initial document incorrectly inferred a single shared learner `users` table across brands from `packages/db`. `apps/api-server/src/modules/auth/brand-db.ts` already routes brands to `@quiz/db-skillup` and `@quiz/db-rth`, whose connectors use `DATABASE_URL_SKILLUP` and `DATABASE_URL_RTH`.
- **Gemini Independent Code Verification**:
  - Checked [`apps/api-server/src/modules/auth/brand-db.ts:93-107`](file:///E:/onlinewebsites/quiz-platform/apps/api-server/src/modules/auth/brand-db.ts#L93-L107):
    - `brand === 'skillup'` returns `{ db: skillupDb, tables: skillupTables }`
    - `brand === 'realtutorialhub'` returns `{ db: realtutorialhubDb, tables: realtutorialhubTables }`
    - `brand === 'skillhubcore'` returns `{ db: defaultDb, tables: defaultTables }`
  - Checked [`packages/db-skillup/src/index.ts:30`](file:///E:/onlinewebsites/quiz-platform/packages/db-skillup/src/index.ts#L30): uses `process.env.DATABASE_URL_SKILLUP`.
  - Checked [`packages/db-rth/src/index.ts:30`](file:///E:/onlinewebsites/quiz-platform/packages/db-rth/src/index.ts#L30): uses `process.env.DATABASE_URL_RTH`.
  - Both packages declare distinct `users` tables in their own schemas. Unique constraints in PostgreSQL apply strictly within each physical database.
  - **Verdict**: **CONFIRMED** ✅. Sonnet updated Section 2.1 and the Evidence Authority Table to document four distinct database roles (default, rth, skillup, people).

### Finding 2: Identity Bridge Semantics (Projection Mapping vs Impersonation)
- **Sol's Finding**: `LoginService` imports `@quiz/identity-bridge`, calls `syncUser` with brand `user.id` as `externalId` and brand as `platform`, stores the returned `shadowUserId` back on the brand user, and issues `originalUserId = user.id` with the bridge ID as `shadowUserId`. This is an existing brand-local-to-SHC projection mapping, NOT administrator impersonation.
- **Gemini Independent Code Verification**:
  - Checked [`apps/api-server/src/modules/auth/login.service.ts:32-52`](file:///E:/onlinewebsites/quiz-platform/apps/api-server/src/modules/auth/login.service.ts#L32-L52) and [`:178-191`](file:///E:/onlinewebsites/quiz-platform/apps/api-server/src/modules/auth/login.service.ts#L178-L191):
    - `ensureShadowUserId` calls `bridge.syncUser({ externalId: user.id, externalBrand: brand, email: user.email, platform: brand })`.
    - Token issuance explicitly binds `userId: user.id`, `originalUserId: user.id`, and `shadowUserId`.
  - Checked [`packages/identity-bridge/src/UserIdentityBridgeService.ts:20-84`](file:///E:/onlinewebsites/quiz-platform/packages/identity-bridge/src/UserIdentityBridgeService.ts#L20-L84):
    - Looks up `(externalId, platform)` in `db-people.users`.
    - If found, updates email and returns `shadowUserId: shadowUser.id`.
    - If not found, inserts new row into `db-people.users` with `(externalId, platform)` and returns `shadowUserId`.
  - **Verdict**: **CONFIRMED** ✅. The dual IDs represent the tenant-local user ID (`originalUserId`) and the central SHC coordination projection ID (`shadowUserId`). All speculative claims of admin impersonation have been completely purged from Sonnet's deliverable.

### Finding 3: The Real Email Conflict in `db-people.users`
- **Sol's Finding**: In `packages/db-people/src/schema/users.ts:10`, `email` has a global unique constraint, while line 26 has a unique index on `(externalId, platform)`. When the bridge inserts projections for learners on different platforms who share an email, a database constraint violation occurs.
- **Gemini Independent Code Verification**:
  - Checked [`packages/db-people/src/schema/users.ts`](file:///E:/onlinewebsites/quiz-platform/packages/db-people/src/schema/users.ts):
    - Line 10: `email: text('email').notNull().unique(),` (Global table-level unique constraint).
    - Line 23: `idxUsersEmailPlatform: index('idx_users_email_platform').on(table.email, table.platform)` (Non-unique index).
    - Line 26: `idxUsersExternalIdPlatform: uniqueIndex('idx_users_external_id_platform').on(table.externalId, table.platform)` (Unique index).
  - Traced execution failure: If Alice registers on SkillUp (`alice@example.com`), `db-people.users` gets an entry with `email='alice@example.com', platform='skillup'`. If Alice independently registers on RTH with `alice@example.com`, the bridge lookup on `(rth_id, 'realtutorialhub')` yields no match and attempts an `INSERT`, which fails due to `email.unique()`.
  - **Verdict**: **CONFIRMED** ✅. Sonnet correctly isolated the problem to `db-people.users` and proposed the smallest surgical correction: changing the global unique constraint on `email` to a composite unique constraint on `(email, platform)`.

### Finding 4: Session Storage Marked Unverified / Unknown
- **Sol's Finding**: Comparing `packages/auth`'s `SessionService` interface with `packages/db`'s `sessions` table did not establish the active repository or runtime storage. Concrete adapters must be traced or marked unresolved.
- **Gemini Independent Code Verification**:
  - `packages/auth/src/session.service.ts` defines an abstract `export interface SessionRepository` with an injected repository pattern.
  - `packages/auth/src/session.types.ts:25` declares `brand: string` in `CreateSessionInput`.
  - In `packages/db/src/schema/auth.ts`, `packages/db-rth/src/schema/users.ts`, and `packages/db-skillup/src/schema/users.ts`, none of the `sessions` tables have a `brand` column.
  - Furthermore, `apps/api-server/src/modules/auth/session.service.ts` defines a separate, un-abstracted `SessionService` directly importing `@quiz/db`.
  - **Verdict**: **CONFIRMED** ✅. Sonnet accurately marked session persistence as **UNVERIFIED / UNKNOWN**, documented the type-to-schema discrepancy, and created follow-on ticket `W1.1.2` to investigate concrete adapters rather than guessing.

### Finding 5: Removal of Premature and Overstated Claims
- **Sol's Finding**: Do not declare `shadowUserId` canonical for all consumers or plan `userId` removal; do not infer impersonation; do not mandate cryptographic signatures for ILS when opaque IDs with server-side validation suffice; align the 5 owner decisions with the document.
- **Gemini Independent Code Verification**:
  - *Canonical ID claim*: Replaced with qualified learner identity `(tenantContext, brandUserId)` with `shadowUserId` defined as a projection mapping.
  - *UserId deprecation*: Removed. Acknowledged as an active compatibility fallback in `apps/skillup-web/src/lib/student-auth.ts:94-99`.
  - *Impersonation*: All references to `originalUserId` meaning "admin impersonator" removed.
  - *ILS Session ID*: Corrected to server-generated, tenant-bound, learner-bound opaque IDs with server-side validation, removing mandatory cryptographic signing.
  - *Owner Decisions*: The 5 unresolved decisions in Section 7 were rewritten to match actual architectural questions:
    1. `db-people.users` email constraint correction (`composite unique (email, platform)` vs partitioned).
    2. Multi-platform token array (`platforms: string[]`) semantics (staff/service scope vs prohibited learner multi-membership).
    3. Session storage investigation and tenant binding (resolving type/schema mismatch).
    4. Administrative impersonation requirements (confirming whether impersonation is required at all).
    5. Architecture document amendment approval (`FinalAechitecture.md` lines 884–935, 2590, 2649–2664).
  - **Verdict**: **CONFIRMED** ✅.
