## 1. Executive Summary

Gemini 3.8 has performed an independent adversarial review of Claude Sonnet 4.5's W1.1.2 Session Persistence Investigation at commit `520e3d42f288e729f1a3000afde0040af67a2a7d`.

### What Sonnet Got Right
1. **Database Routing**: Traced `getAuthBrandContext(brand)` in `apps/api-server/src/modules/auth/brand-db.ts` and confirmed that tenant isolation relies on configuration-based database connection routing rather than schema constraints.
2. **Schema Audit**: Verified that `refresh_tokens` across `db-skillup`, `db-rth`, and `db` has no `brand` or `platform` column. Scoping is enforced solely by database routing and foreign key references to `users.id`.
3. **Broken `logout-all` Endpoint**: Accurately proved that `apps/api-server/src/app/api/auth/logout-all/route.ts` imports the generic `SessionService` from `@quiz/auth/session.service`. The DI container instantiates `new SessionService()` without arguments, leaving `this.repository` undefined, which guarantees a runtime `TypeError`.
4. **Token Refresh Vulnerability**: Accurately identified that `apps/api-server/src/modules/auth/token-refresh.service.ts` line 46 calls `findByHash(oldTokenHash)` on `TokenRepository` without scoping by `userId` or `brand`.
5. **Session Domain Distinction**: Strictly separated authentication sessions (`refresh_tokens`) from ILS tutorial learning sessions (`tutorialLearningSessionId` in `tests/e2e/ils-tutorial-session.spec.ts`).
6. **Strict Read-Only Scope**: Zero production source code, database tables, credentials, or migrations were modified.

### Critical Adversarial Findings & Corrections
1. **MAJOR BLIND SPOT — Missing Route Discovery**:
   Sonnet claimed in Sections 4, 5, 7.4, 10.1.3, and 11.5 that:
   - No session listing route exists (`GET /api/auth/sessions`).
   - No single-session revoke route exists for learners (`DELETE /api/auth/sessions/:id`).
   - The device sessions UI (`src/share-branding/ui/device-sessions.tsx`) is a frontend-only component with no backend.
   
   **Reality Uncovered by Gemini**:
   - `apps/api-server/src/app/api/auth/sessions/route.ts` actively exists and implements:
     - `GET /api/auth/sessions`: Returns active sessions via `GlobalLogoutService.getActiveSessions`.
     - `DELETE /api/auth/sessions`: Executes global logout via `GlobalLogoutService.logoutAllDevices`.
   - `apps/api-server/src/app/api/auth/sessions/[sessionId]/route.ts` actively exists and implements:
     - `DELETE /api/auth/sessions/[sessionId]`: Revokes a specific session via `GlobalLogoutService.revokeSession`.
   - The UI component `src/share-branding/ui/device-sessions.tsx` calls these exact endpoints (`/api/auth/sessions` and `/api/auth/sessions/${sessionId}`).

2. **CRITICAL SECURITY FLAW IN EXISTING `GlobalLogoutService`**:
   In `apps/api-server/src/modules/auth/global-logout.service.ts` line 113:
   `GlobalLogoutService.revokeSession(userId, sessionId, ip, brand)` accepts `userId`, but invokes `await brandTokenRepo.revokeById(sessionId);` **without passing `userId`**!
   Because `TokenRepository.revokeById(id, userId?)` only scopes to `userId` when provided, omitting `userId` allows an authenticated learner to revoke another user's session within the same brand database if the session UUID is known.

3. **Existing Brand Guard Overlooked**:
   Both `/api/auth/sessions` and `/api/auth/sessions/[sessionId]` already invoke `validateBrandOrThrow({ brand: payload.brand, userId: payload.userId }, _req)` from `packages/auth/src/middleware/brand.guard.ts`, proving that brand validation is already implemented for these endpoints.

4. **Line Number Offsets**:
   Sonnet's report contains systemic citation offsets (typically 30–50 lines off) across `brand-db.ts`, `login.service.ts`, `token-refresh.service.ts`, and `token.service.ts` (e.g., citing lines 529–572 for token generation when they are actually verification functions; generation is at lines 281–331).

## 3. Namespace Analysis: `userId` vs `originalUserId` vs `shadowUserId`

The investigation and codebase confirm significant tension across layers:
1. **Database Layer (`refresh_tokens`)**:
   - `userId` (UUID) references `users.id` in `db-skillup` or `db-rth`.
2. **Token Generation (`token.service.ts:290-296`)**:
   - `originalUserId` defaults to `userId` (brand-local learner UUID).
   - `shadowUserId` defaults to `userId`, but during login is populated with the SHC projection ID (`people_db.people.id`).
3. **BFF Gateway Layer (`src/share-branding/middleware/authProxy.ts:400-402`)**:
   - Sets HTTP header `x-user-id` = `shadowUserId`.
   - Sets HTTP header `x-shadow-user-id` = `shadowUserId`.
   - Sets HTTP header `x-original-user-id` = `originalUserId`.
4. **API Server Session Routes (`apps/api-server/src/app/api/auth/sessions/route.ts:36`)**:
   - Explicitly notes: `"CRITICAL: Use the original user ID (not shadow) for session operations: const userId = payload.userId;"`.

**Conclusion**: The authentication session boundary correctly uses `payload.userId` (tenant-local learner ID), but the BFF header rewrite (`x-user-id = shadowUserId`) creates dangerous potential for cross-layer confusion if downstream services read `x-user-id` instead of JWT claims.
