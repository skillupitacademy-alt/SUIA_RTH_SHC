## 3. Production Fix Verification

### 3.1 TokenRepository.revokeById (`token.repository.ts:66-79`)

**PASS — Correctly implemented.**

```typescript
async revokeById(id: string, userId: string) {
  if (typeof userId !== 'string' || userId.trim().length === 0) {
    throw new Error('W1.2-SESS-01: userId is required for session revocation');
  }
  await this.dbInstance.update(this.refreshTokensTable)
    .set({ revoked: true })
    .where(and(
      eq(this.refreshTokensTable.id, id),
      eq(this.refreshTokensTable.userId, userId)
    ));
}
```

Security verification:
- **TypeScript enforcement**: `userId: string` (mandatory, not optional). Previous signature was `userId?: string`.
- **Runtime fail-closed**: Guards against `undefined`, `null`, empty string, whitespace-only, and non-string types via `typeof` + `trim()` check. This catches JavaScript callers, `any` casts, and accidental omissions.
- **Dual WHERE predicate**: `and(eq(id), eq(userId))` — single atomic SQL statement with both session ID and owner ID. No conditional predicate assembly; no fallback to unscoped query.
- **No information disclosure**: Returns void; does not reveal whether the session exists under another owner.
- **Caller audit**: Only one production caller — `global-logout.service.ts:114`. All other references are in test mocks (`vi.fn()`). No unscoped `revokeById` path remains.

## 6. Adversarial Analysis

### 6.1 Can an attacker bypass ownership?

**No.** The verified identity chain is:

```
Bearer token → tokenService.verifyAccessToken() → payload.userId
                                                       ↓
                                        globalLogoutService.revokeSession(userId, ...)
                                                       ↓
                                        brandTokenRepo.revokeById(sessionId, userId)
                                                       ↓
                                        WHERE id = ? AND userId = ?
```

At no point does the route read user identity from request headers, body,
query parameters, or the sessionId path parameter. The only identity source
is the cryptographically verified JWT payload.

### 6.2 Can a JavaScript caller bypass TypeScript enforcement?

**No.** Runtime validation at L68-70 checks `typeof userId !== 'string'`
before any database operation. This catches `undefined`, `null`, numbers,
objects, and any value an `any` cast or JavaScript caller might provide.

### 6.3 Can colliding tenant IDs cause cross-tenant revocation?

**No.** `getAuthBrandContext()` returns distinct `db` instances and `tables`
objects per brand. `TokenRepository.withDb()` creates a new repository instance
bound to the brand-specific database. The tenant isolation test proves this
with identical user-A/session-100 IDs across RTH and SUIA fixtures.

### 6.4 Is the mutation test genuinely sensitive to the fix?

**Yes.** The test reads actual production source from disk, creates a mutant
by regex-removing only the userId equality predicate, and runs the identical
fixture adapter against both versions. The mutant demonstrably changes the
victim row; the production code does not. This is not a handwritten subclass.

### 6.5 Could the `eval`-based mutation approach be fragile?

**Minor concern, not a security gap.** The regex extraction
(`/async revokeById\([^)]*\)\s*\{([\s\S]*?)\n  \}/`) depends on specific
indentation. If the production method's closing brace indentation changes,
the regex would fail. However, this would cause the test to throw
`Failed to extract revokeById from production source` (an explicit failure),
not a silent false positive. The test is fail-safe in this regard.

## 7. Findings

### 7.1 MINOR — Unnecessary `@ts-expect-error` directive

**File:** `global-logout.ownership.test.ts:144`
**Line:** `// @ts-expect-error Testing accidental empty string`
**Issue:** `revokeSession(userId: string, ...)` accepts any `string`, including
empty string `''`. TypeScript does not error on this call, making the directive
unnecessary. With `allowUnusedLabels` or strict `@ts-expect-error` checking
enabled, this would produce an `unused-directive` diagnostic.

**Severity:** Minor hygiene. Not a security gap. Does not affect test
correctness — the test still exercises the empty-string path and verifies the
repository throws.

**Recommendation:** Remove the `@ts-expect-error` comment on L144 or replace
with a plain comment explaining the intent.
