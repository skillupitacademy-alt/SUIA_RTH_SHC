## Why next

Conditional consumption and successor persistence need a single transaction.
The current read-before-transaction and unconditional revoke do not enforce that
at most one request consumes an active parent. Prove the interleaving first and
correct the authoritative repository/service path, without redesigning identity.

PHASE 1 - REPRODUCE BEFORE FIX:
Use actual refresh service/repository code, safe isolated fixtures and deterministic
barriers rather than sleeps. Two requests must both reach the active-parent read
before either consumes. Test distinct successors AND same-second identical signing
inputs, respecting the actual unique-token constraint. Verify real signer behavior
using test-only keys without exposing secrets. Capture old behavior: multiple
consumption/distinct successors or uniqueness failure. Do not force a fixture
claim of two successful inserts when the real unique constraint would reject it.

PHASE 2 - MINIMAL IMPLEMENTATION:
1. Add a dedicated atomic consume operation, leaving generic revokeToken semantics
   intact for other callers. Its update includes token hash, expected row owner,
   revoked=false and appropriate unexpired-state condition, and returns consumed
   row/affected-row evidence. Use the same verified brand-bound table/transaction.
2. Inside one transaction, require exactly one successful parent consumption
   before inserting its successor. Zero/invalid consumption aborts with no
   successor returned or persisted. Insert failure rolls back parent consumption.
   Never continue after a lost compare-and-swap or ignore affected rows.
3. At most one concurrent request returns success. Generated but uncommitted
   tokens must never leak in response/logs. Retain safe existing error contracts
   and avoid revealing token existence. Reuse is rejected; do not automatically
   revoke unrelated sessions or a hypothetical token family.
4. If the first phase proves identical-token collisions, make new refresh tokens
   independently unique via an additive server-generated jti in the existing
   generator. Keep existing legacy refresh tokens accepted by the unchanged
   verifier; do not require old tokens to have jti. Preserve all identity claims,
   keys, audiences, expirations, original/shadow IDs and platform semantics.
5. Preserve session-revocation ownership fix and platform-separated DB selection.
   This task does not certify request tenant authority or fix every refresh risk.

REQUIRED REGRESSIONS:
- Normal rotation consumes one parent and stores exactly one successor.
- Deterministic concurrent requests produce one winner and no second successor.
- Used, expired, absent parent and wrong expected row owner cannot be consumed.
- Failure inserting successor rolls back consumption and leaves no orphan.
- Distinct tenants with colliding local IDs remain isolated.
- Same-second minting yields distinct new tokens if jti is introduced; legacy
