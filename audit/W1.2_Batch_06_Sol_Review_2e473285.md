## A - Infra caller mapping would cause an implementation regression

The tenant-admin scope says no production path passes aud:infra to _verifyAdmin. Actual
API proxy source sets infrastructure scope/audience from the portal header, but its
isInfraRoute predicate covers only /api/admin. Requests under /api/factory and
/api/analytics/admin with that portal select the later isAdminRoute branch and call
_verifyAdmin. Source routes exist under these prefixes, including factory/save and
analytics/admin/topic-skill-heatmap. This is a source-path finding, not a live caller or
exploit claim. A standalone evaluation of the exact current predicates confirmed the
branch distinction without network traffic.

Likewise, the SHC bypass predicate covers /api/admin and /api/factory, not every possible
analytics-admin/header combination. The route-level helper's infra bypass is a separate
fact and cannot prove that the API proxy always bypasses the tenant helper.

Strict aud:admin helper policy therefore needs an explicit caller/routing adaptation
decision and regressions for those combinations. Do not implement from the current
claim of no adaptation. Distinguish observed source, approved policy and unknown external
callers; avoid calling a direct helper weakness a demonstrated deployed vulnerability.

## B - Learner-purpose scope must not create entitlement

The proposal invents a student role when filtering leaves no learner roles, then says
the new session can access all learner courses/exams/dashboards. Authentication purpose
does not grant enrollment, resource ownership or a new role. Preserve legitimate existing
non-admin claims and enforce separate resource authorization; do not synthesize student
authority without an explicit policy decision and regression.

Legacy role-derived behavior must be justified by a caller compatibility inventory,
not merely preserving test outcomes. Define a narrow typed server-purpose contract,
unsupported-value behavior, all public login/signup forwarding points, and consistent
access/refresh/session claims and cookie choice. Do not imply refresh or dedicated
admin/infra compatibility is automatically covered by an access-token example.

## C - Logout-all facts and compatibility contract need correction

Current access tokens use HS256 and an 8h default, not the reported private-key/15-minute
scheme. Do not change TTL or crypto as part of this decision. The legacy route catches
service exceptions and returns handleAuthError's response; the missing-repository defect
does not establish an uncaught process-level crash. requireValidSession currently requests
session validation but its authenticate implementation has that check as a TODO; state
the executed behavior rather than the method name alone.

The canonical DELETE sessions handler does not itself issue cookie clears, and clearing
cookies in the proposed compatibility adapter is a proposed behavior, not inherited
canonical behavior. The undefined old repository has no established DB binding. Explain
the legacy vs refresh-row counting semantics and count-before-revoke race/partial-failure
limits; functional response equivalence cannot be inferred solely from equal field names.
Explicitly decide which principal classes the preserved legacy endpoint accepts before
replacing its generic verifier with user-only verification. No live all-device call is
authorized or required to settle these source/contract questions.

## D - Login fixture keys, containment and report boundaries

The seven controls execute actual LoginService and PasswordService with in-memory
repository adapters; they are useful selected-service evidence. The adapters implement
repository methods, not Drizzle-compatible query surfaces, and do not exercise actual
UserRepository SQL or physical database isolation.

All seeded users have shadowUserId, so ensureShadowUserId returns immediately. The
reported identity-bridge failure/test-environment fallback is not exercised. Correct
the report/handoff and assert which branch is taken rather than claiming fallback use.

Fixture 01 constructs new TokenService() without explicit test keys, so it depends on
the ambient static/env configuration. No test-local outbound transport fail-fast or
identity-bridge non-use assertion is present. The review supplied disposable child-process
environment keys before running, but that does not make the submitted fixture self-contained.
Inject its own disposable keys and guard/mock outbound infrastructure before service
invocation. Restore any altered globals/env and keep wrong-store sensitivity evidence.

## E - Separate cryptographic key rejection from principal/audience rejection

Fixture 02's promoted-learner and user-audience cases mint under ACCESS_SECRET and
verify under a different ADMIN_SECRET. They fail at signature verification before
audience/class enforcement. That proves a distinct-key boundary, not the full stated
principal-policy invariant under the supported ADMIN_JWT_SECRET -> JWT_SECRET fallback.
The shc-admin audience mismatch case does independently exercise an audience check,
but does not substitute for the promoted learner/shared-key case.

An independent two-case crypto-layer probe confirmed: distinct keys produce
ERR_JWS_SIGNATURE_VERIFICATION_FAILED; shared disposable access/admin keys reach
Audience mismatch for the same learner claims. These were offline actual TokenService
calls, not a production configuration claim. Add actual requireAdminRouteAccess cases
with a cryptographically valid signature for the admin verifier, isolating wrong
audience and wrong token class, including the promoted-account fixture. Assert both
the denial reason/layer and zero actual query initiation; do not rely only on generic
rejects.toThrow. Restore the container override after each test rather than leaving
TokenService registered. Describe the helper chain, not an entire executed HTTP route.
