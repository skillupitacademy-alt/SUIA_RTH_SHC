## Approved decision

GitHub provides source control; Hostinger provides hosting/deployment.
W0.2 implements a platform-independent repository command,
`pnpm quality:skillhubcore`, with independently runnable stages and a
fail-fast aggregate covering architecture, security, lint, typecheck, safe
unit tests and build. Existing checks should be reused where sound.

GitHub Actions activation and required GitHub branch checks are `DEFERRED`
at the owner's direction. They are not W0.2 acceptance prerequisites.
Existing disabled workflows remain disabled. No deployment workflow is
authorized. Local hooks supplement, but do not replace, the repository gate.

This decision supersedes W0.2 instructions requiring an active GitHub
workflow, a GitHub CI-green claim or required GitHub status checks. Quality
execution and failure enforcement remain mandatory. It does not close
`RC-CI-01` or waive verification for later application tickets.

## Deployment-path investigation

Repository documentation describes a Hostinger VPS/Docker Compose framework.
However, `deploy-production.sh` disables VPS-side builds by default, and the
repository also contains local image build/save, registry push/pull and image
load entrypoints. This is source evidence, not proof of which path is
currently executed on the host.

Before integration, trace the current build-to-artifact-to-deployment path.
Place quality verification where the tested source is built. If prebuilt
images are deployed, bind verification evidence to the source commit and
image/build provenance; do not require rebuilding on the VPS or treat an
unbound PASS file as authorization to deploy.

Where the active deployment path is not established, provide a clearly
labelled integration proposal and record deployment enforcement as
`IMPLEMENTED_UNVERIFIED` or `PLANNED`, as appropriate. Never infer runtime
verification from repository scripts. Production deployment is outside this
ticket's authorization.

## Acceptance evidence

1. Reproduce the canonical quality command with pinned Node/pnpm/lockfile
   requirements and documented environment prerequisites on supported hosts.
2. All required stages execute and failure yields a nonzero aggregate exit.
3. Demonstrate controlled checker/test failures in isolated fixtures; do not
   weaken checks or leave injected violations in application files.
4. Baseline existing violations explicitly; reject additions and detect
   missing/unscanned paths. Baseline changes require review.
5. Bound safe tests to avoid production DB/network use. Integration/migration
   checks use isolated resources when applicable or retain an explicit gap.
6. Gemini independently reproduces commands and adversarial cases read-only.
7. Document deployment invocation/enforcement and actual evidence separately
   from repository validation. Untested Hostinger behavior remains open.

Evidence has three layers: repository checks; deployment/artifact/startup
verification; runtime authorization/brand/data/browser verification. Passing
the first layer does not establish either later layer.
