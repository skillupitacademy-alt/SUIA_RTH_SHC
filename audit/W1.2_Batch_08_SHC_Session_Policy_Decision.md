## 1. Executive Summary & Problem Statement

The platform's governance administrative portal, **SkillHubCore Admin (`apps/skillhubcore-admin`)**, currently exhibits an unaligned session lifecycle architecture:
1. `apps/skillhubcore-admin/src/app/api/auth/login/route.ts` proxies upstream to `api/shc/auth/login`.
2. `packages/auth/src/token.service.ts` (line 4) defines `const ACCESS_TOKEN_EXPIRE = '8h'`. By default, access tokens (for both learners and administrators) carry an 8-hour cryptographic lifespan (`8h` / 28,800 seconds).
3. In `apps/skillhubcore-admin/src/lib/admin-session-cookies.ts`, four cookies are set upon login: `accessToken`, `admin_accessToken`, `refreshToken`, and `admin_refreshToken`.
4. However, `apps/skillhubcore-admin` has **no `/api/auth/refresh` route mounted**.
5. In `SHCAuthService`, a refresh JWT is minted at login, but no corresponding database insertion or tracking row is created in the shown login path.
6. The client administrative interface relies on an in-memory client state store and a **15-minute client-side idle lock screen** (`AdminLockScreen.tsx`), which prompts for password re-authentication, rather than any automated background sliding refresh.
7. The SHC app does not mount the refresh routes; FetchClient can nevertheless attempt a refresh fallback. This does not establish successful rotation or prove that no other consumer exists.

This document formally presents the two competing session lifecycle models as an **undecided architectural contract decision** for explicit owner selection.

## 2. Accurate Source-Grounded Baseline

### 2.1 Token Lifespan & Expiry Truths
- **Access Token TTL (`packages/auth/src/token.service.ts` line 4):** Default is `8h` (8 hours). Neither learner nor administrator access tokens expire in 15 minutes by default; they remain cryptographically verifiable for 8 hours unless an explicit custom expiration is passed.
- **Refresh Token TTL (`packages/auth/src/token.service.ts` line 5):** Defined as `7d` (7 days).

### 2.2 Database Topography: `people_db` vs `defaultDb`
- `people_db` is the unified auth and identity database repository used for cross-brand principals.
- `defaultDb` is the application database instance for general platform operations.
- They are separate database connections and connection pools, not synonyms.

### 2.3 Upstream SHC Auth & Client Handlers
- **Upstream Handler (`SHCAuthService`)**: Generates an HS256-signed refresh token JWT for the admin principal (`aud: 'shc-admin'`), but does not register the session in an active server-side session table.
- **Admin BFF (`apps/skillhubcore-admin/src/app/api/auth/login/route.ts`)**: Proxies login to `api/shc/auth/login` and invokes `setAdminSessionCookies`.
- **Admin Lock Screen (`apps/skillhubcore-admin/src/components/auth/AdminLockScreen.tsx`)**: Watches for 15 minutes of user inactivity in the browser client. When triggered, the screen locks and requires password entry to unlock via `loginPortalSession`.
- **Server Refresh Gap**: `apps/skillhubcore-admin` does not mount `/api/auth/refresh` or `/api/admin/auth/refresh`. The mounted SHC app provides no corresponding local refresh route; this source observation does not establish the behavior of every direct or legacy upstream caller.

## 3. Undecided Future Contract: Owner Choices

The platform owner and architectural governance body must select between two distinct operational session architectures:

### Option A: Formalize the Absolute Session Model
A fixed-lifetime design is a future option. An 8-hour token expiry alone is not an absolute session-family cap, and cookie removal requires separate approval.

- **Access Token:** Retain the current interim 8-hour per-issued-token lifespan (`ACCESS_TOKEN_EXPIRE = '8h'`).
- **Refresh Tokens:** Deprecate and remove `refreshToken` and `admin_refreshToken` from SHC Admin cookies.
- **Inactivity Protection:** The current client UX includes `AdminLockScreen.tsx` (15-minute idle lock requiring password to unlock).
- **Session Termination:** A future absolute cap would require server enforcement across all issued credentials; current access token expiry alone does not establish it.
- **Trade-offs:**
  - *Pros:* Could simplify refresh choreography if an approved migration removes refresh capability and addresses consumers.
  - *Cons:* Absent an effective revocation check, a compromised access token may remain usable until its issued expiry; refresh credentials and any direct consumers require separate analysis.

### Option B: Consider sliding refresh token rotation
Migrate SHC Admin to an enterprise sliding session model with short-lived access tokens and atomic server-side refresh rotation.

- **Access Token:** Shorten `aud: 'shc-admin'` access token TTL to 15 or 30 minutes.
- **Refresh Token:** Establish stateful single-use refresh token rotation in `people_db`.
- **Refresh Route:** Mount a dedicated `POST /api/auth/refresh` route in `apps/skillhubcore-admin`.
- **Auto-Refresh:** Implement a client-side background timer or fetch interceptor to refresh tokens periodically while active.
- **Inactivity Protection:** Any inactivity limit must be enforced server-side; client refresh timing alone is insufficient.
- **Trade-offs:**
  - *Pros:* Short-lived access limits one access token lifetime; stolen refresh credentials and actual revocation must also be addressed. Replay detection requires server state and a classified policy.
  - *Cons:* Requires substantial new runtime code, new database persistence tables in `people_db`, and integration testing across BFF and client.

## C16 lifecycle recommendation refinement (proposal, no adopted change)

Recommend a server-authoritative session family with a fixed absolute expiry and independently enforced inactivity deadline; access credentials bind to a revocable session identity, and reauthentication creates or upgrades authority only after verified challenge. A stateful single-use refresh rotation should use an atomic consume-and-replace transaction, explicit origin/CSRF checks and durable cross-instance state. One successful concurrent refresh may rotate; competing legitimate retry must have a narrowly specified idempotent recovery/grace rule or fail closed, with replay differentiated from network retry rather than automatically revoking a family on every duplicate. Storage or authorization-service outage denies refresh and privileged session extension with a safe retry response; it must not silently create an untracked session. The owner must choose cap/idle durations, reauthentication step-up triggers, retry/grace and suspicious-replay response, and legacy credential cutover. Legacy credentials without verifiable session binding need a bounded reauthentication or explicitly approved expiry transition; do not infer a stored row from a minted token. Session state and revocation checks must work across instances. Proposed scope includes SHC issuer/logout, token repository and refresh service, session cookies/BFF routes, FetchClient, AdminGuard/lock consumers, schema/session storage and concurrent/outage tests; each requires separate acceptance and implementation authority. Existing 8-hour issuance/cookie compatibility remains the interim selected policy, not a newly adopted lifecycle.
