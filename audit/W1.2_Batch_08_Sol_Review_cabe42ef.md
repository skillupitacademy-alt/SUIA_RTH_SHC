## Confirmed source findings and limits

### Tutorial progress identity

apps/api-server/src/app/api/tutorial/progress/route.ts reads raw x-user-id and uses an
unverified/defaulted x-brand for POST. GET constructs the default tutorial repository.
The submitted fixture mocks both TutorialService and TutorialProgressRepository, so its
passing examples do not establish real engine or repository tenant binding.

Sol linked the actual proxy to GET and POST in offline controls. Forged GET was forwarded
and returned 200. A first POST probe stopped at CSRF, before the handler. After supplying
a matching disposable CSRF cookie/header pair and same-origin request, the actual proxy
forwarded the forged POST and the actual handler returned 200, with a write to the mocked
victim record. Authentication remained absent. This isolates the identity defect while
preserving the independent CSRF precondition. Actual SQL writes were not performed.

Removing the entire /api/tutorial exemption affects unrelated callers and is not selected
as a blanket correction. Route authentication must derive the subject from verified
claims and preserve the legitimate ingress contract. Shared tutorial progress currently
keys userId/subtopicId without a tenant discriminator, and the engine's validateBrandAccess
currently returns true. These are separate resource-binding findings. A JWT check alone
cannot certify independent-tenant progress isolation.

### Export ownership and resource provenance

The actual status handler verifies a user token and loads a job by jobId without checking
job.userId. The non-owner test returned 200 instead of 403. Authorization must precede
workflow reads, storage checks and recovery updates, including stale/missing-job paths.

The download handler checks only userId for both job and exam branches. Sol used actual
TokenService verification and a real foreign-brand token with an equal local user ID
against the existing isolated resource adapters. Both jobId and examId requests returned
200 instead of the required denial. These direct-handler controls establish the absent
brand/resource-context check at that seam. They do not establish deployed database routing.
JobsService imports the default database, and current job schema/payload examples do not
supply an authoritative tenant discriminator. A userId-only guard cannot close this risk.
Legacy resources need an explicit authority/compatibility design, with unknown ownership
denied instead of guessed from a requesting token, raw header or blob path.

### Internal authentication fallthrough

B08-G calls validateRequest and validateGatewaySecret in isolation. Its alleged valid
learner credential is a literal fake token and is never cryptographically verified.
The API proxy instead checks x-internal-key against INTERNAL_API_KEY for a system bypass.
With a real signed learner token, the proxy forwarded a control request. Adding an
explicitly incorrect x-internal-key still produced forwarding status 200. The final probe
requires 403 and fails. This qualifies the proxy boundary, not an executed sensitive
handler or a claim that all public paths require internal secrets. Missing privileged
headers and explicitly rejected privileged credentials require distinct policy handling.
The boundary map also misidentifies gateway middleware's expected legacy secret, which
is INTERNAL_GATEWAY_SECRET rather than GATEWAY_TRUST_SECRET in that helper.

## Evidence corrections

B08-C's sensitivity case directly flips a canary then expects true. It does not redirect
a real operation to a wrong store or require the ordinary isolation assertion to fail.
B08-D uses an unknown brand instead of two canonical conflicting tenant contexts, and
its contradictory boolean token also has user tokenType. Missing mixed-array and actual
route-level downstream assertions need focused controls.

B08-H mocks validateAuthState, clears its own MockClientContext in mocked transport and
resolves a delayed promise that no production state consumer observes. It never exercises
actual cache/storage ownership or a delayed response commit. These are wrapper tests.
The assignment permits NOT EXECUTED with a concrete missing-fixture finding.

B08-I incorrectly describes existing learner access expiry as 15 minutes. The current
TokenService default is 8 hours. people_db is not a synonym for defaultDb. SHCAuthService
mints a refresh JWT without a corresponding insert in the shown login path. Source
comments about storage are insufficient persistence evidence. Screen lock is client UX,
and an 8-hour per-issued access JWT does not itself establish an absolute session-family
cap or server-side inactivity enforcement. FetchClient retry/refresh consumers and mounted
routes need a complete compatibility trace. Session-family replay revocation and a
15-minute SHC target are proposals requiring separate decisions, schema and rollout work.

Architect decision for this review retains the accepted current 8-hour issuance and
existing cookie/consumer compatibility while the SHC design is corrected. Sliding refresh,
refresh mounting, cookie removal, people-store persistence and key/TTL changes are not
approved by this submission. Required future server-side expiry/revocation properties
remain explicit unresolved security requirements.
