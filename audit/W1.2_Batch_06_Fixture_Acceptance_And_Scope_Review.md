## Remaining GUARD-03 corrections

1. The updated caller matrix still claims an analytics route's no-options
   verifyAdminAccessToken call defaults to aud:admin and rejects infra. Actual verifier
   behavior with no requested audience permits admin/infra audience values, then checks
   token class and identity. Separate proxy and handler checks, cookie extraction and
   ANALYTICS_VIEW permissions; do not infer a handler verdict from a fictional default.
2. Proposed infra bypass expansion would remove the existing tenant active-account DB
   check on factory/analytics paths. Preserve equivalent eligibility or make that
   security/compatibility change explicit for architectural decision; it is not merely
   fixing routing. Preserve route-specific permissions in addition to ADMIN_PANEL.
3. The proposed deny-user/unknown-header rule conflicts with the document's preservation
   of absent/default admin callers. Current path-based scope selection can choose admin
   even when the header defaults to user. State exact missing/explicit/unknown-header
   behavior with valid signed admin claims; headers alone are not authority.
4. Learner spec lists tokenType/isAdmin as refreshTokens table columns; they do not
   exist. Preserve the current schema: owner/hash/tenant binding stores the session,
   while signed tokens carry principal metadata. No migration is authorized.
5. Define backward compatibility with the existing fifth positional deviceContext
   argument before introducing nested LoginOptions. Retain device metadata or inventory
   every adapted caller; a new optional type does not automatically preserve old calls.
   Resolve the empty-role recommendation versus an explicitly pending alternative and
   define future service-error-to-HTTP mapping without claiming new classes already exist.

These are bounded specification corrections, not permission to alter gateway roles,
mint new entitlements or implement the future helper/login policy in this batch.

## Remaining SESS-03 corrections

The revised HS256/8h, caught-error, snapshot-count and canonical cookie facts are useful.
Two current-source statements remain too broad: the generic verifier does enforce
token class while omitting a requested audience, and admin keys may be separate from
JWT_SECRET. Describe those actual branches rather than claiming any JWT_SECRET token
passes without tokenType checks.

A thrown revocation query does not prove no rows were revoked: a lost response after
commit can leave an unknown outcome. Distinguish a confirmed pre-commit rollback from
unknown delivery/outcome. AuditService normally absorbs insert failures; do not equate
every audit failure with an exception propagated to the adapter.

The partial-failure result remains ambiguous ('informed or appropriate error'). Specify
one response/count/cookie behavior for each confirmed-revocation, presence-failure,
audit-failure and unknown-outcome case, compatible with current service boundaries.
Do not promise stage-specific handling using only a route whitelist when the service
does not expose that stage. Any necessary future service change must be explicitly
scoped; no implementation or live all-device test is authorized now.
