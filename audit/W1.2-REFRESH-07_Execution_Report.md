## 1. Executive Summary & Production Scope

Task A of Gemini Controlled Batch 05 removes the redundant, pre-transaction timestamp write `brandTokenRepo.updateLastUsed(oldTokenHash)` in `apps/api-server/src/modules/auth/token-refresh.service.ts`.

### Defect Remediation:
- **Prior Flaw**: Prior to this fix, Step 2.8 executed an autocommitted `updateLastUsed(oldTokenHash)` statement against PostgreSQL *before* Step 3 (CPU-bound JWT generation) and *before* Step 4 (Compare-and-Swap database transaction). If token signing failed or if a concurrent request consumed the parent token first, the parent's `lastUsedAt` timestamp remained modified in the database despite the request failing or rolling back.
- **Root Cause Resolution**: `TokenRepository.consumeToken` (`apps/api-server/src/modules/auth/repositories/token.repository.ts:76-87`) already atomically executes:
  ```ts
  .set({
    revoked: true,
    lastUsedAt: now,
  })
  .where(and(
    eq(this.refreshTokensTable.token, tokenHash),
    eq(this.refreshTokensTable.userId, expectedUserId),
    eq(this.refreshTokensTable.revoked, false),
    gt(this.refreshTokensTable.expiresAt, now)
  ))
  ```
  inside the CAS transaction. Removing Step 2.8 ensures that `lastUsedAt` is updated **exclusively upon successful CAS consumption** within the database transaction. If signing fails, if the CAS race is lost, or if child insertion fails, zero timestamp side effects survive in PostgreSQL.

## 5. Optional Revoked-Record Diagnostics Disposition (Design-Only)

As instructed by Batch 05 Task A, diagnostics remains **strictly design-only** in this ticket:
- **Findings from REFRESH-04**: Generic `refresh_tokens` table lacks `consumed_at`, `revoked_at`, and `reason` columns. Therefore, an unfiltered database lookup (`SELECT * FROM refresh_tokens WHERE token = $1`) can only observe `revoked === true`.
- **Classification Limit**: A `revoked === true` record cannot be proven to be a rotated token; it could be a token revoked via global logout, password reset, or admin revocation.
- **Proposed Future Schema**: If diagnostic telemetry is desired in a future ticket, an optional nullable enum column `revocation_reason: 'consumed' | 'logout' | 'security'` could be proposed.
- **Governance Invariant**: No runtime diagnostic lookup, raw-token logging, or automatic multi-device revocation was implemented. All requests presenting invalid or non-active tokens continue to fail closed with HTTP 401 `Invalid refresh token`.

## 6. Engineering Principle Compliance

- **Single Responsibility Principle (SRP)**: `TokenRefreshService` delegates stateful consumption exclusively to `TokenRepository.consumeToken` inside the atomic CAS transaction.
- **KISS & YAGNI**: Removed redundant pre-transaction write instead of adding complex two-phase rollback handlers.
- **Fail-Closed & Defense-in-Depth**: All authority and eligibility checks precede transaction entry; failure at any point leaves the parent token state pristine.
- **Clean Persistence Boundaries**: Transient signing errors and concurrent race losses leave zero metadata trace in the database.
