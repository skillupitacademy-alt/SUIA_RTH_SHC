## Owner-Approved Architecture Direction

From `audit/W1.1_Architecture_Decision_For_Owner_Approval.md`:

1. **SUIA** (`skillup`) and **RTH** (`realtutorialhub`) own independent learner accounts, credentials/session boundaries and learner records
2. The same person can have two independent accounts; matching email/IDs never link accounts or confer access
3. Qualified learner references include verified platform and local learner ID; no duplicate `tenantId` field by default
4. SHC may retain platform-specific infrastructure projections; projection is service cross-reference, not shared global account
5. `shared` describes resource scope; access requires applicable policy, verified caller, tenant entitlement and permission

**Exclusions:** No schema changes, credential/session changes, migration execution, data cleanup, token redesign, impersonation, SSO, cross-tenant automatic linking, deployment or main merge authorized in W1.1.

## Architecture Before/After

### BEFORE (Global Learner Identity Model)

**FinalAechitecture.md Section 3:**
> "Your global identity model should separate the identity of a person from their relationship with a brand."

**Conceptual Model:**
```
people_prod (global identity)
├── users (id = global_user_id)
├── identity_credentials
└── user_brand_memberships
    ├── user_id (FK to people.users.id)
    ├── brand_id
    ├── brand_user_id
    └── status

rth_prod / skillup_prod (brand data)
├── learner_profiles
│   └── global_user_id (references people.users.id)
├── enrollments
└── tutorial_progress
```

**Identity Flow:**
1. Create/verify global identity in `people_prod`
2. Match to offline student record
3. **Assign brand memberships**
4. Validate access to brand services

**Implications:**
- Single global learner identity across both brands
- Brand membership as relationship to global identity
- Implicit account linking by shared `global_user_id`

### AFTER (Independent Tenant Learners + SHC Projection)

**FinalAechitecture.md Section 3:**
> "The identity architecture distinguishes infrastructure identity (SHC people DB projection) from tenant learner identity (brand-owned user accounts)."

**Conceptual Model:**
```
people_prod (SHC infrastructure projections)
├── users (shadow projections)
│   ├── id (shadowUserId, SHC cross-reference)
│   ├── externalId (brand user ID)
│   └── platform (tenant context)
└── platform_access
    ├── userId (references shadow projection)
    └── platform (authorized contexts)

rth_prod / skillup_prod (tenant learner ownership)
├── users
│   ├── id (tenant-scoped learner ID, CANONICAL)
│   └── shadowUserId (optional SHC projection reference)
├── learner_profiles
├── enrollments
└── tutorial_progress
```

**Identity Flow:**
1. Verify person's identity and offline student record
2. **Create or match tenant learner accounts** in applicable databases (SUIA and/or RTH)
3. Create SHC people DB projections if cross-platform coordination needed
4. **Record explicit cross-tenant account link** if required (separate audit trail)
5. Validate access to each tenant's services independently

**Implications:**
- Independent tenant learner identities (SUIA and RTH own their learners)
- SHC projection is optional cross-reference, not replacement identity
- No automatic account linking; controlled linking with audit trail
- Equal IDs/emails across tenants = independent learners, not same person
- `shared` = resource scope requiring authorization, not learner authority

## Key Architectural Distinctions

| Concept | Global Model (Before) | Independent Tenant Model (After) |
|---|---|---|
| **Learner Identity Owner** | People DB (SHC) | Tenant databases (SUIA/RTH) |
| **Canonical Learner ID** | `global_user_id` (people DB) | `brandUserId` (tenant-scoped) |
| **Cross-Brand Access** | Brand membership relationship | Explicit controlled account linking |
| **Same Email/ID Across Tenants** | Same person, shared identity | Independent learners (may be same person or different) |
| **People DB Role** | Global identity authority | Infrastructure projection for service coordination |
| **Account Linking** | Implicit via global_user_id | Explicit, controlled, auditable |
| **SHC `shared` Resources** | Accessed via global membership | Require verified caller + tenant entitlement + resource policy |

## Evidence Corrections Applied

### 1. Governing Architecture File Location

**Correction:** Used `audit/FinalAechitecture.md` (exact spelling) consistently throughout. Cited lines 884-935, 2590, 2649-2664 with exact amendments.

### 2. Database Topology Qualification

**Issue (Sol Review 3021c24d):** Inferred globally shared learner users table from email uniqueness; missed brand-specific database routing

**Evidence:** `brand-db.ts` selects `db-skillup` or `db-rth` based on brand; connection strings `DATABASE_URL_SKILLUP` / `DATABASE_URL_RTH` configure routing

**Correction:** Qualified as source-configured routing, not deployed-state proof. Unique email constraints apply within physical database scope. Do not reveal connection secrets to establish topology.

### 3. Identity Bridge Semantics

**Issue (Sol Review 3021c24d):** Omitted actual bridge and ID producer; inferred impersonation from dual IDs

**Evidence:** `login.service.ts:32-52, :178-185` and `signup.service.ts:88-97` show `originalUserId=user.id` (brand ID) and `shadowUserId` (people DB projection ID) as cross-database mapping

**Correction:** Preserved dual-ID projection mapping; documented as projection not impersonation. Both IDs reference same logical learner in different namespaces.

### 4. People DB Email Uniqueness Conflict

**Issue (Sol Review 3021c24d):** Missed people schema unique email constraint conflicting with platform-specific projections

**Evidence:** `packages/db-people/src/schema/users.ts:10` has `email: text('email').notNull().unique()` WITHOUT platform scoping

**Correction:** Documented email conflict, traced signup retry behavior (emits event but repeats failing insert), identified affected consumers, recommended composite `(email, platform)` uniqueness as separate ticket requiring consumer analysis and migration approval.

### 5. Authority Table Corrections

**Issue (Sol Review 60bd89bb):** Authority table included `shared` in brand token context without distinguishing resource scope from learner authority

**Correction:** `shared` established as resource scope only; access requires verified caller, tenant entitlement, resource policy and permission. A `platforms` array alone never authorizes cross-tenant learner access.

### 6. Unsafe Email Lookup Example Removed

**Issue (Sol Review 147bf562):** Section 4.2 showed optional-platform email query using `.limit(1)` selecting arbitrary first row when duplicates exist

**Correction:** Removed unsafe example. Lookups must scope identity by verified platform or reject ambiguity. Consumer updates must precede or be atomic with any future uniqueness constraint change.

### 7. Retry Execution Qualification

**Issue (Sol Review 147bf562):** Claimed durable retry execution without tracing actual subscribers

**Correction:** Documented event emission `identity.bridge.retry_requested` observed in source; marked durable retry worker execution unverified. Recommend trace event bus consumers in follow-on investigation.

### 8. Session Discovery Scoped as Investigation

**Issue (Sol Review 60bd89bb/147bf562):** Session storage conclusions were unproven; type contract includes `brand` but schema lacks column

**Correction:** Marked session persistence unverified; proposed bounded W1.1.2 read-only investigation ticket. No new storage or speculative schema changes.

### 9. Removed Unrequested Additions

**Issue (Sol Review 147bf562):** Amendment included controlled cross-tenant account linking mechanism and offline-student link records

**Correction:** Removed from governing amendment. Independent tenant accounts do not require explicit linking mechanism to function independently. Linking remains candidate for separate design if offline student use case requires it.

### 10. Distinct Accounts ≠ Different People

**Issue (Sol Review 147bf562):** Amendment stated different accounts mean different people

**Correction:** Distinct account identities; human identity not inferred either way. Same person may have independent SUIA and RTH accounts. Equal emails/IDs across tenants do NOT prove same person or authorize automatic linking.
