## Executive Summary of Corrections

This correction addresses all five findings from Sol's review (`audit/W1.1_Sol_Review_3021c24d.md`). The original W1.1 document made incorrect inferences about database topology, identity bridge semantics, and impersonation. This corrected version traces actual producer-to-consumer paths through connection strings, routing logic, and schema files to establish evidence-based conclusions.

**Key Corrections:**

1. **Database topology:** Separate tenant databases (`DATABASE_URL_SKILLUP`, `DATABASE_URL_RTH`) already exist with brand-specific routing. Email uniqueness is tenant-scoped at brand level.
2. **Identity bridge semantics:** `originalUserId` (brand ID) and `shadowUserId` (people DB projection ID) are NOT impersonation markers. They represent a cross-database projection system for SHC service coordination.
3. **Real email conflict:** `db-people.users` table has global unique `email` constraint without tenant column. This prevents same email from registering in both tenants, contradicting independent learner model.
4. **Session storage:** Unverified. Type contract includes `brand` field but schema files lack `brand` column. Concrete repository not traced. Marked as uncertain rather than speculated.
5. **Corrected recommendations:** Removed impersonation, canonical-ID deprecation, and mandatory cryptographic-session claims. Replaced with evidence-based schema correction (composite unique `(email, platform)` in people DB) and tenant validation registry.

[...] That is direct evidence of an existing brand-local-to-SHC projection mapping, not evidence of administrator impersonation.

  4. Returned `shadowUserId` stored back on brand user.

**Explicit Statement:**

### Finding 3: There Is a Real, Different Email-Uniqueness Concern

**Sol's Finding:**
> The SHC people users schema itself has unique email (packages/db-people/src/schema/users.ts:10) AND a unique externalId/platform index (:26). The bridge inserts email for each platform-specific projection. This can conflict for equal emails across tenant projections.

**Original Error:** Missed the people DB as the source of email conflict. Focused on brand-level email uniqueness instead.

**Correction Applied:**

**Corrected Document Section 4** (entire section) now focuses on people DB email constraint:

- Schema evidence: `packages/db-people/src/schema/users.ts` line 10 shows `email: text('email').notNull().unique()` WITHOUT tenant column.
- Index analysis: `idx_users_email_platform` is **non-unique composite index**. Uniqueness is enforced at column level, not scoped by platform.
- Failure scenario traced step-by-step:
  1. Alice signs up in `skillup` → people DB projection created with `email='alice@example.com'`, `platform='skillup'`. ✅
  2. Alice signs up in `realtutorialhub` → people DB insert fails on unique `email` constraint. ❌
- Current behavior: Brand signup succeeds, bridge sync fails, error logged as `identity_bridge_sync_failed` (signup.service.ts lines 99-121), retry queued but continues failing.

**Proposed Correction (Section 4.2):**

**Option B (Recommended):** Composite unique constraint `(email, platform)` instead of global unique `email`.

Migration strategy:
1. Drop `users_email_unique` constraint.
2. Add `users_email_platform_unique` composite constraint.
3. Test same email across platforms.

**Evidence Citation:** Migration file `packages/db-people/migrations/0000_perpetual_microbe.sql` line 63 confirms constraint exists.

**Conclusion:** This is the **smallest necessary schema change** to align people DB with independent tenant learners. No redesign of tenant databases required.
