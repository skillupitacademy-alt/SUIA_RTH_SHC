## Critical Findings

### 1. Email Uniqueness Conflict

**Issue:** `db-people.users.email` has `.unique()` constraint without platform scoping. When the same email registers in both `skillup` and `realtutorialhub`, the second identity bridge projection fails.

**Source Evidence:**
- `packages/db-people/src/schema/users.ts` line 10: `email: text('email').notNull().unique()`
- `packages/db-people/drizzle/migrations/0000_perpetual_microbe.sql` line 63: `users_email_unique UNIQUE(email)`

**Current Behavior:**
- First tenant registration succeeds; brand user created, people DB projection created
- Second tenant registration: brand user created successfully, bridge projection insert fails on unique email constraint
- Signup catches bridge error, logs `identity_bridge_sync_failed`, emits `identity.bridge.retry_requested`
- Retry repeats same failing insert (no constraint fix)

**Affected Consumers:**
1. `UserRepository.findByEmail` (`services/skillhubcore-service/src/modules/user/user.repository.ts` lines 41-51) - queries people DB without platform filter, returns non-deterministic first match if duplicates exist
2. SHC admin authentication - relies on people DB email lookups

**Recommendation:** Composite unique constraint `(email, platform)` requires:
- Consumer-impact analysis for all `findByEmail` call sites
- Staff authentication disambiguation (admins may need platform-independent lookup)
- Migration design with backward compatibility
- Separate approval ticket (not authorized in W1.1)

### 2. Dual-ID Mapping is Projection, Not Impersonation

**Evidence:** `apps/api-server/src/modules/auth/login.service.ts` lines 178-185 generates tokens with both:
- `originalUserId`: brand user ID (tenant-scoped learner identifier)
- `shadowUserId`: people DB projection ID (SHC cross-reference)

**Interpretation:** Both IDs reference the same logical learner in different namespaces. This is cross-database projection mapping, not administrator impersonation. The bridge creates a shadow record for service coordination, not identity replacement.

### 3. Session Tenant Binding Unverified

**Type Contract:** `CreateSessionInput` includes `brand` field (`packages/auth/src/session.types.ts` lines 20-27)

**Schema Mismatch:** Session tables in `db`, `db-rth`, and `db-skillup` lack `brand` column

**Unknown:**
- Concrete `SessionRepository` implementation (dependency-injected, not traced)
- Actual session storage location (shared vs per-tenant)
- Tenant binding mechanism (explicit column, implicit foreign key, or routing-based)
- Brand validation on refresh token lookup

**Recommendation:** Bounded W1.1.2 investigation ticket (read-only, no new storage)

### 4. Tenant Context Vocabulary

**Existing Wire Values:**
- `skillup` = SUIA tenant context
- `realtutorialhub` = RTH tenant context
- `skillhubcore` = SHC administrative/service context
- `shared` = **resource scope** (content visible to multiple tenants), NOT learner authority

**Authorization Rule:** `shared` resource access still requires verified caller identity, tenant entitlement, resource policy and action permission. A `platforms` array alone never authorizes cross-tenant learner access.

**Recommendation:** No new `tenantId` field required; existing `platform`/`brand` fields serve this purpose.

## Source-Backed Contract

### Authentication Flow (Login)

1. User submits credentials to tenant-specific login endpoint with `brand` parameter
2. `getAuthBrandContext(brand)` selects tenant database (`db-skillup` or `db-rth`)
3. Tenant `UserRepository` queries brand-specific users table
4. Password verified against tenant user record
5. `ensureShadowUserId` checks for existing `shadowUserId` on brand user
6. If missing, `UserIdentityBridgeService.syncUser` creates/updates people DB projection
7. Bridge returns `shadowUserId` (people DB projection ID)
8. Bridge updates brand user record with `shadowUserId`
9. Token generated with:
   - `userId`: brand user ID
   - `originalUserId`: brand user ID (tenant-scoped)
   - `shadowUserId`: people DB projection ID (SHC cross-reference)
   - `brand`: tenant context
10. Token returned to client

### Identity Bridge Projection (syncUser)

**Input:** `{ externalId: brandUserId, platform: brand, email, externalBrand: brand }`

**Lookup:** `db-people.users WHERE externalId = ? AND platform = ? AND deletedAt IS NULL`

**If Exists:**
- Update email (allow email changes within same projection)
- Return existing `shadowUserId`

**If Not Exists:**
- **Insert `db-people.users`:** `(externalId, platform, email, ...)`
- **Unique constraint risk:** If same email exists with different platform, insert fails
- Insert `db-people.platform_access`: `(userId=newShadowUserId, platform)`
- Return new `shadowUserId`

**Failure Handling (in SignupService):**
- Brand user creation **completes successfully**
- Bridge sync failure logged as `identity_bridge_sync_failed`
- Event `identity.bridge.retry_requested` emitted
- **Retry behavior unverified** (event consumer not traced; likely repeats same failing insert)

### Cross-Tenant Scenario: Same Email, Different Tenants

**Scenario:** Alice registers `alice@example.com` in both SUIA and RTH

**Expected Behavior (Independent Accounts):**
1. SUIA registration: `db-skillup.users` insert succeeds, bridge projects to `db-people.users` (success)
2. RTH registration: `db-rth.users` insert succeeds, bridge projection insert **fails** on people DB email unique constraint
3. RTH brand account exists and is usable for brand-specific APIs
4. RTH account lacks `shadowUserId`, blocking cross-platform SHC services
5. Retry event emitted but likely repeats failure

**Correct Behavior (After Composite Constraint):**
1. SUIA registration: both brand user and projection succeed
2. RTH registration: both brand user and projection succeed (email unique per `(email, platform)`)
3. Both accounts independently functional
4. `UserRepository.findByEmail` **must include platform filter** or reject ambiguous lookups

## Conclusion

The identity architecture now distinguishes:
1. **Tenant learner identity:** Brand-owned, tenant-scoped, canonical learner ID
2. **SHC infrastructure projection:** Optional cross-reference for shared service coordination
3. **No automatic account linking:** Cross-tenant access requires explicit controlled linking with audit trail
4. **Resource scope vs authority:** `shared` describes resource visibility, not learner permission

Equal IDs or emails across tenants identify **independent learners**, not the same person. The same person may have multiple independent accounts. Cross-tenant linking is explicit, controlled, and auditable.

The people DB email conflict is a candidate correction requiring separate design, consumer analysis, and migration approval. Session tenant binding requires bounded investigation. W1.2 behavioral changes depend on this W1.1 architecture foundation.
