## Accepted source observations

Sol independently read the actual refresh service, repository, token signing/
verification methods, route and auth facade. The service reads the active row
before its transaction, and revokeToken updates solely by token hash with no
active-state predicate or consumed-row check. The transaction groups revoke and
insert but does not itself establish single consumption under concurrent calls.
findByHash filters revoked=false, so the subsequent revoked branch cannot detect
previously rotated tokens through that production lookup. Brand/subject agreement
is not explicitly compared in this service. Last-used mutation precedes signature
verification. The refresh method lacks a current account-status lookup. Success
audit happens after commit and can affect whether the response reaches the client.

These observations justify bounded follow-ons; they are not evidence that five
Critical production exploits were executed. No live DB, deployment, real user
records or concurrent production execution was inspected. Existing test failures
are reported by the investigator; Sol did not rerun them in this acceptance turn.

## Qualifications that supersede overstated report conclusions

- Database/client routing is observed source configuration, not proof of physical
  deployment separation or a demonstrated cross-tenant attack. Missing explicit
  comparisons are gaps to test, not five automatically Critical exploits.
- Replaying a revoked token is rejected by active-only lookup. The gap is lack
  of reuse classification/family response, not proof that revoked tokens simply
  authenticate. Descendant revocation needs an established family contract first.
- Refresh signing lacks nonce/jti in generateRefreshToken, while token hashes are
  UNIQUE in default, RTH and SUIA schemas. Identical claims/timestamps may yield
  identical JWTs: concurrent inserts may instead collide and roll back. Distinct
  successors can still race. A deterministic reproduction must cover both cases
  before claiming unconditional token forking or fixing rotation.
- The current method does not check blocked/deleted status, but the claim of
  indefinite refresh after suspension depends on actual blocking/revocation and
  expiry lifecycle. Trace those callers before asserting deployed impact.
- Generic refresh helpers omit issuer in both signing and verification, whereas
  other SHC helper methods set it. An issuer-policy change needs compatibility
  design; absence alone does not prove a signature-verification bypass.
- A transaction alone is not a single-use guarantee; a post-commit audit error is
  not a transaction rollback. Do not add a queue/outbox or claim durable retry
  recovery without a separately justified design.
