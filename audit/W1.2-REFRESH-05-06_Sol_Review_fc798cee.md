## Required corrections

### R1 - Trust and invalid request context must be defined end to end

REFRESH-05 calls Host verified. Reading a received Host is not verification of an
authorized origin or proxy. authBffRoute.ts:134-176 starts from incoming headers
and overwrites x-brand only when hostname resolution succeeds. Invalid/unknown
host handling and incoming x-platform therefore need explicit trace. API
request-brand.ts:38-51 maps invalid/shared input to undefined; AuthService.refresh
at auth.service.ts:54 defaults an undefined brand to realtutorialhub. A service-only
check for brand === shared cannot prove the proposed raw-header negative case.

Define missing, conflicting, malformed and unknown hostname/header decisions;
separate source mappings from unverified deployed ingress sanitation. Do not infer
an authenticated tenant from a caller-selected header alone. Propose the minimum
route/resolver files if needed instead of claiming a service-only whitelist covers
this path. No ingress changes are approved by this review.

### R2 - Legacy policy must distinguish absent from malformed claims

Section 5.3 sends empty strings, numbers, arrays and objects through the legacy
fallback. Only a genuinely absent claim may be a legacy candidate; malformed,
unsupported and conflicting claims must fail closed. Specify canonical accepted
values and normalization once. Keep shared out of learner authority.

Option B is a proposal, not yet an approved compatibility decision. Document the
evidence for actual legacy claim shapes, authenticated request scope, active row,
verified subject and expiry prerequisites. State unknown historical usage honestly.
Do not promise zero disruption or a universal seven-day retirement window without
tracing every relevant signer/expiration and old-token acceptance path.

### R3 - Inventory active SHC consumers and keep identity stores distinct

Listing specialized helper definitions is insufficient. Their actual callers
include services/skillhubcore-service/src/modules/auth/auth.service.ts,
token-validator.service.ts and token-rotation.service.ts:32-100. The specialized
rotation uses sub/family, a people-user repository, Redis and family/session state.
It must not be treated as the generic refresh_tokens/userId flow or admitted by
an unexplained userId-or-sub fallback.

The API ShcAuthService imports @quiz/db-people, queries platform=skillhubcore and
uses isActive/role (shc-auth.service.ts:1,37-45,77-124). Generic brand-db.ts:99-102
instead selects @quiz/db default tables despite its stale people_db comment.
SHC generic login emits aud=shc-admin while generic refresh/route.ts:25-26 selects
user/admin/infra. Trace actual refresh callers/cookies/persistence for this flow;
do not claim a tenant UserRepository lookup qualifies every SHC principal.

### R4 - Correct expiry and impact claims

packages/auth/src/token.service.ts:4,281-303 uses an eight-hour default access
lifetime; TokenRefreshService supplies no custom expiry. The claimed universal
15-minute revocation ceiling is false. API admin login stores a 24-hour row
(admin-auth.service.ts:137), but generateRefreshToken signs seven days and rotation
creates a new seven-day row. Distinguish JWT lifetime, stored expiry and rolling
rotation; do not silently introduce a new absolute expiry or TTL behavior.

Describe the refresh eligibility guarantee at the time it is checked. A read
before rotation is not atomic with a concurrent block/demotion, and unblocking
can change eligibility again. Do not promise permanent cutoff or a strict bound
without the corresponding source and policy. Existing tokens may have other TTLs.

### R5 - Fresh roles require an actual strict lookup contract

UserRepository.findByIdWithDetails delegates to hydrateUserDetails
(user.repository.ts:119-125). Role loading catches database errors and returns an
empty array (165-179); profile errors are also swallowed (132-162). Therefore the
claim that a lookup outage always propagates is unsupported. An empty legitimate
role set and a failed authorization query currently look the same.

Define a minimal strict eligibility/role lookup or equally precise error-bearing
repository contract, keeping SQL in the repository and policy in the service.
Identify the smallest repository whitelist expansion actually needed; do not
forbid repository changes while relying on behavior it lacks. Add role-query
failure, successful empty roles and profile-query failure cases. No broad rewrite.

### R6 - Role freshness must preserve the authenticated principal boundary

Recomputing isAdmin from every fresh role can upgrade an existing learner refresh
credential after role promotion. Conversely, demotion changes the signing secret
while the proposal leaves old tokenType and requested admin audience in place.
Define the coherent combinations of audience, principal class, tokenType, key,
roles and isAdmin for learner, tenant-admin and SHC flows.

Recommend no privilege-class escalation via an existing lower-scope refresh
credential; use the appropriate login/re-auth flow for elevated scope. Determine
demoted-admin behavior explicitly. Fresh data alone is not authority to cross
portal/session scope. Exercise actual downstream verifiers, not only flag assertions.

### R7 - Trace lifecycle mutations accurately and within their database scope

drizzle-admin-user.repository.ts:132-138 has separate softDelete and hard delete
methods; the table cites delete as soft deletion. Lines 145-169 implement role
assignment during create, not proof of a demotion/update caller. The repository
imports default @quiz/db tables; identify actual binding before attributing those
mutations to SUIA/RTH stores. Trace an actual role-change caller or mark it unknown.

PasswordRecoveryService.resetPassword:69-99 does call brand-scoped revokeAll after
password update, but these are separate operations. This proves a source call,
not universal successful revocation or an atomic lifecycle transition. Likewise,
W1.2-SESS-01 accepted single-session ownership, not every logout-all path.

### R8 - HTTP, audit and test compatibility must be executable

refresh/route.ts:125 returns ApiResponse.error(error,401) for service exceptions.
The lifecycle contract's assumed 500 on lookup outage needs an actual proposed
error mapping, or a corrected contract; document parent-token preservation without
inventing an existing status. AuditService.log:41 inserts an audit row. Replace
zero database writes with zero refresh/session-state writes while explicitly
allowing security audit attempts. Preserve existing safe logging behavior.

The blocked-account test has a deliberately minimal no-brand payload fixture.
Future authority checks may need fixture updates before that test reaches account
eligibility. Do not promise every existing test becomes green without edits.
Inventory constructor call sites and test fixtures, preserve assertion intent,
permit necessary mocks, and avoid positional dependency-injection breakage.

The forged-token wording in REFRESH-05 also needs qualification: findByHash selects
the SHA-256 of the whole supplied token, not a hash claim supplied inside it.
Changing signed bytes normally misses the stored hash. The ordering problem is
real, but arbitrary tampering is not a demonstrated matching-row write exploit.
