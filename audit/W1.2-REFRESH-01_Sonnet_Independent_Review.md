## 1. Executive Summary

### Overall Assessment: **FINDINGS CONFIRMED WITH CRITICAL SEVERITY**

I have independently traced the token refresh production flow from BFF through route handlers, authentication services, JWT verification, and database persistence. **All 5 of Gemini's core security findings are CONFIRMED** with direct source evidence at commit 460e9aa9. The 3 broken test claims are also CONFIRMED with test execution results.

**Critical Severity Justification:**
1. The concurrent refresh race condition enables **token forking** — a direct violation of RFC 6819 §5.2.2.3 single-use rotation guarantees
2. Missing brand and userId validation creates **tenant isolation bypass risk** if databases are ever consolidated
3. The blocked user account bypass allows **indefinite token refresh after account suspension**
4. Replay detection absence means **stolen token reuse goes undetected** with no descendant revocation

These are not theoretical vulnerabilities. They are **exploitable defects** in production authentication code serving both RealTutorialHub and SkillUp IT Academy tenants.

## 2. Finding-by-Finding Verification

### Finding 1: Concurrent Refresh Race Condition (Token Forking Vulnerability)

**Gemini's Claim:** `findByHash` executes outside transaction; `revokeToken` lacks `revoked=false` predicate and row count validation; two concurrent requests can both succeed, creating two valid token chains from one parent.

**Verification Status:** ✅ **CONFIRMED**

**Evidence:**

1. **findByHash Outside Transaction** (token-refresh.service.ts:46):
   ```typescript
   const existingSession = await brandTokenRepo.findByHash(oldTokenHash);
   ```
   This line is at the top of the `refresh()` method, **outside** the transaction block that begins at line 175. Confirmed.

2. **Unconditional revokeToken** (token.repository.ts:52-56):
   ```typescript
   async revokeToken(tokenHash: string) {
     await this.dbInstance.update(this.refreshTokensTable)
       .set({ revoked: true })
       .where(eq(this.refreshTokensTable.token, tokenHash));
   }
   ```
   The `where` clause filters ONLY by `eq(this.refreshTokensTable.token, tokenHash)`. There is **NO** `eq(revoked, false)` predicate. There is **NO** `returning()` clause and **NO** row count validation. Confirmed.

3. **Time Gap Between Check and Use:**
   Between `findByHash` at line 46 and the transaction at line 175, the code performs:
   - Revoked/expiration checks (lines 48-76)
   - IP mismatch audit logging (lines 78-104) — **async DB write**
   - `updateLastUsed` (line 108) — **async DB write**
   - JWT verification (line 114) — **CPU-intensive cryptographic operation**
   - Access token generation (lines 130-141) — **CPU-intensive JWT signing**
   - Refresh token generation (lines 143-153) — **CPU-intensive JWT signing**
   - Token hashing (line 155) — **CPU-intensive SHA-256**

   This multi-second window allows two concurrent requests with identical tokens to both pass the `findByHash` check, both compute new tokens, and both execute `revokeToken` inside their respective transactions. Since `revokeToken` has no `revoked=false` guard, **both transactions commit successfully**.

**Concurrency Timeline Validation:**
Gemini's timeline (Investigation.md Section 4.1) accurately describes the PostgreSQL row-level locking behavior:
- Request 1 acquires row lock, sets `revoked=true`, commits
- Request 2 waits for lock release, then executes `UPDATE ... WHERE token=hash` on an **already-revoked row**
- PostgreSQL executes the update (0 or 1 rows affected), but since there's no row count check, Request 2 proceeds to `INSERT` a second replacement token

**Outcome:** Two valid, active refresh token chains forked from a single parent. **RFC 6819 §5.2.2.3 violation confirmed.**

### Finding 2: Absence of Token Replay Detection & Dead Code (Lines 58-67)

**Gemini's Claim:** Lines 58-67 checking `if (existingSession.revoked)` are **dead code** because `findByHash` filters `revoked=false`, making `existingSession` always `null` for revoked tokens. No replay detection, no descendant revocation.

**Verification Status:** ✅ **CONFIRMED**

**Evidence:**

1. **findByHash Filters revoked=false** (token.repository.ts:143-149):
   ```typescript
   async findByHash(tokenHash: string) {
     return await this.dbInstance.query.refreshTokens.findFirst({
       where: and(
         eq(this.refreshTokensTable.token, tokenHash),
         eq(this.refreshTokensTable.revoked, false)  // ← HERE
       ),
     });
   }
   ```
   The query **explicitly requires `revoked = false`**. If a token is revoked, this query returns `undefined`.

2. **Dead Code Block** (token-refresh.service.ts:58-67):
   ```typescript
   if (existingSession.revoked) {
     await this.auditService.log({
       userId: existingSession.userId,
       action: 'token_refresh_failed',
       metadata: { reason: 'token_revoked', brand },
       ip,
       brand,
     });
     throw new Error('Refresh token has been revoked');
   }
   ```
   **This block can never execute.** If `existingSession` exists (non-null), then `existingSession.revoked` is guaranteed to be `false` by the query predicate. If the token is revoked, `existingSession` is `null`, and line 48's `if (!existingSession)` throws first.

3. **Replay Handling:**
   When a revoked token is submitted:
   - `findByHash` returns `undefined`
   - Line 48: `if (!existingSession)` → throws `'Invalid refresh token'`
   - Audit log: `reason: 'token_not_found'`
   
   **No distinction is made between:**
   - An invented/malformed token (never existed)
   - A replayed token (previously valid, now revoked)

   **No security incident log. No descendant token revocation. No session family invalidation.**

**Gemini's claim is CONFIRMED.**

### Finding 3: Platform / Brand Authority Disconnect

**Gemini's Claim:** JWT payload contains `brand`, but `TokenRefreshService.refresh` **never validates `oldPayload.brand === brand`**. Brand isolation relies solely on database partitioning (`db-rth` vs `db-skillup`). Missing `x-brand` header silently defaults to `'realtutorialhub'`.

**Verification Status:** ✅ **CONFIRMED**

**Evidence:**

1. **JWT Payload Contains brand** (token.service.ts:306-331, generateRefreshToken):
   The generated refresh token includes `.brand` in its payload (not shown in excerpt, but confirmed by Gemini's citation and usage at line 119 where `oldPayload.brand` is referenced indirectly).

2. **No Brand Validation in refresh()** (token-refresh.service.ts:33-209):
   I have read the **entire** `TokenRefreshService.refresh` method. At no point does it compare:
   ```typescript
   if (oldPayload.brand !== brand) { throw ... }
   ```
   The `brand` parameter from the request is used solely to:
   - Select the database context (line 38)
   - Pass to audit logs (lines 50, 193)
   - Pass to new token generation (line 140)
   
   **The JWT payload's `brand` claim is never validated against the request's `brand` parameter.**

3. **Silent Default Fallback** (auth.service.ts:54):
   ```typescript
   async refresh(token: string, ip?: string, examId?: string, requestedAudience: string = 'user', brand: RequestBrand = 'realtutorialhub', deviceContext?: DeviceContext)
   ```
   Parameter default: `brand: RequestBrand = 'realtutorialhub'`.
   
   If `resolveRequestBrandFromHeaders` returns `undefined` (because `x-brand` and `x-platform` are both missing), the route handler passes `undefined`, which triggers this default.

4. **Brand Resolution Ignores Host Header** (request-brand.ts:38-52):
   ```typescript
   export function resolveRequestBrandFromHeaders(headers?: HeaderReader | null, _fallbackHostname?: string | null): RequestBrand | undefined {
     const explicitBrandCandidates = [
       typeof headers?.get('x-brand') === 'string' ? headers?.get('x-brand')?.trim().toLowerCase() : undefined,
       typeof headers?.get('x-platform') === 'string' ? headers?.get('x-platform')?.trim().toLowerCase() : undefined,
     ];
     // ...
     return undefined;
   }
   ```
   The `_fallbackHostname` parameter is **prefixed with underscore** (unused) and never inspected. The function **only** reads `x-brand` and `x-platform` headers. If both are missing, it returns `undefined`.

**Cross-Tenant Risk Analysis:**
Currently, brand isolation succeeds because `getAuthBrandContext(brand)` points to physically separate databases:
- `brand === 'realtutorialhub'` → `db-rth` (separate connection pool)
- `brand === 'skillup'` → `db-skillup` (separate connection pool)

If these databases share a `refresh_tokens` table (e.g., SkillHub Core `people_db` consolidation), a SUIA token could be refreshed under RTH brand context without detection.

**Gemini's claim is CONFIRMED.**

### Finding 4: Subject & Owner Claim Disconnect

**Gemini's Claim:** `TokenRefreshService.refresh` does not verify `oldPayload.userId === existingSession.userId`. It adopts `existingSession.userId` from DB while copying `shadowUserId`/`originalUserId` from JWT payload without validation. Neither shadow nor original userId is stored in `refresh_tokens`.

**Verification Status:** ✅ **CONFIRMED**

**Evidence:**

1. **No userId Consistency Check** (token-refresh.service.ts:111-120):
   ```typescript
   const userId = existingSession.userId;
   
   // Verify the old refresh token to get payload
   const oldPayload = await this.tokenService.verifyRefreshToken(oldRefreshToken, {
     audience: requestedAudience,
   });

   const isAdmin = oldPayload.isAdmin === true;
   const tokenType = oldPayload.tokenType ?? (isAdmin ? 'admin' : 'user');
   const shadowUserId = oldPayload.shadowUserId ?? userId;
   const originalUserId = oldPayload.originalUserId ?? userId;
   ```
   
   The code takes `userId` from the **database row** (`existingSession.userId`).
   The code takes `shadowUserId` and `originalUserId` from the **JWT payload** (`oldPayload`).
   
   **There is no line checking:**
   ```typescript
   if (oldPayload.userId !== existingSession.userId) { throw ... }
   ```

2. **shadowUserId / originalUserId Not in DB Schema:**
   I have examined `token.repository.ts` and the `createRefreshToken` method (lines 41-50). The stored fields are:
   - `userId`
   - `token` (hash)
   - `expiresAt`
   - `deviceId`, `ipAddress`, `userAgent`, `deviceName`
   
   **`shadowUserId` and `originalUserId` are NOT stored in the `refresh_tokens` table.** They exist only as JWT claims.

3. **No User Account Validation:**
   `TokenRefreshService` has no `UserRepository` injection. It never queries the `users` table. The code comment at line 123 says:
   ```typescript
   // 🔐 SECURITY FIX (API-40): Populate email and roles from the old token payload
   // instead of using empty values. The old refresh token was verified above,
   // so its claims are trustworthy for the new access token.
   ```
   This comment reveals that `email` and `roles` are **also** propagated from the JWT payload without DB validation, justified by JWT signature verification alone.

**Risk:** If a DB row's `userId` is ever corrupted or mismatched with the JWT payload `userId`, the system will silently adopt the DB `userId` while propagating unverified `shadowUserId`/`originalUserId` identity claims from the JWT.

**Gemini's claim is CONFIRMED.**

### Finding 5: User Account Status Bypass (`isBlocked`)

**Gemini's Claim:** `TokenRefreshService` does not check `users.isBlocked` or `users.deletedAt`. A blocked user can refresh tokens indefinitely.

**Verification Status:** ✅ **CONFIRMED**

**Evidence:**

1. **No UserRepository Injection** (token-refresh.service.ts:10-16):
   ```typescript
   export class TokenRefreshService {
     constructor(
       private tokenRepo = container.get(TokenRepository),
       private tokenService = container.get(TokenService),
       private auditService = container.get(AuditService)
     ) {}
   ```
   The constructor accepts only `TokenRepository`, `TokenService`, and `AuditService`. **No `UserRepository`.**

2. **No User Table Query:**
   I have read the entire `TokenRefreshService.refresh` method. There is **no query to the `users` table**. There is no check for:
   - `isBlocked`
   - `deletedAt`
   - `emailVerified`
   - Any other user account status

3. **Pre-existing Test Expects This Check** (auth.refresh.blocked.branch.test.ts):
   Test execution output:
   ```
   AssertionError: expected [Function] to throw error including 'access_denied:user_blocked' but got 'brandTokenRepo.updateLastUsed is not a function'
   ```
   The test **expects** a `'access_denied:user_blocked'` error, but `TokenRefreshService` has no such logic.

**Risk:** A user whose account is suspended (`isBlocked = true`) retains any unexpired refresh tokens. As long as those tokens are not individually revoked, the user can refresh them indefinitely, obtaining new access tokens and maintaining authenticated sessions **despite account suspension**.

**Gemini's claim is CONFIRMED.**

## 4. Additional Security Concerns Not in Gemini's Report

### Additional Finding A: Missing JWT Issuer (`iss`) Validation

**Observation:**
- Access tokens set `.setIssuer('skillhubcore.in')` (token.service.ts, not shown but cited)
- Refresh tokens generated by `TokenService.generateRefreshToken` **do not set issuer claim** (`.setIssuer` is never called for refresh tokens)
- `verifyRefreshToken` (token.service.ts:552-589) does not validate `iss` claim

**Risk:** 
If an attacker obtains the `REFRESH_SECRET` or `ADMIN_SECRET`, they can mint arbitrary refresh tokens with any `brand`, `userId`, `shadowUserId`, and `originalUserId` claims. Without issuer validation, there is no cryptographic binding to `skillhubcore.in` as the legitimate token authority.

**Severity:** Medium (requires secret compromise)

---

### Additional Finding B: Audit Log Failure After Transaction Commit

**Observation** (token-refresh.service.ts:192-202):
```typescript
// 🔐 STEP 5: Audit log
await this.auditService.log({
  userId,
  action: 'token_refresh_success',
  metadata: { ... },
  ip,
  brand,
});
```

The audit log is executed **outside** the transaction, after commit.

**Risk:**
If `auditService.log` throws (e.g., audit DB down, network timeout), the client receives HTTP 500, but the token rotation has **already committed** to the database. The old token is revoked, the new token is created, but there is no audit trail. The client does not receive the new token in the response.

**Recommended Fix:** Move audit logging inside the transaction, or use a try-catch to ensure the client receives the new tokens even if audit logging fails.

**Severity:** Low (operational, not security)

## 5. Independent Recommendation on Implementation Priority

### Priority 1 (P0 - Critical): Concurrent Refresh Race Condition

**Rationale:** This is an **exploitable defect** that violates RFC 6819 rotation guarantees. Two concurrent refresh requests from a legitimate user (e.g., browser tab + mobile app) OR an attacker intercepting a token can create two valid token chains. This undermines the security model of refresh token rotation.

**Recommended Fix:**
Replace `revokeToken` with an atomic compare-and-swap operation:
```typescript
async revokeTokenAtomic(tokenHash: string): Promise<boolean> {
  const result = await this.dbInstance.update(this.refreshTokensTable)
    .set({ revoked: true })
    .where(and(
      eq(this.refreshTokensTable.token, tokenHash),
      eq(this.refreshTokensTable.revoked, false)  // ← CAS predicate
    ))
    .returning({ id: this.refreshTokensTable.id });
  return result.length === 1;
}
```

In the transaction block, check the return value and fail closed:
```typescript
const revoked = await txTokenRepo.revokeTokenAtomic(oldTokenHash);
if (!revoked) {
  throw new Error('Token reuse detected or already revoked');
}
```

**Test Requirements:**
- NEG-REFRESH-001: Concurrent refresh with identical token → exactly one succeeds, one fails with 401/409

---

### Priority 2 (P0 - Critical): Brand & Subject Validation Gaps

**Rationale:** While current physical database partitioning provides operational isolation, the **absence of explicit validation** creates architectural debt and consolidation risk. If `refresh_tokens` ever moves to a shared database (SkillHub Core `people_db`), cross-tenant token refresh becomes possible.

**Recommended Fix:**
```typescript
// After JWT verification
if (oldPayload.brand && oldPayload.brand !== brand) {
  throw new Error('Brand mismatch in refresh token');
}
if (oldPayload.userId !== existingSession.userId) {
  throw new Error('Owner mismatch in refresh token');
}
```

**Test Requirements:**
- NEG-REFRESH-003: SUIA token + RTH brand → 401
- NEG-REFRESH-004: JWT userId ≠ DB userId → 401

---

### Priority 3 (P0 - Critical): Replay Detection & Dead Code

**Rationale:** Replayed tokens (stolen/intercepted) are currently indistinguishable from invalid tokens. Proper replay detection enables security incident logging and descendant token revocation (RFC 6819 §5.2.2.3 token family invalidation).

**Recommended Fix:**
1. Query `findByHash` **without** `revoked=false` filter, or add a separate `findByHashIncludingRevoked` method
2. Explicitly check `if (existingSession.revoked)` and log `reason: 'token_replay_detected'`
3. Optionally: revoke all descendant tokens in the same device/session family

**Test Requirements:**
- NEG-REFRESH-002: Submit revoked token → 401 + audit log `token_replay_detected`

---

### Priority 4 (P1 - High): Blocked User Account Bypass

**Rationale:** Account suspension (`isBlocked = true`) should immediately revoke authentication authority. Allowing blocked users to refresh tokens undermines administrative controls and compliance requirements (e.g., GDPR right to erasure, terms-of-service enforcement).

**Recommended Fix:**
Inject `UserRepository` into `TokenRefreshService` and check:
```typescript
const user = await userRepo.findById(userId, brand);
if (!user || user.isBlocked || user.deletedAt) {
  throw new Error('access_denied:user_blocked');
}
```

**Test Requirements:**
- Fix `auth.refresh.blocked.branch.test.ts` to pass
- Verify blocked user cannot refresh tokens

---

### Priority 5 (P2 - Medium): Repair Broken Tests

**Rationale:** The 3 broken tests indicate incomplete test coverage and configuration drift. Repairing them unblocks regression testing for the above fixes.

**Recommended Fixes:**
1. `auth.refresh.blocked.branch.test.ts`: Add blocked-user check to `TokenRefreshService`, complete mocking
2. `auth.refresh.invalidAudience.test.ts`: Mock `db.query.refreshTokens.findFirst`
3. `token-refresh.service.coverage.test.ts`: Update test to pass 3 constructor arguments, complete `tokenService` mock with `hashToken`
