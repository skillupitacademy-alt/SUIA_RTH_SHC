## F1 - SESS-04 permits explicitly excluded infrastructure audience

The route checks tokenType user/admin and canonical tenant brand, but never restricts
audience. Valid infra tokens have tokenType:admin, not tokenType:infra. Generic
verifyAccessToken deliberately does not enforce a requested audience when none is given.
An actual disposable signed aud:infra/tokenType:admin token with a matching tenant
therefore passes and reaches the revocation engine. The added Scenario 7 fabricates
tokenType:infra and cannot detect this defect. A tenant-brand token with an excluded
shc-admin or contradictory/mixed audience also needs a real verification control.

Independent actual-route probe: permitted user positive control returned 200; excluded
infra negative expected 403 but returned 200. Engine persistence was stubbed, so no
real session was revoked. Enforce permitted audience/class consistency before count
or revocation and test real token shapes with explicit disposable keys.

## F2 - Cookie-authenticated mutation has no demonstrated CSRF boundary

The restored route accepts accessToken cookies but has no origin/CSRF check. The API
proxy explicitly exempts /api/auth paths from csrfProtection, so it is not an upstream
control for this endpoint. A valid fixture cookie with a foreign Origin returned 200
and reached the stub engine; the negative probe expected 403.

This establishes missing source-level protection for the invoked cookie-authenticated
handler, not a demonstrated deployed browser exploit: actual cookie delivery, gateway
routing and production reachability were not tested. Resolve this before accepting the
newly functioning mutation. Inspect actual credential precedence, exact allowed-origin/
CSRF policy and legitimate non-browser bearer compatibility. Adding an arbitrary bearer
header must not bypass protection for an authoritative cookie credential. CORS alone
is insufficient. Do not inherit the shared CSRF helper's substring-origin comparison
as proof of an exact-origin boundary; a broad unrelated middleware rewrite is not required.

## F3 - LOGIN-01 changes generic skillhubcore/default-DB behavior

Both public routes unconditionally pass purpose:learner, and LoginService applies that
purpose for every brand. The accepted task required preserving generic skillhubcore/
default-DB compatibility outside the canonical tenant change. Source still accepts that
brand on the generic login route. An actual-service probe with identical synthetic
admin-role account data observed legacy isAdmin:true versus forwarded-purpose false.
The preservation assertion failed. This is distinct from dedicated SHCAuthService and
does not claim its admin GUI issuer was changed.

Scope learner purpose at the intended canonical tenant ingress and explicitly test
unchanged generic/dedicated paths. Validate unsupported purpose before password/security
success tracking and login_success audit work: current validation runs after those
side effects. Current five tests are service/facade controls; they do not establish the
public login/signup forwarding, actual cookie selection, refresh-token consistency under
shared keys or generic-brand compatibility required by the assignment. The new real
TokenService test uses ambient defaults again; inject disposable keys explicitly.

## F4 - ADMIN-01 proxy adaptation lacks its required actual-branch regression

The low-level 16-case RBAC suite is useful, but the submitted changed tests do not
exercise the new proxy branches. Existing proxy tests cover auth/exempt routing and
basic protected denial, not signed admin/infra/SHC routing across admin/factory/analytics.
The changed requireAdminRouteAccess infra eligibility and SHC analytics behavior also
need linked controls. Do not infer these from _verifyAdmin unit cases or the existing
fixture's /api/admin-only requests.

Add actual proxy/helper coverage with active/blocked/missing tenant records, query-entry
observations, absent/user/unknown headers, invalid signed-principal classes, SHC analytics
early denial, existing /api/admin infra compatibility and preserved handler permissions.
No production defect is inferred merely from the missing tests; acceptance is blocked
on the explicitly required evidence.

## F5 - SESS-04 outcome tests mock away the changed engine/state

The nine route cases stub logoutAllDevices and throw preconstructed stage errors. They
verify response mapping, not whether the real service emits the right stage or preserves
tenant ownership/state under commit-then-error, presence failure, absorbed audit insert
failure or retry. The existing tenant/ownership suites independently passed but cover
single-session revokeSession, not the newly wrapped all-device operation.

Add stateful real-route/real-service or meaningfully linked tests with in-memory
repositories: two tenants with colliding IDs, unrelated users, actual revoke mutations,
commit-then-throw unknown outcome, confirmed revocation/presence failure, actual absorbed
audit failure and idempotent owner retry. Assert no unexpected row restoration or cross-
tenant mutation, and no new Set-Cookie/deprecation metadata. Restore DI mocks afterward.
