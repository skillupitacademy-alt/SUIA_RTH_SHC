## 2. Task A (`W1.2-GUARD-01`) Key Conclusions

1. **Producer-to-Consumer Ingress Tracing**:
   - Learner portals (`apps/skillup-web`, `apps/realtutorialhub-web`) enforce `verifyUserAccessToken(token, { audience: 'user' })` and brand parity against request hostnames (`authProxy.ts:221-231`). Cross-brand or admin tokens fail closed with 401/403.
   - Tenant admin portals (`apps/realtutorialhub-admin`, `apps/skillup-admin`) strictly read `admin_accessToken` and verify `aud: 'admin'` and admin roles.
2. **`LoginService.login` vs. `AdminAuthService.login`**:
   - `LoginService.login` dynamically derives `isAdmin`, `aud`, and `tokenType` based purely on database roles.
   - `AdminAuthService.login` fails closed for non-administrators and enforces `roleNames.includes('infrastructure')` for `aud: 'infra'`.
3. **`RBACService._verifyAdmin` Elevation Defense**:
   - `_verifyAdmin` is audience-agnostic and would elevate learner sessions if called alone on a promoted account.
   - However, its only two production callers (`requireAdminRouteAccess` and gateway `proxy.ts`) strictly execute `verifyAdminAccessToken` (`aud: 'admin'`, `tokenType: 'admin'`) **before** invoking `_verifyAdmin`. Learner sessions cannot reach `_verifyAdmin`.
4. **Three Distinct SHC & Infrastructure Flows**:
   - **In-process API Server SHC Flow (`apps/api-server`)**: `SHCAuthService.login` authenticates against `@quiz/db-people`, mints `aud: 'shc-admin'` tokens, but omits refresh row insertion (`shc-auth.service.ts:129-132`).
   - **Specialized Microservice Helpers (`services/skillhubcore-service`)**: `services/skillhubcore-service/src/modules/auth/auth.routes.ts:120` defines `TokenRotationService.rotate`, sub/family tracking, and Redis compromise tracking. Crucially, `services/skillhubcore-service/src/index.ts:26-31` **does not mount** `createAuthRoutes` in `createApp`. It is unmounted library code.
   - **Generic Infrastructure Flow (`apps/api-server`)**: `POST /api/admin/auth/login` accepts `x-portal-identity: infrastructure` with required tenant brand, enforcing role `'infrastructure'` (`admin-auth.service.ts:94-97`). Calling by cron/CLI is an operational hypothesis, not source evidence.
5. **SHC Resolver Acceptance & Refresh Failure Chain**:
   - `request-brand.ts:1-10, 51-86` explicitly accepts `skillhubcore`, returning `{ brand: 'skillhubcore' }` with exit 0 (no HTTP 400).
   - In `POST /api/auth/refresh`, audience defaults to `'user'`. `brand-db.ts:99-102` maps `skillhubcore` to default `@quiz/db`. In `TokenRefreshService.refresh`, `findByHash` searches `@quiz/db` where `revoked = false`. For tokens issued by this login without a matching default-store row, lookup rejects with internal reason token_not_found. With a matching active row, generic route audiences user/admin/infra differ from shc-admin. This is conditional source analysis, not deployed database/browser evidence.
6. **Inherited Shared-Client Refresh Callers**:
   - `AdminGuard.tsx:35` calls `apiClient.client.setPortalIdentity('admin')`. In `fetch-client.ts:267-280`, any eligible 401 triggers an automatic POST to `/auth/refresh`.
   - On 401 failure, `fetch-client.ts:290-305` fires cancelable `auth:unauthorized`. `AdminGuard.tsx:74-91` cancels this event (`e.preventDefault()`). If locked, it defers to the lock screen protocol; if unlocked, it redirects to `/login`.
7. **Authoritative Host Matrix & Bounded Resource Authorization**:
   - Restored the 6 authoritative environment hosts from REFRESH-05 Section 7. Separately tabulated discovered admin and API endpoints.
   - Resource assertions bound to inspected routes: `POST /api/quiz/submit` (`route.ts:54`) delegates to `ExamEngine.completeExam` (`exam.engine.ts:1, 470`), which validates `exam.userId === userId` against default `@quiz/db`, not an isolated tenant DB. Documented gateway exemptions (`proxy.ts:61-69`) and bypass keys.

## 3. Task B (`W1.2-REFRESH-04`) Key Conclusions

1. **The `findByHash` Replay Blind Spot & Schema Boundaries**:
   - `TokenRepository.findByHash` queries `WHERE token = tokenHash AND revoked = false`.
   - When an already-consumed token (`revoked = true`) is presented, `findByHash` returns `null`.
   - `TokenRefreshService.refresh` logs `reason: 'token_not_found'` and throws HTTP 401. The subsequent check `if (existingSession.revoked)` is **unreachable dead code**.
   - Generic `refresh_tokens` schema has no `consumed_at`, `revoked_at`, or `reason` column. A `revoked = true` row does not prove consumption (`revokeById`/`revokeAll` also set `revoked = true`).
2. **Replay Classification & Concurrency Limits**:
   - Separated unknown tokens, expired tokens, CAS non-consumption (which can reflect concurrent race loss, prior revocation, or expiry between checks), and revoked tokens with unknown cause.
   - Removed arbitrary 5s / 10s grace-period assertions; timing alone cannot distinguish network retries from attacker replays. Maintained fail-closed rejection and no automatic user-wide revocation.
3. **Pre-CAS Autocommitted Metadata Persistence & Interleaving**:
   - Step 2.8 (`brandTokenRepo.updateLastUsed(oldTokenHash)`) executes as an autocommitted statement before the database transaction. If Step 3 throws or Step 4 loses CAS, `lastUsedAt` remains committed.
   - However, `consumeToken` (`token.repository.ts:79`) also updates `lastUsedAt: now()` inside the CAS transaction. Thus, when requests interleave, the final timestamp in PostgreSQL depends on statement scheduling and is not deterministically fixed to the losing request.
4. **Post-Commit Network/Proxy Failures & BFF Fallback Trace**:
   - In `src/share-branding/auth/authBffRoute.ts:423-546`, BFF fallback mode reissues the identical request to `fallbackApiBase` on gateway failure. If primary rotation committed before its response was lost, an enabled fallback can retry the revoked parent; HTTP 401 follows under same-store/valid-context assumptions. Deployed configuration and network behavior remain untested.
   - `globalRefreshPromise` deduplicates concurrent requests only within a single JavaScript module realm (one window/tab/worker).
   - `AuditService.log` ordinarily catches insert errors and logs them without rethrowing.
5. **No Token Families in Generic Tenant Store**:
   - The generic tenant table `refresh_tokens` contains no `family_id` column.
   - Specialized family tracking is not mounted by the inspected services/skillhubcore-service entry point; this is not proof of every deployment entry point. Generic tenant refresh operates strictly without token families or Redis session state.
