## 2. Task A (`W1.2-GUARD-01`) Key Conclusions

1. **Producer-to-Consumer Ingress Tracing**:
   - Learner portals (`apps/skillup-web`, `apps/realtutorialhub-web`) enforce `verifyUserAccessToken(token, { audience: 'user' })` and brand parity against request hostnames (`authProxy.ts:221-231`). Cross-brand or admin tokens fail closed with 401/403.
   - Tenant admin portals (`apps/realtutorialhub-admin`, `apps/skillup-admin`) strictly read `admin_accessToken` and verify `aud: 'admin'` and admin roles.
2. **`LoginService.login` vs. `AdminAuthService.login`**:
   - `LoginService.login` dynamically derives `isAdmin`, `aud`, and `tokenType` based purely on database roles.
   - `AdminAuthService.login` fails closed for non-administrators and enforces `roleNames.includes('infrastructure')` for `aud: 'infra'`.
3. **`RBACService._verifyAdmin` Elevation Defense**:
   - `_verifyAdmin` is audience-agnostic and would elevate learner sessions if called alone on a promoted account.
   - However, its only two production callers (`requireAdminRouteAccess` and gateway `proxy.ts`) strictly execute `verifyAdminAccessToken` (`aud: 'admin'`, `tokenType: 'admin'`) **before** invoking `_verifyAdmin`. Learner sessions cannot reach `_verifyAdmin`.
4. **SkillHubCore (SHC) Admin Flow & Refresh Reality**:
   - SHC Admin authenticates against `@quiz/db-people` (`shc-auth.service.ts`).
   - `SHCAuthService.login` generates tokens with `aud: 'shc-admin'`, but **does not insert refresh tokens into any database** (`shc-auth.service.ts:129-131`).
   - `apps/skillhubcore-admin` sets refresh cookies on login, but has **zero refresh routes or callers**. If SHC refresh were called on `/api/auth/refresh`, it would be rejected with HTTP 400 Bad Request by the strict brand resolver.
5. **Resource Ownership & Forged Headers**:
   - Domain resource handlers (`quiz/submit`, `reports`) derive user identity strictly from verified JWT claims (`payload.userId`). Client-supplied headers (e.g. `x-user-id`) are ignored.

## 3. Task B (`W1.2-REFRESH-04`) Key Conclusions

1. **The `findByHash` Replay Blind Spot**:
   - `TokenRepository.findByHash` queries `WHERE token = tokenHash AND revoked = false`.
   - When an already-consumed token (`revoked = true`) is presented, `findByHash` returns `null`.
   - `TokenRefreshService.refresh` logs `reason: 'token_not_found'` and throws HTTP 401. The subsequent check `if (existingSession.revoked)` is **unreachable dead code**.
   - The server currently cannot distinguish an unknown token from an already rotated token; both appear as `token_not_found`.
2. **Pre-CAS `lastUsedAt` Metadata Persistence**:
   - Step 2.8 (`brandTokenRepo.updateLastUsed(oldTokenHash)`) executes **outside and before** the database transaction.
   - If token signing fails in Step 3 or if a CAS race is lost in Step 4, the transaction rolls back, but `lastUsedAt` remains permanently committed in PostgreSQL.
3. **AuditService Resiliency**:
   - `AuditService.log` wraps all inserts in `try / catch` without rethrowing. Post-commit audit errors never cause an HTTP 500 error in production.
4. **Post-Commit Network/Proxy Failures**:
   - If a network drop or BFF failure occurs after Step 4 commits, the server state has rotated, but the client never receives the new token.
   - Subsequent client requests using the old token fail with 401, forcing the client to `/login`.
5. **No Token Families in Generic Tenant Store**:
   - The generic tenant table `refresh_tokens` contains no `family_id` or `parent_id` column. Generic refresh creates independent rows.
   - Family-wide session termination is not supported and should not be added without a dedicated schema design.
