## 1. Executive Summary & Problem Formulation

In modern identity systems, authentication does not conclude at initial login. An authenticated principal's eligibility and permissions evolve throughout an account's lifecycle:
$$\text{Account Suspended / Blocked} \implies \text{Session Revocation} \implies \text{Refresh Denied} \implies \text{Access Cut Off}$$

### Core Defect Identified
Under the baseline implementation across `@quiz/api-server`:
1. **Lifecycle Blindness during Refresh**: [`TokenRefreshService.refresh`](file:///E:/onlinewebsites/quiz-platform/apps/api-server/src/modules/auth/token-refresh.service.ts#L44-L185) queries only the `refresh_tokens` table. It never checks the `users` table or `UserRepository`. An account blocked by an administrator (`isBlocked = true`) or soft-deleted (`deletedAt != null`) can continue rotating refresh tokens and minting fresh access tokens indefinitely.
2. **Missing Revocation Triggers on Lifecycle Events**: When an administrator blocks a user via [`AdminUserEngine.toggleBlockStatus`](file:///E:/onlinewebsites/quiz-platform/apps/api-server/src/modules/admin-engine/admin.user.engine.ts#L98) or soft-deletes a user via [`DrizzleAdminUserRepository.delete`](file:///E:/onlinewebsites/quiz-platform/apps/api-server/src/repositories/implementations/drizzle-admin-user.repository.ts#L133), the system only updates the `users` row. It never invokes session revocation (`brandTokenRepo.revokeAll`), leaving existing refresh tokens active in the database.
3. **Stale Role and Privilege Propagation**: When rotating tokens, [`token-refresh.service.ts:143-167`](file:///E:/onlinewebsites/quiz-platform/apps/api-server/src/modules/auth/token-refresh.service.ts#L143-L167) carries forward `isAdmin` and copies roles from the predecessor JWT (`oldPayload.roles`). If an administrator is demoted to a standard user in the database, their active refresh session continues generating access tokens with `isAdmin: true` for the remainder of their session lifetime (up to 7 days).
4. **Active Baseline Regression Specification**: The test file [`apps/api-server/src/modules/auth/__tests__/auth.refresh.blocked.branch.test.ts`](file:///E:/onlinewebsites/quiz-platform/apps/api-server/src/modules/auth/__tests__/auth.refresh.blocked.branch.test.ts#L44-L52) explicitly tests this requirement:
   ```typescript
   it('refresh: throws specifically for blocked user', async () => {
     mockTokenRepo.findByHash.mockResolvedValue({ userId: 'u1', expiresAt: ... });
     mockTokenService.verifyRefreshToken.mockResolvedValue({ userId: 'u1', isAdmin: false });
     mockUserRepo.findByIdWithDetails.mockResolvedValue({ id: 'u1', isBlocked: true });

     await expect(service.refresh('token')).rejects.toThrow('access_denied:user_blocked');
   });
   ```
   In the un-remediated codebase, this test fails with `AssertionError: promise resolved instead of rejecting`, documenting the exact architectural omission.

This document defines the formal **Account Lifecycle & Role Freshness Security Contract** for `W1.2-REFRESH-06`.

## 3. Analysis of Downstream Access-Token Consumers vs. Refresh

A complete security analysis must evaluate how permissions and account states are consumed across both **stateless access tokens** and **stateful refresh tokens**:

```
[Client with Existing Access Token (TTL <= 15m) and Refresh Token (TTL <= 7d)]
   │
   ├─► Case 1: Client calls General API Route (e.g. /api/quiz/submit, /api/analytics/user/*)
   │     1. Route calls TokenService.verifyUserAccessToken(token)
   │     2. Signature & expiration validated purely via JWT claims (CPU-only, no DB query)
   │     3. Result: Request SUCCEEDS until the 15-minute access token expires.
   │
   ├─► Case 2: Client calls Identity Endpoint (/api/auth/me)
   │     1. Validates access token.
   │     2. Queries tenant database: brandUserRepo.findByIdWithDetails(payload.userId)
   │     3. Checks user.isBlocked:
   │          if (user.isBlocked) return ApiResponse.error(unauthorized('Account has been blocked'));
   │     4. Result: Blocked user is REJECTED immediately with 401.
   │
   └─► Case 3: Access token expires; Client calls Refresh Route (/api/auth/refresh)
         1. TokenRefreshService.refresh(oldRefreshToken, ...)
         2. CURRENT: Queries only refresh_tokens table -> SUCCEEDS -> Mints new 15m access token!
         3. CONTRACT (W1.2-REFRESH-06): Queries brandUserRepo.findByIdWithDetails(userId)
              -> Detects user.isBlocked === true
              -> FAILS CLOSED with 401 ('access_denied:user_blocked')
              -> Rotation TERMINATES.
```

### Observable Semantics & Honest Limitation Disclosure
1. **Stateless Access Token Latency**: In a stateless JWT architecture, access tokens already held by a client cannot be instantaneously revoked without either:
   - A centralized distributed blocklist (e.g. Redis cache check on every API hit, which defeats stateless scalability).
   - Or waiting for the access token to naturally expire (15-minute TTL).
2. **Refresh Boundary Enforcement**: The refresh rotation endpoint is the **primary security enforcement boundary** where stateful re-validation occurs. By checking account active status during refresh:
   - A blocked or deleted user is permanently cut off from obtaining successor access tokens once their current 15-minute access token expires.
   - If administrative blocking ALSO triggers `brandTokenRepo.revokeAll(userId)`, immediate refresh is prevented across all user devices.

## 4. The Account Lifecycle & Role Freshness Contract

### 4.1 Authoritative Tenant-Local User Repository Identification
- **Authoritative Service Component**: [`UserRepository`](file:///E:/onlinewebsites/quiz-platform/apps/api-server/src/modules/auth/repositories/user.repository.ts#L38) in `@quiz/api-server`.
- **Tenant Context Binding**: Must use `brandUserRepo = this.userRepo.withDb(brandContext.db, brandContext.tables)`.
- **Tenant Tables Used**:
  - `brandContext.tables.users` (contains `id`, `email`, `is_blocked`, `deleted_at`, `email_verified`).
  - `brandContext.tables.userRoles` & `brandContext.tables.roles` (contain canonical active roles).
- **Anti-Pattern Prohibited**: **Never perform an SHC shadow ID lookup in tenant user tables**.
  - `shadowUserId` is a cross-platform projection identifier for SkillHubCore.
  - In tenant databases (`db-rth`, `db-skillup`), the user's primary key is `users.id` (matching `existingSession.userId`).
  - Looking up `shadowUserId` in tenant tables would result in `user_not_found` or identity corruption. The lookup must strictly query `existingSession.userId`.

### 4.2 Exact Refresh Flow Sequence & Timing

```
[TokenRefreshService.refresh Execution Pipeline]
   │
   ├─► 1. Pre-condition Checks & Authority Verification (W1.2-REFRESH-05)
   │      - Cryptographic signature & audience verification.
   │      - Token brand claim parity (oldPayload.brand === brand).
   │      - Existing session row lookup in tenant DB.
   │      - Subject parity (oldPayload.userId === existingSession.userId).
   │
   ├─► 2. Tenant-Local User Status & Lifecycle Revalidation (NEW - REFRESH-06)
   │      - Bind brandUserRepo to brandContext.db.
   │      - Fetch: const user = await brandUserRepo.findByIdWithDetails(userId);
   │      - Evaluate Lifecycle Gates:
   │          a. if (!user) -> FAIL CLOSED (401, 'Invalid refresh token', reason: 'user_not_found')
   │          b. if (user.deletedAt !== null) -> FAIL CLOSED (401, 'Account has been deactivated', reason: 'user_deleted')
   │          c. if (user.isBlocked === true) -> FAIL CLOSED (401, 'access_denied:user_blocked', reason: 'user_blocked')
   │
   ├─► 3. Dynamic Role & Authority Extraction (NEW - REFRESH-06)
   │      - Extract fresh active roles directly from DB:
   │          const roles = user.userRoles.map(ur => ur.role.name?.trim().toLowerCase()).filter(Boolean);
   │      - Recompute administrative privilege dynamically:
   │          const isAdmin = roles.includes('admin') || roles.includes('super_admin') || roles.includes('infrastructure');
   │      - Use fresh email: const email = user.email;
   │
   ├─► 4. Generate Successor Tokens (CPU-only)
   │      - generateAccessToken({ userId, email, roles, isAdmin, tokenType, brand, aud })
   │      - generateRefreshToken(userId, isAdmin, aud, { tokenType, brand, ... })
   │
   └─► 5. Atomic Single-Consumer Transaction (W1.2-REFRESH-02)
          - consumeToken(oldTokenHash, userId) + createRefreshToken(...)
```

### 4.3 Detailed Lifecycle Enforcement Rules

#### Rule 1: Blocked User Rejection (Fixes Baseline Failure)
- If `user.isBlocked === true`:
  - Log audit event:
    ```typescript
    await this.auditService.log({
      userId,
      action: 'token_refresh_failed',
      metadata: { reason: 'user_blocked', brand },
      ip,
      brand,
    });
    ```
  - Throw error: `throw new Error('access_denied:user_blocked');`.
  - HTTP Route maps this to status `401 Unauthorized`.
  - **Zero database mutations occur**: `updateLastUsed` is skipped; `consumeToken` is not called; no successor token is inserted.
  - Satisfies and passes [`auth.refresh.blocked.branch.test.ts`](file:///E:/onlinewebsites/quiz-platform/apps/api-server/src/modules/auth/__tests__/auth.refresh.blocked.branch.test.ts).

#### Rule 2: Soft-Deleted User Rejection
- If `user.deletedAt !== null && user.deletedAt !== undefined`:
  - Log audit event: `action: 'token_refresh_failed'`, `metadata: { reason: 'user_deleted', brand }`.
  - Throw error: `throw new Error('Account has been deactivated');`.
  - HTTP Route returns `401 Unauthorized`.

#### Rule 3: Missing User Rejection (Fail-Closed)
- If `user === undefined || user === null`:
  - The session row references a user ID that does not exist in the tenant's `users` table.
  - Log audit event: `action: 'token_refresh_failed'`, `metadata: { reason: 'user_not_found', brand }`.
  - Throw error: `throw new Error('Invalid refresh token');`.
  - Prevents orphaned sessions from continuing.

#### Rule 4: Dynamic Role & Privilege Freshness
- Access tokens minted during refresh MUST NOT copy stale roles from `oldPayload.roles`.
- Access tokens minted during refresh MUST NOT copy stale `isAdmin` from `oldPayload.isAdmin`.
- Both `roles` and `isAdmin` MUST be derived from the freshly queried `user.userRoles`:
  ```typescript
  const roles: string[] = Array.isArray(user.userRoles)
    ? user.userRoles.map((ur) => ur.role.name?.trim().toLowerCase()).filter((r): r is string => typeof r === 'string' && r.length > 0)
    : [];
  const isAdmin = roles.includes('admin') || roles.includes('super_admin') || roles.includes('infrastructure');
  ```
- **Security Impact**:
  - If an administrator is demoted to a regular user in the database, their next token refresh immediately produces an access token with `roles: ['student']` and `isAdmin: false`. Privilege revocation latency is bounded strictly by the active access token's remaining TTL (maximum 15 minutes).

#### Rule 5: User Lookup Failure & DB Outage Handling
- If `brandUserRepo.findByIdWithDetails` throws an unexpected database error (e.g., connection timeout):
  - The error propagates immediately and aborts the refresh operation before the atomic rotation transaction begins.
  - The parent refresh token remains **unconsumed** and **unrevoked**.
  - When the database recovers, the user can successfully refresh their session without being unexpectedly logged out.
