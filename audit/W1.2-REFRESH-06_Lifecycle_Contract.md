## 2. Actual Token Expiry, Rotation Lifetimes & Impact Analysis (R4)

### 2.1 Token Lifetime Reality in Codebase
A rigorous audit of [`packages/auth/src/token.service.ts`](file:///E:/onlinewebsites/quiz-platform/packages/auth/src/token.service.ts) and [`apps/api-server/src/modules/auth`](file:///E:/onlinewebsites/quiz-platform/apps/api-server/src/modules/auth) reveals the true token expiration parameters:

```typescript
// packages/auth/src/token.service.ts:4-5
const ACCESS_TOKEN_EXPIRE = process.env.ACCESS_TOKEN_EXPIRE ?? '8h';
const REFRESH_TOKEN_EXPIRE = process.env.REFRESH_TOKEN_EXPIRE ?? '7d';
```

1. **Access Token TTL (8 Hours Default)**:
   - Unless explicitly overridden by the `ACCESS_TOKEN_EXPIRE` environment variable, access tokens are minted with an expiration of **8 hours**, NOT 15 minutes.
   - `TokenRefreshService.refresh` passes `{ userId, email, roles, isAdmin, tokenType, brand, aud }` to `generateAccessToken` without specifying a custom `expiresIn`.
   - **Observable Impact**: When an account is blocked or demoted in the database, existing stateless access tokens already in the client's possession remain cryptographically valid at resource endpoints (e.g., `/api/quiz/submit`) for up to **8 hours**, unless the resource endpoint performs stateful database re-verification (such as `/api/auth/me`).

2. **Refresh Token Expiry (JWT vs. Database Row)**:
   - **Learner Refresh Tokens**: `generateRefreshToken` signs a JWT with a 7-day expiration (`7d`). `TokenRefreshService.createRefreshToken` stores a database row with `expiresAt: new Date(Date.now() + 7 * 24 * 60 * 60 * 1000)` (7 days).
   - **Admin Refresh Tokens**: At initial login ([`admin-auth.service.ts:137`](file:///E:/onlinewebsites/quiz-platform/apps/api-server/src/modules/admin-auth/admin-auth.service.ts#L137)), the database row is stored with a 24-hour expiration (`24 * 60 * 60 * 1000`), but the signed JWT uses the default 7-day expiry unless overridden. During rotation in `TokenRefreshService.refresh`, a rolling 7-day successor row is inserted.
   - **Rolling Rotation Model**: Successful refresh consumes the parent token and issues a fresh 7-day row. There is currently no absolute sliding window ceiling (e.g., 30 days max total session lifetime).

### 2.2 Point-in-Time Eligibility Guarantee
The account status check at the refresh boundary provides a **point-in-time eligibility check**, defined precisely as:
$$\text{Eligibility}(t_{\text{refresh}}) = (\text{user exists}) \land (\text{user.deletedAt} = \text{null}) \land (\text{user.isBlocked} = \text{false})$$

- **Non-Atomicity with In-Flight Changes**: A database read of account status occurring milliseconds before an administrator toggles `isBlocked = true` is not atomic with that administrative action.
- **Refresh Barrier**: If eligibility evaluates to `false` at $t_{\text{refresh}}$, rotation is denied, and **zero successor tokens are minted**. The client is permanently blocked from extending their session.
- **Reversibility**: If an administrator subsequently unblocks the user (`isBlocked = false`), the user is eligible to authenticate anew via initial login. (If a refresh token was not revoked in the DB, it would technically become refreshable again, demonstrating why lifecycle mutations should also invoke `revokeAll`).

## 4. Strict Role & User Lookup Contract (R5)

### 4.1 Discovery of Error Swallowing in `UserRepository`
In [`apps/api-server/src/modules/auth/repositories/user.repository.ts:119-179`](file:///E:/onlinewebsites/quiz-platform/apps/api-server/src/modules/auth/repositories/user.repository.ts#L119-L179), `findByIdWithDetails` calls `hydrateUserDetails`:

```typescript
// user.repository.ts:165-179
try {
  roleRows = await db
    .select({ ... })
    .from(this.tables.userRoles)
    .innerJoin(this.tables.roles, eq(this.tables.userRoles.roleId, this.tables.roles.id))
    .where(eq(this.tables.userRoles.userId, user.id));
} catch {
  // Roles are non-critical for basic user info
  roleRows = [];
}
```

Similarly, profile queries catch and swallow errors (`profileRow = null`).

### 4.2 Architectural Impact of Error Swallowing
1. **Masked Outages**: If the database experiences a transient query error or connection timeout during role resolution, the exception is caught, and `roleRows` defaults to `[]`.
2. **Silent Demotion & False State**: A legitimate user with valid administrative roles whose role query fails would be seen as having **zero roles** (`userRoles: []`).
3. **Ambiguity**: The system cannot distinguish between:
   - A legitimate learner who has no administrative roles (`roleRows = []`).
   - A database failure that prevented roles from being retrieved.

### 4.3 Proposed Strict Repository Contract: `findActiveUserWithRoles`
To maintain strict Separation of Concerns (SoC) — keeping SQL in the repository and authorization policy in the service — `UserRepository` must be augmented with a strict lookup method:

```typescript
// Proposed addition to UserRepository in apps/api-server/src/modules/auth/repositories/user.repository.ts
export interface StrictUserEligibility {
  id: string;
  email: string;
  isBlocked: boolean;
  deletedAt: Date | null;
  roles: string[];
}

async findActiveUserWithRoles(userId: string): Promise<StrictUserEligibility | null> {
  const db = this.getDb();

  // 1. Fetch user core record (strictly throws on DB connection/query error)
  const [userRecord] = await db
    .select({
      id: this.tables.users.id,
      email: this.tables.users.email,
      isBlocked: this.tables.users.isBlocked,
      deletedAt: this.tables.users.deletedAt,
    })
    .from(this.tables.users)
    .where(eq(this.tables.users.id, userId))
    .limit(1);

  if (!userRecord) {
    return null; // Legitimate missing user
  }

  // 2. Fetch active roles (STRICT: database errors are NOT caught or swallowed)
  const roleRows = await db
    .select({
      name: this.tables.roles.name,
    })
    .from(this.tables.userRoles)
    .innerJoin(this.tables.roles, eq(this.tables.userRoles.roleId, this.tables.roles.id))
    .where(eq(this.tables.userRoles.userId, userId));

  const roles = roleRows
    .map((r) => r.name?.trim().toLowerCase())
    .filter((name): name is string => typeof name === 'string' && name.length > 0);

  return {
    id: userRecord.id,
    email: userRecord.email,
    isBlocked: Boolean(userRecord.isBlocked),
    deletedAt: userRecord.deletedAt ? new Date(userRecord.deletedAt) : null,
    roles,
  };
}
```

### 4.4 Behavior Under All Failure Modes
1. **Database Outage / Connection Error**: The error throws directly out of `findActiveUserWithRoles` $\to$ caught by `refresh/route.ts` $\to$ maps to HTTP 401 $\to$ **Parent token is NOT consumed and NOT revoked in DB**. When the DB recovers, the user can refresh successfully.
2. **Missing User (`null`)**: Service detects missing account $\to$ throws `new Error('Invalid refresh token')` $\to$ fails closed.
3. **Legitimate Empty Roles (`roles: []`)**: Service evaluates `roles.length === 0` $\to$ user is treated as standard learner (`isAdmin: false`) $\to$ refresh succeeds safely.
4. **Profile Failure Irrelevant**: Because `findActiveUserWithRoles` queries only `users` and `user_roles`, it completely bypasses the `user_profiles` table, eliminating profile query failures from the refresh critical path entirely (YAGNI & SoC).

## 5. Preservation of Principal & Session Boundaries (R6)

A critical vulnerability in dynamic role freshness is accidental **privilege escalation** across session boundaries.

### 5.1 The Principle of Non-Escalation
$$\text{Existing Credential Scope} \cap \text{Elevated Role} \not\to \text{Elevated Credential}$$
An existing session credential issued for a lower privilege tier cannot automatically be elevated into a higher privilege tier simply because the user was granted permissions in the database.

### 5.2 Ecosystem Scope & Key Boundary Matrix

| Principal Scope | Audience (`aud`) | Token Type (`tokenType`) | Signing Secrets | Permitted Fresh Roles | Behavior on DB Role Change |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Learner (SUIA / RTH)** | `'user'` | `'learner'` / `undefined` | `JWT_SECRET`<br>`REFRESH_SECRET` | Any (e.g. `'student'`, `'user'`) | **Promotion in DB**: Session **MUST NOT** escalate to `isAdmin: true` or `aud: 'admin'`. Token remains a learner token. Elevated access requires re-authenticating at `/api/admin/login`. |
| **Tenant Admin** | `'admin'` | `'admin'` | `JWT_ADMIN_SECRET`<br>`REFRESH_ADMIN_SECRET` | `'admin'`, `'super_admin'`, `'infrastructure'` | **Demotion in DB**: If user loses admin roles, refresh **FAILS CLOSED** (`access_denied:insufficient_permissions`). Cannot silently downgrade into learner token (different keys and audiences). |
| **SkillHubCore (SHC)** | `'shc-admin'` | `'shc-admin'` | `SHC_JWT_SECRET`<br>Redis Session Store | Separate `people_db` roles | Separate endpoint (`token-rotation.service.ts`). Generic tenant refresh rejects SHC tokens. |

### 5.3 Enforced Service Boundary Logic
In `TokenRefreshService.refresh`:
```typescript
// 1. Verify that parent credential scope matches requested scope
const isParentAdminSession = oldPayload.isAdmin === true || oldPayload.aud === 'admin';

// 2. Fetch fresh roles via strict repository lookup
const userEligibility = await brandUserRepo.findActiveUserWithRoles(userId);
if (!userEligibility) throw new Error('Invalid refresh token');
if (userEligibility.deletedAt) throw new Error('Account has been deactivated');
if (userEligibility.isBlocked) throw new Error('access_denied:user_blocked');

const dbHasAdminRole = userEligibility.roles.some((r) => ['admin', 'super_admin', 'infrastructure'].includes(r));

// 3. Enforce Strict Boundary Transitions:
if (!isParentAdminSession) {
  // Learner session: NEVER elevate to admin, even if dbHasAdminRole is true!
  // Prevents learner session hijacking from gaining admin portal access.
  successorIsAdmin = false;
  successorAudience = 'user';
  successorTokenType = oldPayload.tokenType ?? 'learner';
  successorRoles = userEligibility.roles; // Roles updated, but privilege tier preserved
} else {
  // Admin session: Demoted admin must fail closed
  if (!dbHasAdminRole) {
    await this.auditService.log({
      userId,
      action: 'admin_session_demoted_revoked',
      metadata: { reason: 'insufficient_permissions', brand },
      ip,
      brand,
    });
    throw new Error('access_denied:insufficient_permissions');
  }
  successorIsAdmin = true;
  successorAudience = 'admin';
  successorTokenType = 'admin';
  successorRoles = userEligibility.roles;
}
```

## 6. Executable HTTP, Audit & Test Compatibility (R8)

### 6.1 Route Handler Error Mapping
In [`apps/api-server/src/app/api/auth/refresh/route.ts:124-126`](file:///E:/onlinewebsites/quiz-platform/apps/api-server/src/app/api/auth/refresh/route.ts#L124-L126):
```typescript
} catch (_error) {
  return ApiResponse.error(_error, 401);
}
```
- **Observed Behavior**: All errors thrown during `service.refresh` (including `access_denied:user_blocked`, `Invalid refresh token`, or repository query errors) are caught by the route handler and returned as HTTP `401 Unauthorized`.
- **Database Safety Under Outage**: When a database outage causes `findActiveUserWithRoles` to throw, the route returns `401`. Crucially, because this occurs **before** the rotation transaction:
  - `brandTokenRepo.updateLastUsed` is skipped.
  - `brandTokenRepo.consumeToken` is skipped.
  - The parent refresh token remains **unrevoked** and **unconsumed**.

### 6.2 Audit Logging vs. Refresh State Writes
To resolve ambiguity regarding "zero database writes":
- **Forbidden State Writes**: Zero writes to `refresh_tokens`, `users`, or `user_roles`. No tokens may be consumed, rotated, or modified when validation fails.
- **Permitted Audit Writes**: Security events MUST be logged via `this.auditService.log(...)` ([`audit.service.ts:41`](file:///E:/onlinewebsites/quiz-platform/apps/api-server/src/modules/auth/audit.service.ts#L41)). Audit logging writes to the `audit_logs` table and is essential for threat detection and incident response.

### 6.3 Test Fixtures & Constructor Dependency Injection
1. **Constructor Signature Preservation**:
   - `TokenRefreshService` constructor currently accepts:
     `constructor(tokenRepo, tokenService, auditService, sessionRepo)`
   - Adding `UserRepository` must be implemented via optional parameter or container injection to prevent breaking existing test suites:
     `constructor(tokenRepo, tokenService, auditService, sessionRepo, userRepo?: UserRepository)`
2. **Minimal Payload Fixtures**:
   - The failing baseline test in [`auth.refresh.blocked.branch.test.ts`](file:///E:/onlinewebsites/quiz-platform/apps/api-server/src/modules/auth/__tests__/auth.refresh.blocked.branch.test.ts) provides a minimal payload `{ userId: 'u1', isAdmin: false }` without a `brand` claim.
   - Under the legacy compatibility contract (Option B in REFRESH-05), absent `brand` claims are accepted and progressively upgraded.
   - Therefore, the baseline test will seamlessly reach the `userRepo.findByIdWithDetails` / `findActiveUserWithRoles` check and assert `access_denied:user_blocked` without breaking!
