## 2. Actual Token Expiry, Rotation Lifetimes & Impact Analysis (R4, B3)

### 2.1 Token Lifetime Reality in Codebase
A rigorous audit of [`packages/auth/src/token.service.ts`](file:///E:/onlinewebsites/quiz-platform/packages/auth/src/token.service.ts) and [`apps/api-server/src/modules/auth`](file:///E:/onlinewebsites/quiz-platform/apps/api-server/src/modules/auth) reveals the true token expiration parameters:

```typescript
// packages/auth/src/token.service.ts:4-5
const ACCESS_TOKEN_EXPIRE = '8h'; // 8 hours for admin sessions
const REFRESH_TOKEN_EXPIRE = '7d';
```

1. **Access Token TTL (8 Hours Hardcoded Default)**:
   - The constant `ACCESS_TOKEN_EXPIRE = '8h'` is hardcoded in `token.service.ts:4`. It does **not** read `process.env.ACCESS_TOKEN_EXPIRE`.
   - While `generateAccessToken` accepts a custom expiration argument, `TokenRefreshService.refresh` supplies none, defaulting to **8 hours**.
   - Note on Cookie TTL: In [`packages/auth/src/middleware/cookie.middleware.ts:126`](file:///E:/onlinewebsites/quiz-platform/packages/auth/src/middleware/cookie.middleware.ts#L126), `buildAccessTokenCookie` sets cookie `maxAge: 15 * 60` (15 minutes). However, the underlying cryptographic JWT payload remains valid for **8 hours**.
   - **Observable Impact**: When an account is blocked or demoted in the database, existing stateless access tokens already held by clients remain cryptographically valid at resource endpoints (e.g., `/api/quiz/submit`) for up to **8 hours**, unless the resource endpoint performs stateful database re-verification (such as `/api/auth/me`).

2. **Refresh Token Expiry (JWT vs. Database Row)**:
   - **Learner Refresh Tokens**: `generateRefreshToken` signs a JWT with a 7-day expiration (`'7d'`). `TokenRefreshService.createRefreshToken` stores a database row with `expiresAt: new Date(Date.now() + 7 * 24 * 60 * 60 * 1000)` (7 days).
   - **Admin Refresh Tokens**: At initial login ([`admin-auth.service.ts:137`](file:///E:/onlinewebsites/quiz-platform/apps/api-server/src/modules/admin-auth/admin-auth.service.ts#L137)), the database row is stored with a 24-hour expiration (`24 * 60 * 60 * 1000`), but the signed JWT uses the default 7-day expiry. During rotation in `TokenRefreshService.refresh`, a rolling 7-day successor row is inserted.
   - **Rolling Rotation Model**: Successful refresh consumes the parent token and issues a fresh 7-day row. There is currently no absolute sliding window ceiling.

### 2.2 Point-in-Time Eligibility Guarantee
The account status check at the refresh boundary provides a **point-in-time eligibility check**, defined precisely as:
$$\text{Eligibility}(t_{\text{refresh}}) = (\text{user exists}) \land (\text{user.deletedAt} = \text{null}) \land (\text{user.isBlocked} = \text{false})$$

- **Non-Atomicity with In-Flight Changes**: A database read of account status occurring milliseconds before an administrator toggles `isBlocked = true` is not atomic with that administrative action.
- **Refresh Barrier**: If eligibility evaluates to `false` at $t_{\text{refresh}}$, rotation is denied, and **zero successor tokens are minted**. The client is permanently blocked from extending their session.
- **Reversibility**: If an administrator subsequently unblocks the user (`isBlocked = false`), the user is eligible to authenticate anew via initial login.

## 4. Strict Role & User Lookup Contract (R5, B3)

### 4.1 Discovery of Error Swallowing in `UserRepository`
In [`apps/api-server/src/modules/auth/repositories/user.repository.ts:119-179`](file:///E:/onlinewebsites/quiz-platform/apps/api-server/src/modules/auth/repositories/user.repository.ts#L119-L179), `findByIdWithDetails` calls `hydrateUserDetails`:

```typescript
// user.repository.ts:165-179
try {
  roleRows = await db
    .select({ ... })
    .from(this.tables.userRoles)
    .innerJoin(this.tables.roles, eq(this.tables.userRoles.roleId, this.tables.roles.id))
    .where(eq(this.tables.userRoles.userId, user.id));
} catch {
  // Roles are non-critical for basic user info
  roleRows = [];
}
```

Similarly, profile queries catch and swallow errors (`profileRow = null`).

### 4.2 Architectural Impact of Error Swallowing
1. **Masked Outages**: If the database experiences a query error or connection timeout during role resolution, the exception is swallowed, and `roleRows` defaults to `[]`.
2. **Silent Demotion & False State**: A legitimate user with valid administrative roles whose role query fails would be seen as having **zero roles** (`userRoles: []`).
3. **Ambiguity**: The system cannot distinguish between a legitimate learner who has no administrative roles and a database failure that prevented roles from being retrieved.

### 4.3 Proposed Strict Repository Contract: `findActiveUserWithRoles`
To maintain strict Separation of Concerns (SoC) — keeping SQL in the repository and authorization policy in the service — `UserRepository` must be augmented with a strict lookup method using its inherited `this.dbInstance` ([`BaseRepository:8`](file:///E:/onlinewebsites/quiz-platform/apps/api-server/src/modules/core/repositories/base.repository.ts#L8)):

```typescript
// Proposed addition to UserRepository in apps/api-server/src/modules/auth/repositories/user.repository.ts
export interface StrictUserEligibility {
  id: string;
  email: string;
  isBlocked: boolean;
  deletedAt: Date | null;
  roles: string[];
}

async findActiveUserWithRoles(userId: string): Promise<StrictUserEligibility | null> {
  const db = this.dbInstance;

  // 1. Fetch user core record (strictly throws on DB connection/query error)
  const [userRecord] = await db
    .select({
      id: this.tables.users.id,
      email: this.tables.users.email,
      isBlocked: this.tables.users.isBlocked,
      deletedAt: this.tables.users.deletedAt,
    })
    .from(this.tables.users)
    .where(eq(this.tables.users.id, userId))
    .limit(1);

  if (!userRecord) {
    return null; // Legitimate missing user
  }

  // 2. Fetch active roles (STRICT: database errors are NOT caught or swallowed)
  const roleRows = await db
    .select({
      name: this.tables.roles.name,
    })
    .from(this.tables.userRoles)
    .innerJoin(this.tables.roles, eq(this.tables.userRoles.roleId, this.tables.roles.id))
    .where(eq(this.tables.userRoles.userId, userId));

  const roles = roleRows
    .map((r) => r.name?.trim().toLowerCase())
    .filter((name): name is string => typeof name === 'string' && name.length > 0);

  return {
    id: userRecord.id,
    email: userRecord.email,
    isBlocked: Boolean(userRecord.isBlocked),
    deletedAt: userRecord.deletedAt ? new Date(userRecord.deletedAt) : null,
    roles,
  };
}
```

### 4.4 Behavior Under All Failure Modes
1. **Database Outage / Connection Error**: The error throws directly out of `findActiveUserWithRoles` $\to$ caught by `refresh/route.ts` $\to$ maps to HTTP 401 $\to$ **Parent token is NOT consumed and NOT revoked in DB**. When the DB recovers, the user can refresh successfully.
2. **Missing User (`null`)**: Service detects missing account $\to$ throws `new Error('Invalid refresh token')` $\to$ fails closed.
3. **Legitimate Empty Roles (`roles: []`)**: Service evaluates `roles.length === 0` $\to$ user is treated as standard learner (`isAdmin: false`) $\to$ refresh succeeds safely.
4. **Profile Failure Irrelevant**: Because `findActiveUserWithRoles` queries only `users` and `user_roles`, it completely bypasses the `user_profiles` table, eliminating profile query failures from the refresh critical path entirely (YAGNI & SoC).

## 5. Preservation of Principal & Session Boundaries (R6, B1, B3)

A critical vulnerability in dynamic role freshness is accidental **privilege escalation** across session boundaries.

### 5.1 The Principle of Non-Escalation
$$\text{Existing Credential Scope} \cap \text{Elevated Role} \not\to \text{Elevated Credential}$$
An existing session credential issued for a lower privilege tier cannot automatically be elevated into a higher privilege tier simply because the user was granted permissions in the database.

### 5.2 Ecosystem Scope & Key Boundary Matrix

| Principal Scope | Audience (`aud`) | Token Type (`tokenType`) | Signing Secrets | Permitted Fresh Roles | Behavior on DB Role Change |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Learner (SUIA / RTH)** | `'user'` | `'user'` | `ACCESS_SECRET`<br>`REFRESH_SECRET` | Any learner roles (`'student'`, `'learner'`) | **Promotion in DB**: Session **MUST NOT** escalate to `isAdmin: true` or `aud: 'admin'`. Administrative roles (`['admin', 'super_admin', 'infrastructure']`) **MUST BE FILTERED OUT** of `successorRoles`. Elevated access requires re-authenticating at `/api/admin/login`. |
| **Tenant Admin** | `'admin'` | `'admin'` | `ADMIN_SECRET` | `'admin'`, `'super_admin'`, `'infrastructure'` | **Demotion in DB**: If user loses admin roles, refresh **FAILS CLOSED** (`access_denied:insufficient_permissions`). Cannot silently downgrade into learner token. |
| **SkillHubCore (SHC)** | `'shc-admin'` | `'admin'` / host cookies | `ADMIN_SECRET`<br>Redis Session Store | Separate `people_db` roles | Separate endpoint (`token-rotation.service.ts`). Generic tenant refresh rejects SHC tokens. |

*Type and Secret Source Note*:
- [`TokenPayload`](file:///E:/onlinewebsites/quiz-platform/packages/auth/src/token.service.ts#L40) specifies `tokenType?: 'user' | 'admin'`.
- Secrets in `TokenService:81-93` (`ACCESS_SECRET`, `REFRESH_SECRET`, `ADMIN_SECRET`) share fallbacks (`ADMIN_JWT_SECRET ?? JWT_SECRET`).

### 5.3 Enforced Service Boundary Logic & Downstream RBAC Analysis (B1)
In `TokenRefreshService.refresh`:

#### Detailed Downstream RBAC Interaction & Honest Limitation Disclosure
1. **JWT Payload Check Prevention**: In [`apps/api-server/src/modules/auth/rbac.service.ts:11-15`](file:///E:/onlinewebsites/quiz-platform/apps/api-server/src/modules/auth/rbac.service.ts#L11-L15), `_verifyAdmin` computes:
   ```typescript

       ['admin', 'super_admin', 'infrastructure'].includes(r.toLowerCase())
   );
   const isAdminInToken = _payload.isAdmin === true || tokenRoles;
   if (isAdminInToken === true) return true; // Fast payout
   ```
   If newly granted administrative roles were copied into `successorRoles`, `isAdminInToken` would evaluate to `true` despite `isAdmin: false`, granting administrative access! Filtering administrative roles out of learner successor tokens prevents this bypass.
2. **Honest System Limitation**: In `_verifyAdmin:54-66`, step 2 performs a live database query against `authContext.tables.userRoles`. If a user is promoted in the database, any endpoint invoking `_verifyAdmin` will still authorize them via live database verification! A token refresh check alone cannot enforce a universal portal isolation guarantee. We recommend a separate bounded guard review for downstream portal enforcement; do not silently alter RBAC in this refresh contract.
