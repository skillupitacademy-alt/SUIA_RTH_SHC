## 1. Executive Summary

Task B of Gemini Controlled Batch 04 performs an exhaustive, source-backed investigation into refresh-token lifecycle edge cases across `@quiz/api-server`, including:
1. Revoked-token lookup, expired-token handling, and CAS race losses.
2. Replay classification: distinguishing unknown tokens, consumed tokens, legitimate client concurrency races, and malicious reuse signals.
3. Pre-CAS metadata side effects: verifying the persistence of `lastUsedAt` updates when later operations fail.
4. Post-commit completion: tracing the execution path through `AuditService`, `AuthService`, route cookie serialization, and the BFF to identify where committed rotations can yield failed client responses.
5. Separation of the generic tenant refresh path from specialized SkillHubCore (SHC) family/Redis policies.

### Primary Source Conclusions:
1. **The `findByHash` Replay Blind Spot**:
   - `TokenRepository.findByHash(tokenHash)` (`token.repository.ts:181-188`) queries `WHERE token = tokenHash AND revoked = false`.
   - Consequently, when an already-consumed refresh token (`revoked = true`) is presented, `findByHash` returns `null`.
   - `TokenRefreshService.refresh` (`token-refresh.service.ts:60-68`) catches this null and logs `reason: 'token_not_found'`, throwing `Invalid refresh token`.
   - **Crucial finding**: The subsequent check `if (existingSession.revoked)` (`token-refresh.service.ts:70-79`) is **unreachable dead code**. The server currently cannot distinguish an unknown/forged token from a previously rotated token; both appear identically as `token_not_found`.
2. **Pre-CAS `lastUsedAt` Update Does Not Roll Back**:
   - In `TokenRefreshService.refresh:401-403`, `brandTokenRepo.updateLastUsed(oldTokenHash)` is executed at Step 2.8, **outside and prior to** the CAS database transaction at Step 4 (`token-refresh.service.ts:444`).
   - If token signing in Step 3 throws, or if another concurrent request consumes the token first (causing `consumeToken` to return `null` in Step 4), the transaction rolls back, but **the `lastUsedAt` timestamp update in PostgreSQL remains permanently committed**.
3. **AuditService Resiliency**:
   - `AuditService.log` (`audit.service.ts:45-53`) wraps all database inserts in `try / catch` and logs errors to stdout without rethrowing (`// Do not block primary flows if audit logging fails`).
   - Therefore, a post-commit audit logging failure does **not** fail the HTTP response or cause a 500 error in production.
4. **Post-Commit Failure & Client Impact**:
   - If a network drop, browser crash, or BFF cookie-forwarding failure occurs after the database transaction commits at Step 4, the database has consumed the parent token and created the child token, but the browser never receives the replacement token.
   - When the client subsequently retries with the parent token, `findByHash` returns `null` (`revoked = false` filter), the server returns HTTP 401, and `fetch-client.ts:303` forcefully redirects the user to `/login?reason=session_expired`.
5. **No Token Families in Generic Tenant Refresh**:
   - The generic tenant database table `refresh_tokens` (`packages/db/src/schema/auth.ts:84-105`) contains **no `family_id`, `parent_id`, or `token_family` column**. Generic refresh rotations create completely independent row records linked only by `userId`.
   - Family-wide session termination cannot and should not be implemented without a dedicated, approved schema design.

## 3. The Four Lifecycle Token States & Replay Classification

Currently, when a refresh request arrives, it falls into one of four distinct states. The table below details current source behavior, security classification, and proposed minimal policy:

| State | Concrete Source Condition | Current System Behavior | Security Classification | Proposed Policy & Concurrency Safety |
|---|---|---|---|---|
| **1. Unknown Token** | `tokenHash` not found in `refresh_tokens` table | `findByHash` returns `null`; logs `token_not_found`; throws HTTP 401 | **Invalid / Expired Cleanup**: Hash was never issued or was purged. | Maintain current behavior. Reject with HTTP 401 `Invalid refresh token`. No user identity available to penalize. |
| **2. Expired Token** | `existingSession.expiresAt < now()` | `new Date(session.expiresAt) < new Date()`; logs `token_expired`; throws HTTP 401 | **Normal Session Expiration**: Learner inactive > 7 days. | Maintain current behavior. Reject with HTTP 401 `Refresh token has been expired`. Force clean login. |
| **3. Concurrent Race Loser** | Token exists, was active when request started, but CAS in Step 4 returns `null` because a concurrent request won the CAS | Request 1 commits. Request 2 CAS fails; transaction rolls back; logs error; throws `Refresh token has been revoked or already consumed` (HTTP 401). | **Benign Client Concurrency**: Two tabs opened simultaneously, or fast page reload triggered concurrent refreshes. | **Do NOT penalize or revoke user sessions!** Client `fetch-client.ts` should coordinate refreshes using `globalRefreshPromise`. If race occurs within grace window (< 5s), return standard 401 without security escalation. |
| **4. Credible Replay / Reuse Signal** | A token that was already consumed (`revoked = true` in DB) is presented long after rotation (> 10s or hours later) | `findByHash` returns `null` due to `revoked = false` filter; server logs `token_not_found` and throws HTTP 401. | **Suspected Token Replay**: Stolen token replayed by adversary, or severely stale client. | Current code cannot distinguish this from State 1. To enable detection, `tokenRepo` could inspect revoked tokens in audit logs, but **must NOT automatically destroy all user sessions** without explicit approval. |

## 4. Pre-CAS `lastUsedAt` Metadata Persistence Analysis

### The Code Pattern (`token-refresh.service.ts:401-448`):
```ts
// Step 2.8: Update last_used_at BEFORE transaction
await brandTokenRepo.updateLastUsed(oldTokenHash);

// Step 3: CPU-bound token generation
const newAccessToken = await this.tokenService.generateAccessToken(...);
const newRefreshToken = await this.tokenService.generateRefreshToken(...);

// Step 4: Atomic CAS Transaction
await targetDb.transaction(async (tx) => {
  const txTokenRepo = brandTokenRepo.withDb(tx, ...);
  const consumedParent = await txTokenRepo.consumeToken(oldTokenHash, userId);
  if (!consumedParent) {
    throw new Error('Refresh token has been revoked or already consumed');
  }
  await txTokenRepo.createRefreshToken(...);
});
```

### Consequences:
1. **Uncommitted State Update**: `updateLastUsed` is executed as an independent autocommit statement in PostgreSQL.
2. **If Step 3 Fails**: If JWT generation encounters a CPU, memory, or crypto error, the request aborts, but the old token's `last_used_at` timestamp in the database has already been updated to the current wall-clock time.
3. **If Step 4 Loses the CAS Race**: If Request A and Request B both pass Step 2.8:
   - Request A updates `lastUsedAt = T1`.
   - Request B updates `lastUsedAt = T2`.
   - Request A wins CAS and consumes the token.
   - Request B loses CAS and aborts with an error.
   - The row in `refresh_tokens` will reflect `last_used_at = T2` (Request B's timestamp) even though Request B was denied and rolled back.
4. **Architectural Evaluation**:
   - Moving `updateLastUsed` after pre-rotation authorization and eligibility checks (Batch 03 fix) successfully resolved the primary security defect: blocked, deleted, missing, or demoted accounts **never** update `lastUsedAt`.
   - However, for concurrent race losers or unexpected crypto failures, `lastUsedAt` persists because it occurs before the CAS transaction.
   - In a future maintenance pass, `consumeToken` already updates `lastUsedAt: now` during atomic consumption (`token.repository.ts:79`). Eliminating the redundant pre-transaction `updateLastUsed` entirely would ensure that **only the successful consumer** modifies timestamps.

## 5. Post-Commit Completion & Failure Mode Analysis

When the database transaction in Step 4 commits, the server state has permanently transitioned:
- Old token: `revoked = true`, `last_used_at = now()`.
- New token: inserted into `refresh_tokens`, valid for 7 days.

We traced the execution flow immediately following commit:

### 1. `AuditService.log` (`token-refresh.service.ts:466-476`)
- Calls `this.auditService.log({ action: 'token_refresh_success', ... })`.
- **Source Inspection** (`apps/api-server/src/modules/auth/audit.service.ts:45-53`):
  ```ts
  } catch (_error: unknown) {
    // Do not block primary flows if audit logging fails.
    this.logInstance.error(
      { error: _error instanceof Error ? _error.message : 'unknown error' },
      'Failed to write audit log',
    );
  }
  ```
- **Finding**: Audit insert failures are caught internally and logged to stdout/stderr. They do **not** throw and do **not** abort the refresh flow. An audit failure will never cause an HTTP 500 error in production.

### 2. Service Return & Route Cookie Serialization (`refresh/route.ts:81-128`)
- `authService.refresh` returns `{ accessToken, refreshToken, ... }`.
- `tokenService.getExpiration(accessToken)` decodes the JWT to calculate `maxAge`.
- `ApiResponse.success({ success: true, expiresAt })` creates the Next.js `NextResponse`.
- `setAuthCookies(response, accessToken, newRefreshToken, cookieBrand, isAdmin)` writes `Set-Cookie` headers.

### 3. Potential Failure Points Where Replacement Tokens Are Lost:
1. **Network Drop / TCP Reset**: The server commits the database transaction and begins transmitting HTTP headers, but the client connection drops before receiving the response body and `Set-Cookie` headers.
2. **Reverse Proxy / BFF Timeout**: If the BFF proxy fronting the API server times out or crashes during response transmission, the API server has committed the rotation, but the browser never receives the new cookies.
3. **Browser Cookie Rejection**: If cookie attributes (e.g. `domain`, `sameSite`, `secure`) conflict with the current browser origin (such as during local development or misconfigured reverse proxies), the browser ignores the `Set-Cookie` header.

### 4. Client Behavior on Lost Replacement Token:
- The browser retains the old refresh token in its cookie store.
- On the next background refresh or 401 retry, the browser sends the old refresh token.
- Server receives old refresh token -> computes hash -> calls `findByHash`.
- `findByHash` searches `WHERE revoked = false`. Because the old token was committed as `revoked = true`, `findByHash` returns `null`.
- Server returns HTTP 401 `Invalid refresh token` (`reason: 'token_not_found'`).
- In `packages/api-client/src/core/fetch-client.ts:290-305`:
  ```ts
  if (response.status === 401) {
    window.location.href = `/login?redirect=${redirectUrl}&reason=session_expired`;
  }
  ```
- The user is logged out and redirected to `/login`.

## 6. Separation from Specialized SkillHubCore (SHC) Redis/Family Policy

The codebase contains two distinct authentication systems:

| Feature | Generic Tenant Auth (`realtutorialhub`, `skillup`) | Specialized SkillHubCore Auth (`skillhubcore`) |
|---|---|---|
| **Storage Engine** | PostgreSQL (`refresh_tokens` table in tenant DB) | `@quiz/db-people` (users table) / Memory |
| **Token Family Tracking** | **None**. No `family_id` column or JWT family claim. | Present in JWT signing helper `signSkillHubCoreRefreshToken(userId, familyId)` (`token.service.ts:366`). |
| **Refresh Persistence** | Inserted into PostgreSQL with device context. | **Not persisted**. `shc-auth.service.ts:129` omits DB insert. |
| **Refresh Route** | Supported at `POST /api/auth/refresh`. | Not supported. Rejected by strict tenant brand resolver. |
| **Redis Usage** | Redis is used for rate limiting and cache; **not** for session state. | Redis session projection discussed in legacy notes, not used in active refresh. |

**Governance Rule**: The generic tenant authentication service must **not** borrow or conflate SHC family identifiers or Redis projections without an explicit, approved architectural plan.

## 7. Recommended Minimal Follow-On Scope (When Authorized)

When implementation is subsequently approved by Sol, the following bounded, minimal refinements are recommended:

1. **Eliminate Redundant Pre-Transaction `updateLastUsed`**:
   - In `apps/api-server/src/modules/auth/token-refresh.service.ts`, remove Step 2.8 (`await brandTokenRepo.updateLastUsed(oldTokenHash)`).
   - `consumeToken` (`token.repository.ts:79`) already updates `lastUsedAt: now` inside the atomic CAS transaction.
   - Eliminating the pre-transaction update ensures that failed requests or concurrent race losers leave zero metadata side effects in PostgreSQL.
2. **Reachable Revocation Detection**:
   - In `TokenRepository`, implement `findTokenRecord(tokenHash)` querying `refresh_tokens` without `revoked = false`.
   - Allows `TokenRefreshService` to distinguish an unknown token (`token_not_found`) from an already-consumed token (`token_already_consumed`).
   - If an already-consumed token was rotated within the last 5 seconds, log `concurrent_refresh_race` (benign) rather than an alarming security alert.
3. **Preserve Current Anti-Cascade Policy**:
   - Do **not** implement family-wide session termination or automatic multi-device logout on a single replay detection, as that would penalize users experiencing network retries or multi-tab concurrency.
