## 1. Executive Summary

Task B of Gemini Controlled Batch 04 investigates refresh-token lifecycle edge cases, replay detection, concurrency, and post-commit failure modes across `@quiz/api-server`, client runtimes, and reverse proxies:
1. Revoked-token lookup, expired-token handling, and Compare-And-Swap (CAS) race outcomes.
2. Replay classification: differentiating unknown tokens, tokens revoked without recorded cause, legitimate client concurrency races, and reuse signals.
3. Pre-CAS metadata side effects: verifying the persistence and interleaving of `lastUsedAt` updates when later operations fail.
4. Post-commit completion: tracing the execution path through `AuditService`, route cookie serialization, BFF response proxying, and client event handlers.
5. Separation of the generic tenant refresh path from specialized SkillHubCore (SHC) family/Redis policies and generic infrastructure flows.

### Primary Source Conclusions:
1. **The `findByHash` Replay Blind Spot**:
   - `TokenRepository.findByHash(tokenHash)` (`apps/api-server/src/modules/auth/repositories/token.repository.ts:181-188`) queries `WHERE token = tokenHash AND revoked = false`.
   - Consequently, when an already-consumed refresh token (`revoked = true`) is presented, `findByHash` returns `null`.
   - `TokenRefreshService.refresh` (`apps/api-server/src/modules/auth/token-refresh.service.ts:60-68`) catches this null and logs `reason: 'token_not_found'`, throwing `Invalid refresh token` (HTTP 401).
   - **Crucial finding**: The subsequent check `if (existingSession.revoked)` (`token-refresh.service.ts:70-79`) is **unreachable dead code**. The server currently cannot distinguish an unknown/forged token from a previously revoked token; both appear identically as `token_not_found`.
2. **Schema Information Limits**:
   - The generic tenant table `refresh_tokens` (`packages/db/src/schema/auth.ts:84-105`) contains **no `consumed_at`**, **no `revoked_at`**, and **no `revocation_reason`** column.
   - A row with `revoked = true` indicates only that the token was revoked; it does not indicate whether it was consumed via normal rotation (`consumeToken`), revoked by ID (`revokeById`), revoked globally (`revokeAll`), or revoked on password change.
3. **Pre-CAS `lastUsedAt` Persistence & Interleaving**:
   - In `TokenRefreshService.refresh:401-403`, `brandTokenRepo.updateLastUsed(oldTokenHash)` executes at Step 2.8, **outside and prior to** the CAS database transaction at Step 4 (`token-refresh.service.ts:444`).
   - If Step 3 throws, or if Step 4 loses the CAS race, the autocommitted `lastUsedAt` update in PostgreSQL remains committed.
   - Crucially, `consumeToken` (`token.repository.ts:79`) **also** updates `lastUsedAt: now()` inside the CAS transaction. Therefore, when concurrent requests interleave, the final timestamp in PostgreSQL depends on the exact scheduling of statements; it is not deterministically fixed to the timestamp of the losing request.
4. **Post-Commit Failure & Client Interception**:
   - If the upstream database transaction commits at Step 4, but the connection drops before the client receives the replacement token, the browser retains the parent token.
   - When the client retries, `findByHash` returns `null`, and the server returns HTTP 401.
   - In `packages/api-client/src/core/fetch-client.ts:290-305`, a 401 dispatches a cancelable `auth:unauthorized` CustomEvent. `AdminGuard.tsx:74-91` cancels this event (`e.preventDefault()`). If locked, it defers to the lock screen protocol; if unlocked, it redirects to `/login`. Clients are therefore not unconditionally forced to login.
   - In `src/share-branding/auth/authBffRoute.ts:423-546`, BFF fallback mode reissues the identical request to `fallbackApiBase` on gateway failure. If upstream rotation committed before the response was lost, an enabled fallback can present the revoked parent; it rejects with HTTP 401 if it reaches the same store with otherwise valid request context. Deployment flags, destination parity and network behavior were not tested.
5. **Separation of Distinct Flows**:
   - Generic tenant refresh uses brand-bound `@quiz/db-skillup` or `@quiz/db-rth` in production binding mode, with default `@quiz/db` on preserved default/test paths (`brand-db.ts:1-40, 93-107`). No generic token-family linkage exists.
   - Specialized `services/skillhubcore-service` helper `TokenRotationService.rotate` implements token family tracking and Redis persistence, but is **unmounted** in `services/skillhubcore-service/src/index.ts`.
   - Generic infrastructure flow (`POST /api/admin/auth/login`) operates on tenant or default tables with `aud: 'infra'`, distinct from inferred cron/CLI tools.

## 3. Token States & Replay Classification

Currently, when a refresh request arrives, it falls into one of four states based on observable database conditions:

| State | Concrete Source Condition | Current System Behavior | Security Interpretation Limits | Proposed Design Hypothesis (Unapproved) |
|---|---|---|---|---|
| **1. Unknown Token** | `tokenHash` not found in `refresh_tokens` | `findByHash` returns `null`; logs `token_not_found`; throws HTTP 401 | Could be an unissued forged token, or a record purged by database maintenance. | Maintain fail-closed HTTP 401 `Invalid refresh token`. No user identity available to penalize. |
| **2. Expired Token** | `existingSession.expiresAt < now()` | Caught at Step 2; logs `token_expired`; throws HTTP 401 | Normal session expiration (e.g., learner inactive > 7 days). | Maintain fail-closed HTTP 401 `Refresh token has been expired`. Force re-authentication. |
| **3. CAS Non-Consumption** | Token exists and passes Step 1, but CAS in Step 4 returns `null` | Transaction rolls back; logs error; throws `Refresh token has been revoked or already consumed` (HTTP 401). | Can occur due to concurrent race loss, revocation by another thread, or expiry between checks. **Timing alone does not prove benign concurrency versus theft.** | Return fail-closed HTTP 401. Do not penalize or revoke user sessions across other devices. Rely on client coordination (`globalRefreshPromise`). |
| **4. Revoked Token with Unknown Cause** | Token exists in database with `revoked = true` | `findByHash` returns `null` due to `revoked = false` filter; server logs `token_not_found` and throws HTTP 401. | Schema has no `revoked_at` or `reason`. Could be a normally rotated parent token replayed, a token revoked via `revokeById`, or global logout. | Maintain fail-closed HTTP 401. Do not introduce automatic user-wide session termination without an approved schema and policy design. |

### Governance Invariant:
No arbitrary timing window (e.g. 5s or 10s) proves benign intent or malicious replay. The current implementation safely fails closed on all non-consumable tokens. Automatic multi-device session revocation remains unauthorized without dedicated schema support and Sol approval.

## 4. Pre-CAS Autocommitted Metadata Persistence

### Source Code Pattern (`token-refresh.service.ts:401-448`):
```ts
// Step 2.8: Update last_used_at BEFORE transaction
await brandTokenRepo.updateLastUsed(oldTokenHash);

// Step 3: CPU-bound token generation
const newAccessToken = await this.tokenService.generateAccessToken(...);
const newRefreshToken = await this.tokenService.generateRefreshToken(...);

// Step 4: Atomic CAS Transaction
await targetDb.transaction(async (tx) => {
  const txTokenRepo = brandTokenRepo.withDb(tx, ...);
  const consumedParent = await txTokenRepo.consumeToken(oldTokenHash, userId);
  if (!consumedParent) {
    throw new Error('Refresh token has been revoked or already consumed');
  }
  await txTokenRepo.createRefreshToken(...);
});
```

### Analysis of Metadata Side Effects:
1. **Autocommitted Statement**: `brandTokenRepo.updateLastUsed(oldTokenHash)` executes outside any transaction block. In PostgreSQL, this statement commits immediately upon execution.
2. **Failure in Step 3**: If token signing fails due to CPU exhaustion, memory limits, or key errors, the refresh request terminates, but `last_used_at` in the database reflects the updated timestamp.
3. **Interleaving During Concurrent Requests**:
   - In `TokenRepository.consumeToken` (`token.repository.ts:79`), the atomic CAS update statement also writes:
     ```ts
     .set({ revoked: true, lastUsedAt: now })
     ```
   - When Request A and Request B race concurrently:
     - Request A executes Step 2.8 (`updateLastUsed`) at time $T_{1a}$.
     - Request B executes Step 2.8 (`updateLastUsed`) at time $T_{2a}$.
     - Request A enters Step 4 and executes `consumeToken` at time $T_{1b}$, committing `revoked = true` and `lastUsedAt = T_{1b}`.
     - Request B enters Step 4, finds zero rows updated (`revoked = true`), and rolls back.
   - The final value of `last_used_at` in the database row depends on the execution interleaving of $T_{1b}$ versus $T_{2a}$. It is **not** deterministically fixed to the losing request's timestamp.
4. **Verification Boundary**:
   Autocommitted metadata updates survive subsequent rollback in application logic. However, exact final column values are subject to database engine thread scheduling; no live PostgreSQL concurrency trace was empirically executed in this read-only review.

## 5. Post-Commit Completion, Client Interception & BFF Proxy Trace

When the database transaction in Step 4 commits, the server state has permanently transitioned:
- Parent token: `revoked = true`.
- Replacement token: inserted into `refresh_tokens`, valid for 7 days.

We traced the execution path following commit:

### 5.1 `AuditService.log` Resiliency (`token-refresh.service.ts:466-476`)
- Calls `this.auditService.log({ action: 'token_refresh_success', ... })`.
- In `apps/api-server/src/modules/auth/audit.service.ts:45-53`:
  ```ts
  } catch (_error: unknown) {
    // Do not block primary flows if audit logging fails.
    this.logInstance.error(
      { error: _error instanceof Error ? _error.message : 'unknown error' },
      'Failed to write audit log',
    );
  }
  ```
- **Finding**: Audit insert failures are ordinarily caught and logged to stdout/stderr. They do not rethrow or abort the response. However, this does not guarantee that exotic runtime crashes (e.g. out-of-memory or process termination during logging) cannot occur.

### 5.2 Client Coordination & Event Interception (`fetch-client.ts`)
- **Single-Realm Deduplication**:
  In `packages/api-client/src/core/fetch-client.ts:271-275`:
  ```ts
  if (!globalRefreshPromise) {
    globalRefreshPromise = this.performRequest('/auth/refresh', { method: 'POST', _isRetry: true });
  }
  await globalRefreshPromise;
  globalRefreshPromise = null;
  ```
  `globalRefreshPromise` deduplicates concurrent 401 refreshes **only within a single JavaScript module realm** (a single window, tab, or worker). It does not coordinate requests across separate browser tabs or server-side rendering workers.
- **Cancelable Unauthorized Event**:
  In `fetch-client.ts:290-305`:
  ```ts
  if (response.status === 401) {
    if (typeof window !== 'undefined') {
      const event = new CustomEvent('auth:unauthorized', { cancelable: true });
      const shouldRedirect = window.dispatchEvent(event);

      const currentPath = window.location.pathname;
      const isLoginPage = currentPath === '/login';
      const isAlreadyRedirecting = (window as any).__authRedirecting;

      if (shouldRedirect && !isLoginPage && !isAlreadyRedirecting) {
        (window as any).__authRedirecting = true;
        const redirectUrl = encodeURIComponent(currentPath + window.location.search);
        window.location.href = `/login?redirect=${redirectUrl}&reason=session_expired`;
      }
    }
  }
  ```
  Redirection occurs **only if `shouldRedirect` is true**. If an event listener invokes `event.preventDefault()`, `window.dispatchEvent` returns `false`, and default redirection is suppressed.
- **AdminGuard Handling**:
  `apps/skillhubcore-admin/src/components/auth/AdminGuard.tsx:74-91` listens for `auth:unauthorized` and calls `e.preventDefault()`. If the admin lock screen is active (`isLocked === true`), it logs `Circuit Breaker: 401 detected while LOCKED. Deferring to Lock Protocol.` and suppresses login redirection. Unlocked sessions redirect to `/login` without query parameters.

### 5.3 BFF Request Proxying & Fallback Retries (`authBffRoute.ts`)
In `src/share-branding/auth/authBffRoute.ts:423-546`:
1. **Primary Request**:
   - `unifiedFetch` forwards the refresh request to `targetUrl`.
   - On success (`status < 500`), reads payload `arrayBuffer()`, filters hop-by-hop headers, rewrites `Set-Cookie` headers via `rewriteSetCookie(cookie, requestHost)`, and returns the response.
2. **Gateway Failure & Strict Mode**:
   - If `unifiedFetch` returns 5xx or throws a network error:
   - If `AUTH_CONFIG.STRICT_GATEWAY` is true, immediately returns HTTP 503 `NextResponse.json({ error: 'Authentication service temporarily unavailable' }, { status: 503 })`.
3. **Fallback Reissue Risk**:
   - If `AUTH_CONFIG.ENABLE_FALLBACK` is enabled and `options.fallbackApiBase` is set:
   - Reissues the identical request (same method, headers, and body) to `fallbackApiBase`.
   - **Conditional availability/failure scenario, not a demonstrated critical exploit**: If the primary request committed rotation but its response was lost, an enabled fallback can reissue the request with the already-consumed parent token. Deployed flags and this network interleaving were not tested.
   - If the fallback targets the same authoritative token store with valid request context, `findByHash` excludes the revoked parent and returns null; the service rejects with HTTP 401. Different routing, missing headers/cookies or upstream failures can produce other responses and remain unqualified.

## 6. Separation from Specialized SkillHubCore & Infrastructure Flows

The repository contains three structurally distinct authentication flows that must not be conflated:

| Attribute | Generic Tenant Auth | In-Process API Server SHC Flow | Specialized SHC Microservice Helper |
|---|---|---|---|
| **Location** | `apps/api-server/src/modules/auth` | `apps/api-server/src/modules/auth/shc-auth.service.ts` | `services/skillhubcore-service/src/modules/auth` |
| **Ingress Route** | `POST /api/auth/refresh` | `POST /api/shc/auth/login` | `POST /refresh` (in `auth.routes.ts`) |
| **Registration Status** | Fully mounted in Next.js router | Fully mounted in Next.js router | **UNMOUNTED**. `services/skillhubcore-service/src/index.ts` does not register `createAuthRoutes` in `createApp`. |
| **Database Target** | Tenant DBs / Default `@quiz/db` | `@quiz/db-people` (users table) | `@quiz/db-people` & Redis |
| **Token Claims** | `aud: 'user' \| 'admin'`, `brand` | `aud: 'shc-admin'`, `brand: 'skillhubcore'` | `sub`, `family`, `platforms`, `subscriptions` |

| **Compromise Policy** | Fails closed on single token (HTTP 401). | Re-login on token expiry. | Calls `markTokenFamilyCompromised`, revokes all sessions for user. |

The inspected specialized service entry point does not mount its auth routes; a deployed browser journey through those helpers has not been established. ## 8. Minimal Proposed Follow-Up Scope (When Authorized)

When implementation is subsequently approved by Sol, the following minimal refinements are recommended:
1. **Eliminate Redundant Pre-Transaction `updateLastUsed`**:
   - In `apps/api-server/src/modules/auth/token-refresh.service.ts`, remove Step 2.8 (`await brandTokenRepo.updateLastUsed(oldTokenHash)`).
   - `consumeToken` (`token.repository.ts:79`) already updates `lastUsedAt: now` inside the atomic CAS transaction.
   - Eliminating the pre-transaction update ensures that failed requests or concurrent race losers leave zero metadata side effects in PostgreSQL.
2. **Reachable Revocation Detection**:
   - In `TokenRepository`, implement `findTokenRecord(tokenHash)` querying `refresh_tokens` without `revoked = false`.
   - Could distinguish an unknown hash (`token_not_found`) from a known revoked record (`token_revoked`, proposed internal reason). It cannot establish consumption versus logout/revocation without additional evidence. Validate signature/audience before attributing a reuse signal; no raw token logging or externally distinguishable response is authorized here.
3. **Preserve Current Anti-Cascade Policy**:
   - Maintain fail-closed rejection on invalid, revoked or otherwise non-consumable tokens. Preserve client response compatibility; proposed audit names and lookup changes require a separately scoped implementation ticket.
   - Do **not** implement family-wide session termination or automatic multi-device logout on a single replay detection without dedicated schema support and Sol approval.
