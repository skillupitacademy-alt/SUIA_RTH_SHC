## Stage 1 - establish actual local readiness

1. Confirm branch/HEAD and existing work. Identify approved local project origins/ports,
   BFF, API/gateway and relevant local database services. Inspect process ownership and
   build metadata without dumping command lines containing environment credentials.
   A listening port is not proof of the application or database behind it.
2. Establish exact running source/build revision for each relevant application and
   upstream, using verifiable build/start provenance. An arbitrary TEST_BUILD_REVISION
   string or a current repository HEAD alone does not establish running-code provenance.
3. Confirm effective database configuration targets isolated local fixture stores, using
   a redacted parser that reports only safe facts such as local/nonlocal, fixture role
   and qualification outcome. Never print connection URLs, passwords, environment files,
   token values or hashes. Read variable names/presence and parse required values only
   in memory; do not dump .env files or expose secret-bearing process arguments.
   localhost is insufficient if a proxy/tunnel routes to remote data. Use source/config
   and fixture-owner provenance; unknown isolation is a failed readiness prerequisite.
4. Map the owner-provided SHC admin, RTH learner and SUIA learner accounts through secure
   environment injection to the approved local fixtures. Do not copy passwords into
   Markdown, shell history, source files, screenshots, console or Playwright traces.
   Account details in chat do not prove those identities exist in isolated databases.
   Verify role/tenant/readiness without reading/logging password hashes or private data.
   No credentials need to be re-requested in chat. If they are not securely available
   to the process, record credential injection as missing; do not hardcode them.
5. Confirm installed matching Chromium executable and accepted reporter/ownership guards.
   Explicitly retain headless mode; never use --headed, visible GUI, codegen or inspector.
6. Verify configured origins and every local browser/API destination match the approved
   exact-origin boundaries. Resolve current login/dashboard/protected-route selectors
   from actual application source/config. For example, an assumed /admin/overview must
   be established as real and authorized before being treated as a positive control.
   Do not add arbitrary local hosts or relax guards to bypass a routing mismatch.
7. Record PASS/FAIL/UNKNOWN per prerequisite and safe source evidence. Only then supply
   readiness flags/account requirements to the runner. Flags record verified conditions;
   they must never manufacture readiness.
