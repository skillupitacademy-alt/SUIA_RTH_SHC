# Progress identity and entitlement — decision input

Status IMPLEMENTED_UNVERIFIED as a design sketch, not a schema or authorization decision. Requirement: independently valid `(tenant, local subject)` owns progress even when two tenants share local IDs, email and content IDs. Parent RC-ID-01 remains IN_PROGRESS.

`apps/api-server/src/app/api/tutorial/progress/route.ts` derives subject and brand from verified learner token. GET calls `TutorialProgressRepository.getProgress(userId, subtopicId)`; POST calls `TutorialService` and `TutorialEngine.trackProgress`, which passes only userId and subtopicId to the same repository. `TutorialEngine.getTutorialContent` also reads progress; `isSubtopicComplete`, `getCompletedSubtopics`, `resetProgress`, and `findById` expose further repository consumers. Audit all callsites and interfaces before changing the contract. The engine's `validateBrandAccess` currently returns true: shared versus exclusive content entitlement is not enforced there, regardless of subject authentication.

`packages/db-tutorial/src/schema/tutorial-progress.ts` declares unique `(userId, subtopicId)` and a nullable deletedAt, with uniqueness not conditioned on deletion. Repository active reads filter deletedAt and update by id; markBlockComplete does read then insert/update and increments version, but the observed code does not prove conflict-safe concurrent merging. Review deleted-row reactivation, concurrent insert and lost-update semantics explicitly.

A new test invokes the actual repository with an isolated shared adapter and equal local/content IDs: owner control passes; required foreign read and write denials fail. Its adapter supplies one shared row without silently enforcing tenant isolation, but does not execute SQL, physical database routing, entitlement or full engine. The repository signature has no tenant argument, so the fixture cannot itself transmit a foreign tenant; it demonstrates the missing authority at that boundary, not deployment behavior.

Prospective decision: identify whether a trusted per-tenant tutorial database binding is available for *every* read/write. If not, persist an authoritative canonical tenant discriminator with local subject and subtopic and use it in every query, uniqueness rule and identity-bearing event. Even with physical partitioning, verify all routes, background paths and cross-tenant shared infrastructure use the correct binding. Shared tutorial content does not imply shared learner progress; define visibility/entitlement against existing authoritative content policy before reads and writes. No email merge, synthetic prefix, global uniqueness assumption or SHC people projection supplies tenant ownership.

Before implementation Sol must choose legacy provenance: provably owned rows can be backfilled from authoritative records; ambiguous rows are quarantined or denied, never assigned from the current caller. Plan dual-read/write compatibility only when provenance and authority are explicit, tenant-aware unique indexing and deleted-state semantics, transactional atomic merge/upsert for concurrent completion, idempotency, monitoring and rollback that does not reopen cross-tenant access. Test colliding subjects, equal content, shared/exclusive entitlement, delete/restore, simultaneous writes and both tenant directions against the real repository and database routing. No migration or runtime change is authorized by this design.

### Canonical identity and trust details

`packages/db-tutorial/src/schema/tutorial-navigation-progress.ts` stores active unique `(userId, navigationNodeId)` plus subtopic, nullable section and `completedBlocks` of blockId/version; no tenant column. `block-learning-state.ts` stores unique `(userId, navigationNodeId, blockId, blockVersion)` and `block-telemetry-events.ts` uniquely indexes eventId with user/node/block/version/time. All use `packages/db-tutorial/src/db.ts` shared tutorial database binding; source comments saying user is already brand-scoped are not proof under independently colliding tenant IDs. Verify actual DB partition authority and both cross-tenant directions before any acceptance.

`TutorialSectionRepository.getTutorialByPageIdentity` filters subtopic, node, nondeleted and brand equal to signed/internal context or shared, using `limit(1)` without demonstrated explicit brand-preference order or brandVisibility predicate. `validateNavigationHierarchy` checks the resolved section and optional sectionId. `recordBlockCompletion` validates input formats and hierarchy, records client-supplied blockId/type/version, then computes server-required instructional block IDs/versions; source inspection did not find a membership check before the write. `recordBlockVisit` searches top-level blocks for expected time but proceeds even if not found. This is source evidence for a missing membership qualification, not an executed exploit. `resolveRequiredBlocks` iterates top-level versioned blocks, defaults missing role to instructional, excludes declared structural/assessment roles. Quiz assessment completion must remain separately authoritative: viewing a quiz type does not establish quiz completion.

For nested renderers, `packages/ui/src/tutorial/TutorialBlockRenderer.tsx` recursively passes the same `runtimeContext` to children. Whether a child renderer or active-block observer replaces the identity needs an executed mounted fixture; inherited parent context cannot establish correct child identity. Exercise parent and child with different IDs and validate section/node/block hierarchy at the service boundary. Exact new test scope and any runtime correction require separate Sol authorization; no canonical production edits are assigned here.

`recordBlockCompletion` and `completeNode` are distinct: completion records a block; complete-node resolves server requirements and evaluates completion. Visits track sessions/revisions, active-time increments are capped and do not directly complete a block. Provider retries active-time events with the same eventId; service claims event and adds time in one transaction, compares immutable fields for duplicates, and rejects conflicts. Event IDs are not ownership or entitlement. Out-of-order completion/telemetry, cross-tenant event collision, retries across reload, and storage rollback require isolated real-boundary fixtures. Automatic completion is conditional and uses policy evaluation; telemetry receipt alone is not completion.
