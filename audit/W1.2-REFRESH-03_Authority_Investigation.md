## 1. Executive Summary

Under Gemini Controlled Batch 01 (`audit/W1.2_Gemini_Controlled_Batch_01.md`), Task B authorizes a strictly read-only investigation into token authority, tenant boundary verification, and account lifecycle enforcement during refresh rotation.

This investigation traces the entire request journey:
$$\text{BFF / Proxy / Client} \longrightarrow \text{Next.js API Handler} \longrightarrow \text{AuthService Facade} \longrightarrow \text{TokenRefreshService} \longrightarrow \text{TokenService (Verifier)} \longleftrightarrow \text{TokenRepository (DB)}$$

### Key Discoveries & Vulnerability Posture
1. **Unauthenticated Header Trust for Tenant DB Selection**: Brand resolution in [`apps/api-server/src/lib/request-brand.ts`](file:///E:/onlinewebsites/quiz-platform/apps/api-server/src/lib/request-brand.ts#L38-L52) prioritizes `x-brand` and `x-platform` HTTP headers directly from incoming requests. While internal BFF gateways set these headers (`apps/skillup-web/src/lib/skillup-api.ts:33-42`), external ingress network topology (whether reverse proxies strip or overwrite untrusted client headers) remains unverified.
2. **Missing Token-to-Tenant Brand Binding (Defence-in-Depth Gap)**: [`TokenRefreshService.refresh`](file:///E:/onlinewebsites/quiz-platform/apps/api-server/src/modules/auth/token-refresh.service.ts#L38-L145) never cross-validates the cryptographic `brand` claim in the verified refresh token against the requested tenant brand or the target database. Because token hashes are looked up in the per-brand database selected by the request header, cross-tenant replay is mitigated in separated multi-database setups (a token for Brand A will not exist in Brand B's DB), but becomes exploitable in shared-database or fallback-to-default-database configurations.
3. **No Issuer (`iss`) Enforcement**: [`packages/auth/src/token.service.ts`](file:///E:/onlinewebsites/quiz-platform/packages/auth/src/token.service.ts#L553-L590) verifies signatures with `REFRESH_SECRET` and `ADMIN_SECRET` but does not enforce an `issuer` constraint, permitting token confusion across sub-ecosystems sharing secrets.
4. **Account Lifecycle Blindness (Scoped to Refresh Path)**: `TokenRefreshService` queries `refresh_tokens` exclusively. It never consults `UserRepository` or `users` table to verify whether an account has been suspended, blocked (`isBlocked = true`), soft-deleted (`deletedAt != null`), or underwent a security event (e.g. password reset / `tokenVersion` bump). While downstream endpoints may independently check user status upon access token usage, the refresh service will continue indefinitely issuing new access tokens for blocked users until absolute session expiration.
5. **Stale Role & Email Re-Minting**: In [`token-refresh.service.ts:126-133`](file:///E:/onlinewebsites/quiz-platform/apps/api-server/src/modules/auth/token-refresh.service.ts#L126-L133), roles and email for newly minted access tokens are copied verbatim from the decrypted claims of the predecessor refresh token. Demoted or revoked administrators retain elevated claims indefinitely across token rotations until absolute session expiration.
6. **Decoupled Identity Authorities**: Stored-row `userId` (from DB) and token claim `userId` (from JWT) are handled separately without an identity parity check, creating potential identity discrepancy.

## 4. Source-Backed Findings & Detailed Evidence

### Finding 1: Header Trust for Brand Determination (Ingress Topology Unverified)
- **Source Citation**: [`apps/api-server/src/lib/request-brand.ts:38-52`](file:///E:/onlinewebsites/quiz-platform/apps/api-server/src/lib/request-brand.ts#L38-L52)
  ```typescript
  export function resolveRequestBrandFromHeaders(headers?: HeaderReader | null, _fallbackHostname?: string | null): RequestBrand | undefined {
    const explicitBrandCandidates = [
      typeof headers?.get('x-brand') === 'string' ? headers?.get('x-brand')?.trim().toLowerCase() : undefined,
      typeof headers?.get('x-platform') === 'string' ? headers?.get('x-platform')?.trim().toLowerCase() : undefined,
    ];
    for (const candidate of explicitBrandCandidates) {
      const resolved = resolveRequestBrand(candidate);
      if (resolved !== undefined) return resolved;
    }
    return undefined;
  }
  ```
- **Architectural Flaw**: The tenant brand is resolved primarily from request headers (`x-brand`, `x-platform`). Internal BFF gateways populate these headers (e.g. `skillup-api.ts:33-42`), and `brand.guard.ts` expects them as authoritative gateway signals. However, whether reverse proxies or cloud edge gateways sanitize or strip external client-provided headers before reaching `api-server` depends on network infrastructure topology that remains unverified.
- **Impact**: If external clients can reach the API server directly or pass unsanitized headers through ingress, clients can dictate database routing independently of token authenticity.

### Finding 2: Missing Cross-Validation Between Token Brand Claim and Target Database (Defence-in-Depth Gap)
- **Source Citation**: [`apps/api-server/src/modules/auth/token-refresh.service.ts:38, 143`](file:///E:/onlinewebsites/quiz-platform/apps/api-server/src/modules/auth/token-refresh.service.ts#L38-L145)
  ```typescript
  const brandContext = getAuthBrandContext(brand);
  // ...
  const oldPayload = await this.tokenService.verifyRefreshToken(oldRefreshToken, { audience: requestedAudience });
  // Notice: oldPayload.brand is NEVER checked against brand!
  ```
- **Architectural Analysis**: The incoming refresh token contains a signed `brand` claim (`oldPayload.brand`), but `TokenRefreshService` never asserts `oldPayload.brand === brand`.
- **Actual Exploitability**: In standard multi-tenant operation where databases are isolated per tenant (e.g., `rthDb` vs `suiaDb`), `brandTokenRepo.findByHash(oldTokenHash)` queries the DB specified by `brand`. Because the token hash was only stored in the originating brand's DB, presenting a Brand A token with `x-brand: Brand B` results in `token_not_found` and fails closed. Direct cross-tenant replay is therefore **not an unconstrained Critical exploit**; it is a **defence-in-depth gap** that becomes exploitable only if tenants share a single database or fall back to a default database context.

### Finding 3: Missing Token Issuer (`iss`) Validation
- **Source Citation**: [`packages/auth/src/token.service.ts:553-590`](file:///E:/onlinewebsites/quiz-platform/packages/auth/src/token.service.ts#L553-L590)
  ```typescript
  async verifyRefreshToken(token: string, options?: { audience?: string }): Promise<RefreshTokenPayload> {
    // ...
    const { payload } = await jwtVerify(token, this.REFRESH_SECRET, audienceOption);
    return validateAudience(payload);
  }
  ```
- **Architectural Flaw**: `jwtVerify` does not specify an `issuer` option for standard refresh tokens (unlike `verifySkillHubCoreJWT` which specifies `{ issuer: 'skillhubcore.in' }`).
- **Impact**: Tokens issued by disparate microservices sharing the refresh secret can be interchanged without issuer domain boundaries.

### Finding 4: Account Lifecycle Blindness (Scoped to Refresh Path)
- **Source Citation**: [`apps/api-server/src/modules/auth/token-refresh.service.ts:45-78`](file:///E:/onlinewebsites/quiz-platform/apps/api-server/src/modules/auth/token-refresh.service.ts#L45-L78)
- **Architectural Flaw**:
  1. `TokenRefreshService` only checks `brandTokenRepo.findByHash(oldTokenHash)`.
  2. It never queries `UserRepository.findById` or checks user account status.
  3. Proved by `auth.refresh.blocked.branch.test.ts`: The test expects `service.refresh()` to throw `access_denied:user_blocked`, but `TokenRefreshService` lacks this check entirely and successfully mints a new token pair.
- **Impact & Scope**: Within the refresh rotation loop, a security administrator blocking an account in `users` (`isBlocked = true`) will NOT revoke the user's active session. The blocked user can continue rotating refresh tokens. The full system impact is qualified by whether individual downstream API endpoints re-verify `user.isBlocked` on access-token presentation (e.g. via middleware or `/me`), meaning rotation succeeds even if certain authenticated actions are blocked.

### Finding 5: Stale Role & Identity Propagation Without DB Revalidation
- **Source Citation**: [`apps/api-server/src/modules/auth/token-refresh.service.ts:126-145`](file:///E:/onlinewebsites/quiz-platform/apps/api-server/src/modules/auth/token-refresh.service.ts#L126-L145)
  ```typescript
  // 🔐 SECURITY FIX (API-40): Populate email and roles from the old token payload
  const email: string = typeof oldPayload.email === 'string' ? oldPayload.email : '';
  const roles: string[] = Array.isArray(oldPayload.roles)
    ? oldPayload.roles.filter((r): r is string => typeof r === 'string')
    : [];
  // Newly minted access token copies oldPayload.roles directly:
  const newAccessToken = await this.tokenService.generateAccessToken({
    userId, originalUserId, shadowUserId, email, roles, isAdmin, tokenType, brand, aud: requestedAudience
  });
  ```
- **Architectural Flaw**: Roles are treated as immutable properties stored inside the JWT. Refresh rotation never fetches updated `userRoles` from `UserRepository.findByIdWithDetails(userId)`.
- **Impact**: Privilege revocation latency: Demoting an administrator from `ADMIN` to `USER` in the database does NOT demote their active refresh session. They continue receiving `ADMIN` access tokens on every rotation.

### Finding 6: Decoupling of Stored-Row Owner and Token Subject
- **Source Citation**: [`apps/api-server/src/modules/auth/token-refresh.service.ts:114, 136-150`](file:///E:/onlinewebsites/quiz-platform/apps/api-server/src/modules/auth/token-refresh.service.ts#L114-L150)
  ```typescript
  const userId = existingSession.userId; // From DB row
  const shadowUserId = oldPayload.shadowUserId ?? userId; // From JWT
  const originalUserId = oldPayload.originalUserId ?? userId; // From JWT
  ```
- **Architectural Flaw**: If `existingSession.userId !== oldPayload.userId`, the code does not reject the mismatch; it silently mixes DB `userId` with JWT `shadowUserId` and `originalUserId`.
- **Impact**: Confusion of shadow identity and physical tenant identity across multi-tenant bounds.

## 5. Recommended Minimal Follow-On Scope

To address these findings systematically without destabilizing core auth or bloating scope, we recommend dividing future work into two sequential, surgical tickets (renumbered to avoid collision with `W1.2-REFRESH-04: Replay Classification and Post-Commit Failure Policy`):

### Recommendation 1: `W1.2-REFRESH-05` — Token Authority & Brand Binding Integrity
- **Scope**:
  1. Enforce Token Brand Match: If `oldPayload.brand` is present, assert `oldPayload.brand === brand`; fail closed with `Invalid refresh token brand` if mismatched.
  2. Enforce Subject Parity: Assert `oldPayload.userId === existingSession.userId`.
  3. Validate Hostname vs Header: Verify `requestBrand` against verified request hostname candidates.
- **Estimated Effort**: Small (1 service file, ~20 lines, 1 focused test suite).

### Recommendation 2: `W1.2-REFRESH-06` — Account Lifecycle & Fresh Role Revalidation
- **Scope**:
  1. Inject `UserRepository` into `TokenRefreshService`.
  2. Query user status inside refresh flow: verify user exists, `!user.isBlocked`, `!user.deletedAt`.
  3. Fetch fresh `userRoles` and `email` from `userRepo.findByIdWithDetails(userId)` to re-mint access token with live authorities rather than relying on stale JWT claims.
  4. Resolves the long-standing baseline failure in `auth.refresh.blocked.branch.test.ts`.
- **Estimated Effort**: Medium (inject `UserRepository`, update unit tests, 1 test suite).
