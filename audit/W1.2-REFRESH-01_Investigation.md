## 1. Executive Summary

Ticket `W1.2-REFRESH-01` investigates the end-to-end token refresh path across the platform—tracing requests from the frontend/BFF boundaries of RealTutorialHub (RTH) and SkillUp IT Academy (SUIA), through the API Gateway, API Server route handlers, authentication services, JWT verifiers, and the database persistence layer (`refresh_tokens` table).

### Key Investigation Findings

1. **Concurrent Refresh Race Condition (Token Forking Vulnerability)**:
   The rotation mechanism (`TokenRefreshService.refresh`) does NOT perform atomic compare-and-swap or row-count validation on token revocation. `findByHash` is executed outside the database transaction. Within the transaction, `revokeToken` executes an unconditional `UPDATE refresh_tokens SET revoked = true WHERE token = $1` without filtering `revoked = false` and without checking affected row count. Consequently, two concurrent refresh requests submitting the same valid refresh token will both succeed, creating **two distinct, active replacement token chains** from a single token (violating single-use rotation).

2. **Absence of Token Replay Detection & Invalidation**:
   When an already-revoked token is submitted, `findByHash` filters by `revoked = false`, causing `existingSession` to be `null`. The system logs `token_not_found` and throws `Invalid refresh token`. It does not detect that a previously valid token was replayed, nor does it revoke descendant tokens or invalidate the session family. Furthermore, lines 58–67 of `token-refresh.service.ts` (`if (existingSession.revoked)`) constitute **dead code** that is logically unreachable.

3. **Platform / Brand Authority Disconnect**:
   `TokenService.generateRefreshToken` embeds `brand` in the JWT payload, but `TokenRefreshService.refresh` **never validates `oldPayload.brand === brand`**. Brand isolation currently relies solely on ambient database partitioning (`db-rth` vs `db-skillup`). If a client omits the `x-brand` header, the route handler passes `undefined`, which silently falls back via default parameter to `'realtutorialhub'` (`auth.service.ts:54`), causing SUIA tokens to fail lookup in RTH's database.

4. **Subject & Owner Claim Disconnect**:
   `TokenRefreshService.refresh` does not verify that `oldPayload.userId === existingSession.userId`. It silently adopts `existingSession.userId` from the database row while copying `originalUserId` and `shadowUserId` from the JWT payload. Neither `shadowUserId` nor `originalUserId` is stored in `refresh_tokens`, nor are they validated against the `users` table during refresh.

5. **User Account Status Bypass (`isBlocked`)**:
   `TokenRefreshService` does not inject `UserRepository` and never checks whether the user account is blocked (`isBlocked = true`) or soft-deleted (`deletedAt`). A blocked user whose refresh token has not been individually revoked can continue to rotate refresh tokens and obtain fresh access tokens indefinitely.

6. **Broken Pre-existing Refresh Unit Tests**:
   Three pre-existing test files in `@quiz/api-server` fail:
   - `auth.refresh.blocked.branch.test.ts` (1 test fails: expects `access_denied:user_blocked`, but `TokenRefreshService` has no such check).
   - `auth.refresh.invalidAudience.test.ts` (1 test fails: unmocked database query).
   - `token-refresh.service.coverage.test.ts` (2 tests fail: constructor called with 5 arguments instead of 3).

## 4. Deep-Dive Security & Concurrency Analysis

### 4.1 Concurrent Refresh with Identical Token (Token Forking / Race Condition)

#### The Vulnerability Mechanism
`TokenRefreshService.refresh` exhibits a classic Time-of-Check to Time-of-Use (TOCTOU) concurrency vulnerability:

1. **Step 1 (Check outside transaction)**:
   ```typescript
   // apps/api-server/src/modules/auth/token-refresh.service.ts:46
   const existingSession = await brandTokenRepo.findByHash(oldTokenHash);
   ```
   This query is executed with standard `SELECT` (no `FOR UPDATE` lock) outside any transaction.

2. **Step 2 (Lengthy non-transactional computation)**:
   Between Step 1 and Step 4, the application performs:
   - IP mismatch validation and optional warning audit logging (async DB write).
   - `updateLastUsed(oldTokenHash)` (async DB write).
   - Cryptographic JWT verification (`jwtVerify`).
   - Cryptographic JWT generation (`SignJWT.sign` for access token).
   - Cryptographic JWT generation (`SignJWT.sign` for refresh token).
   - SHA-256 token hashing (`crypto.subtle.digest`).

3. **Step 3 (Unconditional update inside transaction)**:
   ```typescript
   // apps/api-server/src/modules/auth/token-refresh.service.ts:175-189
   await brandDb.transaction(async (tx: any) => {
     const txTokenRepo = brandTokenRepo.withDb(tx, { refreshTokens: brandContext.tables.refreshTokens });
     await txTokenRepo.revokeToken(oldTokenHash);
     await txTokenRepo.createRefreshToken({ ... });
   });
   ```
   And in `TokenRepository.revokeToken`:
   ```typescript
   // apps/api-server/src/modules/auth/repositories/token.repository.ts:52-56
   async revokeToken(tokenHash: string) {
     await this.dbInstance.update(this.refreshTokensTable)
       .set({ revoked: true })
       .where(eq(this.refreshTokensTable.token, tokenHash));
   }
   ```

#### Concurrency Execution Timeline

```
Time  Request 1 (Client A)                           Request 2 (Client B - Concurrent / Race)
───   ────────────────────────────────────────────   ────────────────────────────────────────────
T0    findByHash(hash) -> returns unrevoked row      findByHash(hash) -> returns unrevoked row
T1    check expiration -> OK                         check expiration -> OK
T2    updateLastUsed(hash)                           updateLastUsed(hash)
T3    verifyRefreshToken() -> OK                     verifyRefreshToken() -> OK
T4    generateAccessToken() / generateRefreshToken() generateAccessToken() / generateRefreshToken()
T5    BEGIN TRANSACTION                              .
T6    UPDATE refresh_tokens SET revoked=true         . (waiting for row lock on hash row)
      WHERE token = hash (row marked revoked)        .
T7    INSERT INTO refresh_tokens (Token 1)           .
T8    COMMIT TRANSACTION (row lock released)         BEGIN TRANSACTION
T9    [Client 1 receives Token 1]                    UPDATE refresh_tokens SET revoked=true
                                                     WHERE token = hash (row ALREADY revoked;
                                                     PostgreSQL updates 0 or 1 rows with no error)
T10                                                  INSERT INTO refresh_tokens (Token 2)
T11                                                  COMMIT TRANSACTION
T12                                                  [Client 2 receives Token 2]
```

#### Outcome
Because `revokeToken` does not require `and(eq(token, tokenHash), eq(revoked, false))` and does not verify `rowCount === 1`, **both concurrent requests commit successfully**. The single parent refresh token successfully branches into **two valid, independent active refresh token trees**. This directly violates RFC 6819 §5.2.2.3 single-use rotation guarantees.

### 4.2 Replay Handling & Token Family Invalidation

- **Current Behavior**:
  When an already-rotated token is submitted again:
  `findByHash` executes:
  ```typescript
  where: and(
    eq(this.refreshTokensTable.token, tokenHash),
    eq(this.refreshTokensTable.revoked, false)
  )
  ```
  Since `revoked === true` in the DB, the query returns `undefined`.
  `TokenRefreshService` line 48 triggers:
  ```typescript
  if (!existingSession) {
    await this.auditService.log({
      action: 'token_refresh_failed',
      metadata: { reason: 'token_not_found', brand },
      ...
    });
    throw new Error('Invalid refresh token');
  }
  ```
- **Consequences**:
  1. The server cannot distinguish between an invented invalid token and a stolen/replayed token that was already consumed.
  2. The server does not log a security incident for token reuse.
  3. The server does not revoke descendant tokens or invalidate the session family. The attacker or legitimate user holding the descendant token remains active.
  4. Lines 58–67 of `token-refresh.service.ts` checking `if (existingSession.revoked)` can **never execute** because `existingSession` will always be `null` for revoked tokens.

---

### 4.3 Tenant & Brand Authority Agreement

- **Brand Assertion Flow**:
  1. The client browser connects to `user.skillupitacademy.com` or `user.realtutorialhub.com`.
  2. The BFF extracts `host`, calls `resolveBrandFromHostname(host)`, and sets `x-brand: skillup` or `x-brand: realtutorialhub`.
  3. The route handler calls `resolveRequestBrandFromHeaders(_req.headers)`.
  4. If `x-brand` is present, `requestBrand` is set. If absent, `requestBrand` is `undefined`.
  5. `authService.refresh` has a default parameter: `brand: RequestBrand = 'realtutorialhub'`.
- **Gaps Identified**:
  1. **Unenforced Brand Claim**: `oldPayload.brand` is present in the JWT, but `TokenRefreshService` never checks `oldPayload.brand === brand`.
  2. **Reliance on Physical Partitioning**: Brand isolation succeeds only because `getAuthBrandContext(brand)` points to separate DB connection instances (`db-skillup` vs `db-rth`). The token hash is simply not found in the other database.
  3. **Multi-Tenant / Shared DB Risk**: If SkillHub Core (`brand === 'skillhubcore'`) or a consolidated database (`people_db`) is queried, the lack of `oldPayload.brand === brand` validation allows cross-tenant token refresh.
  4. **Silent Default Fallback**: If `x-brand` is missing on a request for a SUIA session, `brand` defaults to `'realtutorialhub'`, querying `realtutorialhubDb`, which fails to find the token and returns 401 Unauthorized.

---

### 4.4 Subject & Identity Namespaces (`userId`, `shadowUserId`, `originalUserId`)

- In `TokenRefreshService.refresh`:
  ```typescript
  const userId = existingSession.userId;
  const oldPayload = await this.tokenService.verifyRefreshToken(oldRefreshToken, { audience: requestedAudience });
  const shadowUserId = oldPayload.shadowUserId ?? userId;
  const originalUserId = oldPayload.originalUserId ?? userId;
  ```
- **Gaps Identified**:
  1. **No Ownership Consistency Check**: `oldPayload.userId` is never compared with `existingSession.userId`. If a DB row's `user_id` did not match the JWT payload `userId`, the DB row `userId` would be adopted while `shadowUserId` and `originalUserId` would be inherited from the JWT payload.
  2. **Unvalidated Shadow Identity**: `shadowUserId` and `originalUserId` are not stored in the `refresh_tokens` database table. They exist solely as unverified string claims in the JWT payload and are passed into newly minted access and refresh tokens without DB validation.
  3. **No Account Status Check (`isBlocked`)**: `TokenRefreshService` does not check the `users` table for `isBlocked` or `deletedAt`. A blocked user can refresh tokens indefinitely.

---

### 4.5 Token Issuer & Audience Validation

- **Issuer (`iss`)**:
  - Access tokens have `.setIssuer('skillhubcore.in')`.
  - Refresh tokens generated by `TokenService.generateRefreshToken` **do not have an issuer claim set** (`.setIssuer` is never called).
  - `verifyRefreshToken` does not validate `issuer`.
- **Audience (`aud`)**:
  - In `apps/api-server/src/app/api/auth/refresh/route.ts:25-26`:
    ```typescript
    const portalIdentity = _req.headers.get('x-portal-identity') ?? 'user';
    const audience = portalIdentity === 'infrastructure' ? 'infra' : portalIdentity === 'admin' ? 'admin' : 'user';
    ```
  - The audience requested during refresh is determined entirely by the client-supplied HTTP header `x-portal-identity`.
  - If a user sends `x-portal-identity: admin`, `route.ts` looks for cookie `admin_refreshToken` and requests `audience: 'admin'`.
  - `verifyRefreshToken` validates that the token's `aud` matches the requested audience. This prevents a user refresh token from being refreshed under the admin scope (which correctly throws an audience mismatch error).

## 6. Proposed Negative Test Scenarios for Follow-On Remediation

1. **NEG-REFRESH-001 (Concurrent Rotation Race)**:
   Simultaneously invoke `refresh()` with the same valid refresh token across two concurrent promises. Exactly one invocation must succeed (200 OK); the second must fail closed (e.g. 409 Conflict or 401 Unauthorized), resulting in exactly ONE active replacement token in the database.
2. **NEG-REFRESH-002 (Replay / Revoked Token Rejection)**:
   Submit an already-revoked refresh token. The system must recognize that the token was previously rotated/revoked, reject the request, log a security breach audit event (`token_replay_detected`), and optionally revoke all descendant tokens.
3. **NEG-REFRESH-003 (Brand Claim Mismatch)**:
   Present a valid refresh token whose payload contains `brand: 'skillup'` to `TokenRefreshService.refresh` with `brand: 'realtutorialhub'`. The service must fail closed before any database update.
4. **NEG-REFRESH-004 (Subject / Stored Owner Mismatch)**:
   Present a refresh token whose JWT payload `userId` does not match the database row's `userId`. The service must reject the request.
5. **NEG-REFRESH-005 (Blocked User Account)**:
   Present a valid refresh token belonging to a user whose record in `users` has `isBlocked = true`. The service must reject with `access_denied:user_blocked` without issuing new tokens.

## 7. Recommended Follow-On Implementation Ticket: `W1.2-REFRESH-02`

We recommend a tightly scoped, bounded follow-on implementation ticket (`W1.2-REFRESH-02`):

### Target Production Scope
- `apps/api-server/src/modules/auth/token-refresh.service.ts`
- `apps/api-server/src/modules/auth/repositories/token.repository.ts`

### Recommended Invariants
1. **Atomic Compare-and-Swap Revocation**:
   In `TokenRepository`, replace unconditional `revokeToken(tokenHash)` with an atomic conditional update:
   ```typescript
   async revokeTokenAtomic(tokenHash: string): Promise<boolean> {
     const result = await this.dbInstance.update(this.refreshTokensTable)
       .set({ revoked: true })
       .where(and(
         eq(this.refreshTokensTable.token, tokenHash),
         eq(this.refreshTokensTable.revoked, false)
       ))
       .returning({ id: this.refreshTokensTable.id });
     return result.length === 1;
   }
   ```
   If `revokeTokenAtomic` returns `false` inside the transaction, throw `TokenReuseError` / rollback immediately.
2. **Explicit Brand & Subject Consistency Validation**:
   In `TokenRefreshService.refresh`, verify:
   ```typescript
   if (oldPayload.brand && oldPayload.brand !== brand) {
     throw new Error('Brand mismatch in refresh token');
   }
   if (oldPayload.userId !== existingSession.userId) {
     throw new Error('Owner mismatch in refresh token');
   }
   ```
3. **Replay Detection & Dead Code Elimination**:
   Remove the dead code `if (existingSession.revoked)` or query `findByHash` without `revoked = false` so revoked tokens can be explicitly recognized as replayed.
4. **Repair Failing Test Files**:
   Update `auth.refresh.blocked.branch.test.ts`, `auth.refresh.invalidAudience.test.ts`, and `token-refresh.service.coverage.test.ts` to reflect the updated constructor and dependencies.
