**Status:** `CLOSED` (source investigation accepted by Sol; security defect remains open)

**Starting commit:** `e6e2096f44aaba49ac3794c1091a67a0154ab124`

## Executive summary

Session persistence for SUIA and RTH learners uses **brand-specific database routing** with **refresh_tokens stored per brand** and **userId as the FK owner**. Token claims carry `brand`, `originalUserId`, and `shadowUserId` fields. The `originalUserId` is the brand-local user FK; the `shadowUserId` references an SHC people projection.

**Critical ownership defect (SU-SESSION-010):** `GlobalLogoutService.revokeSession` (line 113) calls `brandTokenRepo.revokeById(sessionId)` **without passing userId**. `TokenRepository.revokeById` conditionally applies userId ownership filtering only if the parameter is supplied (lines 59-65). This allows revocation by session ID alone when the optional userId is omitted, creating potential cross-user session revocation within the same brand database.

**Generic SessionService wiring concern:** `POST /api/auth/logout-all` imports `SessionService` from `@quiz/auth` (line 9). The container lazily constructs this generic service, but its `SessionRepository` interface is not wired to the brand-specific `TokenRepository`. Runtime behavior is unverified.

**Tenant isolation mechanism:** refresh_tokens tables have no platform/brand column. Tenant isolation depends on brand-specific database routing (`db-skillup` vs `db-rth`) and userId FK constraints. If deployed and selected correctly, separate databases constrain storage scope; signatures establish token integrity, not complete ownership/tenant authorization. Route authority and stored-session claims still require verification. Source configuration routing is observed; deployed database separation is not verified in this read-only investigation.

### refresh_tokens schema

**Files:**
- `packages/db-skillup/src/schema/users.ts:77-100`
- `packages/db-rth/src/schema/users.ts:77-100`
- `packages/db/src/schema/auth.ts:84-107`

**Schema (all three databases have identical structure):**
```typescript
export const refreshTokens = pgTable("refresh_tokens", {
  id: uuid("id").primaryKey().defaultRandom(),
  userId: uuid("user_id")
    .notNull()
    .references(() => users.id, { onDelete: "cascade" }),
  token: text("token").notNull().unique(),
  expiresAt: timestamp("expires_at").notNull(),
  revoked: boolean("revoked").notNull().default(false),
  lastActiveAt: timestamp("last_active_at").notNull().defaultNow(),
  createdAt: timestamp("created_at").notNull().defaultNow(),
  deviceId: text("device_id"),
  ipAddress: text("ip_address"),
  userAgent: text("user_agent"),
  deviceName: text("device_name"),
  lastUsedAt: timestamp("last_used_at").defaultNow(),
}, (t) => ({
  idx_refresh_tokens_user_id: index("idx_refresh_tokens_user_id").on(t.userId),
  idx_refresh_tokens_device_id: index("idx_refresh_tokens_device_id").on(t.deviceId),
  idx_refresh_tokens_user_device: index("idx_refresh_tokens_user_device").on(t.userId, t.deviceId),
  idx_refresh_tokens_ip: index("idx_refresh_tokens_ip").on(t.ipAddress),
}));
```

**Critical observation:**
- ❌ **No `brand` or `platform` column**
- ✅ `userId` FK references `users.id` in the **same database**
- ✅ `token` has unique constraint (hash collision safety)
- ❌ No composite unique constraint on (userId, deviceId, brand)

**Tenant isolation mechanism:** Physical database separation + userId FK scoping. If an attacker can route to the wrong database or supply a userId that exists in both databases, **schema constraints do not prevent cross-tenant access**.

## Tenant verification gaps

### 1. Single-session revocation drops userId (SU-SESSION-010)

**Confirmed defect:** `GlobalLogoutService.revokeSession` receives userId from the authenticated caller but does not pass it to `TokenRepository.revokeById`. The repository conditionally applies ownership filtering only when userId is supplied.

**Call path:**
- Route: `apps/api-server/src/app/api/auth/sessions/[sessionId]/route.ts:89` passes userId
- Service: `apps/api-server/src/modules/auth/global-logout.service.ts:113` calls `brandTokenRepo.revokeById(sessionId)` **without userId**
- Repository: `apps/api-server/src/modules/auth/repositories/token.repository.ts:62` accepts optional userId but applies WHERE filter only if present

**Impact:** Within the same brand database, any authenticated user could revoke another user's session by supplying a valid session ID. Brand-specific database routing prevents cross-platform revocation.

**End-to-end exploitability:** Not executed against live deployment. Requires:
1. Attacker obtains valid access token for brand A
2. Attacker discovers victim's session ID from the same brand
3. Attacker calls DELETE /api/auth/sessions/[victimSessionId]
4. Service revokes victim's session without ownership check

**Mitigation:** RBAC permission check (PERMISSIONS.PROFILE_WRITE) applies, but permissions alone do not enforce per-session ownership. Session ID discovery is required for exploitation.

### 2. Generic SessionService wiring unresolved

**Concern:** `POST /api/auth/logout-all` (line 30) obtains `SessionService` from the container. The generic service delegates to a `SessionRepository` interface, but the container binding to `TokenRepository` is not located.

**Method name mismatch:** Generic interface expects `revokeAllForUser(userId)` (line 23); `TokenRepository` implements `revokeAll(userId)` (line 68).

**Runtime behavior:** Unknown without execution. Possible outcomes:
- Container fails to resolve SessionRepository (error at request time)
- Container provides a different repository implementation
- An adapter bridges the interface mismatch

**Separate working implementation:** `DELETE /api/auth/sessions` (line 169) calls `GlobalLogoutService.logoutAllDevices` with proper brand-specific TokenRepository binding. This path works correctly.

### 3. refresh_tokens has no brand column

**Observation:** Schema stores userId FK and session metadata but no explicit brand column. Tenant isolation relies on:
- Physical database separation (db-skillup vs db-rth)
- Brand-specific database routing via `getAuthBrandContext(brand)`
- JWT signature validation preventing claim forgery

**Not a defect without demonstrated necessity:** The absence of a brand column is not inherently a vulnerability. FK constraints and database routing provide isolation. Adding a redundant column without a demonstrated failure mode or specific consumer requirement is premature schema expansion.

**When brand column would be required:**
- If databases were consolidated into schemas within a single database
- If cross-brand session queries were intentionally needed for analytics
- If brand-based session cleanup or migration were implemented

### 4. Refresh token lookup before JWT verification

**Observation:** `TokenRefreshService.refresh` (line 54) looks up the session by hash before verifying the JWT signature and claims (line 90-105).

**Hash entropy:** Refresh tokens are high-entropy JWTs. Hash collision within a database is statistically improbable.

**Authority flow:**
1. Hash lookup finds existing session (line 54)
2. JWT signature verified (line 90-96)
3. Claims extracted (originalUserId, shadowUserId, brand) from verified JWT
4. New tokens issued with verified claims (line 109-147)

**Not a defect:** Hash-only lookup is safe due to token entropy. The verified JWT claims, not the database row, establish authority for the new tokens. Cross-user exploitation requires either JWT forgery (prevented by signature) or hash collision (statistically negligible).

**Potential consistency check:** Compare verified JWT brand claim against request brand before issuing new tokens. This is defense-in-depth, not correction of a demonstrated vulnerability.

### Identified defects and concerns

1. ❌ **SU-SESSION-010: userId dropped in GlobalLogoutService.revokeSession** (line 113)
   - Service receives userId from authenticated route
   - Service calls `brandTokenRepo.revokeById(sessionId)` without passing userId
   - Repository conditionally applies ownership filter only if userId is supplied
   - **Impact:** Within same brand, user could revoke another user's session by ID

2. ⚠️ **Generic SessionService wiring unresolved** (POST /api/auth/logout-all)
   - Route imports generic SessionService from @quiz/auth
   - Container binding to TokenRepository not located
   - Method name mismatch: interface expects `revokeAllForUser`, TokenRepository implements `revokeAll`
   - **Impact:** Runtime behavior unknown; likely fails or uses unexpected implementation
   - **Alternative:** DELETE /api/auth/sessions provides same functionality via GlobalLogoutService

3. ⚠️ **No brand column in refresh_tokens schema**
   - Not a defect; brand is encoded in database routing and JWT claims
   - Physical database separation provides tenant isolation
   - Adding column without demonstrated necessity is premature

4. ⚠️ **Refresh token hash lookup before JWT verification**
   - Not a defect; high-entropy token makes collision negligible
   - Verified JWT claims establish authority, not database lookup
   - Defense-in-depth brand comparison optional but not required

### Risk assessment

**HIGH (P0):** Single-session revocation lacks userId ownership enforcement (SU-SESSION-010)
- Requires session ID discovery for exploitation
- RBAC permissions apply but do not enforce per-session ownership
- Corrected by passing userId to repository (W1.2-SESS-01)

**MEDIUM (P1):** POST /api/auth/logout-all wiring unresolved
- Runtime behavior unknown without execution
- Alternative working implementation exists (DELETE /api/auth/sessions)
- Separate investigation or removal recommended

**LOW (P2):** No schema-level brand isolation column
- Mitigated by physical database separation and JWT signature validation
- No demonstrated vulnerability requiring schema change

## Recommendations

### Immediate (P0) - W1.2-SESS-01

1. **Enforce userId ownership in GlobalLogoutService.revokeSession** (line 113)
   - Pass userId to `brandTokenRepo.revokeById(sessionId, userId)`
   - Make userId parameter required in TokenRepository.revokeById signature
   - Verify all callers supply authenticated userId from verified JWT claims
   - Execute regression tests for cross-user and cross-platform denial

**Acceptance criteria:** TypeScript compilation succeeds; all 10 regression tests pass; independent security review completed; Sol acceptance recorded.

### Short-term (P1) - Separate investigation

1. **Investigate POST /api/auth/logout-all runtime behavior**
   - Execute request against staging to confirm success or failure
   - If broken: remove route and document DELETE /api/auth/sessions as alternative
   - If working: document container binding and repository wiring

2. **Verify deployed database separation**
   - Confirm db-skillup, db-rth, and db (SHC) are separate PostgreSQL instances
   - Review connection string configuration and access controls

### Optional (P2) - Defense in depth (no demonstrated vulnerability)

1. **Add brand consistency check to token refresh**
   - Compare verified JWT brand claim against request brand
   - Log warning on mismatch; consider rejection if mismatch pattern emerges

2. **Load test concurrent token refresh**
   - Verify transaction isolation prevents race conditions
   - Consider pessimistic locking if replay succeeds under load

**Not recommended:**
- Adding brand column to refresh_tokens (redundant with database routing)
- Creating duplicate session routes (existing routes are present)
- Schema migrations without demonstrated defect or consumer requirement
