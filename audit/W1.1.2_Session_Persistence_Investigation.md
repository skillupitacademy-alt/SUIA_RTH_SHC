## Executive summary

Session persistence for SUIA and RTH learners uses **brand-specific database routing** with **refresh_tokens stored per brand** and **userId as the FK owner**. Token claims carry `brand`, `originalUserId`, and `shadowUserId` fields. The `originalUserId` is the brand-local user FK; the `shadowUserId` references an SHC people projection.

**Critical finding:** refresh_tokens tables have **no platform/brand column**. Tenant isolation depends entirely on routing to the correct brand database (`db-skillup` vs `db-rth`) and userId FK scoping. Cross-platform session access is **not prevented by schema constraints** if the attacker can forge the database routing or supply a colliding userId.

Session revocation and logout operations consume `userId` from the JWT access token payload. There is **no explicit verification** that the userId belongs to the requesting brand before session listing, revoke, or logout. The brand context is established from request hostname/headers and used to select the database, but the userId itself is **not validated against brand ownership**.

**Files:**
- `packages/db-skillup/src/schema/users.ts:77-100`
- `packages/db-rth/src/schema/users.ts:77-100`
- `packages/db/src/schema/auth.ts:84-107`

```typescript
export const refreshTokens = pgTable("refresh_tokens", {
  id: uuid("id").primaryKey().defaultRandom(),
  userId: uuid("user_id")
    .notNull()
    .references(() => users.id, { onDelete: "cascade" }),
  token: text("token").notNull().unique(),
  expiresAt: timestamp("expires_at").notNull(),
  revoked: boolean("revoked").notNull().default(false),
  lastActiveAt: timestamp("last_active_at").notNull().defaultNow(),
  createdAt: timestamp("created_at").notNull().defaultNow(),
  deviceId: text("device_id"),
  ipAddress: text("ip_address"),
  userAgent: text("user_agent"),
  deviceName: text("device_name"),
  lastUsedAt: timestamp("last_used_at").defaultNow(),
}, (t) => ({
  idx_refresh_tokens_user_id: index("idx_refresh_tokens_user_id").on(t.userId),
  idx_refresh_tokens_device_id: index("idx_refresh_tokens_device_id").on(t.deviceId),
  idx_refresh_tokens_user_device: index("idx_refresh_tokens_user_device").on(t.userId, t.deviceId),
  idx_refresh_tokens_ip: index("idx_refresh_tokens_ip").on(t.ipAddress),
}));
```

**Critical observation:**
- ❌ **No `brand` or `platform` column**
- ✅ `userId` FK references `users.id` in the **same database**
- ✅ `token` has unique constraint (hash collision safety)
- ❌ No composite unique constraint on (userId, deviceId, brand)

**Tenant isolation mechanism:** Physical database separation + userId FK scoping. If an attacker can route to the wrong database or supply a userId that exists in both databases, **schema constraints do not prevent cross-tenant access**.

## Identity namespace mapping

### userId (brand-local learner ID)

**Source:** Brand-specific `users.id` (UUID)
**Database:** `db-skillup.users` or `db-rth.users`
**FK constraint:** `refresh_tokens.userId` → `users.id` (cascade delete)
**JWT claim:** `payload.userId`
**Scope:** **Platform-specific**. A SkillUp learner and RTH learner can have the same email but **different userId UUIDs**.

**Authorization:** User operations (logout, session listing, profile) consume this ID. The brand database routing ensures queries go to the correct tenant's users table.

### originalUserId (identity bridge source)

**Source:** Set to the brand user ID during login
**File:** `apps/api-server/src/modules/auth/login.service.ts:153-165`
**JWT claim:** `payload.originalUserId`
**Purpose:** According to W1.1 architecture, this records which brand user ID initiated the session. It is **not** an impersonation field.

**Evidence:** Always set to `user.id` at login (L153: `originalUserId: user.id`).

### shadowUserId (SHC projection)

**Source:** `people_db.people.id` (SHC unified identity projection)
**Bridge:** `packages/identity-bridge` via `UserIdentityBridgeService`
**File:** `apps/api-server/src/modules/auth/login.service.ts:35-60`
**JWT claim:** `payload.shadowUserId`

**Creation/sync:** `login.service.ts:47-55`

```typescript
const result = await bridge.syncUser({
  externalId: user.id,

  platform: brand,

await bridge.updateShadowUserId(brandContext.db, brandContext.tables.users, user.id, result.shadowUserId);
```

**Purpose:** The shadowUserId is an SHC-managed projection for service coordination. It is **not** a global learner identity or permission authority.

**Authorization scope:** The W1.1 architecture forbids using shadowUserId for learner authorization. Shared resources require explicit permission checks, not automatic access.

## Tenant verification gaps

### 1. refresh_tokens has no brand column

**Risk:** If two users with the same email exist on both platforms and an attacker can control the `x-original-host` header, they could **attempt database routing switch** during token refresh.

**Mitigation (current):** 
- Token hash uniqueness prevents replay **within a database**
- Physical database separation prevents **cross-database hash collision**
- JWT signature validation prevents **token forgery**

**Remaining risk:** If an attacker can **forge the brand routing header** and the JWT claims are not cross-checked against the database, the refresh operation could succeed with mismatched tenant context.

### 2. userId not validated against brand

**Operations affected:**
- Session listing (logout-all)
- Session revocation (revokeById if exposed)
- Logout (trusted from JWT)

**Current behavior:** The `userId` from the JWT is **assumed correct** for the selected brand database. No verification that this userId belongs to the requesting brand.

**Example attack scenario:**
1. Attacker obtains valid SkillUp access token (userId=A, brand=skillup)
2. Attacker sends request to RTH endpoint with forged `x-original-host: realtutorialhub.com`
3. Server selects RTH database
4. If RTH also has a user with userId=A (collision unlikely but possible), operations could succeed

**Mitigation (current):** UUID collision is statistically unlikely. However, **schema constraints do not enforce this**.

### 3. Generic SessionService not wired

**Operations affected:**
- `logout-all` route
- Session listing UI

**Current status:** The `@quiz/auth` SessionService uses a generic `SessionRepository` interface that is **not connected** to the brand-specific `TokenRepository`.

**Runtime behavior:** **Uncertain**. Likely throws error at runtime or returns empty results.

**Required fix:** Wire TokenRepository as SessionRepository adapter with brand context, or remove generic SessionService imports and use TokenRepository directly.

### 4. No revoke-by-id route for learners

**Missing:** `/api/auth/sessions/:id/revoke` or equivalent
**Impact:** Users cannot revoke individual device sessions from UI
**Current UI:** `src/share-branding/ui/device-sessions.tsx` exists but backend is missing
