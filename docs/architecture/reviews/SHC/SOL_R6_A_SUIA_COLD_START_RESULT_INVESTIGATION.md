## Smallest diagnostic and conditional correction proposal

The first proposed change is an evidence-only reproduction harness, requiring owner approval for local process execution and any fixture/session effects. For every result attempt, capture a generated correlation ID, exact synthetic exam ID and tenant, start/end timestamps, status, content type, sanitized response body, request/correlation IDs from all hops, and the exception class/code where available. Capture SUIA, gateway and backend logs for that run. Avoid credentials, cookies, authorization headers and raw SQL connection strings in saved artifacts. Record per-process readiness and target route compilation, rather than treating a health200 as proof that the result route is warm.

Use an existing approved synthetic SUIA owner and a pre-provisioned started exam. Password login, refresh or profile validation may themselves write session/audit/last-login data, even when the final result request is a GET. The isolated execution environment must explicitly permit those effects or use in-memory/session/provider fixtures that cannot reach a real database. The original run's synthetic users and exams were already cleaned up. Their IDs and old cookies are unsuitable for replay.

For an isolated reproduction, bind SUIA3009, gateway8787 and backend3000 to localhost, supply synthetic signing/internal secrets, disable real report/PDF/AI/provider calls, and supply controlled account/session and exam boundaries. Start from the same frozen source hashes. Run these bounded conditions in sequence.

1. Process startup followed by the first authorized result request, preserving all hop receipts. Compare a subsequent request for the same owned started exam.
2. Process Ready with the result route still cold, then one owner request and one foreign-owner request. Verify expected202 and403 respectively and verify zero scoring/report invocation for started exams.
3. A gateway-to-backend connection failure, a BFF-to-gateway connection failure and an interrupted upstream response body. Record where an exception becomes a response and whether every response prohibits private caching and sanitizes its body.
4. A controlled current-session dependency failure. Verify the existing fail-closed status and continued denial for revoked/wrong-brand credentials.
5. A controlled MainDB exam-read failure, then recovery. Preserve owner predicates and distinguish operational failure from invalid request data.

Do not retry authenticated mutations as part of this diagnosis. The original case is a GET. Any retry proposal should apply only to the demonstrated safe read contract after authorization and deadline behavior are understood.

If correlation proves a BFF transport/body exception, the smallest source correction would catch that specific failure at the existing BFF boundary and return a sanitized operational502/503/504 under an approved error contract. Configuration defects should remain distinguishable in private diagnostics. Do not convert every upstream500 to503 without determining its meaning. The shared helper serves multiple apps, so caller compatibility and status/body/header regression tests are required.

If the gateway generated500 for an unavailable backend, the smallest correction would classify that verified transport failure at the existing gateway catch, retain request correlation, sanitize public diagnostics and preserve authentication/tenant headers. A startup race in local Next.js compilation may instead require a diagnostic-harness/readiness correction. No production behavior change is justified until the failing boundary is reproduced.

The controlled generic MainDB exception currently returning400 is a verified secondary error-taxonomy issue. Correcting it would require a separately approved source change to the existing result error path and tests for client errors, authorization denials, sanitized operational errors and processing202 behavior. It is not established as the original500 cause.
