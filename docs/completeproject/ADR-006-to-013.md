# ADR-006: Monorepo Strategy — Turborepo

**Date:** 2026-03-19
**Status:** Accepted
**Deciders:** Platform team

## Context
Exam Engine exists as a standalone pnpm monorepo (quiz-platform).
Tutorial Engine, SkillHubCore, and SkillUp are being added.
Decision: one repo or many?

## Decision
**One Turborepo monorepo** for all services and apps.

## Rationale
| Factor | Decision |
|---|---|
| Shared types (Domain hierarchy) | Monorepo prevents drift |
| Small team | Polyrepo coordination overhead too high |
| Independent deployments needed | Turborepo supports this |
| Shared packages (auth, events, ui) | Monorepo makes this trivial |
| CI/CD | One pipeline, per-service deploy jobs |

## Consequences
- All teams work in one repository
- `pnpm-workspace.yaml` defines all packages
- `turbo.json` defines build/test/deploy pipeline
- Each service has its own `package.json` and is independently deployable
- Breaking changes in shared packages require updating all consumers

## Trigger to revisit
Team size > 15 engineers → evaluate polyrepo per domain team

# ADR-007: API Gateway on Cloudflare Workers

**Date:** 2026-03-19
**Status:** Accepted

## Context
All frontends need a single entry point. Options: Nginx, Kong, Cloudflare Workers, AWS API Gateway.

## Decision
**Hono on Cloudflare Workers** as the API Gateway.

## Rationale
- Zero cold starts (Workers run at edge)
- Global by default (200+ PoPs)
- Free for first 100,000 req/day
- JWT verification at edge (no service call needed)
- Native Cloudflare WAF + DDoS integration
- Hono is Workers-native and extremely lightweight

## Rejected Alternatives
- Nginx: needs VM, no edge, cold start
- Kong: heavy, expensive, needs Postgres
- AWS API Gateway: vendor lock-in, high cost at scale

## Consequences
- Gateway logic must be edge-compatible (no Node.js-only APIs)
- `jose` library used for JWT (edge-compatible, not `jsonwebtoken`)
- Business logic stays in Railway-hosted services (not Workers)

# ADR-008: People DB Shared Between Two Services

**Date:** 2026-03-19
**Status:** Accepted

## Context
Student-faculty-service and CRM-service both need user/student data.
Can they share one Neon database?

## Decision
**Yes — shared People DB** with strict table ownership rules.

## Rationale
- Students and CRM enquiries are the same people (pre/post admission)
- Two separate DBs would require cross-DB sync for admission conversion
- Table ownership enforced by convention + RLS policies (not separate DBs)
- Both services use same Neon project, different Drizzle schema exports

## Table Ownership Rules
```
student-faculty-service OWNS:
  users, students, faculty, batches, batch_sessions,
  batch_enrollments, attendance_records, faculty_availability

crm-service OWNS:
  enquiries, enquiry_follow_ups, admissions,
  student_documents, demo_sessions

NEITHER service directly writes to the other's tables.
Cross-service writes happen via QStash events ONLY.
```

## Consequences
- Shared Neon connection pool must be monitored carefully
- CRM enquiry → admission conversion fires QStash event → student-faculty-service creates student record
- DB migrations require coordination between both service teams

# ADR-009: Payment DB Fully Isolated

**Date:** 2026-03-19
**Status:** Accepted

## Context
Financial data (payment ledger, transactions) — should it share People DB?

## Decision
**Completely isolated Payment DB** — separate Neon project.

## Rationale
- Financial data has different retention rules (7 years legal minimum)
- `payment_transactions` is append-only — no UPDATE/DELETE ever
- Audit trail must be immutable and independently verifiable
- PCI-DSS compliance considerations (even if not storing card data)
- Scaling independently: payment writes spike on due dates

## Consequences
- payment-service is the ONLY service with Payment DB credentials
- All other services get payment status via:
  1. QStash events (payment.received, payment.overdue)
  2. payment-service REST API (sync queries, rare)
- No cross-DB foreign keys from People DB to Payment DB

# ADR-010: QStash as Event Bus

**Date:** 2026-03-19
**Status:** Accepted

## Context
Services need to communicate asynchronously. Options: Kafka, RabbitMQ, AWS SQS, Upstash QStash.

## Decision
**Upstash QStash** as the event bus.

## Rationale
| Factor | QStash | Kafka | SQS |
|---|---|---|---|
| Cost at our scale | Free tier (10K/day) | Expensive | Cheap |
| Serverless-friendly | ✅ Native | ❌ Needs broker VMs | ✅ |
| HTTP-based | ✅ | ❌ | ✅ |
| Built-in retries | ✅ (3 retries) | Manual | ✅ |
| Dead letter queue | ✅ | Manual | ✅ |
| Delay/scheduling | ✅ | ❌ | Limited |
| Already in stack | ✅ (exam-service uses it) | ❌ | ❌ |

## Consequences
- All cross-service async communication goes via QStash
- Each consumer endpoint MUST verify QStash signature
- Events are HTTP POST — consumers must be HTTP-accessible services
- QStash has 10K free messages/day — upgrade at scale

## Trigger to revisit
> 500K messages/day → evaluate Kafka on OCI or Upstash Kafka

# ADR-011: Hono for Backend Services

**Date:** 2026-03-19
**Status:** Accepted

## Context
Which backend framework for Node.js microservices? Express, Fastify, NestJS, Hono?

## Decision
**Hono** for all backend services.

## Rationale
- Edge-compatible (runs on Cloudflare Workers AND Node.js/Railway)
- TypeScript-first with excellent type inference on routes
- Fastest Node.js framework in benchmarks (comparable to Fastify)
- Middleware composable — perfect for our withRateLimit→withAuth→handler pattern
- Same framework as API Gateway — team learns one tool
- Tiny bundle size — important for cold start on Railway

## Rejected Alternatives
- Express: no TypeScript-first, slow, no edge support
- NestJS: heavy abstractions, opinionated, slow startup
- Fastify: good but no edge runtime support

## Consequences
- All services use Hono router
- Middleware pattern: `app.use(rateLimitMiddleware).use(authMiddleware)`
- OpenAPI generation via `hono-openapi` or `@hono/zod-openapi`

# ADR-012: Razorpay + Stripe Payment Abstraction

**Date:** 2026-03-19
**Status:** Accepted

## Context
Platform serves India (INR) and international (USD/EUR). Which gateway(s)?

## Decision
**Both Razorpay (India) and Stripe (International)** behind a shared `IPaymentGateway` interface.

## Currency Routing Logic
```
INR + country = IN → Razorpay
USD/EUR/GBP/AED + country != IN → Stripe
Manual/offline → ManualGateway (admin entry)
```

## Interface Contract
```typescript
interface IPaymentGateway {
  createOrder(params): Promise<GatewayOrder>
  verifyPayment(params): Promise<VerifyResult>
  processRefund(params): Promise<RefundResult>
  getPaymentStatus(id): Promise<PaymentStatus>
}
```

## Consequences
- New gateway (e.g., PayPal) → implement `IPaymentGateway`, add to routing table
- All webhook handlers verify gateway signature before processing
- Idempotency keys prevent double-charging on webhook retries
- `gateway_webhook_logs` table ensures each webhook processed exactly once

# ADR-013: Notification Service — Stateless Dispatcher

**Date:** 2026-03-19
**Status:** Accepted

## Context
Every service needs to send emails, WhatsApp, SMS. Centralize or not?

## Decision
**Centralized stateless notification-service** that only responds to QStash events.

## Architecture
```
Any service → publishEvent('payment.received') → QStash
  → notification-service consumes
  → selects template based on event type
  → routes to correct channel(s) (Email/WhatsApp/SMS/Push)
  → logs to notification_log table (own small DB or table in People DB)
```

## Why Stateless
- notification-service has NO knowledge of business logic
- It maps: eventType → template → channel(s)
- If notification fails → QStash retries automatically
- Can be deployed on Railway serverless (scales to zero when no events)

## Channel Priority
```
CRITICAL events (payment overdue, exam result):  ALL channels
TRANSACTIONAL (receipt, OTP):                     Email + SMS
ENGAGEMENT (new content, streak):                 Push + WhatsApp
MARKETING:                                        Email + WhatsApp
```

## Consequences
- All notification templates live in notification-service only
- Adding new notification → add event consumer + template in notification-service only
- Other services have zero notification code
- WhatsApp templates must be pre-approved by Meta before use
