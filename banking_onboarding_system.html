Background

RBI Compliance

SWIFT Protocol

Every account must carry a swift_code for wire routing.

KYC Protocol

Every account must carry a kyc_level.

What You Need to Build
Cooperative mixin classes (RBI, SwiftProtocol, KYCProtocol) that call super().__init__(*args, **kwargs).
A composite class IntlSBI that works regardless of mixin order and accepts branch_code.
Two @classmethod factories that parse different inputs generically (no hardcoded field-by-field mapping).
Extensibility: A new mixin (FraudRiskProfile) can be added without modifying existing code.
Big Picture Architecture
Part A – Core Requirements
A1 Cooperative Multiple Inheritance
Create mixin classes: RBI, SwiftProtocol, KYCProtocol.
Each accepts exactly one attribute it owns.
Each MUST call super().__init__(*args, **kwargs).
A2 The Composite Class
Create IntlSBI(RBI, SwiftProtocol, KYCProtocol).
Accepts its own attribute: branch_code.
All four attributes must be set correctly.
No hardcoded routing of fields.
A3 @classmethod Factories
from_swift_message(raw: str) → Parses semicolon format: "CCY;...;SWIFT;...;BRANCH;...;KYC;..."
from_admin_registration(json: str) → Parses JSON generically and forwards via cls(**data).

Why Order Matters?

The order RBI, SwiftProtocol, KYCProtocol determines the Method Resolution Order (MRO). Python calls super() according to this order.

IntlSBI(RBI, SwiftProtocol, KYCProtocol) RBI → SwiftProtocol → KYCProtocol → object
VS
IntlSBI(KYCProtocol, RBI, SwiftProtocol) KYCProtocol → RBI → SwiftProtocol → object
What Changes If Reordered?
The initialization call order changes.
super() will follow the new MRO.
All attributes still set (if each mixin cooperates).
But debugging order & side-effects may differ.
