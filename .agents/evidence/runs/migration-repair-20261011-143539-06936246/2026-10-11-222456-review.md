## Exit code validation gap closed

Lines 169-172 add exit code validation to `verify_commit_identity()`:

```python
# Validate git command succeeded
if result.exit_code != 0:
    # Non-zero exit code indicates failure
    return False, None, None
```

The function returns `(False, None, None)` before attempting to read `result.stdout`, preventing downstream code from treating error output as a valid SHA when `git rev-parse HEAD` fails.

## Orphaned function — no call site

The function is never called in production code. Searching the codebase for `format_commit_message(` returns only:
- The function definition in final_gate_agent.py (line 137)
- Two test calls in test_migration_repair_agent_final_gate_agent.py (lines 105, 111)

The migration repair workflow's commit pathway is in the repair_implementer agent. That agent calls `git rev-parse HEAD` before and after applying changes to track commit SHAs (lines 121, 183 of repair_implementer.py), but it doesn't create commits itself — it assumes commits are made externally or by file operations that auto-commit. The publisher_agent (W9) explicitly does not push commits and only records publication state.

The test `test_git_operations_real.py::test_publisher_agent_commits_with_metadata` (line 157-158) expects commits to include "Run ID: test-run-123" in the message body, confirming the feature is required. But the production code that would produce this format doesn't exist.

To complete the fix, `format_commit_message()` must be called wherever commits are created in the workflow, passing `context.run_id` (or equivalent) and using the returned string as the `-m` argument to `git commit`.
