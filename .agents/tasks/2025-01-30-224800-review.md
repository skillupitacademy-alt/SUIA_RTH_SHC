# Wave 0 Canonical Workflow Authority Freeze

**Branch:** m2-project-ai-canonical-wiring  
**Commits:** cb45462d (initial), 9dc47b46 (main implementation), 0d7e782a (review fixes)  
**Design:** `.agents/tasks/w0-design-doc.md`  
**Plan:** `.agents/tasks/w0-implementation-plan.md`  
**Evidence:** `.agents/tasks/architecture-freeze-report.json`

Wave 0 establishes the canonical workflow authority infrastructure by creating a 17-state `CanonicalWorkflowState` enum, `ProjectLLMWorkflow` model with hash-bound artifact tracking, `WorkflowGovernanceService` as the single point of authority for state transitions, and REST API endpoints for workflow operations. The implementation resolves the multiple-authority conflict identified in the audit by wiring governance service into approval routes, deprecating task routes, and updating workflow engine to execute based on canonical states.

The governance service enforces state transition validation, terminal state immutability, and hash-bound authorization gates with self-approval prevention. The workflow model tracks lifecycle state, artifact bindings (contract, candidate, manifest, snapshot), approval records, and complete state transition history. Five REST endpoints expose workflow creation, state retrieval, transition execution, history access, and artifact binding.

**Watch for:** WorkflowEngine integration is stubbed—most state transitions execute stub code instead of real agents. Agent coordinator was not updated to use governance service. Frontend integration is documented but not implemented (backend-only scope).

**Verdict**: APPROVED

---

## High-level view

The 17-state canonical workflow enum defines the complete block engineering lifecycle from REQUESTED through DISCOVERY, gate approvals (AWAITING_GATE_1, AWAITING_IMPLEMENTATION_APPROVAL, AWAITING_GATE_2), candidate audit, placement, verification, and terminal states (CERTIFIED, REJECTED). Each state documents its purpose, activities, next states, and gate requirements. The `VALID_TRANSITIONS` dictionary enforces valid progressions; terminal states have empty transition lists.

`WorkflowGovernanceService` centralizes all workflow state mutations: create_workflow initializes in REQUESTED state, transition_state validates and executes transitions with authorization checks for IMPLEMENTING, validate_transition enforces state machine rules and terminal state boundaries, register_approval binds approval records, and bind_artifact attaches hash-verified artifacts. The service uses in-memory storage for Wave 0 with database persistence deferred to Wave 1+.

Authorization for IMPLEMENTING transition enforces six gates: approval record must exist, status must be APPROVED, candidate hash must match, manifest ID must match, manifest hash must match, and approver must not be the requester. Each check returns detailed failure reasons. Hash verification uses exact SHA-256 string comparison.

Governance routes were updated to call governance_service.transition_state when approving or rejecting placements, maintaining backwards compatibility via adapter pattern with legacy _workflow_states dict. Task routes were marked deprecated with migration guidance to /workflows endpoints. WorkflowEngine.execute_workflow_stage reads canonical state from governance service and calls transition_state after agent execution, though most agent logic is stubbed.

REST API provides POST /workflows (create), GET /workflows/{id} (retrieve), POST /workflows/{id}/transition (internal state change), GET /workflows/{id}/history (audit trail), and POST /workflows/{id}/artifacts (bind hashes). Pydantic schemas validate requests and serialize responses. All endpoints return appropriate status codes (201, 200, 400, 404).

Test coverage includes 36 new unit tests: workflow model tests verify creation, serialization, terminal/gate state detection, artifact binding, and state history; governance service tests cover workflow creation, retrieval, transition validation, authorization gates, approval registration, and artifact binding for all four types. All new tests pass. Evidence report shows 269 overall passing tests with 55 pre-existing failures (confirmed unrelated to Wave 0 changes).

Scope was intentionally reduced from original plan: AgentCoordinator was not updated, WorkflowEngine agent execution is mostly stubbed, frontend integration is documented but not implemented. The retirement plan documents the migration timeline for competing authorities (TaskState workflow usage, frontend independent state machine, legacy workflow dicts).

## Canonical state machine design

The state machine was designed and implemented in this wave, not integrated from pre-existing code. VALID_TRANSITIONS dictionary maps each state to valid next states; terminal states (CERTIFIED, REJECTED) map to empty lists preventing further transitions. Helper functions is_valid_transition, is_gate_state, and is_terminal_state provide validation API.

## Authorization gate enforcement

Authorization for IMPLEMENTING transition enforces six checks via can_transition_to_implementing: approval record exists for workflow_id, status is APPROVED, candidate hash matches, manifest ID matches, manifest hash matches, and approver differs from requester. Each check returns (False, reason) on failure. Hash verification uses exact SHA-256 string comparison. Missing required parameters cause immediate failure.

WorkflowGovernanceService.transition_state calls can_transition_to_implementing before executing IMPLEMENTING transitions, raising ValueError if authorization fails.

## Workflow model and artifact binding

ProjectLLMWorkflow dataclass tracks workflow identity, lifecycle state, artifact bindings (contract/candidate/manifest/snapshot with SHA-256 hashes), approval records, and state history. StateTransition records from_state, to_state, timestamp, triggered_by, evidence_id, and reason. Both provide to_dict methods for serialization.

Artifact binding via WorkflowGovernanceService.bind_artifact accepts artifact_type, artifact_id, and artifact_sha256. Invalid artifact types raise ValueError. The model uses field(default_factory) for mutable defaults preventing shared-state bugs.

## Governance service integration

Governance routes (approve_placement) call governance_service.transition_state when approving or rejecting placements, maintaining backwards compatibility via adapter pattern with legacy _workflow_states dict. When approved, the endpoint verifies hashes, prevents self-approval, creates ImplementationApproval, registers it, then transitions to IMPLEMENTING. On rejection, transitions to REJECTED.

WorkflowEngine.execute_workflow_stage accepts workflow_id, retrieves workflow from governance service, reads current_state, executes agents, and calls transition_state after completion. Most agent execution is stubbed—only REQUESTED (discovery agents) and CANDIDATE_AUDIT/VERIFYING (gate agents) execute real code. Other states transition immediately with placeholder messages.

## Task routes deprecation

Task routes were marked deprecated: router includes deprecated=True, endpoint docstrings include migration warnings, comments document replacement paths (POST /tasks → POST /workflows, GET /tasks/{id} → GET /workflows/{id}, POST /tasks/{id}/approve → POST /workflows/{id}/transition). Routes remain functional for backwards compatibility. Retirement plan documents Wave 0 marks deprecation, Wave 1 delegates internally, Wave 2+ removes entirely.

## Test coverage

36 new unit tests cover workflow model (StateTransition, workflow creation, terminal/gate state detection, serialization, artifact binding, state history) and governance service (creation, retrieval, transition validation, authorization gates with all six checks, approval registration, artifact binding). Authorization tests verify can_transition_to_implementing blocks on missing approval, wrong status, hash mismatches, and self-approval.

Evidence report shows 269 passing tests, 55 failing (pre-existing from certification gate modules), 6 skipped. All 36 new tests pass in isolation.

## Scope reduction

Scope was intentionally reduced: AgentCoordinator not updated, WorkflowEngine integration partial (stubbed agent logic for most states), frontend integration documented but not implemented. Retirement plan documents phased migration to avoid breaking changes. TaskState workflow-level usage deprecated, agent-level usage preserved. Frontend independent state machine remains (backend-only scope). Legacy _workflow_states dict preserved for backwards compatibility.
