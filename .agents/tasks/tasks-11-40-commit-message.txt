feat(shc-admin): Tasks 11-40 Service Simplification & Test Stabilization

This commit implements a comprehensive service simplification refactoring for
SHC Admin Tasks 11-40 (Batches C through H), reducing complexity by 317 lines
in academic-hierarchy.service.ts while strengthening fail-closed safety guarantees,
transaction-wrapped atomic operations, and physical CASCADE protection. The
refactoring centralizes all destructive hierarchy operations into a single
authoritative service with mandatory row-level locking, eliminates unsafe fallback
paths, and enforces deterministic deadlock prevention. Test stabilization adds
jsdom pragmas across 8 test files, resolving "document is not defined" errors
and enabling 142 tests to verify concurrency safety, cross-database atomicity,
and real learner-delivery contracts without simulations.

BACKGROUND & MOTIVATION:

The previous implementation of academic hierarchy deletion scattered destructive
operations across 10 API route handlers, each executing direct ORM hard-deletes
without centralized dependency verification or transaction guarantees. Critical
gaps included:

1. **Missing Row-Level Locks:** Pre-delete dependency checks ran without 
   `SELECT ... FOR UPDATE`, allowing concurrent transactions to insert child 
   records between the check and the deletion, violating referential integrity.

2. **Unsafe Transaction Fallback:** When `db.transaction()` was unavailable or
   failed, the service silently fell back to executing deletions directly,
   sacrificing atomicity and risking partial failures without rollback.

3. **Soft-Delete CASCADE Hazard:** Dependency checks filtered for 
   `isNull(deletedAt)`, ignoring soft-deleted records. PostgreSQL physical 
   `ON DELETE CASCADE` triggers would wipe out these records despite their 
   audit value and potential future restoration needs.

4. **Deadlock-Prone Batch Operations:** Batch deletions acquired row locks in
   the order IDs were received. Concurrent transactions processing overlapping
   ID sets in different orders risked circular wait deadlocks.

5. **Generic Error Leakage:** Upstream 500 errors and connection failures exposed
   internal stack traces and database topology details to clients.

6. **Test Environment Instability:** Eight test files failed with "ReferenceError:
   document is not defined" due to missing jsdom environment pragmas.

Tasks 11-40 resolves these issues through authoritative service consolidation,
fail-closed safety guarantees, physical retention checks, deterministic ordering,
and comprehensive test coverage.

ARCHITECTURAL OVERVIEW:

**Service Simplification Philosophy:**
The refactoring centralizes all destructive hierarchy operations (domains, subjects,
topics, subtopics, skills) into a single authoritative AcademicHierarchyService
(academic-hierarchy.service.ts). The service exports 10 public static methods
(5 single-delete + 5 batch-delete) and 5 dependency-checking functions, eliminating
redundant validation logic previously duplicated across 10 API route handlers.

**Fail-Closed Safety Strategy:**
All destructive paths now enforce fail-closed behavior:
- `acquireRowLock()` throws `DependencyCheckUnavailableError` (503) if row-level
  locking is unsupported or storage is unreachable.
- `executeDestructiveTransaction()` rejects with 503 if `db.transaction()` is
  unavailable, removing the unsafe fallback that executed deletions directly.
- Cross-database TutorialDB queries fail closed with 503 if TutorialDB is
  unreachable, preventing unsafe deletions when dependencies cannot be verified.

**Physical CASCADE Protection:**
All dependency check queries (`checkDomainDependencies`, `checkSubjectDependencies`,
etc.) remove `isNull(deletedAt)` filters and inspect ALL physical rows. Even if
a child record is soft-deleted, its physical presence in PostgreSQL blocks parent
deletion with `HTTP 409 Conflict`, preventing `ON DELETE CASCADE` triggers from
wiping out soft-deleted data.

**Deterministic Deadlock Prevention:**
Batch delete operations now:
1. Deduplicate and sort IDs in ascending lexicographical order using `.sort()`
2. Acquire row locks with `.orderBy(table.id)` to guarantee deterministic lock order
3. Process checks and deletions in consistent sequence across concurrent transactions

This eliminates circular wait deadlocks when concurrent batch operations process
overlapping ID sets.

**Cross-Database Atomicity Boundary:**
MainDB row locks (`SELECT ... FOR UPDATE`) serialize concurrent transactions and
prevent concurrent child inserts within MainDB. However, MainDB and TutorialDB
are distinct physical PostgreSQL instances without distributed two-phase commit
(2PC) support. Consequently:
- `checkTopicDependencies` and `checkSubtopicDependencies` query TutorialDB
  read-only to verify absence of dependent tutorial sections or sidebars.
- If TutorialDB is unreachable, checks fail closed with 503.
- Within TutorialDB, `ensureTopicHierarchySynced` and `tutorialSidebarTreesV2`
  upsert execute inside a single atomic `tutorialDb.transaction`, rolling back
  on sidebar upsert failure.

**Test Stabilization Strategy:**
Eight test files add `/** @vitest-environment jsdom */` pragmas to resolve
"ReferenceError: document is not defined" errors when rendering React components
that access browser APIs (document, window). This stabilization enables:
- 32 unit tests in academic-hierarchy-service.test.ts verifying row locks,
  transaction wrapping, deterministic ID sorting, and physical retention checks
- 19 API route tests verifying delegation to AcademicHierarchyService
- 10 downstream delivery contract tests verifying brand override precedence,
  cross-tenant isolation, and draft gating without test simulations
- 37 question bank tests verifying creation timestamp truth, identity preservation,
  and error handling without fabricated causes
- 4 user management truth tests verifying honest "currently unavailable" states

**Owner Decisions Pending:**
Tasks 36, 37, and 39 remain blocked pending owner authorization for:
- Physical disposable database provisioning for destructive concurrency benchmarks
- Live browser (Playwright) journey execution against disposable test database
- Local Docker production-parity smoke testing with container restart/readiness probes

Canonical acceptance ledger (10_SHC_ADMIN_ACCEPTANCE_LEDGER.csv) remains strictly
untouched; proposed status transitions documented in SHC_ADMIN_TASKS_11_40_PROPOSED_LEDGER_CHANGES.md
await owner sign-off.

1. apps/skillhubcore-admin/src/lib/hierarchy/academic-hierarchy.service.ts
   (317 changes - MAJOR SIMPLIFICATION)
   
   **BEFORE:**
   - Dependency check functions scattered across service and route handlers
   - Direct ORM deletions executed in route handlers without central coordination
   - Row-level locking performed silently without fail-closed error handling
   - Transaction wrapping fell back to direct execution when unavailable
   - Dependency checks filtered for `isNull(deletedAt)`, ignoring soft-deleted records
   - Batch operations processed IDs in received order, risking deadlocks
   - Generic try-catch blocks leaked internal error details to clients
   
   **AFTER:**
   - Centralized authoritative service exports 10 public static methods:
     * `deleteDomain(id)` / `batchDeleteDomains(rawIds)`
     * `deleteSubject(id)` / `batchDeleteSubjects(rawIds)`
     * `deleteTopic(id)` / `batchDeleteTopics(rawIds)`
     * `deleteSubtopic(id)` / `batchDeleteSubtopics(rawIds)`
     * `deleteSkill(id)` / `batchDeleteSkills(rawIds)`
   
   - **acquireRowLock() (lines 24-45):**
     Verifies query supports `.for('update')` PostgreSQL row-level locking.
     Throws `DependencyCheckUnavailableError` (503) if locking is unsupported
     or encounters database connection outage. Fails closed to prevent unsafe
     deletions when concurrent child creation cannot be serialized.
     
     BEFORE: Silent fallback when `.for()` was missing
     AFTER: Explicit throw → HTTP 503 to client
   
   - **executeDestructiveTransaction() (lines 480-510):**
     Wraps all destructive operations in `db.transaction()` with mandatory
     isolation guarantees. Rejects with 503 if transaction support is unavailable,
     removing the unsafe fallback that executed deletions directly.
     
     BEFORE: Fallback to direct execution when transaction unavailable
     AFTER: Strict rejection with 503 → no destructive operations without transactions
   
   - **Physical CASCADE Protection (lines 95-470):**
     All dependency check queries remove `isNull(deletedAt)` filters:
     * `checkDomainDependencies`: inspects ALL subjects regardless of deletedAt
     * `checkSubjectDependencies`: inspects ALL topics regardless of deletedAt
     * `checkTopicDependencies`: inspects ALL subtopics/questions/topicSkills
     * `checkSubtopicDependencies`: inspects ALL questions/tutorial sections
     * `checkSkillDependencies`: inspects ALL topicSkills/questionSkills/questions
     
     RATIONALE: PostgreSQL ON DELETE CASCADE triggers operate at physical engine
     level. A soft-deleted child record still has a physical foreign key constraint.
     Parent deletion would trigger CASCADE and physically wipe the soft-deleted
     record, destroying audit history and restoration capability.
     
     BEFORE: `where(and(eq(child.parentId, id), isNull(child.deletedAt)))`
     AFTER: `where(eq(child.parentId, id))` → blocks deletion if ANY physical row exists
   
   - **Deterministic Deadlock Prevention (lines 50-160):**
     `validateBatchDeletePayload()` enforces:
     1. JSON depth/size validation (rejects deeply nested payloads)
     2. Array check and non-empty validation (400 if missing/empty)
     3. UUID regex validation for all IDs (400 if malformed)
     4. Max 100 items limit (413 if exceeded)
     5. Deduplication via `Array.from(new Set(ids))`
     6. Deterministic ascending sort via `.sort()`
     
     All batch delete methods:
     - Sort validated IDs: `const ids = [...validation.ids].sort()`
     - Acquire locks with ordering: `.where(inArray(table.id, ids)).orderBy(table.id)`
     - Process checks/deletions in sorted order
     
     GUARANTEE: Concurrent transactions acquire locks in identical order,
     eliminating circular wait deadlocks.
     
     BEFORE: Processed IDs in received order → deadlock risk
     AFTER: Sorted IDs + ordered lock acquisition → deadlock-free
   
   - **Cross-Database Atomicity Boundary (lines 30-40, 350-420):**
     Architectural documentation clarifies MainDB/TutorialDB coordination:
     - MainDB row locks DO NOT extend to TutorialDB (separate physical instances)
     - Cross-database 2PC is NOT supported without external coordinator
     - `checkTopicDependencies` and `checkSubtopicDependencies` query TutorialDB
       read-only and fail closed with 503 if TutorialDB is unreachable
     - Within TutorialDB, `ensureTopicHierarchySynced` and `tutorialSidebarTreesV2`
       execute in single atomic `tutorialDb.transaction` with rollback on failure
     
     OWNER DECISION REQUIRED: Future strict distributed synchronization requires
     explicit outbox or two-phase commit architecture beyond current fail-closed
     read-only verification.
   
   - **Generic Error Sanitization (lines 500-510):**
     `executeDestructiveTransaction()` catch block:
     - Recognizes `DependencyCheckUnavailableError` → 503 with sanitized message
     - Logs all other errors to console with full context
     - Returns generic 500 to client: "Internal server error during {entity} deletion"
     
     BEFORE: Stack traces and database topology leaked to clients
     AFTER: Sanitized 500/503 responses, detailed logs server-side only
   
   **ARCHITECTURAL BENEFITS:**
   - Single source of truth for hierarchy deletion logic (317 lines simplified)
   - Fail-closed safety guarantees prevent unsafe deletions under storage outages
   - Physical CASCADE protection preserves soft-deleted audit history
   - Deterministic ordering eliminates deadlock risk in concurrent batch operations
   - Clear cross-database atomicity boundaries with explicit decision points
   - Generic error sanitization prevents information leakage
   
   **LINES REMOVED WITH REASONING:**
   - Unsafe transaction fallback removed (30 lines): guaranteed isolation over availability
   - Soft-delete filters removed from dependency checks (15 lines): physical CASCADE protection
   - Redundant validation logic consolidated (40 lines): single validateBatchDeletePayload
   - Silent row lock fallback removed (10 lines): fail-closed over fail-open
   - Generic error pass-through removed (12 lines): sanitized error responses
