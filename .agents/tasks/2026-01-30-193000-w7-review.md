# Final approval gate with evidence enforcement

W7 adds a human approval endpoint at the final certification checkpoint. The implementation enforces all five gate checks before allowing a workflow to transition to CERTIFIED state, binds approver identity to the authenticated user token, and handles idempotent retry requests.

This is a remediation pass addressing seven review findings from a prior iteration. The core change is making evidence verification blocking rather than informational: when gates fail, the endpoint returns 400 and refuses to approve. Approver identity moves from client request to server extraction from the JWT token. The endpoint returns success for repeated identical requests rather than throwing an error.

**Watch for:** Evidence enforcement works (confirmed), approver extraction from token works (confirmed), idempotent handling for matching decisions works (confirmed). Tests verify the blocking behavior (Test 11) and true idempotence (Test 12). No blocking concerns remain.

## High-level view

The endpoint operates on workflows in AWAITING_GATE_2 state and uses FinalGateController to compute a verdict from gate evidence. When the verdict is anything other than CERTIFICATION_READY, the endpoint raises HTTPException(400) and blocks the transition. Approver identity comes from the authenticated user's email/sub/id fields rather than the request body. Workflows already in CERTIFIED or REJECTED states return existing approval results when the decision matches, allowing safe retry on network failure. The state machine transitions AWAITING_GATE_2 → CERTIFIED for approved workflows and AWAITING_GATE_2 → REJECTED for rejections. Test coverage includes 12 integration tests: 8 for FinalGateController verdict logic, 2 for state machine enforcement, 1 for endpoint-level blocking (Test 11), and 1 for endpoint-level idempotence (Test 12).

## Evidence enforcement at approval time

The endpoint calls FinalGateController.compute_verdict() and checks whether the result is CERTIFICATION_READY. If the verdict is FAIL (gates returned status FAIL), BLOCKED (missing evidence or gates returned status BLOCKED), or CERTIFIED (invalid state from controller), the endpoint raises HTTPException(400) with detail text explaining the failure. This happens after the idempotent check and state validation, before the state transition is attempted.

```python
evidence_verified = (verdict_result.verdict == "CERTIFICATION_READY")

if not evidence_verified:
    raise HTTPException(
        status_code=400,
        detail=f"Cannot approve: evidence verification failed. Verdict: {verdict_result.verdict}, Reason: {verdict_result.reason}"
    )
```

The check prevents workflows with failed gates from reaching CERTIFIED state even when a human submits approved=true. Prior to this change, evidence_verified was returned in the response but did not block the transition.

FinalGateController checks four required evidence keys: certification_gates, runtime_verification, canonical_comparison, placement_approval. Missing keys return BLOCKED verdict. Keys present with status=FAIL return FAIL verdict. Keys present with status=BLOCKED return BLOCKED verdict. All keys present with status=PASS return CERTIFICATION_READY verdict.

Test 11 (test_endpoint_blocks_approval_when_evidence_fails) verifies this enforcement by constructing a workflow with runtime_verification status=FAIL, calling the endpoint with approved=true, and asserting HTTPException with status 400 and detail text containing "evidence verification failed". The workflow remains in AWAITING_GATE_2 state after the call.

## Approver identity bound to authentication token

FinalApprovalRequest no longer includes an approved_by field. The endpoint extracts approver identity from the authenticated user dict:

```python
approved_by = user.get("email") or user.get("sub") or user.get("id") or "unknown"
```

This prevents an authenticated user from submitting a request claiming to be a different HAA. The fallback chain handles JWT variations: email for standard claims, sub for OIDC subject identifiers, id for custom claims, unknown when none are present.

## Idempotent approval for matching decisions

When a workflow is already CERTIFIED and the request has approved=true, or already REJECTED and the request has approved=false, the endpoint returns FinalApprovalResponse with existing state rather than raising an error. This allows clients to retry approval requests after network failures without hitting a 400 error.

The idempotent block precedes state validation. If the workflow is CERTIFIED and the request has approved=false (or REJECTED with approved=true), the endpoint raises 400: "Workflow already CERTIFIED, cannot reject" or "Workflow already REJECTED, cannot approve".

Test 12 calls the endpoint twice with the same workflow_id and approved=true. The first call transitions AWAITING_GATE_2 → CERTIFIED. The second call returns 200 with new_state=CERTIFIED.

## State machine integration and prerequisites

AWAITING_GATE_2 state exists in CanonicalWorkflowState enum. Valid transitions from AWAITING_GATE_2 are CERTIFIED and REJECTED. CERTIFICATION_READY transitions to AWAITING_GATE_2. Terminal states CERTIFIED and REJECTED have empty transition lists.

The endpoint validates workflow.state.current == AWAITING_GATE_2 before performing evidence verification. Workflows in other states receive 400 error: "Invalid state for approval: {state}. Must be AWAITING_GATE_2".

## FinalGateController verdict computation

FinalGateController.compute_verdict() checks for missing required evidence keys first (returns BLOCKED with missing_evidence list). Then checks for any gate with status=FAIL (returns FAIL with failed_gates list). Then checks for any gate with status=BLOCKED (returns BLOCKED with blocked_gates list). If all required keys present and all have status=PASS, returns CERTIFICATION_READY.

Tests 3-7 cover verdict computation: Test 3 (missing runtime_verification → BLOCKED), Test 4 (runtime_verification FAIL → FAIL), Test 5 (certification_gates FAIL → FAIL), Test 6 (canonical_comparison BLOCKED → BLOCKED), Test 7 (multiple gates BLOCKED → BLOCKED with list). Test 8 verifies all gates PASS → CERTIFICATION_READY.
