# Wave 1C security remediation implementation

Implements brand isolation checks with privileged role enforcement for infrastructure bypass, standardizes user_id extraction to prevent identity spoofing, and adds self-approval prevention logic to governance routes. Addresses four security findings from the Wave 1C plan: infrastructure bypass abuse, NULL brand candidate access, self-approval rejection, and defensive user_id extraction.

**Watch for:** Infrastructure bypass logic is improved but still relies on client-asserted roles (confirmed); NULL brand candidate protection implemented redundantly in two layers (confirmed); self-approval test exists but is marked as skipped integration test rather than executable unit test (confirmed); 11 integration tests remain skipped including critical JWT identity extraction tests (confirmed).

**Verdict:** NEEDS_CHANGES

## High-level view

The `verify_brand_access` function now rejects `brand=None` principals unless they carry `super_admin` or `infrastructure` roles, closing the unconditional infrastructure bypass. The implementation assumes roles arrive verified in the JWT; if the JWT validation layer does not enforce role integrity, an attacker could still forge privileged roles. NULL brand candidates are protected in two places: first in `verify_brand_access` (which permits infrastructure users), then again in the candidate execution route with a second role check. This creates redundant gates that could drift out of sync. The self-approval prevention logic in governance.py extracts approver identity from the JWT using defensive `user.get("user_id")` and compares it to the workflow's `requester_id`, rejecting matches. However, the corresponding test `test_self_approval_prevention_with_jwt_identity` is marked as skipped, so the end-to-end enforcement path is not verified in the test suite. User_id extraction is now standardized across workflow creation and approval routes using the same defensive pattern, but there is no negative test proving a malformed JWT triggers a controlled error rather than a `KeyError`.

## Infrastructure bypass now requires privileged role

The original Wave 1C finding reported that `verify_brand_access()` treated any `brand=None` principal as infrastructure-level without verifying privileged status. The remediation adds a role check:

```python
if user_brand is None:
    roles = principal.get("roles", [])
    if "super_admin" not in roles and "infrastructure" not in roles:
        logger.warning(
            f"Infrastructure bypass denied: user_id={principal.get('user_id')} lacks privileged role"
        )
        raise HTTPException(
            status_code=403,
            detail="Infrastructure access requires super_admin or infrastructure role"
        )
    logger.debug("Infrastructure user bypassing brand check (user brand=None)")
    return
```

The fix assumes that the `roles` claim in the JWT is cryptographically verified and cannot be forged by a client. If the JWT validation layer does not enforce role integrity, an attacker could still craft a token with `{"brand": null, "roles": ["super_admin"]}` and gain infrastructure access. The test `test_infrastructure_bypass_requires_privileged_role` verifies that the function rejects a principal with `brand=None` and no privileged roles, but does not verify that the JWT signature validation prevents role forgery.

## NULL brand candidates protected twice

Candidate execution enforces two separate checks for NULL brand candidates. First, `verify_brand_access(user, package.brand)` is called, which permits infrastructure users with privileged roles. Then, immediately after, the route performs a second role check:

```python
if package.brand is None:
    user_roles = user.get("roles", [])
    if "super_admin" not in user_roles and "infrastructure" not in user_roles:
        logger.warning(
            f"Access to NULL brand candidate denied: user_id={user.get('user_id')}, "
            f"candidate_id={candidate_id}"
        )
        raise HTTPException(
            status_code=403,
            detail="Access to unbranded candidates requires super_admin or infrastructure role"
        )
```

This creates two gates enforcing the same rule. If the first gate (`verify_brand_access`) is sufficient, the second is redundant. If the second gate exists to enforce a stricter policy (e.g., requiring different roles or logging differently), it should be documented. As written, the two checks could drift if one is updated and the other is not.

## Self-approval prevention logic implemented but test is skipped

The governance route `approve_placement` extracts the approver identity from the JWT and compares it to the workflow's requester:

```python
if not (approved_by := user.get("user_id")):
    raise HTTPException(401, "Missing user_id claim")

if workflow_requester and approved_by == workflow_requester:
    raise HTTPException(
        status_code=403,
        detail={
            "error": "SELF_APPROVAL_REJECTED",
            "message": f"Self-approval rejected. User '{approved_by}' cannot approve their own workflow. Separation of duties required.",
            "workflowRequester": workflow_requester,
            "attemptedApprover": approved_by
        }
    )
```

The test `test_self_approval_prevention_with_jwt_identity` in `tests/security/test_authorization.py` is marked as `@pytest.mark.skip(reason="Requires integration test setup with TestClient and database")`, so the self-approval enforcement path is not covered by an executable test that simulates JWT-based identity extraction. The integration test `test_self_approval_rejected` in `tests/integration/test_implementation_approval.py` exists, but the integration-results.txt shows 11 tests skipped, suggesting integration tests may not be running in the remediation verification suite.

## User_id extraction standardized but no negative test for missing claim

Both workflow creation (`workflows.py`) and approval (`governance.py`) now use the same defensive pattern:

```python
if not (requester_id := user.get("user_id")):
    raise HTTPException(401, "Missing user_id claim")
```

No test in the security test suite verifies this behavior. Without a negative test, a regression could reintroduce a crash on malformed tokens.

## Integration test coverage gap

The integration-results.txt shows 21 tests passed, 11 skipped. The skipped tests include:

- 4 JWT identity extraction integration tests (`TestIdentityExtractionFromJWT`)
- 5 route-level brand enforcement tests (`TestBrandEnforcementInRoutes`)
- 2 valid path smoke tests (`TestValidPathSmokeTests`)

The unit tests in `test_authorization.py` verify the `verify_brand_access` function in isolation, but do not prove that the route handlers call it correctly, that JWT parsing and validation work as expected, or that HTTP requests with real tokens are handled properly.
