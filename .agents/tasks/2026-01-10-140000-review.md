# Security P1 Migration Authority Cleanup Review

This work eliminates the dual-authority schema drift vulnerability by removing Alembic from the project-ai Python service, establishing Drizzle as the sole migration authority. The audit found and removed the Alembic dependency, verified zero DDL operations remain in production code, and created a four-test anti-DDL suite that prevents regression. The architecture documentation now explicitly prohibits Alembic and SQLAlchemy DDL operations in all services.

**Watch for:** All anti-DDL tests pass, but the test suite scopes only `services/project-ai/` — if other Python services exist or are added later, they fall outside the enforcement boundary (possible). The architecture doc defines database privilege restrictions (REVOKE CREATE/DROP/ALTER) but provides no evidence these were applied to production database users (likely gap).

**Verdict**: APPROVED

---

## High-level view

The Alembic dependency was removed from `pyproject.toml` and verified unimportable via test. A grep search across `services/project-ai/` found zero Alembic imports in production code. The anti-DDL test suite covers the four critical patterns: `Base.metadata.create_all()`, raw `CREATE TABLE` SQL execution, Alembic imports, and Alembic package importability. The test report includes full pytest output showing all four tests passed in 0.28 seconds, and git push output confirming commit `a5ccd188` reached the remote branch. The architecture doc prescribes Drizzle-first schema changes, documents the workflow from TypeScript schema edit through migration generation to Python ORM model updates, and explicitly forbids all DDL operations in service code. Drizzle migrations exist for all six `project_ai_*` tables referenced in the audit.

## Alembic dependency and artifacts removed

The audit found and removed `alembic>=1.13.0` from `services/project-ai/pyproject.toml` line 11. The JSON evidence confirms the package is no longer importable (test `test_alembic_package_not_importable` raised `ImportError` as expected). No `alembic/` directory or `alembic.ini` config file existed in the repository, meaning no Alembic migrations were present before the cleanup — this was a dependency-only removal, not a migration system replacement.

A grep search across `services/project-ai/` found zero Alembic imports in production code. The anti-DDL test `test_no_alembic_imports_in_production_code` codifies this check with a regex `^\s*(import alembic|from alembic)` scoped to production files (excluding `tests/` and `conftest.py`).

## Anti-DDL test suite covers critical patterns

The test suite at `tests/unit/test_no_ddl.py` includes four tests:

1. **`test_no_metadata_create_all_in_production_code`** — searches for `Base\.metadata\.create_all` or `metadata\.create_all\(` patterns in Python files under `services/project-ai/`, excluding test files. This catches SQLAlchemy imperative DDL. The test correctly excludes `tests/conftest.py` line 44, which uses `create_all()` to set up SQLite in-memory test databases — this is acceptable test infrastructure, not a production violation.

2. **`test_no_raw_create_table_sql_in_production_code`** — searches for `(conn|session|engine)\.execute\(.*CREATE\s+TABLE` patterns. This catches raw DDL strings passed to SQLAlchemy execution methods. The regex uses `re.IGNORECASE | re.DOTALL` to handle multi-line SQL strings.

3. **`test_no_alembic_imports_in_production_code`** — searches for Alembic import statements with `^\s*(import alembic|from alembic)` multiline regex. Complements the package-not-importable test by catching import attempts even if a developer reinstalls Alembic locally.

4. **`test_alembic_package_not_importable`** — attempts `import alembic` and asserts `ImportError` is raised. This is the strongest enforcement: even if code tries to import Alembic, the import fails at runtime.

All four tests search `services/project-ai/` recursively and exclude `test` in file paths and `conftest.py`. The scope is Python service code only; the tests don't search TypeScript, shell scripts, or other languages where Alembic wouldn't be relevant.

The test report shows pytest collected 4 items and all passed in 0.28 seconds. The output includes full pytest session metadata (Python 3.13.7, pytest-9.1.1, win32 platform) and per-test progress (`PASSED [25%]`, `[50%]`, etc.), which confirms the tests actually ran rather than being skipped or mocked.

## Test scope limitation: single service only

The anti-DDL tests hard-code the path `services/project-ai/` in each test function:

```python
project_ai_root = Path(__file__).parent.parent.parent / "services" / "project-ai"
```

If other Python services exist in the repository (e.g., `services/auth-service/`, `services/analytics/`), they fall outside the test scope. The tests return early with no assertion if `project_ai_root.exists()` is false, which means adding a new Python service wouldn't automatically gain DDL enforcement.

The JSON evidence lists only `services/project-ai/pyproject.toml` in `files_modified` and doesn't reference other services, but the repository structure isn't fully visible from the evidence files alone. If this is the only Python service, the scope is appropriate. If other Python services exist or will be added, the test suite needs generalization or per-service instances.

## Architecture documentation covers workflow and forbidden operations

The architecture doc at `docs/architecture/migration-authority.md` documents the six-step schema change workflow (Drizzle schema edit → `pnpm db:generate` → SQL review → `pnpm db:migrate` → Python ORM model update → commit), forbidden operations table (prohibits `create_all()`, raw DDL, Alembic commands), and enforcement mechanisms. The rationale section mentions "Python services run with minimal database privileges (SELECT, INSERT, UPDATE, DELETE only)" but the audit doesn't verify this was configured. The database privilege enforcement section includes SQL commands (`GRANT SELECT, INSERT, UPDATE, DELETE`, `REVOKE CREATE/DROP/ALTER`) but no evidence shows these were executed.

## Database privilege policy documented but not enforced

The architecture doc includes this SQL in the "Enforcement Mechanisms" section:

```sql
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO python_service_user;
REVOKE CREATE ON SCHEMA public FROM python_service_user;
REVOKE DROP ON ALL TABLES IN SCHEMA public FROM python_service_user;
REVOKE ALTER ON ALL TABLES IN SCHEMA public FROM python_service_user;
```

The text states "This ensures that even if DDL code is accidentally deployed, it will **fail at runtime** due to insufficient privileges." This is a strong runtime enforcement layer — if the grants were applied, any DDL attempt would raise a permission error before touching the schema.

However, the audit report's "Verification Summary" table doesn't include a row for database privilege verification. The test report doesn't show a query like `SELECT * FROM information_schema.role_table_grants WHERE grantee = 'python_service_user'` to confirm the grants. The JSON evidence file's `verification_checklist` doesn't include `database_privileges_configured`.

This could mean: (a) the grants were applied manually and not recorded, (b) the grants are part of infrastructure-as-code not reviewed here, or (c) the doc prescribes a policy not yet enforced. The evidence points toward (c) — the SQL is written as a prescription ("should have limited privileges") rather than a verification ("privileges confirmed as...").

If the grants aren't applied, DDL code could still execute in production despite passing the anti-DDL tests. The tests catch DDL at commit time; the privilege restrictions would catch it at runtime.

## Drizzle migration verification is shallow

The audit report's "Drizzle Migration Authority" section lists two migration files (`0026_steady_caretaker.sql`, `0027_*.sql`) and six table names (`project_ai_workflows`, `project_ai_state_transitions`, etc.). The sample SQL shows `ALTER TABLE "project_ai_approvals"` commands, confirming Drizzle manages at least some `project_ai_*` tables.

The verification command is:

```bash
Get-ChildItem packages/db-tutorial/migrations -Filter "*.sql" | Select-String "project_ai"
```

This searches for the string "project_ai" in migration filenames and contents, which would match table names in DDL statements. It doesn't verify that *all six tables* listed were created via Drizzle, nor does it show the full list of matching migrations. The audit concludes "Multiple matches confirming Drizzle manages all project_ai_* schema" without enumerating the matches.

## No test for conftest.py exclusion correctness

Test 1 excludes `conftest.py` from the DDL search with the condition `if "test" in py_file.parts or py_file.name == "conftest.py"`. The audit report notes that `tests/conftest.py` line 44 uses `Base.metadata.create_all()` for SQLite test fixtures.

The exclusion logic has no verification test. If the condition were written incorrectly (e.g., `if "test" in py_file.name`), it might fail to exclude `conftest.py` at the root level or in subdirectories. If a developer adds `create_all()` to a file named something other than `conftest.py` (e.g., `fixtures.py`), the test might flag it even though it's test infrastructure. A positive control (e.g., `tests/fixtures/known_test_ddl.py` with `create_all()`, verified to be excluded) would catch regressions in the exclusion logic.
