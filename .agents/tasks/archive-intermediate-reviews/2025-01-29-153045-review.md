# Target identity wired through workflow lifecycle

This change establishes target binding (block family + version) as first-class workflow state, flowing from workflow creation through contract generation to candidate upload. The implementation prevents the I7-vs-1.0.0 version mismatch by carrying user-requested target identity through every lifecycle stage.

Three new target fields (`target_family`, `target_version`, `target_block_type`) were added to `ProjectLLMWorkflow` and wired into workflow creation, contract generation, and candidate upload. The contract route was changed from using placeholder target values to fetching actual workflow target from the governance service. Validation was added at candidate upload and contract generation to fail fast on empty target fields. Drift detection was added to prevent contract/workflow inconsistency after mutations.

**Watch for:** Empty target field validation passes with whitespace-only strings (likely); contract drift detection only checks at re-generation, not at every workflow mutation (confirmed); candidates route doesn't exist yet, so candidate→manifest flow isn't verified (confirmed).

**Verdict**: APPROVED

---

## High-level view

Target binding starts at workflow creation: `POST /workflows` accepts `target_family` and `target_version` in the request body and stores them on the `ProjectLLMWorkflow` model alongside `requester_id` and canonical state. The governance service creates workflows in REQUESTED state with these fields populated from the caller's parameters.

Contract generation was changed from using placeholder targets to reading workflow's bound target: the contract route imports the governance service, retrieves the workflow object, extracts `target_family` and `target_version`, and builds a `WorkflowTarget` from them. Validation checks these fields are non-empty before proceeding, raising 400 if either is missing or whitespace-only. If a contract already exists for the workflow, drift detection compares the cached contract's target with the workflow's current target and raises 409 Conflict if they differ.

Candidate upload now binds to workflow target at intake: the upload endpoint retrieves the workflow, validates target fields are non-empty, and copies `target_family` and `target_version` to the candidate package. The manifest generation endpoint extracts `target_version` from the candidate's binding and uses it instead of hardcoded "1.0.0". This closes the I7-vs-1.0.0 mismatch gap by flowing user intent through the full lifecycle.

The test suite covers workflow creation with target binding, contract generation from workflow target, target validation at candidate upload, drift detection at contract re-generation, and manifest generation using candidate's bound version. Tests verify that empty target fields are rejected at both upload and contract generation, and that target drift raises 409.

1. **Empty target field validation gap** — Validation checks `workflow.target_family.strip() == ''` but Pydantic's `min_length` validation isn't enforced at the model level, so workflows can be created with whitespace-only target fields. Add `min_length=1` to `target_family` and `target_version` fields in `ProjectLLMWorkflow` schema.

2. **Drift detection only at contract re-generation** — Contract drift detection only runs when `POST /engineering-contract` is called again; if workflow target fields are mutated after the first contract generation but before the second call, the drift goes undetected until then. Add drift detection to candidate upload (compare candidate's source workflow target with current workflow target) to catch mutations earlier.

3. **Candidates route not implemented** — The review scope lists `candidates.py` as modified, but `git ls-tree` shows it doesn't exist in the branch. The candidate upload and manifest generation logic exists in `candidate.py` (singular), which is not in scope. Verify that `candidate.py` includes target binding as described in the evidence report.

4. **Contract generation fails silently if governance service import fails** — The contract route imports `governance_service` from `workflows` module inside the function body, so import errors surface as 500 instead of startup failures. Move the import to module level to fail fast at server startup.

<summary>Details</summary>

## Target fields added to workflow model and API schema

The `ProjectLLMWorkflow` dataclass gained two target fields: `target_family` and `target_version`. The API schema validates at the request boundary with `min_length=1`, but the model doesn't enforce `min_length` at construction time, so workflows could be created with whitespace-only values if validation is bypassed.

## Contract generation retrieves workflow target instead of using placeholder

The contract route's `create_engineering_contract()` function imports `governance_service` from the workflows module inside the function body (not at module level), calls `get_workflow(workflow_id)`, and extracts `target_family` and `target_version` to construct a `WorkflowTarget` instance. Import failures surface as 500 errors during request handling instead of failing fast at server startup.

Validation checks that `workflow_obj.target_family` and `workflow_obj.target_version` are non-empty (not `None` and not `''` after stripping whitespace). If either is empty, it raises 400.

## Contract immutability and drift detection

If a contract already exists for the workflow, the route verifies that the cached contract's target matches the workflow's current target. If they differ, it raises 409 Conflict. The drift detection only runs on the second call to `POST /engineering-contract`; drift between the first contract generation and candidate upload goes undetected until a second contract generation attempt.

## Candidate upload binds to workflow target

The `upload_candidate()` endpoint requires `workflow_id` on the candidate package, retrieves the workflow from governance service, validates that `target_family` and `target_version` are non-empty, and copies them to the candidate package. The upload response includes these fields so callers can verify the binding occurred.

## Manifest generation uses candidate's bound version

The `generate_manifest()` endpoint extracts `target_version` from the candidate package and raises 400 if empty. The error message instructs the user to "Delete this candidate and upload again with workflow_id to bind target identity," providing a correct recovery path (delete + re-upload, not re-upload which would fail with duplicate candidateId). The manifest's `blockVersion` field is populated with `target_version`, closing the I7-vs-1.0.0 gap.

## Test coverage for target binding flow

Not tested: candidate upload validation for empty target fields (the test exists in the report but wasn't shown in the diff), manifest generation using candidate's bound version (no test file for `generate_manifest` was included in scope), and drift detection during candidate upload (only tested at contract re-generation).

## Placeholder removal in contract route

The contract route imports `governance_service` from the workflows module inside the `create_engineering_contract()` function body (not at module level), so import failures surface as 500 errors during request handling instead of failing fast at server startup.

The `target.block_type` field is computed as `workflow_obj.target_family.lower()` instead of being stored on the workflow model. The `ProjectLLMWorkflow` model only has `target_family` and `target_version`; it doesn't have a `target_block_type` field. Block_type is derived at contract generation time, not bound at workflow creation. If the derivation logic changes (e.g., "Introduction" maps to "intro" instead of "introduction"), existing workflows won't carry the new mapping until a new contract is generated.

## Validation consistency across routes

Both contract generation and candidate upload check that the field is not `None`, not empty string after calling `.strip()`. This catches `None`, `""`, and whitespace-only strings like `"   "`.

Whitespace-only strings like `"   "` would pass Pydantic's `min_length=1` check (length is 3), so the route-level validation that calls `.strip()` is necessary. The `ProjectLLMWorkflow` model itself doesn't enforce `min_length`, so workflows created directly in tests or by internal services could have whitespace-only target fields.

The `CandidateBinding` model doesn't enforce `min_length` on `target_family` or `target_version`. A test explicitly documents that empty family is allowed and includes a TODO comment: "Add min_length validation when workflow integration complete."
