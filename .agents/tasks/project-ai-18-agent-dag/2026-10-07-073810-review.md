# Project AI 15-Agent DAG Implementation

The implementation consolidates the Project AI certification workflow into a clean 15-agent architecture with proper model separation, comprehensive gate coverage, and evidence-driven verification.

After the consolidation pass (commit 3e242e66), the agent count mismatch between DAG (24 agents), registry (28 agents), and design docs (15 agents) was resolved. The current implementation shows 15 agents in both DAG and registry, with certification gates properly implemented as methods within the certification controller rather than standalone agents.

**Watch for:** 90 failing tests remain after consolidation, primarily certification gate tests expecting gates as standalone agents rather than methods, and integration tests needing updates for the new 15-agent architecture. The agent registry and workflow engine tests pass (23/23), confirming the consolidation is structurally sound, but gate test refactoring is incomplete. **(confirmed)**

**Verdict**: CHANGES_REQUESTED

## High-level view

The 15-agent DAG is structurally complete with proper dependency chains from repository audit through final certification. All agents are registered in the agent registry with correct types and capabilities. AgentResult, GateStatus, and related models were successfully extracted from agent_coordinator.py into dedicated model files, eliminating scattered type definitions.

The certification gates implementation includes 11 methods in gates.py (Contract, Dependency, UBRC, Registry, Renderer, Brand, Theme, Composer, Evidence, Runtime, Browser), exceeding the required 9+ gates. Each gate accepts a manifest parameter and returns evidence_ids, meeting the architectural requirement for evidence binding.

Snapshot immutability is enforced: Agent 02 (Snapshot Authority) generates the snapshot once via TypeScript discovery, and Agent 11 (Post-Placement Verification) uses git diff instead of regenerating. Brand and Theme gates consume snapshot data rather than scanning files directly, as specified.

The Playwright agent orchestrates Node via subprocess (pnpm exec playwright test), not Python Playwright, and the approval/certification agents implement database polling workflows with configurable timeouts.

The test suite shows 363 passing tests (agent registry: 11/11, workflow engine: 12/12) but 90 failures concentrated in certification gate tests and integration tests. The failures stem from tests expecting the old 24-agent architecture where gates were separate agents, not from implementation errors in the consolidated architecture.

## Agent architecture alignment

The 15-agent architecture is fully implemented with correct naming between DAG and registry. The workflow_dag.py defines 15 agents using snake_case identifiers that map 1:1 to AgentType enum values in agent_registry.py.

Certification gates run within Agent 12 (certification_controller) as methods, not as separate DAG nodes. The 11 gate methods execute within that agent's turn, eliminating the earlier mismatch where gates appeared as 10 separate DAG nodes. Runtime and browser verification are separate DAG nodes after certification_controller (Agents 13 and 14).

The validate_dag() function enforces exactly 15 agents, checks for cycles via DFS, and verifies all dependencies reference existing agents.

## Model extraction and evidence binding

AgentResult, AgentStatus, and GateStatus were extracted from agent_coordinator.py into app/models/agent_result.py. The coordinator now imports these with no local class definitions remaining.

The evidence_ids field in every gate result binds verification to specific evidence records from the TypeScript-generated snapshot. Each gate searches snapshot['evidence'] for relevant records by kind, path, or symbol, extracts their evidenceId values, and returns them in the GateExecutionResult. If no matching evidence exists, the gate returns BLOCKED with empty evidence_ids rather than PASS with synthetic IDs.

The models/__init__.py exports all new models. Import tests confirm these are accessible from app.models.

## Certification gates implementation

The certification/gates.py file contains 11 gate methods in the CertificationGateExecutor class: Contract, Dependency, UBRC, Registry, Renderer, Brand, Theme, Composer, Evidence Binding, Runtime, and Browser. This exceeds the required 9+ gates. ILS, LSNB, and RSSB gates are intentionally deferred to Phase 2.

All gate methods accept candidate_blocks (or candidate_files for brand gate) and manifest parameters, and return GateExecutionResult with status (PASS/FAIL/BLOCKED), message, evidence_ids, and blockers. The manifest parameter enables validation at each gate via _validate_manifest() helper.

Each gate reads from the TypeScript-generated snapshot stored in self.snapshot rather than scanning repository files directly. Brand and theme gates specifically access snapshot.get('brand') and snapshot.get('theme') data, not Path.read_text() operations, meeting the "NO file scanning" requirement.

Gates enforce evidence binding: a gate that cannot find relevant evidence in the snapshot returns BLOCKED with empty evidence_ids rather than PASS. The execute_evidence_binding_gate specifically validates that all prior evidence binds to the current commit_sha and snapshot_hash, checking for orphaned evidence or mismatched hashes.

## Snapshot immutability and placement verification

Agent 02 (snapshot_authority.py) calls TypeScript discovery once via subprocess.run(['pnpm', 'tsx', '.agents/scripts/regenerate-m1-snapshot.mjs']) with a 5-minute timeout. It extracts snapshot['canonicalHash'] (computed by TypeScript, never recomputed in Python) and copies the snapshot to .project-ai/runs/{run-id}/snapshot.json.

Agent 03 (evidence_freeze.py) validates the snapshot structure without re-reading source files. It checks required fields, validates contentHash format (64-character SHA-256 hex), checks for duplicates and orphans, and creates an evidence index. The code does not call any file reading or hashing functions, only validates existing hash formats.

Agent 11 (post_placement_verification.py) uses git diff HEAD to verify placement changes instead of regenerating the snapshot, preserving the frozen snapshot from Agent 02 as the evidence baseline for the entire workflow.

Agents 03-15 never call pnpm tsx to regenerate repository facts. They read from the frozen snapshot created by Agent 02.

## Playwright orchestration via Node

Agent 14 (playwright_browser_agent.py) orchestrates Node Playwright via subprocess with command ['pnpm', 'exec', 'playwright', 'test', '--config=playwright.project-ai.config.ts'], sets environment variables (PROJECT_AI_BASE_URL, PROJECT_AI_RUN_ID, PROJECT_AI_COMMIT_SHA, PROJECT_AI_SNAPSHOT_HASH), and uses a 600-second timeout.

No import playwright appears in the file, only subprocess.run for process execution. After execution, the agent parses .project-ai/runs/current/results/playwright.json for test results. The Python agent acts as orchestrator only: it starts the Node process, waits for completion, parses JSON results, and returns an AgentResult.

The playwright.json path is hardcoded to use "current" instead of the actual run_id from context, which could cause race conditions in concurrent runs.

## Approval and certification polling

Agent 09 (approval.py) implements database polling for human approval. It creates a record in approval_requests with status='PENDING', then polls every 30 seconds checking for status changes. The timeout comes from PROJECT_AI_APPROVAL_TIMEOUT_SEC (default 24 hours, min 60s, max 7 days). When approved, the agent validates manifest_hash matches to detect tampering.

Agent 15 (human_certification.py) mirrors this for final certification, polling certification_reviews with timeout from PROJECT_AI_CERTIFICATION_TIMEOUT_SEC.

Both agents return BLOCKED until a human decision is recorded. The approval schema exists in migrations/001_approval_requests.sql; the certification schema is documented but may not exist as a migration file yet.
