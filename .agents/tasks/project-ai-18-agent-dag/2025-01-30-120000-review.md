# Project AI 15-Agent DAG Implementation Review

**Verdict**: CHANGES_REQUESTED

This implementation establishes the 15-agent DAG architecture with parallel certification gates, database polling for approvals, and snapshot immutability. The foundational structure is solid, but test failures in certification gates and manifest validation reveal gaps in evidence binding and semantic validation that must be addressed before production readiness.

**Watch for:** 
- **Evidence binding validation failures** (confirmed) — 83 test failures related to manifest validation with empty evidenceIds lists and semantic binding validation rejecting test snapshots
- **Brand and theme gate test failures** (confirmed) — All brand/theme gate tests failing, likely due to manifest parameter requirements not met in test fixtures
- **Certification gate implementation gaps** (confirmed) — UBRC, registry, renderer, composer, runtime, browser gate tests failing with manifest validation errors

## High-level view

All 15 agents are registered and importable with correct signatures. The DAG validation passes with no cycles, and agent dependencies follow the sequential foundation → candidate pipeline → parallel gates → runtime chain → final sequence pattern. AgentResult was successfully extracted from agent_coordinator.py into models/agent_result.py.

The certification gates exist as 11 methods in certification/gates.py (CONTRACT, DEPENDENCY, UBRC, REGISTRY, RENDERER, BRAND, THEME, COMPOSER, EVIDENCE, RUNTIME, BROWSER) with evidence_ids parameters, meeting the "9+ gates" requirement. However, the DAG structure shows certification gates consolidated into a single "certification_controller" node rather than executing as a parallel_group, which differs from the design specification's requirement for parallel execution.

Post-placement verification correctly uses git diff instead of regenerating the snapshot, preserving snapshot immutability. The Playwright browser agent orchestrates Node via `pnpm exec playwright test` with subprocess calls, correctly avoiding Python Playwright.

Approval and certification use database polling with configurable timeouts via environment variables (PROJECT_AI_APPROVAL_TIMEOUT_SEC). The approval agent creates request records, polls every 30 seconds, and validates manifest hash matches.

The 83 test failures stem from manifest validation requirements added to gates after tests were written. Tests call gate methods without providing valid PlacementManifest objects, triggering "Manifest validation failed" blocks. The semantic evidence binding validation expects populated evidenceIds and snapshot evidence, which test fixtures don't provide.

## 15-agent registration and DAG structure

Agent registry contains all 15 required agents matching AgentType enum values: repository_auditor, snapshot_authority, evidence_freeze, block_specification, candidate_intake, candidate_classification, canonical_comparison, placement_manifest, human_approval, placement_executor, post_placement_snapshot, certification_controller, runtime_verification, browser_verification, final_gate_controller.

AGENT_WORKFLOW_DAG in workflow_dag.py defines 15 nodes with validate_dag() passing structural checks (no cycles, no missing dependencies, no self-references). Dependencies flow correctly from foundation sequence (agents 1-4) through candidate pipeline (5-11) to certification and final sequence (12-15).

However, certification gates appear as a single "certification_controller" node rather than separate parallel nodes. Design specification states: "Certification gates (12A-12J) go in parallel_group 'certification-gates' all depending on agent-11-post-placement-verification". The current DAG has no parallel_group attributes and consolidates gate execution within the controller agent. This matches the FEAT-001 finding ("certification gates (12A-12J) are consolidated into agent-12-certification-gates") but conflicts with the design requirement for parallel execution visibility.

```python
# Current DAG structure
"certification_controller": {
    "name": "Certification Controller",
    "depends_on": ["post_placement_snapshot"],
    "parallel_group": None
}
```

The design intent was 11 gate nodes executing in parallel after agent 11, but implementation groups them into a single orchestrator. This architectural decision should be explicitly documented if intentional, or the DAG should be expanded to 11 gate nodes if parallel tracking is required.

## Certification gate methods with evidence_ids

CertificationGateExecutor in certification/gates.py contains 11 gate methods meeting the "9+ gate methods" requirement:

1. execute_contract_gate — Verifies TutorialBlock interface compliance from snapshot type evidence

6. execute_brand_independence_gate — Brand independence checks

8. execute_composer_verification_gate — Composer integration verification
9. execute_evidence_binding_gate — Evidence binding validation
10. execute_runtime_verification_gate — Runtime verification
11. execute_browser_verification_gate — Browser verification

All gate methods accept `manifest: PlacementManifest` parameter and call `_validate_manifest(manifest)` before execution, enforcing manifest validation across all gates. Each method signature follows the pattern:

```python
def execute_<gate>_gate(
    self,
    candidate_blocks: List[str],
    manifest: PlacementManifest
) -> GateExecutionResult
```

GateExecutionResult includes evidence_ids field populated from snapshot evidence records, meeting the evidence binding requirement.

The _validate_manifest method performs two checks:
1. _validate_manifest_structure — Checks required fields present (manifest_id, candidate_id, evidence_ids, snapshot_hash)
2. _validate_evidence_semantic_binding — Validates evidence_ids in manifest exist in snapshot and bind to commit_sha + snapshot_hash

This validation is production-correct but breaks test suite because test fixtures provide empty evidence_ids lists.

## Snapshot immutability post-placement

Post-placement verification agent (post_placement_verification.py) correctly implements snapshot immutability rule:

```python
"""Post-placement verification agent using git diff."""

async def execute_post_placement_verification(context: AgentContext) -> AgentResult:
    """
    Verifies placement changes using git diff:
    - Uses git diff HEAD to verify placement changes
    - NO new snapshot generation (snapshot immutability rule)
    - Validates changed files match PlacementManifest entries
    """
```

The agent calls `_get_git_diff_files(repository_root)` which runs `git diff --name-only HEAD` to capture changes without regenerating the snapshot. This satisfies the design requirement: "Do NOT regenerate snapshot after placement. Snapshot ONLY generated once at Agent 02."

Agent 11 is named "post_placement_snapshot" in the DAG but the implementation file is post_placement_verification.py. The verification behavior is correct (uses git diff, no snapshot regeneration), but the agent name in workflow_dag.py is misleading. The design doc renamed this agent to "Post-Placement Verification" but the DAG still uses the old "post_placement_snapshot" identifier.

Test-results.txt documents the root cause and resolution options:

> **Root Cause**: Tests using mock manifests with:
> - Empty evidenceIds list
> - Simple mock snapshot with no or minimal evidence
> - Semantic evidence binding validation failing
> 
> **Resolution Required**: 
> - Option A: Add proper evidence IDs to test snapshots and manifests
> - Option B: Modify _validate_evidence_semantic_binding to handle empty evidence gracefully in tests
> - Option C: Add test mode flag to skip semantic binding validation

Option C (test mode flag) is cleanest: production code enforces strict validation, test code can bypass for unit testing. Option A (fix all test fixtures) is production-correct but requires updating 83+ test cases. Option B (loosen validation) weakens production guarantees.

## Evidence binding throughout implementation

All gate methods populate evidence_ids from snapshot evidence records and return them in GateExecutionResult. AgentResult dataclass declares "No evidence_ids = BLOCKED" rule, but enforcement is inconsistent: gate validation enforces it via _validate_evidence_semantic_binding, but some agent implementations may return SUCCESS with empty evidence_ids. Final Gate Controller validates evidence binding across complete workflow from snapshot freeze through final certification.
