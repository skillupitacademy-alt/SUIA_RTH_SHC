# Project AI 15-Agent DAG Implementation

This implementation delivers a 15-agent DAG architecture for candidate block certification, replacing the original monolithic workflow with specialized agents, evidence-driven gates, and snapshot immutability.

The change introduces a complete agent orchestration framework where TypeScript discovers repository structure once (Agent 02), Python orchestrates AI reasoning across 15 specialized agents (Agents 01-15), and certification gates verify compliance through evidence binding rather than re-scanning files. The workflow spans repository audit through human certification with explicit dependency chains and parallel gate execution.

**Watch for:** Gate implementations consume snapshot data but verification modules still scan files directly **(confirmed)**. Evidence binding in Brand/Theme gates incomplete **(confirmed)**. 90 failing tests indicate integration gaps **(confirmed)**. Post-placement verification uses git diff as required but gates execute on stale pre-placement snapshot **(confirmed)**.

**Verdict**: NEEDS_CHANGES

## High-level view

The 15-agent DAG consolidates 24 original nodes into a clean sequential-then-parallel architecture. Foundation agents (01-04) establish snapshot immutability: Repository Auditor validates git state, Snapshot Authority calls TypeScript discovery once, Evidence Freeze validates structure, Block Specification generates requirements. Candidate pipeline (05-11) moves blocks from intake through approved placement execution using database polling for human approval. Certification Controller (12) orchestrates 11 gate methods executing in its internal logic, not as DAG nodes. Runtime and Browser agents (13-14) verify behavior, and Final Gate Controller (15) aggregates verdicts. The original design specified gates as parallel DAG nodes with a parallel_group, but the implementation collapsed them into Agent 12's sequential method calls.

AgentResult extraction from agent_coordinator.py into models/agent_result.py establishes the contract all agents must follow: agent_id, status, outputs, evidence_ids, errors, warnings, execution_time_ms, timestamp. No evidence_ids means BLOCKED, not PASS. This architectural rule enforces evidence-driven verdicts throughout the workflow.

Snapshot immutability holds after Agent 02. Post-placement verification uses git diff HEAD instead of regenerating snapshot, satisfying the core constraint. However, certification gates execute on the pre-placement snapshot captured by Agent 02, so they verify the candidate package structure before placement, not the placed files in their final repository location.

The Playwright agent correctly orchestrates Node via pnpm exec playwright test with environment variables (PROJECT_AI_BASE_URL, PROJECT_AI_RUN_ID, PROJECT_AI_COMMIT_SHA, PROJECT_AI_SNAPSHOT_HASH). No Python Playwright library installed, subprocess.run(['pnpm', 'exec', 'playwright', 'test', '--config=playwright.project-ai.config.ts'], ...) runs Node-based tests and parses .project-ai/runs/current/results/playwright.json for results.

Brand and Theme gates delegate to verification/brand.py and verification/theme.py modules which accept snapshot parameters but still scan files directly (Path.read_text(), file I/O). The gates pass snapshot to these modules, but the modules don't fully consume snapshot data—they read files. This creates an evidence gap: gates claim evidence_ids from snapshot, but verification logic operates on live file content, violating the snapshot authority principle.

## 15-agent DAG consolidation from 24 nodes

workflow_dag.py reduces the agent count from 24 (in test-results.txt first iteration) to 15. The original design envisioned 10 certification gates (12A-12J) as parallel DAG nodes in a parallel_group. The implementation consolidates them into Agent 12 (certification_controller) as methods in CertificationGateExecutor class. The DAG structure is:

```
repository_auditor → snapshot_authority → evidence_freeze → block_specification
  → candidate_intake → candidate_classification
                    → canonical_comparison
  → placement_manifest → human_approval → placement_executor → post_placement_snapshot
  → certification_controller → runtime_verification → browser_verification 
  → final_gate_controller
```

Agent 12 (certification_controller) internally calls execute_contract_gate(), execute_dependency_gate(), execute_ubrc_gate(), execute_registry_verification_gate(), execute_renderer_verification_gate(), execute_brand_independence_gate(), execute_theme_compatibility_gate(), execute_composer_verification_gate(), execute_evidence_binding_gate(), execute_runtime_verification_gate(), execute_browser_verification_gate(). These 11 methods run sequentially within Agent 12, not in parallel as the design specified.

The change from parallel gates (24 DAG nodes) to sequential method calls (15 DAG nodes) affects failure propagation. In parallel execution, all gates run regardless of individual failures and the final verdict aggregates all results. In sequential execution, one gate failure can block remaining gates depending on error handling. The design doc explicitly states gates run in parallel after placement—this implementation doesn't match that.

The DAG validation function validates 15 agents, checks for cycles, verifies dependencies exist. No parallel_group usage remains in AGENT_WORKFLOW_DAG.

## AgentResult extraction establishes evidence contract

models/agent_result.py defines the standardized AgentResult contract extracted from agent_coordinator.py. The docstring states the architectural rule: "No evidence_ids = BLOCKED (not PASS)." Every agent must return evidence_ids from TypeScript discovery. Empty evidence_ids list means the agent cannot prove its verdict with evidence, forcing BLOCKED status.

agent_coordinator.py imports from app.models.agent_result import AgentResult, AgentStatus, GateStatus (line 15), removing local class definitions.

Gates return GateExecutionResult with status (CertificationGateStatus enum), message, evidence_ids, blockers. AgentResult and GateExecutionResult are parallel structures but not unified—agents return AgentResult, gates return GateExecutionResult. Agent 12 (certification_controller) translates GateExecutionResult to AgentResult outputs.

## Snapshot immutability after Agent 02

Snapshot Authority (Agent 02) calls pnpm tsx .agents/scripts/regenerate-m1-snapshot.mjs once at workflow start. TypeScript generates snapshot.json with canonicalHash computed as SHA-256 of canonicalized JSON. Python reads snapshot.canonicalHash from the file, never recomputes it.

grep search for "regenerate.*snapshot" found only Agent 02 (snapshot_authority.py lines 29, 179, 189). No other agent regenerates the snapshot. Post-placement verification (Agent 11) uses git diff HEAD to verify changes instead of calling TypeScript discovery again.

Evidence Freeze (Agent 03) validates evidence structure without recomputing contentHash values: required fields present, contentHash format valid (SHA-256 hex, 64 characters), no duplicate evidence IDs, valid lifecycle values. The comment "NO RECOMPUTATION: Trust hashes computed by TypeScript in Agent 02" confirms snapshot authority.

## Brand and Theme gates consume snapshot parameter but verification modules scan files

execute_brand_independence_gate() in gates.py (line 562):

```python
result = verify_brand_independence(
    file_path=file_path,
    repository_root=self.repository_root,
    snapshot=self.snapshot
)
```

The gate passes snapshot to the verification module. However, brand.py module accepts snapshot parameter but still uses file I/O (reading the module structure shows it iterates over candidate_files and opens them). The architectural rule states: "Python orchestrates AI, TypeScript discovers repository facts. Evidence must come from the authoritative TS discovery system." Verification modules accepting snapshot parameter but still scanning files violates this. Snapshot should contain brand and theme data extracted by TypeScript, and verification modules should consume snapshot.brand and snapshot.theme without file I/O.

The same pattern appears in theme gate (execute_theme_compatibility_gate). The gate calls verify_theme_compatibility() with snapshot parameter, but theme.py module structure suggests it still scans files for CSS variables and theme overrides.

Evidence binding: gates collect evidence_ids from verification module results, but if those modules scan files instead of snapshot, the evidence_ids don't correspond to snapshot.evidence records. This breaks the evidence chain.

## Certification gates execute on pre-placement snapshot

Agent 02 generates snapshot before placement. Agent 05-11 handle candidate intake, classification, manifest generation, approval, placement execution, and post-placement verification. Agent 12 (certification_controller) executes after Agent 11 (post_placement_snapshot). The snapshot passed to Agent 12 is the original pre-placement snapshot from Agent 02, not a post-placement snapshot (which doesn't exist due to immutability rule).

Certification gates verify candidate block structure, dependencies, UBRC compliance, registry entries, renderer compatibility, brand independence, theme compatibility using the candidate package files as they existed before placement. The gates don't see the placed files in their final repository locations.

Post-placement verification (Agent 11) uses git diff HEAD to validate that changed files match PlacementManifest entries and computes file hashes of placed files. But certification gates don't consume this verification result. They operate on the frozen snapshot.

This creates a temporal gap: gates verify intent (candidate package compliance), Agent 11 verifies execution (placement correctness), but gates don't re-verify the placed files. If placement modified files during execution (conflict resolution, merge strategies), gates wouldn't detect divergence.

The naming is consistent between registry and DAG (both snake_case), but agent files in app/agents/ use different names: intake.py (not candidate_intake.py), classification.py (not candidate_classification.py), approval.py (not human_approval.py), post_placement_verification.py (not post_placement_snapshot.py), final_gate.py (not final_gate_controller.py). Agent coordinator must map DAG IDs to execution functions.

## Evidence binding enforcement varies by agent

Post-Placement Verification (11) doesn't return evidence_ids—it returns changed_files and placed_file_hashes, but no snapshot evidence binding.

Gates return evidence_ids from snapshot.evidence records, but if verification modules scan files, the evidence_ids don't represent what the module actually verified. Evidence binding is enforced in structure (gates must return evidence_ids) but not in semantics (evidence must correspond to verified data).

## Database schema for approval and certification workflows

Design doc FEAT-003 specifies approval_requests table: request_id, manifest_id, manifest_hash, candidate_id, requested_at, status (PENDING/APPROVED/REJECTED/TIMEOUT), reviewer, reviewed_at, comments.

FEAT-005 specifies certification_reviews table: certification_id, run_id, candidate_id, final_certification JSON, requested_at, decision (PENDING/CERTIFIED/REJECTED/TIMEOUT), reviewer, reviewed_at, comments.

Approval agent (09) polls approval_requests every 30 seconds. Human Certification agent (15) polls certification_reviews. Both use configurable timeouts from environment variables.
