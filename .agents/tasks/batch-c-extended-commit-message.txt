ARCHITECTURAL OVERVIEW

Downstream Delivery Contracts and Their Purpose:
The new downstream-delivery-contracts.test.ts file establishes verification patterns for the 
contracts that real learners depend on when accessing tutorial content. These contracts ensure 
that the tutorialDeliveryService.getTutorialByPage resolver always returns content that matches 
the brand context, respects lifecycle states (only deployed content is accessible), and 
correctly maps MainDB hierarchy UUIDs to TutorialDB external_id foreign keys.

The cross-database identity verification ensures that when a learner requests content for a 
specific subtopic and navigation node, the system can reliably traverse from MainDB's 
authoritative taxonomy records (domains, subjects, topics, subtopics) to TutorialDB's 
delivery-optimized records (tutorial_domains, tutorial_subjects, tutorial_topics, 
tutorial_subtopics, tutorial_sections) via the external_id linkage.

Sidebar Synchronization Safety Mechanisms:
The tutorial-left-sidebar route now implements ensureTopicHierarchySynced, a comprehensive 
function that guarantees complete hierarchy synchronization before sidebar publication. This 
function executes in phases (SYNC-01 through SYNC-13), each with dedicated logging:

1. SYNC-01 to SYNC-04: Fetch MainDB records (topic → subject → domain, plus active subtopics)
2. SYNC-05 to SYNC-08: Upsert hierarchy chain into TutorialDB within atomic transaction
3. SYNC-09: Transaction commit confirmation
4. SYNC-10 to SYNC-13: Post-commit verification of all external_id mappings

This design ensures that if any step fails (missing parent, broken foreign key, database 
unavailability), the entire operation rolls back, preventing partial or inconsistent 
hierarchy states in TutorialDB.

MainDB→TutorialDB Propagation Patterns:
The synchronization follows a strict parent-first propagation pattern:
- Domain (MainDB domains.id → TutorialDB tutorial_domains.external_id)
- Subject (MainDB subjects.id → TutorialDB tutorial_subjects.external_id, FK to tutorial_domains)
- Topic (MainDB topics.id → TutorialDB tutorial_topics.external_id, FK to tutorial_subjects)
- Subtopics (MainDB subtopics.id → TutorialDB tutorial_subtopics.external_id, FK to tutorial_topics)

Each upsert uses ON CONFLICT DO UPDATE to ensure idempotency, with updated_at timestamps and 
deleted_at nullification to handle soft-delete resurrection scenarios.

Navigation Node Consistency Guarantees:
The sidebar validation pipeline (validateNavigationDepth, validateNodeTypes, 
validateUniqueCanonicalNavigationIds) ensures that navigation structures conform to delivery 
constraints before publication. Navigation nodes are normalized to canonical IDs, transformed 
with slugs/URLs, and then wrapped in a single TutorialDB transaction alongside the hierarchy 
sync, guaranteeing atomicity across both the sidebar tree and its referenced subtopics.

Cross-Database Identity Verification:
The verifyCrossSystemIdentity function introduced in cross-system-hierarchy-contracts.ts 
validates that MainDB UUIDs exactly match TutorialDB external_id values for topics and 
subtopics, and that navigation node IDs are consistent between sidebar trees and section 
records. This prevents delivery failures caused by UUID mismatches or orphaned foreign keys.

1. apps/skillhubcore-admin/src/lib/hierarchy/academic-hierarchy.service.ts (871 lines changed - MAJOR EXPANSION)

   This file undergoes the most significant transformation in this commit, expanding from a 
   basic hierarchy service to a comprehensive, production-ready taxonomy management system 
   with fail-closed safety guarantees.

   DependencyCheckUnavailableError Class (NEW):
   - Custom error class extending Error with entityType, entityId, and causeError properties
   - Thrown when dependency verification storage (MainDB or TutorialDB) becomes unreachable
   - Implements fail-closed pattern: if dependencies cannot be verified, deletion aborts with 503
   - Constructor signature: (entityType: string, entityId: string, causeError?: unknown)
   - Used throughout all check*Dependencies functions to propagate storage outage signals

   Direct Schema Imports Replacing Reflection (BC-CORR-02):
   BEFORE: Used dynamic schema access patterns that could fail silently
   AFTER: Direct imports from '@quiz/db' for questions, questionSkills, topicSkills tables
   
   Example transformation:
   BEFORE: const questionsTable = db.schema['questions'] // Unsafe reflection
   AFTER: import { questions, questionSkills, topicSkills } from '@quiz/db'
   
   This change ensures TypeScript compile-time verification of schema references and 
   eliminates runtime reflection errors that could cause silent dependency check failures.

   Transaction-Wrapped Atomic Deletions (BC-CORR-03):
   Every delete method now wraps dependency checking and deletion within a database transaction:
   
   Pattern:
   ```typescript
   const runInTx = async (tx: DbExecutor): Promise<HierarchyDeleteResult> => {
     const conflict = await checkDomainDependencies(id, tx);
     if (conflict) return { status: 409, error: conflict.message, ... };
     
     const [deleted] = await tx.delete(domains).where(eq(domains.id, id)).returning();
     if (!deleted) return { status: 404, error: 'Domain not found' };
     
     return { status: 200, message: 'Domain deleted successfully' };
   };
   
   return await db.transaction(runInTx);
   ```
   
   This prevents race conditions where dependencies are created between check and delete,
   and ensures rollback on any failure within the deletion sequence.

   Dependency Check Functions (NEW):
   
   checkDomainDependencies(domainId, executor?):
   - Queries subjects table for any subject with subjects.domainId = domainId
   - Filters results to ensure foreign key match (defensive against query bugs)
   - Returns DependencyConflict if count > 0, null if safe to delete
   - Throws DependencyCheckUnavailableError on database error (fail-closed)
   
   checkSubjectDependencies(subjectId, executor?):
   - Queries topics table for any topic with topics.subjectId = subjectId
   - Same filtering and error handling pattern as checkDomainDependencies
   
   checkTopicDependencies(topicId, executor?):
   - Multi-database check across MainDB and TutorialDB:
     * MainDB: subtopics, questions (via questions.topicId), topicSkills mappings
     * TutorialDB: tutorial_sidebar_trees_v2 records
   - Aggregates all dependency counts into single DependencyConflict object
   - Fails closed if either database becomes unavailable
   
   checkSubtopicDependencies(subtopicId, executor?):
   - MainDB: questions referencing questions.subtopicId
   - TutorialDB: tutorial_sections via tutorial_subtopics.external_id linkage
   - Two-phase query: first find tutorial_subtopics by external_id, then sections by subtopicId
   
   checkSkillDependencies(skillId, executor?):
   - MainDB checks for: topicSkills, questionSkills, legacy questions.skillId
   - Aggregates all three dependency types into single conflict report

   Single Delete Methods (UPDATED):
   All five entity types now implement the same safety pattern:
   - deleteDomain(id: string): Promise<HierarchyDeleteResult>
   - deleteSubject(id: string): Promise<HierarchyDeleteResult>
   - deleteTopic(id: string): Promise<HierarchyDeleteResult>
   - deleteSubtopic(id: string): Promise<HierarchyDeleteResult>
   - deleteSkill(id: string): Promise<HierarchyDeleteResult>
   
   Each method:
   1. Validates UUID format (400 if invalid)
   2. Wraps operation in transaction
   3. Checks dependencies within transaction (409 if conflicts found)
   4. Executes deletion (404 if not found, 200 if successful)
   5. Catches DependencyCheckUnavailableError and returns 503
   6. Catches other errors and returns 500 with safe error message

   Batch Delete Methods (NEW):
   All five entity types now support bounded batch deletion:
   - batchDeleteDomains(rawIds: unknown): Promise<HierarchyDeleteResult>
   - batchDeleteSubjects(rawIds: unknown): Promise<HierarchyDeleteResult>
   - batchDeleteTopics(rawIds: unknown): Promise<HierarchyDeleteResult>
   - batchDeleteSubtopics(rawIds: unknown): Promise<HierarchyDeleteResult>
   - batchDeleteSkills(rawIds: unknown): Promise<HierarchyDeleteResult>
   
   Each batch method:
   1. Validates payload with validateBatchDeletePayload (400/413 if invalid)
   2. Wraps operation in single transaction
   3. Iterates through all IDs checking dependencies
   4. Aggregates conflicts across all items
   5. Returns 409 with conflictingIds array if any item has dependencies
   6. Executes batch deletion via inArray() if all items are safe
   7. Returns 503 on DependencyCheckUnavailableError

   UUID Validation and Batch Size Limits:
   - MAX_BATCH_DELETE_SIZE constant set to 100 items
   - UUID_REGEX: /^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i
   - isValidUuid(id: string): boolean helper function
   - validateBatchDeletePayload validates: JSON depth, JSON size, array non-empty, 
     UUID format for all items, batch size ≤ 100, deduplicates IDs

   HTTP Status Code Contracts:
   - 200: Successful deletion
   - 400: Invalid UUID format, malformed payload, empty batch
   - 404: Entity not found
   - 409: DEPENDENCY_CONFLICT (child records exist)
   - 413: Payload Too Large (batch size > 100)
   - 503: Service Unavailable (dependency storage unreachable, fail-closed)

   TypeScript Types (NEW):
   - DependencyConflict: { entityType, entityId, message, dependents: Record<string, number> }
   - BatchValidationResult: { success, ids?, error?, status? }
   - HierarchyDeleteResult: { status, message?, error?, conflictType?, entityType?, 
     entityId?, dependencies?, conflictingIds? }
   - DbExecutor: Union type of DbClient | TransactionClient for transaction compatibility

   async function ensureTopicHierarchySynced(
     topicId: string,
     externalTx?: TutorialTransaction
   ): Promise<{
     domain: { externalId: string; internalId: string };
     subject: { externalId: string; internalId: string };

   SYNC-06: TutorialDB Subject Upsert (inside transaction)
   - INSERT INTO tutorial_subjects with ON CONFLICT DO UPDATE
   - Links: domainId → tutorialDomain.id (parent foreign key)
   - Logs: externalId, internalId, parentDomainId
   
   SYNC-07: TutorialDB Topic Upsert (inside transaction)
   - INSERT INTO tutorial_topics with ON CONFLICT DO UPDATE
   - Links: subjectId → tutorialSubject.id (parent foreign key)
   - Logs: externalId, internalId, parentSubjectId
   
   SYNC-08: TutorialDB Subtopic Upserts (inside transaction, loop)
   - Iterates through all activeSubtopics
   - INSERT INTO tutorial_subtopics with ON CONFLICT DO UPDATE for each
   - Links: topicId → tutorialTopic.id (parent foreign key)
   - Logs: externalId, internalId for each subtopic
   
   SYNC-09: Transaction Commit Confirmation
   - Logs: "All TutorialDB hierarchy upserts completed inside transaction"
   - Returns complete mapping structure
   
   SYNC-10: Domain Verification (post-commit)
   - SELECT from tutorial_domains WHERE externalId = domain.externalId
   - Throws if verification fails
   - Logs: verified=true on success
   
   SYNC-11: Subject Verification (post-commit)
   - SELECT from tutorial_subjects WHERE externalId = subject.externalId
   - Throws if verification fails
   
   SYNC-12: Topic Verification (post-commit)
   - SELECT from tutorial_topics WHERE externalId = topic.externalId
   - Throws if verification fails
   
   SYNC-13: Subtopic Verification (post-commit, loop)
   - SELECT from tutorial_subtopics WHERE externalId = subtopic.externalId for each
   - Throws if any subtopic verification fails
   - Logs: count, verified=true on success

   - inspectHierarchySyncError(error): Extracts PostgreSQL error details (code, constraint,

   - If externalTx provided: runs sync within caller's transaction
   - If no externalTx: creates new TutorialDB transaction for entire sync operation

ARCHITECTURAL ENHANCEMENTS

Fail-Closed Dependency Checking with DependencyCheckUnavailableError:
The new DependencyCheckUnavailableError class implements a critical safety pattern: when 
dependency verification storage becomes unavailable (network partition, database outage, query 
timeout), the system fails closed rather than failing open. This prevents cascade deletions 
that could orphan child records when the dependency check cannot be reliably performed.

The pattern is implemented consistently across all check*Dependencies functions:
1. Attempt dependency query against MainDB or TutorialDB
2. If query throws any error, wrap in DependencyCheckUnavailableError
3. Propagate to delete method, which catches and returns 503 status
4. Delete operation aborts without executing deletion

This is verified in tests by setting mockDb.throwOnSelect = true and asserting that 
mockDb.deleteCalls.length = 0, proving deletion was never attempted.

Transaction-Wrapped Atomic Deletions Preventing Race Conditions:
Every delete method now wraps both dependency checking and deletion within a single database 
transaction. This prevents the TOCTOU (Time-Of-Check-Time-Of-Use) race condition where a child 
record could be created between the dependency check and the deletion.

The transaction pattern ensures:
- Dependency check sees consistent snapshot of database state
- No concurrent inserts can occur between check and delete
- If dependency check passes, deletion is guaranteed safe
- If any step fails, entire transaction rolls back

This is critical for maintaining referential integrity in a concurrent multi-user admin 
environment where multiple users may be creating and deleting hierarchy entities simultaneously.

Direct Schema Imports Replacing Unsafe Reflection Patterns:
The original implementation used runtime reflection or dynamic schema access patterns that could 
fail silently or become stale when schema definitions changed. The new implementation imports 
schema tables directly from @quiz/db:

```typescript
import {
  questions,
  questionSkills,
  topicSkills,
} from '@quiz/db';
```

This provides:
- Compile-time TypeScript verification of schema references
- IDE autocomplete and refactoring support
- Elimination of runtime reflection errors
- Explicit dependency declarations for build systems

Cross-Database Dependency Verification (MainDB + TutorialDB):
The hierarchy service now performs dependency checks across both MainDB (authoritative taxonomy) 
and TutorialDB (delivery-optimized cache). For example, checkTopicDependencies verifies:
- MainDB: subtopics, questions, topicSkills
- TutorialDB: tutorial_sidebar_trees_v2

This ensures that a topic cannot be deleted if it has either:
- Authoritative child records in MainDB (subtopics, questions)
- Delivery artifacts in TutorialDB (published sidebars)

The fail-closed pattern applies to both databases: if either becomes unavailable, the deletion 
aborts with 503.

Bounded Bulk Operations (max 100 items, 413 on overflow):
All batch delete operations enforce a hard limit of MAX_BATCH_DELETE_SIZE = 100 items. This 
provides:
- Protection against accidental mass deletion requests
- Predictable transaction size and duration
- Bounded memory consumption during batch processing
- Clear error signaling (413 Payload Too Large) for oversized batches

The validation occurs before any database operations, ensuring that oversized requests are 
rejected immediately without consuming database resources.

UUID Validation and Format Enforcement:
All entity IDs are validated against the canonical UUID v4 format using UUID_REGEX. This 
provides:
- Protection against SQL injection attempts (e.g., "id' OR '1'='1")
- Early rejection of malformed requests (400 Bad Request)
- Consistent ID format across the system
- Type safety beyond TypeScript's compile-time checks

UUID validation occurs before any database operations, preventing invalid IDs from reaching 
the query layer.

Comprehensive HTTP Status Code Contracts (200, 400, 404, 409, 413, 503):
Every delete method returns a HierarchyDeleteResult with explicit status codes:
- 200 OK: Successful deletion
- 400 Bad Request: Invalid UUID, malformed payload, empty batch
- 404 Not Found: Entity does not exist
- 409 Conflict: DEPENDENCY_CONFLICT (child records exist)
- 413 Payload Too Large: Batch size exceeds 100 items
- 503 Service Unavailable: Dependency storage unreachable (fail-closed)

This contract allows route handlers to map service results directly to HTTP responses without 
additional logic, and provides clear signals to API clients about the nature of failures.


DOWNSTREAM DELIVERY CONTRACTS

Cross-Database Identity Mapping Verification (external_id consistency):
The new downstream-delivery-contracts.test.ts file establishes verification that MainDB UUIDs 
are correctly propagated to TutorialDB external_id foreign keys. The verifyCrossSystemIdentity 
function validates:
- mainTopicId === tutorialTopicExternalId
- mainSubtopicId === tutorialSubtopicExternalId
- sidebarNavigationNodeId === sectionNavigationNodeId

This ensures that when ensureTopicHierarchySynced upserts hierarchy records into TutorialDB, 
the external_id mappings remain consistent with MainDB's authoritative UUIDs. Any mismatch 
would break the foreign key linkage and cause delivery failures.

tutorialDeliveryService.getTutorialByPage Brand Precedence Resolution:
The delivery service implements deterministic brand precedence when resolving content:
1. Check for brand-specific deployed content (e.g., skillup + deployed)
2. Fall back to shared canonical deployed content (shared + deployed)
3. Return null if neither exists

This is verified in tests by:
- Providing both deployedShared and deployedSkillup → expects skillup (override wins)
- Providing only deployedShared → expects shared (fallback)
- Providing only deployedRth to skillup learner → expects null (cross-tenant isolation)

Brand-Specific Override > Shared Canonical Fallback Pattern:
The content resolution pattern allows brands to override shared canonical content while still 
falling back to shared when no brand-specific version exists. This supports:
- Gradual brand-specific content creation (start with shared, override selectively)
- Shared canonical as safety net (always available)
- Zero downtime during brand-specific content authoring (fall back to shared)

Cross-Tenant Negative Enforcement (SUIA ≠ RTH Isolation):
The tests verify that brands are strictly isolated: a skillup learner cannot access 
realtutorialhub-branded content even if it's the only deployed version. This is critical for:
- Customer data isolation (tenant separation)
- Brand-specific licensing and access control
- Compliance with multi-tenant SaaS security requirements

Draft/Approved Content Lifecycle Gating for Learners:
The tests verify that draft and in_review content is never delivered to learners, even if the 
brand matches. Only deployed content is accessible. This ensures:
- Work-in-progress content remains internal
- Quality gate enforcement (only reviewed content is public)
- Protection against accidental early publication

getPublishedTutorialPagePayload Hierarchical Assembly:
The full integration test verifies that getPublishedTutorialPagePayload correctly assembles 
a complete TutorialPagePayload by:
1. Verifying hierarchy sync (hierarchySyncVerified flag)
2. Resolving published sidebar for brand + topic
3. Resolving deployed content for brand + subtopic + navigationNodeId
4. Assembling hierarchy metadata (domain, subject, topic, subtopic)
5. Constructing navigation tree with active URL highlighting
6. Attaching content blocks from resolved section

The test confirms that all pieces are correctly wired together and that failure at any step 
(unverified sync, draft sidebar, draft content) causes the entire resolution to fail closed 
(return null).

Navigation Node Consistency Across MainDB and TutorialDB:
The navigation node ID used in the sidebar tree (tutorial_sidebar_trees_v2.tree) must match 
the navigation_node_id in tutorial_sections. This consistency is verified by 
verifyCrossSystemIdentity, which checks:
- sidebarNavigationNodeId === sectionNavigationNodeId

Mismatches would cause the sidebar to display a node that has no corresponding content section, 
resulting in 404 errors for learners.


SIDEBAR SAFETY MECHANISMS

Tutorial Left Sidebar Atomic Publication with Single TutorialDB Transaction:
The POST route now wraps both hierarchy synchronization and sidebar upsert within a single 
TutorialDB transaction. This guarantees:
- Hierarchy sync (domain, subject, topic, all subtopics) completes before sidebar upsert
- Sidebar upsert references validated hierarchy records via foreign keys
- Any failure at any point causes full rollback (no partial state)
- Atomicity across potentially dozens of individual upserts (1 domain + 1 subject + 1 topic + 
  N subtopics + 1 sidebar)

ensureTopicHierarchySynced Comprehensive Hierarchy Verification:
This function implements a 13-phase verification and synchronization pipeline with 
comprehensive logging (PHASE_11_18E). Each phase has START/SUCCESS/FAILED logging with 
structured details, enabling:
- Debugging of sync failures in production
- Performance analysis of sync operations
- Audit trail of hierarchy propagation
- Failure isolation (precisely which phase failed)

The function guarantees that:
- All parent records exist before child upserts (domain → subject → topic → subtopics)
- Every external_id mapping is verified post-commit
- Foreign key constraints are satisfied (subject.domainId → domain.id, etc.)
- Soft-deleted records are resurrected (deletedAt set to null on upsert)

Navigation Structure Validation (depth, node types, ID uniqueness):
The validation pipeline enforces constraints before publication:
- validateNavigationDepth: Max 3 levels (group → group → page)
- validateNodeTypes: Group nodes must have children, page nodes must be leaves
- validateUniqueCanonicalNavigationIds: No duplicate IDs across entire tree

These validations prevent malformed navigation structures that would break the learner UI, 
such as infinite recursion (circular references), broken links (duplicate IDs), or unusable 
navigation (groups with no children).

Fail-Closed on Hierarchy Sync Failure (500 with rollback):
If any phase of ensureTopicHierarchySynced fails (missing parent, broken FK, database 
unavailable), the entire TutorialDB transaction rolls back and the POST route returns 500. 
This ensures:
- No partial sidebar publication (sidebar without complete hierarchy)
- No orphaned sidebar records (sidebar referencing non-existent topicId)
- No delivery failures for learners (all foreign keys guaranteed valid)

Draft Save Bypassing Pre-Publish Sync Requirement:
When saving a sidebar with status='draft', the route skips ensureTopicHierarchySynced. This 
allows:
- Fast iterative authoring without sync overhead
- Work-in-progress saves even if hierarchy is incomplete
- Sync deferred until publish (when completeness is required)

The publish operation (status='published') enforces the full sync, ensuring that only complete, 
verified hierarchies are made available to learners.

Parent-Child Relationship Validation (Domain → Subject → Topic → Subtopic):
The getHierarchyNames function now validates that the provided IDs form an actual parent-child 
hierarchy chain. It verifies:
- subject.domainId === domainId (subject belongs to claimed domain)
- topic.subjectId === subjectId (topic belongs to claimed subject)
- subtopic.topicId === topicId (subtopic belongs to claimed topic)

If any relationship is invalid, the function throws with a detailed error message including 
the actual vs expected IDs. This prevents sidebar publication with mismatched hierarchy 
references that would cause delivery failures.
