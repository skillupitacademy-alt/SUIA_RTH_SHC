## Overview

This design implements tenant-scoped email uniqueness to fix the foreign-tenant admission defect and establish email lookup patterns for FND16/FND18. The implementation modifies the database schema, admission route, authentication services, and all email lookup consumers to enforce platform-scoped uniqueness with canonical normalization (lowercase + trim).

**Core changes:**
1. Database schema: Add composite unique index `(email, platform)`, remove global constraint
2. Admission route: Add platform filter to email lookup, handle foreign-tenant collisions
3. Auth services: Update `findByEmail` to require platform parameter
4. Email normalization: Apply `toLowerCase().trim()` at all entry points
5. Migration: Safe multi-phase rollout with rollback procedures

```typescript
    updatedAt: timestamp('updated_at', { withTimezone: true, mode: 'date' }).notNull().defaultNow(),
    externalId: uuid('external_id'),
    externalBrand: text('external_brand'),
  },
  (table) => ({
    // ✅ Replace non-unique index with unique constraint
    uniqEmailPlatform: uniqueIndex('uniq_users_email_platform')
      .on(sql`LOWER(TRIM(${table.email}))`, table.platform)
      .where(sql`${table.deletedAt} IS NULL`),

      .where(sql`${table.externalId} IS NOT NULL`),
```

**Index properties:**
- **Functional index:** `LOWER(TRIM(email))` enforces normalization at database level
- **Composite key:** `(email, platform)` scopes uniqueness to tenant
- **Partial index:** `WHERE deleted_at IS NULL` allows email reuse after soft deletion
- **Unique constraint:** Prevents duplicate active users within same platform

**Migration SQL (generated by Drizzle Kit, then manually edited):**


## Email Normalization Helper

### File: `packages/db-people/src/utils/email-normalization.ts` (NEW)

```typescript
/**
 * Normalizes email address for storage and lookup.
 * - Converts to lowercase (emails are case-insensitive per RFC 5321)
 * - Trims leading/trailing whitespace
 * - Does NOT perform Unicode normalization (emails must be ASCII)
 * 
 * @param email Raw email address
 * @returns Normalized email address
 * @throws {Error} If email is invalid
 */
export function normalizeEmail(email: string): string {
  if (typeof email !== 'string') {
    throw new Error('Email must be a string');
  }
  
  const normalized = email.trim().toLowerCase();
  
  if (normalized === '') {
    throw new Error('Email cannot be empty');
  }
  
  // Basic RFC 5322 validation
  const emailRegex = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
  if (!emailRegex.test(normalized)) {
    throw new Error('Invalid email format');
  }
  
  if (normalized.length > 254) {
    throw new Error('Email exceeds maximum length');
  }
  
  return normalized;
}

/**
 * Validates and normalizes email address.
 * Use this at API boundaries before storing or querying.
 * 
 * @param email Raw email input
 * @returns Normalized email or null if invalid
 */
export function safeNormalizeEmail(email: unknown): string | null {
  try {
    if (typeof email !== 'string') return null;
    return normalizeEmail(email);
  } catch {
    return null;
  }
}
```

**Rationale:**
- **Centralized logic:** Single source of truth for normalization rules
- **Type safety:** Validates input types
- **Error handling:** Throws on invalid input (safe variant returns null)
- **No external dependencies:** Uses native JavaScript methods
- **RFC compliance:** Enforces basic email structure validation

```typescript
      isNull(users.deletedAt)

    .limit(1);

    existingUser?.id ??

      .insert(users)
      .values({
        email: normalizedEmail, // ✅ Store normalized email
        passwordHash,
        role: 'student',
        platform: targetPlatform,
        isActive: true,
        deletedAt: null,
      })
      .returning({ id: users.id })
      .then((rows) => rows[0]?.id ?? null));

  if (userId === null) {
    return jsonError('Could not create student user', 500);
  }

  await db.insert(userProfiles).values({ userId, name: enquiry.studentName }).onConflictDoNothing();

  // ... (rest of admission/enrollment logic unchanged)

```

**Behavior changes:**
- **Before:** Lookup finds user on ANY platform → reuses foreign userId → creates cross-tenant admission (DEFECT)
- **After:** Lookup scoped to `platform='skillup'` → creates new skillup user if email exists elsewhere → separate tenant identity

**Error handling:**
- `normalizeEmail()` throws on invalid format → caught by Next.js error boundary → returns 500 with error message
- User creation failure → returns 500 (unchanged)
- Transaction rollback → database ensures atomicity (unchanged)

**Edge cases:**
1. **Same email, same platform:** Reuses existing user (✅ correct)
2. **Same email, different platform:** Creates new user (✅ correct per policy)
3. **Deleted user email:** Creates new user (✅ partial index allows reuse)
4. **Invalid email format:** normalizeEmail throws → 500 error (✅ appropriate)
5. **Concurrent admission:** Database unique index prevents race condition (✅ serializable)

## Error Handling

### Database-Level Errors

**Unique constraint violation (expected):**
```typescript
// When attempting to create duplicate email on same platform
try {
  await db.insert(users).values({ email, platform, passwordHash, role });
} catch (error) {
  if (error instanceof Error && error.message.includes('unique constraint')) {
    return jsonError('Email already registered on this platform', 409);
  }
  throw error; // Unexpected error
}
```

**Foreign key violation (should not occur):**
- Not applicable to this change (no new foreign keys)

**Transaction rollback (existing behavior):**
- Admission route uses `db.transaction()` for atomic admission+enrollment
- Rollback behavior unchanged

### Application-Level Errors

**Invalid email format:**
```typescript
try {
  const normalized = normalizeEmail(email);
} catch (error) {
  return jsonError('Invalid email format', 400);
}
```

**Missing platform parameter:**
```typescript
async findByEmail(email: string, platform: PeoplePlatform): Promise<...> {
  if (!platform) {
    throw new Error('Platform parameter is required');
  }
  // ...
}
```

**Platform mismatch (auth):**
```typescript
// User authenticated on skillup tries to access realtutorialhub resource
if (authenticatedPlatform !== resourcePlatform) {
  return jsonError('Cross-platform access denied', 403);
}
```

### Failure Recovery

**Scenario: Schema migration fails mid-execution**
- **Cause:** Duplicate emails exist within same platform
- **Recovery:**
  1. Migration will fail at `CREATE UNIQUE INDEX` step
  2. Identify duplicates with pre-migration query
  3. Manually resolve duplicates (soft-delete or merge)
  4. Retry migration

**Scenario: Code deployment breaks authentication**
- **Cause:** Missing platform parameter in caller
- **Recovery:**
  1. Feature flag OFF immediately
  2. Hotfix: Add platform parameter to broken caller
  3. Redeploy with fix
  4. Re-enable feature flag

**Scenario: Cross-platform duplicate created after deployment**
- **Cause:** Race condition or missed consumer
- **Recovery:**
  1. Identify affected users
  2. Schema rollback NOT possible
  3. Manual resolution: Keep both accounts or link via FND18

## Performance Considerations

### Index Performance

**Query pattern (before):**
```sql
SELECT id FROM users WHERE email = 'user@example.com' LIMIT 1;
-- Uses: users_email_unique index (implicit from constraint)
-- Scan: Index Scan on users_email_unique (cost=0.42..8.44 rows=1)
```

**Query pattern (after):**
```sql
SELECT id FROM users
WHERE LOWER(TRIM(email)) = 'user@example.com'
  AND platform = 'skillup'
  AND deleted_at IS NULL
LIMIT 1;
-- Uses: uniq_users_email_platform index
-- Scan: Index Scan on uniq_users_email_platform (cost=0.42..8.44 rows=1)
```

**Performance impact:**
- **Index size:** Composite index slightly larger than single-column (negligible)
- **Query cost:** Identical (both use index scan)
- **Normalization overhead:** `LOWER(TRIM(email))` applied once at insert/update, free at query (functional index)
- **Platform filter:** Adds selectivity (improves performance on large tables)

**Benchmark (estimated on 1M users):**
- Before: 0.05ms avg lookup time
- After: 0.05ms avg lookup time (no degradation)

### Write Performance

**Insert performance:**
- Before: Check global unique constraint
- After: Check composite unique constraint
- Impact: Negligible (same index lookup cost)

**Update performance:**
- Email updates rare (not supported in current design)
- If implemented: Same constraint check cost

## Security Implications

### Positive Security Improvements

1. **Tenant isolation enforced at database level:**
   - Prevents cross-platform account hijacking
   - Admission route cannot accidentally link foreign users to batches

2. **Normalization prevents case-variation bypass:**
   - `User@Example.com` and `user@example.com` treated as same email
   - Prevents duplicate account creation via casing tricks

3. **Email enumeration resistance:**
   - Password recovery: Returns success regardless of user existence
   - Login: Does not reveal which platform has the email

### Remaining Security Concerns

1. **Cross-platform email enumeration via timing:**
   - **Risk:** Attacker could measure response time differences between platforms
   - **Mitigation:** Constant-time password hashing already in place
   - **Residual:** Negligible (timing differences below threshold)

2. **Account takeover via platform confusion:**
   - **Risk:** User mistakes which platform they registered on, resets wrong account
   - **Mitigation:** Password recovery email includes platform name
   - **Residual:** User education required

3. **Foreign-tenant session hijacking:**
   - **Risk:** JWT token from one platform used on another
   - **Mitigation:** JWT `brand` claim verified at gateway (existing)
   - **Residual:** FND03/FND18 will strengthen with explicit tenantId

5. **Migration:** Multi-phase rollout with feature flags and rollback procedures
