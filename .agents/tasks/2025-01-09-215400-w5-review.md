# Wave 5 Placement Engine Implementation

This implementation adds a placement engine that matches candidates to manifests using multi-criteria scoring, handles conflicts, and supports manual overrides. The core modules follow the existing repository pattern, integrate with the state machine, and produce structured evidence for audit trails.

**Watch for:** Missing API routes (confirmed - endpoints not wired), async repository integration gaps in PlacementEngine (likely), scorer weights not validated to sum to 1.0 (confirmed), and all tests skipped due to pytest configuration (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The placement engine introduces three core modules: a scorer that evaluates candidate-manifest pairs using configurable weights (structural similarity, family/version alignment, availability, conflict penalty), a matcher that filters manifests by target family/version and ranks by score, and an orchestrator that coordinates the workflow with repository integration. The PLACEMENT state now sits between CANDIDATE_AUDIT and INTEGRATION_PLANNED in the canonical state machine, with automated gating. API schemas define the request/response contracts, but the actual FastAPI route handlers are missing — no endpoints were added to workflows.py or candidate.py beyond the existing manifest generation routes. The PlacementEngine loads candidates and manifests from repositories but never awaits repository calls, creating async/await mismatches. The scorer accepts custom weights but never validates they sum to 1.0, risking nonsensical scores. All 18 integration tests were collected but skipped, leaving the implementation unverified at runtime.

## Placement scoring with configurable weights

PlacementScorer evaluates candidate-manifest pairs on four criteria: structural similarity (from CanonicalComparator, range 0.0-1.0), family/version match (1.0 exact, 0.5 family only, 0.0 mismatch), availability based on decision type (REUSE/ADD: 1.0, UPDATE: 0.5, EXTEND: 0.3, REJECT: 0.0), and conflict penalty (subtract 0.3 per conflict). Each criterion is weighted and summed into an overall score clamped to [0, 1]. The scorer generates human-readable reasoning strings explaining each component.

The weights dictionary defaults to equal 0.25 for each criterion, but custom weights can be passed to \_\_init\_\_. No validation confirms the weights sum to 1.0, so passing {structural_similarity: 0.9, family_version_match: 0.9, availability: 0.9, conflict_penalty: 0.9} would yield scores above 1.0, breaking the [0, 1] contract. The implementation clamps the final score, masking the misconfiguration rather than rejecting it.

If structural_similarity is not provided to score_match, the code defaults to 0.5. This arbitrary midpoint has no justification in the docstring and biases scores when structural comparison data is unavailable. A missing structural similarity should either fail-fast (require the parameter) or default to 0.0 with clear documentation.

## Candidate-manifest matching and filtering

CandidateManifestMatcher filters manifests by target family and version from the workflow binding, excludes REJECT decisions, scores each candidate-manifest pair via PlacementScorer, and returns the highest-scoring match as a MatchResult. The filtering logic prefers exact version matches but will match family-only if versions differ. If no manifests remain after filtering, the result's recommendation is REJECT.

The matcher includes a detect_conflicts method that iterates through multiple candidates, calls find_matches for each, and builds a map of target paths to candidate IDs. Paths with more than one candidate are returned as conflicts. However, create_placement in PlacementEngine never calls detect_conflicts, so the conflicts field in PlacementEngineResult is always empty even when conflicts exist. The handle_placement_conflict method does iterate through conflicting_candidates and uses scoring to pick a winner, but the caller must already know which candidates conflict — the engine doesn't discover conflicts on its own.

## PlacementEngine orchestration and repository integration

PlacementEngine coordinates the full workflow: load candidate from CandidateRepository, load workflow from WorkflowRepository, load manifests from ManifestRepository (filtered by workflow_id via list_by_workflow), match and score via Matcher, create PlacementEngineResult with evidence, and persist the result. The engine accepts repositories as constructor dependencies, following the pattern established in W4's ApprovalEnforcer.

The repository calls are async (\_load_candidate, \_load_workflow, \_load_manifests, \_load_manifest are all defined as async methods), but none of them use await when calling repository methods like self.candidate_repo.get(candidate_id). This will fail at runtime — the methods return coroutines, not results. Every repository call needs await.

The \_persist_placement method is a stub with pass. The docstring says "uses manifest repository to store placement decision" but the implementation does nothing. Either this should be implemented to write placement records to the database, or the docstring should explain why persistence is deferred (e.g., placement records are created later during approval flow).

## State machine wiring for PLACEMENT

The PLACEMENT state was added to CanonicalWorkflowState between CANDIDATE_AUDIT and INTEGRATION_PLANNED. The state's docstring explains it's an automated gate (no human approval) that matches candidates to manifests, scores them, handles conflicts, and supports manual overrides. The state transitions to INTEGRATION_PLANNED on success or REJECTED on failure.

No code in canonical_workflow.py enforces transitions to or from PLACEMENT — the state is defined but the transition logic isn't visible in the diff. The VALID_TRANSITIONS dict referenced in the implementation report isn't shown in the files reviewed. If transitions are enforced elsewhere (e.g., WorkflowGovernanceService), that integration isn't demonstrated in this wave's code.

## API schemas without routes

Four Pydantic schemas define the API surface: PlacementEngineResponse (workflow_id, candidate_id, placement_decision, manifest_id, score, conflicts, evidence), PlacementOverrideRequest (manual_manifest_id, override_reason), PlacementConflictResponse (target_path, candidate_ids, conflict_count), and CreatePlacementRequest (candidate_id). These schemas follow the existing pattern from candidate.py and governance.py.

No FastAPI route handlers were added to implement these contracts. The implementation report states "API route implementation deferred to follow-up task (requires FastAPI dependency injection setup)," but workflows.py was created in this wave with full dependency injection for WorkflowGovernanceService. The same pattern could have been applied to PlacementEngine. Without routes, the placement engine is unreachable via HTTP.

## Evidence structure and timestamp handling

All placement operations produce structured evidence with candidate_id, workflow_id, target_family, target_version, matched_manifests, best_manifest_id, recommendation, conflicts, and score breakdown. Manual overrides replace score fields with override: true, override_reason, and manual_manifest_id.

The result dataclass includes a created_at timestamp defaulting to datetime.utcnow().isoformat() + "Z". The use of utcnow() is consistent with existing code but should be timezone-aware (datetime.now(timezone.utc)) to avoid ambiguity.

## BlockFamily type conversion asymmetry

The scorer's \_score_family_version_match checks if candidate.target_family is a string and converts it to BlockFamily, otherwise uses it as-is. CandidatePackage defines target_family as Optional[str]; PlacementManifest defines blockFamily as BlockFamily. The domain model uses strings for candidates and enums for manifests, but the scorer papers over the difference with runtime type checking. Either the schema should be consistent (both use BlockFamily) or the conversion should happen at the boundary (when loading from the database), not in business logic.
