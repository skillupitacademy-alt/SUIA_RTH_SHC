EXECUTIVE SUMMARY

This continuation work expands the SkillHubCore Admin hierarchy service with 198 lines of comprehensive
deletion safety infrastructure, refactors 10 admin API routes to delegate to the centralized service layer,
enhances gateway test coverage with 112 lines of refactoring, aligns tutorial progress schema with tenant
boundaries through a new SQL migration, and refines authentication tests across RTH, SkillUp, and Gateway
applications. The work delivers production-grade referential integrity enforcement with cross-database
dependency checks, batch deletion capabilities with deadlock prevention, and fail-closed error handling
when storage is unavailable. Despite adding substantial functionality, the net change is -8 lines,
demonstrating effective code consolidation through architectural improvements.

The hierarchy service expansion introduces transaction-wrapped deletion methods for all five taxonomy
entities (domains, subjects, topics, subtopics, skills), each with row-level locking, dependency
verification across MainDB and TutorialDB, and structured conflict reporting. Ten admin API routes
(domains, subjects, topics, subtopics, skills - each with collection and individual resource handlers)
now delegate all mutations to AcademicHierarchyService, eliminating inline business logic and ensuring
consistent validation, normalization, and error handling. The gateway test suite consolidates route
verification patterns, adds coverage for SHC admin portal identity preservation, and validates tenant
isolation enforcement. Tutorial progress schema gains tenantId column with constraints, indexes, and
a unique composite key enforcing one-progress-per-tenant-user-subtopic, supported by a guarded SQL
migration for empty-table alignment.

ARCHITECTURAL OVERVIEW

Hierarchy Service Architectural Evolution:
The AcademicHierarchyService evolves from a basic CRUD facade into an authoritative taxonomy coordination
layer with production-grade deletion safety. The new executeDestructiveTransaction() method enforces
strict transactional boundaries, failing closed (503) when transaction support is unavailable rather
than executing unprotected deletions. Five entity-specific delete methods (deleteDomain, deleteSubject,
deleteTopic, deleteSubtopic, deleteSkill) and five batch equivalents acquire row-level locks with
PostgreSQL FOR UPDATE, check dependencies (including cross-database TutorialDB lookups for topics and
subtopics), and return structured HierarchyDeleteResult with conflict details. Batch operations sort
UUIDs deterministically to prevent concurrent deadlocks. The service documents architectural boundaries:
MainDB row locks cannot coordinate with TutorialDB inserts (separate PostgreSQL instances without 2PC),
so checkTopicDependencies and checkSubtopicDependencies query TutorialDB read-only and fail closed on
network errors. This design prevents unsafe cascades while acknowledging that race conditions between
deletion verification and concurrent TutorialDB writes remain theoretically possible without distributed
transaction coordination (marked as "OWNER DECISION REQUIRED" for future 2PC or outbox architecture).

Route Simplification Pattern:
Ten admin routes migrate from inline validation/mutation logic to thin delegation layers. POST routes
sanitize JSON depth/size, parse with domain schemas, and call AcademicHierarchyService.create*().
PUT/PATCH routes extract IDs, normalize conflicting field pairs (order/orderIndex, depth/depthLevel,
complexity/complexityLevel), validate with partial schemas, and call service.update*(). DELETE routes
extract single ID or comma-separated IDs, invoke service.delete*() or service.batchDelete*(), and
return structured 200/404/409/503 responses. Route handlers no longer touch database clients directly.
This pattern eliminates duplication across 10 route files and ensures all mutations flow through the
centralized authorization, normalization, and referential integrity layer.

Progress Tenant Alignment Design:
The tutorialProgress table gains tenantId enforcement at the schema level. The new column uses CHECK
constraint to permit only 'skillup', 'realtutorialhub', 'skillhubcore'. A unique composite index
(tenant_id, user_id, subtopic_id) replaces the prior (user_id, subtopic_id) index, enforcing
one-progress-record-per-tenant-user-subtopic. A dedicated tenant index accelerates tenant-scoped
queries. The manual SQL migration (20261112_progress_tenant_empty_table.sql) documents that it runs
outside the historical Drizzle migration sequence and requires companion runner validation (zero rows,
exact prior schema) before applying. This alignment closes a tenant isolation gap where a shadow user
across multiple brands could collide on progress records without tenant scoping.

Gateway Test Consolidation:
The gateway test suite refactors 112 lines to consolidate route verification patterns, eliminate
duplicate token generation, and expand coverage for SHC admin portal workflows. A new test verifies
that internal SHC admin requests with x-portal-identity='shc-admin' and verified super_admin tokens
preserve SHC principal identity (x-user-id, x-user-roles) when forwarding to exam service Questions
API. Another test proves that tenant administrator tokens attempting to forge SHC admin headers are
rejected before forwarding (403, no fetch). Additional tests cover user/admin host routing, placement
handoff API routing, CORS preflight with X-Brand headers, and admin_accessToken cookie enforcement.
The refactoring consolidates token generation into a reusable makeToken() helper and uses .each()
parameterized tests to cover 30+ route rewrites in a single test case.

   CODE SAMPLE (delete method pattern):
   ```typescript
   static async deleteTopic(id: string): Promise<HierarchyDeleteResult> {
     if (!isValidUuid(id)) {
       return { status: 400, error: 'Invalid UUID format for Topic ID' };
     }

     const runInTx = async (tx: DbExecutor): Promise<HierarchyDeleteResult> => {
       // 1. Acquire row lock to serialize concurrent transactions
       await acquireRowLock('topic', id, tx.select({ id: topics.id }).from(topics).where(eq(topics.id, id)));

       // 2. Verify dependencies within the transaction
       const conflict = await checkTopicDependencies(id, tx);
       if (conflict) {
         return {
           status: 409,
           error: conflict.message,
           conflictType: 'DEPENDENCY_CONFLICT',
           entityType: 'topic',
           entityId: id,
           dependencies: conflict.dependents,
         };
       }

       const [deleted] = await tx.delete(topics).where(eq(topics.id, id)).returning();
       if (!deleted) {
         return { status: 404, error: 'Topic not found' };
       }

       return { status: 200, message: 'Topic deleted successfully' };
     };

     return await this.executeDestructiveTransaction('topic', runInTx);
   }
   ```

   - Documents cross-database coordination limitations and marks future 2PC decision as owner call
   - Enables batch deletions with deadlock prevention and structured conflict reporting
   - Centralizes all referential integrity logic, removing burden from route handlers
