# JWT Configuration Alignment with SHC Platform

Wave 1A eliminates the parallel authentication system between the Python project-ai service and the TypeScript SHC platform by aligning JWT configuration, implementing issuer validation, and adding admin token support. The Python service now reads JWT_SECRET and ADMIN_JWT_SECRET directly from environment variables (replacing JWT_SECRET_KEY), validates that all tokens originate from issuer 'skillhubcore.in', and implements dual-secret verification that accepts both user and admin tokens following the SHC TokenService pattern.

The implementation successfully delivers all three features: config alignment (FEAT-001), JWT validation enhancements (FEAT-002), and comprehensive test coverage (FEAT-003). All 8 JWT alignment tests pass, auth module coverage exceeds 90% (98% actual), and documentation is in place. The dual-secret verification correctly mirrors SHC's fallback pattern where tokens are tried with the user secret first, then the admin secret, accepting whichever succeeds.

**Watch for:** Token claim extraction mismatch (confirmed) — `get_current_user` in dependencies.py extracts `user_id` from the `sub` claim, but SHC access tokens created by `generateAccessToken` use `userId` not `sub`. This breaks identity extraction for real SHC tokens despite tests passing (tests include both claims). Admin token privilege escalation gap (likely) — the Python service accepts admin tokens but doesn't expose the `tokenType` or `isAdmin` flags to downstream code, so elevated privileges cannot be enforced.

**Verdict**: NEEDS_CHANGES

## High-level view

The config module now mirrors SHC's environment variable names (JWT_SECRET and ADMIN_JWT_SECRET), with ADMIN_JWT_SECRET falling back to JWT_SECRET when not set. Both secrets are validated to be at least 32 characters, matching the security baseline. The .env.example documents all four JWT environment variables with clear references to SHC alignment.

JWT validation adds issuer enforcement and dual-secret verification. Every token must have `iss='skillhubcore.in'` or face 401 rejection. The decode_access_token function tries the user secret first, then the admin secret on signature failure, matching SHC TokenService.verifyAccessToken. Audience and tokenType validation now accept both 'user' and 'admin' values. Identity claims validation (userId, originalUserId, shadowUserId) remains strict and unchanged.

Test coverage is comprehensive with 8 JWT alignment tests covering issuer validation (missing and wrong issuer), dual-secret verification, user and admin token acceptance, identity claims validation, token expiration, and external secret rejection. Tests use actual jose.jwt.encode to generate tokens (no mocks). Combined auth test suite has 32 tests (8 alignment + 8 config + 9 dependencies + 7 jwt) all passing with 98% coverage on app/auth.

The token claim extraction in get_current_user expects `sub` but SHC's generateAccessToken produces tokens with `userId`. The test suite masks this by including both claims in test tokens, so the mismatch only surfaces with real SHC tokens. This is outside Wave 1A scope (dependencies.py is new, not modified by the wave) but blocks integration.

Admin tokens are accepted by JWT validation but the `tokenType` and `isAdmin` flags are not surfaced to FastAPI dependencies or route handlers. Without access to these flags, the application cannot distinguish admin tokens from user tokens or enforce elevated privileges. This leaves the admin token acceptance feature incomplete.

## Config module alignment with SHC environment variables

The config module (services/project-ai/app/auth/config.py) eliminates JWT_SECRET_KEY in favor of JWT_SECRET and ADMIN_JWT_SECRET, matching the SHC platform's environment variable names exactly. The get_jwt_config function returns a dictionary with `user_secret` (from JWT_SECRET) and `admin_secret` (from ADMIN_JWT_SECRET, falling back to JWT_SECRET if not set). This fallback pattern mirrors SHC TokenService lines 87-91 where ADMIN_SECRET falls back to ACCESS_SECRET (which reads JWT_SECRET).

Both secrets are validated to be at least 32 characters. The .env.example file documents all four JWT environment variables (JWT_SECRET, ADMIN_JWT_SECRET, JWT_ALGORITHM, JWT_ACCESS_TOKEN_EXPIRE_MINUTES) with comments explaining SHC alignment and the fallback behavior.

## Issuer validation and dual-secret verification

The decode_access_token function (services/project-ai/app/auth/jwt.py lines 52-147) now enforces issuer validation: every token must have `iss='skillhubcore.in'` or face 401 with "Invalid token issuer". This matches SHC TokenService which sets the issuer in signSkillHubCoreAccessToken (line 357) and verifySkillHubCoreJWT validates it (line 485).

Dual-secret verification implements the pattern from SHC TokenService.verifyAccessToken (lines 415-442): iterate through [user_secret, admin_secret], try to decode with each, accept the first success, raise 401 if both fail. The Python implementation uses a for loop (lines 79-143) that tries config["user_secret"] first, then config["admin_secret"]. On HTTPException (validation errors for issuer, audience, claims) it re-raises immediately without trying the second secret. On JWTError or JWTClaimsError (signature failure, malformed token) it saves the error and continues to the next secret. If both secrets fail, it raises 401 "Invalid or expired token".

Audience validation now accepts both 'user' and 'admin' (line 97: `if audience not in ["user", "admin"]`). TokenType validation matches (line 104: `if token_type not in ["user", "admin"]`). Identity claims validation (userId, originalUserId, shadowUserId) remains unchanged — all three must be non-empty strings.

## Token claim extraction mismatch in get_current_user

The get_current_user function (dependencies.py lines 11-46) extracts `user_id` from `payload.get("sub")` at line 44. However, SHC's generateAccessToken function (token.service.ts lines 281-296) creates tokens with `userId` in the payload, not `sub`. The SignJWT call at line 293 includes `{ ...payload, originalUserId, shadowUserId, tokenType, brand }` where payload is a TokenPayload with `userId: string` (type definition at line 32-47).

There are two separate token types in SHC:
- TokenPayload (used by generateAccessToken, generateRefreshToken): has `userId`, `originalUserId`, `shadowUserId`, `tokenType`, `aud`, `isAdmin`
- SkillHubCoreTokenPayload (used by signSkillHubCoreAccessToken): has `sub`, `roles`, `subscriptions`, `platforms`, `iss`

The JWT validation logic in jwt.py validates `userId` as a required identity claim (line 110: `required_claims = ["userId", "originalUserId", "shadowUserId"]`), confirming that Wave 1A expects tokens with `userId`. The test suite in test_auth_dependencies.py includes both `sub` and `userId` in the token payload (lines 34-39), which masks the mismatch — the test passes because `sub` is present, but a real SHC token without `sub` would fail when get_current_user tries to extract it.

This is outside Wave 1A scope because dependencies.py is a new file (git diff shows it as new, not modified). However, it's a blocking integration issue. When the Python service receives a real token from SHC's generateAccessToken, get_current_user will extract `None` for user_id, breaking authentication.

The fix: change line 44 to `"user_id": payload.get("userId")`. If backward compatibility with tokens containing `sub` is required, use `"user_id": payload.get("userId") or payload.get("sub")`.

## Admin token acceptance without privilege enforcement

The JWT validation accepts admin tokens (tokenType='admin', aud='admin') but get_current_user doesn't expose the token type or admin flag to the application. The payload returned by decode_access_token includes `tokenType` and could include `isAdmin`, but get_current_user only extracts `user_id` and `roles` (lines 43-46).

Without access to the token type, FastAPI route handlers and dependencies cannot distinguish admin tokens from user tokens. The require_contract_admin dependency (lines 49-70) checks for "contract_admin" in the roles list, not for tokenType='admin'.

The fix: add `"token_type": payload.get("tokenType")` and `"is_admin": payload.get("tokenType") == "admin"` to the return dict in get_current_user.

## Dual-secret verification and privilege confusion risk

The dual-secret verification tries user_secret first, then admin_secret, accepting whichever succeeds. This means:
- A token with tokenType='admin' signed with JWT_SECRET (user secret) is accepted
- A token with tokenType='user' signed with ADMIN_JWT_SECRET (admin secret) is accepted

In environments where the secrets differ, this creates a privilege confusion risk:

1. An attacker with access to JWT_SECRET can forge admin tokens (set tokenType='admin') that the Python service will accept via the user secret verification path
2. A token intended as a user token but accidentally signed with ADMIN_JWT_SECRET will be accepted as valid

If the intention is that admin tokens MUST be signed with ADMIN_JWT_SECRET and user tokens MUST be signed with JWT_SECRET, the verification logic should check tokenType first and try only the matching secret. If the intention is to accept tokens signed with either secret (for rotation or fallback), this should be documented clearly.

## Integration gaps with SHC token structure

Beyond the `sub` vs `userId` mismatch, there's a structural question about which SHC token type the Python service is intended to consume.

SHC has three token creation methods:
1. generateAccessToken (lines 281-296): creates TokenPayload with userId, tokenType, aud, isAdmin
2. generateRefreshToken (lines 298-323): creates refresh tokens with userId, tokenType, aud, isAdmin
3. signSkillHubCoreAccessToken (lines 332-361): creates SkillHubCoreTokenPayload with sub, roles, subscriptions, platforms, iss

The JWT validation in jwt.py validates `iss='skillhubcore.in'`, which is set by signSkillHubCoreAccessToken but NOT by generateAccessToken. The generateAccessToken function (line 293) uses SignJWT without calling setIssuer. This means tokens created by generateAccessToken will fail issuer validation in the Python service.

However, the test tokens in test_jwt_alignment.py use the generateAccessToken structure (userId, tokenType, aud) but add iss='skillhubcore.in' manually (line 71: `if include_issuer: payload["iss"] = issuer`). This creates test tokens that don't match either SHC production path.

The context.json file (line 8) says "Python service consuming tokens from TypeScript SHC platform" and references TokenService lines 82-94 (which is in the middle of the constructor and static secret initialization), not pointing to a specific token creation method.

This suggests either:
1. The SHC TokenService.generateAccessToken should be updated to set issuer='skillhubcore.in' (TypeScript change outside Wave 1A)
2. The Python service should accept tokens without issuer from generateAccessToken (rollback of FEAT-002 issuer validation)
3. The Python service is intended to consume signSkillHubCoreAccessToken tokens (which use `sub` not `userId`, contradicting the identity claims validation)

The FEAT-002 verification log (FEAT-002.json lines 30-36) doesn't mention this gap — it confirms issuer validation works but doesn't verify against actual SHC token creation methods.

This is a specification gap that spans both codebases. The review can flag it but resolution requires coordination between Python and TypeScript changes.
