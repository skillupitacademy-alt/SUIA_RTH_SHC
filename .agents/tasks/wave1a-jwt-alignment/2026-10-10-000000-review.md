## High-level view

Config alignment is complete with JWT_SECRET and ADMIN_JWT_SECRET matching SHC's environment variable names exactly. The fallback pattern (ADMIN_JWT_SECRET defaults to JWT_SECRET) mirrors SHC TokenService. Both secrets are validated to be at least 32 characters. The .env.example documents all JWT variables with clear SHC alignment notes.

JWT validation enforces issuer='skillhubcore.in' for all tokens and implements strict secret-to-tokenType binding: user tokens must verify with JWT_SECRET, admin tokens must verify with ADMIN_JWT_SECRET. This prevents privilege escalation where an attacker with the user secret could forge admin tokens. The dual-secret verification loop tries both secrets but enforces the tokenType-to-secret match after successful decode.

The dependencies module now extracts user_id from the `userId` claim (with `sub` fallback for backward compatibility) and exposes `token_type` and `is_admin` flags to application code. The RBAC dependencies (`require_contract_admin`, `require_contract_reviewer`, `require_contract_viewer`) enforce role-based access control with proper 403 rejection of unauthorized users.

TypeScript integration is complete: `generateAccessToken` in token.service.ts now calls `.setIssuer('skillhubcore.in')` (line 298), ensuring tokens issued by SHC pass issuer validation in the Python service.

Test coverage includes all prior scenarios plus new tests for userId-only tokens (confirming real SHC tokens work), strict secret binding rejection (admin token with user secret rejected, user token with admin secret rejected), and admin privilege enforcement (valid user token rejected with 403 when accessing admin route).

## Transport abstraction via Stream interface

The decode_access_token function implements strict secret-to-tokenType binding using a two-phase verification approach. Phase 1 tries both secrets in sequence (user_secret, admin_secret) to decode the token and extract the tokenType claim. Phase 2 enforces that the tokenType matches the secret that succeeded: if tokenType='admin' but the token verified with user_secret, reject with 401 "Admin token must be signed with admin secret". The inverse check also applies for user tokens.

This prevents two attack scenarios: (1) attacker with JWT_SECRET cannot forge admin tokens even if they set tokenType='admin', because the token will verify with user_secret and fail the binding check; (2) legitimate admin tokens cannot be accidentally signed with the wrong secret, which would indicate a configuration or issuance error. The binding is enforced at lines 135-143 of jwt.py after successful decode.

The verification loop (lines 79-102) uses a try-except pattern that distinguishes signature failures (JWTError, JWTClaimsError) from validation failures (HTTPException for issuer/audience/claims). Signature failures trigger retry with the next secret. Validation failures re-raise immediately because no secret will fix a structural problem. ExpiredSignatureError is treated as a signature failure for error message clarity but raises immediately with "Invalid or expired token" rather than trying the second secret.

## Identity claim extraction aligns with SHC token structure

The get_current_user dependency (dependencies.py lines 46-49) now extracts user_id from `payload.get("userId")` first, falling back to `payload.get("sub")` only if userId is missing. This matches SHC's TokenPayload structure where `userId` is the canonical user identifier. The fallback preserves compatibility with tokens from signSkillHubCoreAccessToken (which uses `sub`) without breaking the primary path.

The test suite includes test_get_current_user_with_userid_only (test_auth_dependencies.py line 53) which creates a token with only `userId` (no `sub` claim) and verifies successful extraction. This confirms that real SHC tokens from generateAccessToken will work correctly. The original test_get_current_user_valid includes both claims to verify the fallback path.

## Admin privilege flags exposed to application layer

The get_current_user return dict now includes `token_type` (extracted from payload tokenType claim) and `is_admin` (derived from payload isAdmin claim, defaulting to False). This enables FastAPI route handlers and dependencies to distinguish admin tokens from user tokens and enforce elevated privileges.

The test_admin_privilege_enforcement_rejects_user_token integration test (test_jwt_alignment.py lines 313-341) verifies end-to-end privilege enforcement. It creates a valid user token, confirms that get_current_user succeeds and returns token_type='user', then calls require_contract_admin and expects 403 "Requires contract_admin role". This confirms that the admin flag exposure integrates correctly with RBAC dependencies.

## Issuer validation integration with TypeScript token issuance

The TypeScript TokenService.generateAccessToken function (token.service.ts line 298) now calls `.setIssuer('skillhubcore.in')` in the SignJWT chain, matching the issuer validation requirement in Python's decode_access_token (jwt.py line 112). This closes the integration gap identified in the prior review where Python required issuer validation but TypeScript token creation didn't set it.

Tokens created by generateAccessToken now include iss='skillhubcore.in' and will pass issuer validation in the Python service. Tokens created by signSkillHubCoreAccessToken already set the issuer (line 357) and are unaffected. This change spans both codebases and required coordination between Python (FEAT-002) and TypeScript (single-line addition).
