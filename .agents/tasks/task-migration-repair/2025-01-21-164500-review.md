# Migration Repair Workflow System Implementation

This implementation adds 13 specialized agents across a 9-wave execution DAG for autonomous migration repair. The system performs read-only baseline audits, generates schema-preserving patches, executes verification pipelines against disposable databases, and publishes changes only after fail-closed gate approval. Changes span 1016 files with substantial additions to `services/project-ai/app/workflows/migration_repair/`.

The system establishes production database protection through enumerated forbidden markers, enforces fail-closed evaluation where SKIPPED or BLOCKED checks prevent approval, and logs all agent executions to append-only JSONL evidence ledgers. Integration tests require `TEST_DATABASE_URL_TUTORIAL` and skip gracefully when unconfigured.

**Watch for:** Missing workflow_controller agent (confirmed), agent count mismatch between registry and implementation (13 agent files vs. 14 expected including W0), and incomplete test coverage verification (no automated coverage report in evidence).

**Verdict**: NEEDS_CHANGES

## High-level view

The agent registry correctly defines 28 total agents (15 original + 13 migration repair), with all 13 new agent types properly enumerated in `AgentType` and routed through `agent_coordinator.py`. However, the W0 workflow_controller agent—the dependency root for all W1 agents—is missing from the implementation. All 13 agent files that do exist log to the evidence ledger using `app.evidence.ledger.append_agent_run()`.

Database safety validation implements production protection through `FORBIDDEN_PRODUCTION_MARKERS` and rejects VERIFY mode access to any database containing "prod", "production", "tutorial_prod", "neon-prod", "_prod", or "-prod" markers. The `DatabaseTarget` dataclass enforces validation in `__post_init__`, and `validate_target()` additionally blocks MIGRATE mode operations against production environments.

The final gate implements fail-closed logic: missing, FAIL, BLOCKED, or SKIPPED statuses for any of 7 required checks result in CheckStatus.BLOCKED. Only unanimous PASS across migration_execution, schema_verification, package_tests, integration_tests, security_tests, evidence_complete, and commit_identity yields CheckStatus.PASS.

Integration tests cover W0-W9 execution flow, parallel W1 execution, dependency propagation from W1→W2, verification pipeline stage blocking, and final gate evaluation. Tests use `pytest.mark.skipif` to check for `TEST_DATABASE_URL_TUTORIAL` before running database operations, with graceful skip messages when unconfigured.

Documentation exists at `docs/migration-repair-workflow.md` covering architecture, agent responsibilities, safety constraints, and verification stages. The CLI script `scripts/run-migration-repair.py` provides `--dry-run`, `--verbose`, and `--database-url` options, generating execution plans and final reports to `.agents/tasks/migration-repair-{workflow_id}-report.json`.

No hardcoded absolute paths detected across agent implementations—all use `context.repository_root` or Path operations relative to the workspace root.

## Agent registry integration and missing workflow_controller

The `agent_coordinator.py` file routes all 13 new agent types with lazy imports to their respective `execute_*()` functions. Test assertions verify 28 agents registered, 28 enum values, and that no agent has "stub" or "TODO" in capabilities.

The agent files directory contains only 13 Python files: 12 agents that match the routing table, but not workflow_controller. The `agents/__init__.py` exports 13 functions, none is `execute_workflow_controller`. The plan specifies Agent0 (workflow_controller) in W0 as the dependency root, but no implementation exists. W1 agents declare dependencies on "Agent0" in `plan.py`, but the coordinator has no route to satisfy that dependency.

## Database safety validation enforces production protection

The `DatabaseTarget` dataclass checks `self.name.lower()` against `FORBIDDEN_PRODUCTION_MARKERS` in `__post_init__`, raising `ValueError` if the database name contains any marker and `mode == DatabaseMode.VERIFY`. The `validate_target()` function additionally blocks MIGRATE mode when `env == "production"`.

All 14 safety tests pass, confirming production database protection is enforced with case-insensitive string matching against 6 markers: "tutorial_prod", "neon-prod", "production", "prod", "_prod", "-prod".

## Final gate implements fail-closed evaluation

The `gate.py` module defines 7 required checks. The `evaluate_final_gate()` function returns `CheckStatus.PASS` only when all 7 checks have `CheckStatus.PASS`. Any other status—FAIL, BLOCKED, SKIPPED, or missing key—results in `CheckStatus.BLOCKED`.

The gate never returns FAIL or SKIPPED—only PASS or BLOCKED. Gate tests verify that partial results, skipped checks, blocked checks, failed checks, and missing checks all result in BLOCKED.

## Agent implementations log to evidence ledger

All 12 implemented agent files log start, completion, duration, and structured evidence to `ledger.append_agent_run()`. The `evidence_ids` field in `AgentResult` consistently includes `["agent-runs.jsonl"]`. Agent execution errors are caught and logged with `status="failed"`.

## Integration tests skip gracefully when database unconfigured

The integration test file uses `pytestmark = pytest.mark.skipif(not os.environ.get("TEST_DATABASE_URL_TUTORIAL"), reason="...")` at module level. The test `test_verification_runner_creates_disposable_db` references a `db_session` fixture that is never defined—this causes test failure if executed, but the skipif marker prevents execution when the environment variable is unset.

All tests use mocked agent execution with `AsyncMock` return values rather than real database operations, so the `TEST_DATABASE_URL_TUTORIAL` skip condition may be overly conservative.

## Documentation and CLI script complete

The `docs/migration-repair-workflow.md` includes execution DAG diagram, architectural principles, wave-by-wave agent descriptions, safety constraints, and verification stages V0-V10.

The CLI script implements `--dry-run`, `--verbose`, `--database-url`, and `--workflow-id` options. The `_dry_run_preview()` method logs the execution plan and returns `dry_run: true` without calling `_execute_agent()`. No automated test verifies this behavior.
