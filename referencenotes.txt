1. Dev Server vs. Production Build
When you run npm run dev locally, Next.js uses Turbopack/Webpack in a "lazy" way. It only compiles the specific files and pages you are currently viewing in your browser.

Example: If you are working on the Login page, the build system might never actually check 
GovernanceInventory.tsx
 or 
CascadingSelect.tsx
.
Vercel, however, runs a mandatory next build, which compiles every single file in the project at once and performs a strict TypeScript check. If one icon is missing anywhere, the whole build fails.
2. VS Code "Soft" Errors
When I am editing code, VS Code shows red squiggles (TypeScript errors), but it doesn't stop the code from being saved or even running in "dev mode." Locally, we tend to rely on the IDE to tell us about errors. Vercel doesn't have an IDE; it uses a strict CLI build that treats any warning or missing name as a fatal error.

3. Path Alias Resolution (@/)
In the monorepo, the apps are configured to understand @/ as src/. When I moved components into the shared @quiz/ui package:

Locally: Sometimes the build tool "guesses" the path or uses a local cache from when the file was still in the app.
Vercel: It starts with a 100% clean, empty machine. It follows the 
tsconfig.json
 of the package strictly. Since the @quiz/ui package doesn't have a @/ alias (it shouldn't, as it's a shared library), it failed to find files that worked fine when they were still "local" to the Admin app.
4. Case Sensitivity (Windows vs. Linux)
You are on Windows (which is case-insensitive), but Vercel runs on Linux (which is case-sensitive).

If I imported Plus from lucide-react but the file reference in a local cache was plus, Windows would let it slide. Linux (Vercel) will throw a "File not found" error immediately.
How we prevent this now:
Moving forward, I will run pnpm build or pnpm tsc --noEmit locally before we push. This forces the local machine to act like Vercel and check every single line of code for missing imports or type errors.
