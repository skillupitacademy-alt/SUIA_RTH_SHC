## Decision Log

### Decision 1: expectedTimeSec Placement

**Options Considered:**
- A: Add to BaseBlock (TypeScript convenience)
- B: Add to each instructional interface explicitly (semantic precision)

**Decision:** Option A with Zod enforcement

**Rationale:**
- TypeScript: `BaseBlock` includes `expectedTimeSec?: number` (convenience)
- Zod: D1/C1 schemas explicitly include field (validation + documentation)
- Schemas use `.strict()` by default, so unknown fields are stripped
- Future S1/I1/O1 blocks can opt-in by adding to their schemas

**Trade-off:** TypeScript allows it on all blocks, but Zod enforces instructional-only

---

### Decision 2: Explicit Zod Fields vs .passthrough()

**Options Considered:**
- A: Add `presentation` + `expectedTimeSec` explicitly to D1/C1 schemas
- B: Use `.passthrough()` to allow unknown fields

**Decision:** Option A (explicit fields)

**Rationale:**
- Validation: Explicit fields enforce type constraints
- Documentation: Fields appear in generated types
- Safety: `.passthrough()` allows any unknown field (dangerous)
- Intentionality: Each block version opts-in deliberately

---

### Decision 3: Database Identity

**Options Considered:**
- A: `(userId, navigationNodeId, blockId, blockVersion)` - frozen architecture
- B: Add `brandId` column for multi-tenant scope

**Decision:** Option A (NO brand column)

**Rationale:**
- `userId` already provides brand/platform scope
- Authentication layer enforces brand isolation
- Adding `brandId` creates redundant denormalization
- Frozen architecture explicitly rejects brand column

---

### Decision 4: Session Tracking

**Options Considered:**
- A: Add `lastSessionId` to `block_learning_state`
- B: Manage session state at visit/page level (Phase 4.2+)

**Decision:** Option B (NO session column)

**Rationale:**
- Sessions are page-level concerns (visit-owned)
- Block state is independent of session
- Session IDs belong in visit telemetry, not block telemetry
- Frozen architecture explicitly rejects session column
